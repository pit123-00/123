# Подробный анализ набора навыков Superpowers

## Введение
Superpowers — это не просто коллекция промптов, а целостная операционная система для ИИ-агентной разработки. Каждый "навык" (skill) представляет собой формализованный инженерный протокол, который направляет поведение модели, предотвращает типичные ошибки ИИ и навязывает дисциплину высокого уровня.

---

## 1. Brainstorming (Мозговой штурм)
**Цель:** Трансформация размытых идей в четкие технические спецификации.
**Механика:**
- **Сократовский метод:** Агент обязан задавать уточняющие вопросы по одному. Это предотвращает "когнитивную перегрузку" как пользователя, так и самой модели.
- **Hard Gate:** Запрет на любое написание кода до утверждения дизайна.
- **Visual Companion:** Интеграция с локальным сервером для отображения макетов и диаграмм (подробнее в отдельном отчете).
- **Выходной артефакт:** Дизайн-документ (Spec) в `docs/superpowers/specs/`, который становится "источником истины" для всей дальнейшей работы.

## 2. Using Git Worktrees (Использование рабочих деревьев)
**Цель:** Обеспечение полной изоляции среды разработки.
**Механика:**
- Вместо простого переключения веток (`git checkout`), навык инициирует создание `git worktree`.
- Это позволяет ИИ иметь отдельную физическую директорию для каждой задачи.
- **Преимущество:** Исключается риск загрязнения основной ветки временными файлами, а также обеспечивается чистое окружение для прогона тестов без влияния текущих правок пользователя.

## 3. Writing Plans (Написание планов)
**Цель:** Декомпозиция сложной спецификации на атомарные, проверяемые задачи.
**Механика:**
- **Правило микро-задач:** Каждая задача должна занимать не более 2-5 минут ИИ-времени.
- **Формат:** Обязательное указание путей к файлам, ожидаемого поведения и способов верификации.
- **Зависимости:** Четкое выстраивание очереди выполнения (Task A must complete before Task B).

## 4. Subagent-Driven Development (SDD) / Executing Plans
**Цель:** Масштабирование выполнения через специализированных агентов.
**Механика:**
- **Паттерн "Исполнитель-Контролер":** Основная модель (Orchestrator) запускает субагентов для каждой задачи.
- **Многоуровневое ревью:** После того как субагент написал код, он проходит через:
    1. **Spec Review:** Соответствует ли реализация плану?
    2. **Code Quality Review:** Соответствует ли код принципам DRY, YAGNI и чистоте стиля?
- Это минимизирует "галлюцинации" и гарантирует, что код не просто работает, но и пригоден для поддержки.

## 5. Test-Driven Development (TDD)
**Цель:** Гарантия корректности и предотвращение регрессий.
**Механика:**
- **"Железный закон":** Никакого кода без падающего теста. Если код написан до теста, он должен быть удален.
- **Цикл Red-Green-Refactor:** Строгая последовательность: падение -> минимальная реализация -> улучшение структуры.
- **База знаний анти-паттернов:** Навык включает справочник плохих практик (например, "тесты-пустышки"), которые агент обязан избегать.

## 6. Systematic Debugging (Систематическая отладка)
**Цель:** Переход от "угадывания" к научному методу поиска ошибок.
**Механика:**
- **4-фазный процесс:**
    1. Сбор улик и симптомов.
    2. Формулирование гипотез.
    3. Создание воспроизводящего теста (Repro-test).
    4. Исправление корневой причины (Root Cause).
- **Root Cause Tracing:** Обязательное отслеживание цепочки "почему это произошло" до самого основания.

## 7. Requesting & Receiving Code Review
**Цель:** Формализация процесса человеко-машинного взаимодействия при проверке кода.
**Механика:**
- **Requesting:** Перед запросом ревью агент прогоняет чек-лист: тесты, документация, отсутствие отладочных логов.
- **Receiving:** Инструкции по конструктивному восприятию критики и итеративному исправлению замечаний. Ошибки делятся по критичности (Critical, Major, Minor).

## 8. Finishing a Development Branch
**Цель:** Чистое завершение жизненного цикла фичи.
**Механика:**
- Финальная верификация всех тестов проекта (не только затронутых).
- Выбор стратегии слияния (Merge, PR или сохранение ветки).
- Автоматическая очистка временных ресурсов и worktrees.

## 9. Writing Skills (Мета-навык написания навыков)
**Цель:** Расширение системы самой собой.
**Механика:**
- **TDD для документации:** Тот же "Железный закон" — нельзя создать навык, не написав сначала "падающий тест" (сценарий, где агент без этого навыка ошибается).
- **Rationalization Table:** Обязательное включение таблицы типичных оправданий ("это слишком просто для теста"), которые агент должен игнорировать.

## 10. Verification before Completion
**Цель:** Последний барьер перед сдачей работы.
**Механика:**
- Агент обязан перепроверить, что проблема действительно решена, а не просто "кажется исправленной".
- Инструкция требует прямого доказательства (вывод команды, прохождение конкретного теста).

---

## Заключение
Навыки Superpowers создают симбиотическую среду, где ИИ вынужден работать по стандартам Senior-разработчика. Главная инновация здесь — не в содержании советов, а в **обязательности процедур** (Hard Gates), которые превращают хаотичный чат в предсказуемый инженерный процесс.
