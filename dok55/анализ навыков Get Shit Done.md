# Анализ навыков и ролевой модели Get Shit Done (GSD)

## 1. Концепция "Мета-промптинга" и контекстной инженерии

Get Shit Done (GSD) — это высокоорганизованная система мета-промптов, разработанная для борьбы с "деградацией контекста" (context rot) в больших ИИ-сессиях. В отличие от простых наборов инструкций, GSD представляет собой полноценный фреймворк управления вниманием ИИ.

Основная проблема современных LLM — потеря точности при заполнении контекстного окна. GSD решает это не просто за счет "чистки" истории, а через архитектурное разделение задач и ответственности, превращая хаотичный поток сознания модели в структурированный инженерный процесс.

---

## 2. Ролевая модель: Армия специализированных агентов

В репозитории представлено более 30 специализированных ролей (агентов). Это критический архитектурный паттерн, который позволяет минимизировать шум и повысить точность за счет узкой специализации.

### Основные категории агентов:

1.  **Исследователи и Аналитики:**
    - **`gsd-ai-researcher`**: Специализируется на поиске оптимальных библиотек и подходов.
    - **`gsd-assumptions-analyzer`**: Критически оценивает предположения, заложенные в план, выявляя скрытые риски.
    - **`gsd-domain-researcher`**: Погружается в специфику бизнес-домена проекта.

2.  **Проектировщики и Планировщики:**
    - **`gsd-planner`**: "Мозг" системы, отвечающий за декомпозицию фаз на планы (PLAN.md).
    - **`gsd-roadmapper`**: Управляет высокоуровневым видением проекта через `ROADMAP.md`.

3.  **Исполнители и Исправители:**
    - **`gsd-executor`**: Модель, сфокусированная исключительно на написании кода по заданному плану.
    - **`gsd-debugger` / `gsd-code-fixer`**: Специалисты по поиску и устранению багов.

4.  **Аудиторы и Верификаторы:**
    - **`gsd-code-reviewer`**: Проводит глубокий аудит кода перед его финализацией.
    - **`gsd-security-auditor`**: Проверяет решения на соответствие модели угроз STRIDE.
    - **`gsd-verifier`**: Отвечает за проверку "наблюдаемых истин" после выполнения этапа.

Такое разделение предотвращает "размывание" фокуса, когда одна модель пытается быть одновременно и архитектором, и исполнителем. Каждый агент получает только тот набор инструкций (contract), который необходим для его узкой задачи.

## 3. Командная структура и фазовое развитие

GSD навязывает строгий жизненный цикл разработки через систему команд, разделенных на логические фазы.

### Основные фазы:
1.  **Discovery & Research (`gsd-discuss-phase`, `gsd-research-phase`):**
    Прежде чем писать код, система заставляет ИИ провести исследование и зафиксировать контекст. Создается `DISCOVERY.md` или `RESEARCH.md`, которые становятся "базой знаний" для планирования.
2.  **Planning (`gsd-plan-phase`):**
    Использование "Целевого-обратного планирования" (goal-backward methodology). Агент сначала формулирует конечные наблюдаемые истины, а затем выводит задачи для их достижения. План разбивается на "волны" (waves) для управления зависимостями.
3.  **Execution (`gsd-execute-phase`, `gsd-do`):**
    Атомарное выполнение планов. Каждая задача выполняется в максимально чистом контексте. Используется механизм "автономного" и "интерактивного" режима выполнения.
4.  **Verification & UAT (`gsd-verify-work`, `gsd-audit-uat`):**
    Многоуровневая проверка результата. Система требует доказательств ("observable truths") и не принимает отчет "готово" без верификации.

## 4. Уникальные паттерны и инновации GSD

### Паттерн: "Целевое-обратное планирование" (Goal-Backward)
В файле `gsd-planner.md` описан процесс вывода "Must-Haves" из цели. Агент не просто перечисляет задачи ("сделать API"), он определяет, какие артефакты должны существовать, чтобы цель считалась достигнутой.
- **Observable Truths:** Наблюдаемые факты (например, "В базе появилась запись с корректным ID").
- **Reachability Check:** Проверка того, что до каждого нового компонента можно добраться из существующего кода.

### Паттерн: "Интеллектуальный слой" (Intel & Learnings)
GSD вводит понятие "Intel" — это накопленные технические знания о проекте, которые не являются кодом или документацией, а представляют собой "заметки инженера" о тонкостях реализации.
- **`gsd-intel-updater`**: Автоматически обновляет базу знаний проекта после каждой сессии.
- **Global Learnings**: Возможность переносить опыт между разными репозиториями, используя систему тегов.

### Паттерн: "Борьба с галлюцинациями через Nyquist Auditor"
Специфическая роль `gsd-nyquist-auditor` (упоминаемая в списке агентов) подразумевает контроль частоты дискретизации информации — проверку того, не упустил ли агент важные детали при высокоуровневом планировании.

## 5. Плюсы и минусы системы GSD

### Плюсы (Сильные стороны):
1.  **Масштабируемость:** Единственная система, способная адекватно управлять проектами, размер которых в десятки раз превышает контекстное окно модели.
2.  **Прозрачность и Аудируемость:** Каждое решение записано в `.planning/`. Вы всегда можете восстановить цепочку рассуждений ИИ.
3.  **Высочайшее качество проектирования:** Благодаря фазам обсуждения и исследования, архитектурные ошибки выявляются до написания кода.
4.  **Ролевая гибкость:** Вы можете "нанять" только нужных агентов для конкретной задачи.

### Минусы (Слабые стороны):
1.  **Огромный "когнитивный налог":** Пользователь должен понимать структуру фаз и уметь пользоваться десятками команд. Это не "магическая кнопка", а профессиональный инструмент.
2.  **Затратность по токенам:** Из-за обилия фаз планирования, ревью и верификации, расход токенов на одну фичу может быть значительно выше, чем в более простых системах.
3.  **Медленный старт:** Подготовка к написанию первой строчки кода в новом проекте может занять 15-20 минут обсуждений с ИИ.

---

## 6. Итоговый вывод
Навыки Get Shit Done представляют собой наиболее зрелую попытку формализации процесса разработки с ИИ. Это система для "тяжелой атлетики" в программировании — когда нужно построить сложную, надежную систему, сохранив контроль над каждым архитектурным решением на протяжении месяцев разработки. GSD превращает ИИ из "кодинг-бота" в полноценный инженерный отдел.
