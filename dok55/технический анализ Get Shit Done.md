# Технический анализ реализации и логики Get Shit Done (GSD)

## 1. Архитектура системы: CLI как управляющая надстройка

Get Shit Done (GSD) технически реализован как гибридная система, сочетающая Node.js CLI и набор структурированных Markdown-команд. В отличие от Superpowers, которые живут внутри `skills/`, GSD выносит логику в папку `get-shit-done/bin` и связывает её с промптами через механизмы инструментов.

### Ключевые компоненты:
- **`gsd-tools.cjs`**: Ядро системы на Node.js. Оно отвечает за:
    - Валидацию фронтматтера планов по JSON-схеме.
    - Автоматическое управление `STATE.md` (чтение, парсинг, обновление).
    - Расчет зависимостей и назначение "волн" (waves).
    - Генерацию и обновление роадмапов.
- **`get-shit-done/bin/lib/`**: Библиотека специализированных JS-модулей (`phase.cjs`, `roadmap.cjs`, `security.cjs`), которые реализуют бизнес-логику системы.
- **`commands/`**: Директория с исполняемыми Markdown-инструкциями. Каждая команда (например, `do.md`) содержит детальный `<execution_flow>`, который агент обязан интерпретировать.

## 2. Логика управления контекстом (Context Engineering)

GSD решает проблему "гниения контекста" (context rot) через агрессивную фрагментацию задач и использование внешних файлов состояния. Это технически более сложный подход, чем простое удаление старых сообщений.

**Основные механизмы:**
- **External State Management:** Файл `.planning/STATE.md` служит внешней оперативной памятью. Он содержит:
    - Текущую активную фазу и план.
    - Реестр принятых решений (decisions).
    - Список "отложенных" проблем (concerns) и "всплывших" задач (inbox).
- **Context Budgeting:** Система навязывает лимит: 2-3 задачи на один `PLAN.md`. Это гарантирует, что при выполнении плана (через `/gsd-do`) агент будет оперировать минимально необходимым набором файлов и инструкций, высвобождая ресурсы модели для качественного кодинга.
- **Incremental Documentation:** Вместо огромных спецификаций GSD генерирует серию мелких "Summary" файлов после каждой подзадачи, создавая цепочку контекста, которую легко "проматывать".

## 3. Техническая реализация Планирования: Wave & Dependency

Алгоритм планирования в GSD (`gsd-planner.md`) технически реализует построение графа зависимостей:

1.  **Dependency Graph Mapping:** Для каждой задачи агент определяет `needs` (что должно существовать) и `creates` (что будет создано).
2.  **Wave Assignment:** Скрипты GSD анализируют этот граф. Задачи с нулевыми зависимостями попадают в `Wave 1`. Задачи, зависящие только от `Wave 1`, попадают в `Wave 2` и так далее.
3.  **Conflict Detection:** Система проверяет `files_modified` в планах одной волны. Если два плана пытаются менять один и тот же файл одновременно, один из них принудительно переносится в следующую волну.

Этот подход позволяет системе работать в "автономном режиме" (`/gsd-autonomous`), где последовательность действий математически предопределена графом зависимостей.

## 4. Логика верификации и обратной связи

GSD использует строго формализованную логику проверки результата:

- **Observable Truths (Наблюдаемые истины):** Это не просто "тесты прошли", а конкретные утверждения, которые можно проверить командой (например, `grep`, `ls`, `curl`).
- **Reachability Check:** Техническая проверка "связности". Агент обязан доказать, что новый код достижим (wired) в общей архитектуре. Например, если создан новый компонент, должен быть показан файл, который его импортирует.
- **Gap Closure Mode:** Если верификация падает, система переходит в специальный режим `gaps-only`, где планируются задачи только на закрытие обнаруженных пробелов, не возвращаясь к общему планированию.

## 5. Безопасность и Аудит (Security Enforcement)

GSD интегрирует модель угроз STRIDE непосредственно в процесс разработки:
- **Threat Model Injection:** При включенной опции `security_enforcement`, в каждый план встраивается `<threat_model>`.
- **Mitigation Tracking:** Каждая угроза должна иметь статус (mitigate, accept, transfer) и ссылку на конкретную реализацию в коде.
- **Security Checklists:** Использование шаблонов (например, `templates/SECURITY.md`) для формализации аудита безопасности на уровне фаз.

## 6. Мета-промптинг и шаблонизация

GSD использует сложную систему шаблонов (`get-shit-done/templates/`):
- **XML-структуры:** Планы и отчеты используют XML-теги (`<step>`, `<action>`, `<verify>`), что облегчает парсинг вывода модели скриптами и повышает структурированность ответов.
- **Inheritance (Наследование):** Команды могут наследовать контекст из `DESCRIPTION.md`, `ARCHITECTURE.md` и `CONVENTIONS.md`, создавая иерархию правил проекта.

## Резюме технического анализа
С технической точки зрения, Get Shit Done — это наиболее продвинутая надстройка над ИИ-агентами. Она переносит центр тяжести с "предсказания следующего токена" на "исполнение формализованных алгоритмов".

Использование Node.js для валидации и управления графом зависимостей в сочетании со строгой Markdown-структурой команд делает GSD полноценной средой промышленной разработки, минимизирующей влияние ограничений современных LLM (короткая память, галлюцинации, потеря фокуса). Это "операционная система", где ИИ-модель выступает лишь в роли исполнительного процессора.
