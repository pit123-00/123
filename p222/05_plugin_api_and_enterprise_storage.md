# Отчёт 5: Глубокий анализ Dynamic Plugin API и Enterprise-архитектуры хранения данных в CLIProxyAPI

Настоящий отчёт детально исследует две уникальные технические подсистемы CLIProxyAPI:
1. **Dynamic Plugin API** — бинарный C ABI и RPC-протокол межпроцессного взаимодействия (IPC), позволяющий расширять шлюз без его перекомпиляции.
2. **Enterprise Resilient Storage** — промышленную подсистему распределённого хранения без жесткой привязки к локальной файловой системе (S3/MinIO, синхронизация кулдаунов в PostgreSQL и версионирование пула учетных записей в Git).

---

## 1. Dynamic Plugin API: Бинарный протокол плагинов через C ABI и RPC/IPC

В отличие от стандартных веб-прокси, где расширения требуют изменения исходного кода или использования медленных внешних HTTP-вебхуков, в CLIProxyAPI реализована высокопроизводительная система динамических плагинов (`internal/pluginhost`, `sdk/pluginabi`, `sdk/pluginapi`).

### 1.1. Бинарный уровень (Native C ABI v1)
Загрузка и связывание плагинов реализованы в `internal/pluginhost/loader_unix.go` (через `dlopen`/`dlsym` на Linux/macOS/FreeBSD) и `loader_windows.go` (через `LoadLibrary`/`GetProcAddress`).

Архитектура обмена данными на уровне языка C:
```c
typedef struct {
    void* ptr;
    size_t len;
} cliproxy_buffer;

typedef int (*cliproxy_host_call_fn)(void* ctx, const char* method, const uint8_t* payload, size_t len, cliproxy_buffer* out);
typedef void (*cliproxy_host_free_fn)(void* ptr, size_t len);

typedef struct {
    uint32_t abi_version;
    void* host_ctx;
    cliproxy_host_call_fn call;
    cliproxy_host_free_fn free_buffer;
} cliproxy_host_api;

typedef struct {
    uint32_t abi_version;
    cliproxy_plugin_call_fn call;
    cliproxy_plugin_free_fn free_buffer;
    cliproxy_plugin_shutdown_fn shutdown;
} cliproxy_plugin_api;

typedef int (*cliproxy_plugin_init_fn)(const cliproxy_host_api* host, cliproxy_plugin_api* plugin);
```
- **Zero-Copy / Shared Buffers:** Передача байтовых буферов `cliproxy_buffer` осуществляется напрямую по указателям памяти с явным освобождением ресурсов (`free_buffer`).
- **Двунаправленный вызов (Bi-directional Callbacks):** Плагин может не только отвечать на вызовы хоста, но и сам инициировать вызовы к ядру через `cliproxy_host_call_fn` (например, запрашивать метаданные моделей, логировать события, проверять квоты).

### 1.2. Протокол сериализации и эволюция RPC Schema (v1 – v10)
Поверх C ABI работает типизированный JSON RPC протокол (`sdk/pluginabi/types.go`), версия которого динамически согласуется при регистрации плагина (`plugin.register`). Кодовая база насчитывает 10 версий схемы контракта:
- **Schema v2:** Добавлено асинхронное завершение жизненного цикла запроса (`RequestLifecyclePlugin`) и принудительное завершение зависших запросов.
- **Schema v3 и v5:** Оптимизация потоковой передачи. Для экономии полосы пропускания и памяти хост исключает повторную отправку тела исходного запроса и истории на каждый чанк стрима (оставляя их только в инициализирующем заголовке нулевого чанка).
- **Schema v7:** Режим `omit_body`. Плагины авторизации и интерцепторы могут объявить `frontend_auth_provider_omit_body` или `request_interceptor_omit_body_before`. В этом случае ядро шлюза вообще не читает и не копирует многомегабайтные полезные нагрузки клиентов, исключая аллокации памяти.
- **Schema v8 (Byte-Range Patching):** Внедрён механизм точечного патчинга тел запросов (`request.patch_body_before` и `request.patch_body_after`). Сырые байты запроса передаются через C ABI без Base64/JSON-оберток, а плагин возвращает массив инструкций замены диапазонов байт `[offset, length, replacement]`. Хост накладывает эти правки за один линейный проход.
- **Schema v10:** Поддержка множественных провайдеров (`MultiAuthProvider`) в рамках одного бинарного плагина.

### 1.3. Точки расширения плагинов (Capabilities)
В структуре `pluginapi.Capabilities` (`sdk/pluginapi/types.go`) определены более 20 интеграционных шлюзов:
1. `FrontendAuthProvider`: кастомная аутентификация клиентов перед попаданием в прокси.
2. `Scheduler`: переопределение алгоритма выбора аккаунта/токена из пула до запуска стандартного планировщика.
3. `ModelRouter`: динамическая маршрутизация запроса на внешние кастомные исполнители.
4. `RequestNormalizer` и `RequestTranslator`: двунаправленная трансформация диалектов запросов в канонический формат и обратно.
5. `StreamChunkInterceptor`: модификация чанков стримингового ответа в реальном времени.
6. `WebSocketResponseObserver`: перехват и инспекция событий в дуплексных вебсокетах.
7. `ThinkingApplier`: инъекция и нормализация блоков рассуждений (`reasoning/thinking`).
8. `UsagePlugin`: учет расхода токенов и биллинг во внешних системах.

## 2. Промышленная отказоустойчивость хранения (Enterprise Resilient Storage)

CLIProxyAPI разработан с расчетом на развертывание в кластерных, бессерверных и геораспределенных средах (Kubernetes, AWS ECS, Fly.io), где локальный диск контейнера является эфемерным (ephemeral).

В `internal/store/` и `internal/kvstore/` реализованы четыре независимых бэкенда хранения.

### 2.1. Хранение токенов в S3 / MinIO (`ObjectTokenStore`)
В файле `internal/store/objectstore.go` реализован драйвер на базе `github.com/minio/minio-go/v7`:
- **Топология:**
  - Конфигурация сохраняется по ключу `config/config.yaml`.
  - Учетные данные OAuth и токены сохраняются в префиксе `auths/`.
- **Локальное зеркалирование (Local Workspace Mirror):**
  При старте инстанс выгружает актуальные токены из S3-бакета в локальную директорию (`Bootstrap`), что позволяет ядру работать с максимальной скоростью файловой системы.
- **Двусторонняя реактивная синхронизация:**
  - При получении новых OAuth-токенов через веб-колбэк или Management API метод `uploadAuth` автоматически отправляет JSON-файл в S3-бакет с вычислением MD5/SHA256 контрольных сумм.
  - При удалении токена вызывается `deleteAuthObject`.

### 2.2. Синхронизация кулдаунов и состояния через PostgreSQL (`PostgresStore` и `PostgresCooldownStore`)
В файлах `internal/store/postgresstore.go` и `internal/store/postgres_cooldown_store.go` реализована поддержка СУБД PostgreSQL:
- **Проблема нескольких реплик:**
  Если за балансировщиком запущено 10 реплик шлюза, ошибка 429 (Rate Limit) на одной реплике должна мгновенно заблокировать использование перегруженного токена на остальных 9 репликах.
- **Таблица кулдаунов (`cpa_cooldown_states`):**
  Реализована схема с полями `auth_id`, `model_name`, `cooling_until`, `reason`, `updated_at`.
- **Методы `Save` и `Load`:**
  - При фиксации ошибки квоты инстанс выполняет атомарный `UPSERT` в PostgreSQL.
  - Фоновый цикл считывает глобальное состояние кулдаунов, поддерживая единый распределенный таймлайн доступности учетных данных во всем кластере.
- **Хранение конфигураций:**
  Таблицы `cpa_configs` и `cpa_auth_files` позволяют полностью отказаться от монтирования общих томов (NFS/EFS) в Kubernetes.

### 2.3. Версионирование пула учетных записей в Git (`GitTokenStore`)
В файле `internal/store/gitstore.go` реализован контроллер хранения токенов в Git-репозитории:
- **Audit Trail & GitOps:**
  Любое добавление, обновление или инвалидация OAuth-токена оформляется как коммит в Git (`commitAndPushLocked`).
- **Слияние веток и защита от конфликтов:**
  Используется `checkoutConfiguredRemoteTrackingBranch` и автоматический pull с ребейзом. При обнаружении конфликтов токенов система объединяет JSON-состояния или производит мягкое разрешение коллизий.
- **Сборка мусора и сжатие истории (`maybeRunGC`, `rewriteHeadAsSingleCommit`):**
  При частой ротации токенов Git-репозиторий быстро растет. Драйвер умеет автоматически запускать `git gc` и схлопывать историю коммитов (squash) до одного базового коммита, предотвращая разрастание `.git`.

### 2.4. Сравнительная матрица подсистем хранения CLIProxyAPI

| Подсистема | Назначение | Режим работы | Преимущество в Enterprise |
| :--- | :--- | :--- | :--- |
| **bbolt (Embedded KV)** | Локальный кэш кулдаунов и сессионных пинов | Локальный диск | Zero-latency, ACID-транзакции без сетевых зависимостей |
| **ObjectStore (S3/MinIO)** | Хранение токенов и файлов конфигурации | S3 API | Идеально для Serverless / K8s Stateless Pods |
| **PostgresStore** | Централизованное хранение токенов и кулдаунов | PostgreSQL | Мгновенная синхронизация 429-лимитов между всеми узлами кластера |
| **GitStore** | Версионирование и синхронизация пула аккаунтов | Git (SSH/HTTPS) | GitOps-пайплайн, аудит изменений токенов, бэкап в GitHub/GitLab |

## 3. Выводы

Реализация **Dynamic Plugin API** и **Enterprise Resilient Storage** выделяет CLIProxyAPI в категорию промышленных решений операторского уровня:
1. За счет **C ABI v1** и **RPC Schema v10** расширения могут работать с минимальными накладными расходами на копирование памяти и производить прямой байт-патчинг запросов без десериализации JSON.
2. Благодаря поддержке **S3, PostgreSQL и Git**, система готова к развертыванию в распределенных кластерах высокой доступности (HA) с автоматическим шарингом состояния перегрузки провайдеров между всеми подами.
