# Отчёт 4: Плюсы и минусы решений с точки зрения управления агентами (LLM/MCP), CLI, API, субагентов и автоматизации пайплайнов

Данный отчёт содержит практический и технический анализ применимости **Dokku** и **Dokploy** в сценариях интеграции с автономными ИИ-агентами, протоколом **MCP (Model Context Protocol)**, инструментами командной строки (CLI), REST/tRPC API, субагентами и CI/CD пайплайнами развертывания.

---

## 1. Интеграция с AI/LLM агентами и MCP-серверами (Model Context Protocol)

### Dokploy:
В кодовой базе Dokploy заложена прямая ориентация на мир AI-агентов и экосистему MCP:
1. **Автоматический генератор MCP-сервера в CI/CD:**
   * В файле `.github/workflows/sync-openapi-docs.yml` настроен автоматический пайплайн: при каждом обновлении роутеров tRPC (`apps/dokploy/server/api/routers/**`), сервисов или схем базы данных запускается шаг `pnpm generate:openapi`.
   * Сгенерированный файл `openapi.json` коммитится и пушится напрямую в официальный репозиторий **Dokploy/mcp** (`https://github.com/Dokploy/mcp.git`), а также в `cli` и `sdk`.
   * Это означает, что любой агент, поддерживающий MCP (Claude Desktop, Cursor, Agency, Jules и др.), получает автогенерируемые типизированные инструменты (tools) для вызова любых операций Dokploy (создать проект, задеплоить приложение, накатить бэкап, проверить логи).
2. **Встроенный AI-сервис (`packages/server/src/services/ai.ts`):**
   * В Dokploy интегрирован движок генерации инфраструктуры по промпту пользователя.
   * Функция `suggestVariants` принимает текстовый запрос на естественном языке (например, *"deploy Chatwoot with postgres"* или *"personal blog"*) и с помощью LLM (поддерживаются кастомные провайдеры через `selectAIProvider`) генерирует валидные конфигурации `docker-compose.yml`, переменные окружения, домены и маппинги томов по строгой Zod-схеме (`fullSchema`).
3. **Готовые скиллы агентов:** В репозитории уже присутствует `.claude/skills/fix-issue/SKILL.md` с описанием использования `mcp__dokploy__*` инструментов.

*Плюсы Dokploy для агентов:*
* Готовая интеграция с MCP «из коробки» за счёт синхронизируемого OpenAPI контракта.
* Структурированные JSON-ответы API облегчают парсинг агентами (нет необходимости регулярными выражениями парсить текст терминала).
* Возможность программного создания и валидации инфраструктуры через Zod-схемы.

*Минусы Dokploy для агентов:*
* Ошибки в TypeScript типах или валидации Drizzle/Zod могут приводить к отказу процедур tRPC, требуя точного знания схемы данных.
* Наличие платных Enterprise-фич (SSO, Audit Log) ограничивает возможности агентов в бесплатных окружениях при попытке работы с enterprise-роутерами.

### Dokku:
В Dokku нативная поддержка MCP или встроенных AI-модулей в кодовой базе отсутствует:
1. **Интерфейс общения агента с Dokku:** Агент может взаимодействовать с Dokku исключительно через выполнение Bash-команд (Bash Tool) по SSH или в локальной сессии: `dokku apps:create <name>`, `dokku config:set <key>=<val>`.
2. **Формат вывода данных:**
   * Команды Dokku ориентированы на терминал человека (цветной текст, отступы, псевдографика).
   * Однако Dokku поддерживает флаги `--json` и плагин `report` (`common.ReportSingleApp`), что позволяет агентам получать структурированные свойства приложений: `dokku --json apps:report <app>`.

*Плюсы Dokku для агентов:*
* **Детерминированность и простота CLI:** Любой агент общего назначения, умеющий запускать bash-команды, может управлять Dokku без необходимости установки тяжелых клиентских библиотек или генерации OpenAPI-клиентов.
* **Идемпотентность многих команд:** Большинство команд установки свойств (`config:set`, `domains:set`, `proxy:set`) идемпотентны, что снижает риск ошибок при повторных попытках агента.
* **Прозрачность файловой системы:** Агент может напрямую проинспектировать `/home/dokku/<app>/ENV` или `/var/lib/dokku/data/` для получения фактов о состоянии хоста.

*Минусы Dokku для агентов:*
* Отсутствие официального MCP-сервера: разработчику приходится либо писать свой MCP-адаптер над SSH/CLI, либо давать агенту полный shell-доступ.
* Риск деструктивных действий: ошибка агента в shell-команде (`rm -rf` или некорректный `sudo`) может повредить систему, так как права внутри хоста шире, чем у строгого REST API.

## 2. Сравнение CLI (Command Line Interface)

| Критерий CLI | Dokku | Dokploy |
| :--- | :--- | :--- |
| **Реализация CLI** | Нативный скрипт `/dokku` (Bash) + Go-плагины. Удаленный доступ через `contrib/dokku_client.sh` по SSH. | Отдельный репозиторий `Dokploy/cli` (автогенерируемый на базе OpenAPI/SDK), общающийся с сервером по HTTP API. |
| **Скорость отклика** | Мгновенный запуск процессов без накладных расходов на инициализацию JS-рантайма. | Зависит от Node.js рантайма CLI-утилиты и сетевой задержки HTTP-запросов к API. |
| **Полнота покрытия функций** | **100%**. Любая фича ядра Dokku доступна из CLI, так как CLI — это единственный первичный интерфейс системы. | Основной функционал доступен через API, но некоторые низкоуровневые операции быстрее выполнять через UI. |
| **Вывод ошибок** | Логи сбоев компиляции, проверок `check-deploy` и контейнеров транслируются прямо в STDOUT/STDERR сессии. | Ошибки возвращаются как JSON RPC ошибки (`TRPCError`) или пишутся в лог деплоя в БД, требуя отдельного запроса логов. |

## 3. Сравнение API (REST, tRPC, OpenAPI)

### Dokku:
* В ядре Dokku **нет встроенного HTTP API**.
* Для программного вызова Dokku использует протокол **SSH command exec**:
  ```bash
  ssh -p 22 dokku@server apps:list
  ssh -p 22 dokku@server config:set myapp KEY=VALUE
  ```
* Любая автоматизация и сторонние оркестраторы вынуждены либо оборачивать SSH-вызовы, либо поднимать сторонние демоны (например, сторонние комьюнити-плагины Dokku HTTP API).

### Dokploy:
* Вся система спроектирована **API-First**:
  1. **tRPC Endpoint (`/api/trpc`):** Внутренний RPC-протокол между веб-интерфейсом и сервером. Гарантирует типобезопасность на этапе компиляции TypeScript.
  2. **Microservice Hono API (`apps/api`):** Высокопроизводительный шлюз для внешних интеграций:
     * Аутентификация по заголовку `X-API-Key` (`isValidApiKey` через безопасное сравнение `timingSafeEqual`).
     * Эндпоинты `/deploy`, `/cancel-deployment`, `/jobs`, `/health`.
  3. **OpenAPI Спецификация (`openapi.json`):** Полный снимок всех роутеров, на базе которого генерируются клиентские библиотеки (Go, Python, TypeScript) и MCP-инструменты.

## 4. Пайплайны, субагенты и фоновые процессы

### Управление субагентами и фоновыми задачами в Dokku:
* Dokku выполняет деплой **синхронно в рамках одной сессии**. Если агент запускает `git push dokku main` или `dokku ps:rebuild`, команда не вернет управление, пока не завершатся все этапы: сборка образа, запуск проверок, переключение Nginx.
* **Плюс для простых пайплайнов:** Легко встраивать в стандартный GitHub Actions runner (`git remote add dokku ... && git push dokku`). Не нужен поллинг статуса.
* **Минус для распределенных агентов/субагентов:** Нельзя запустить параллельно несколько деплоев на одно приложение; долгие сборки могут отваливаться по SSH-таймауту. Нет нативного механизма отмены зависшего шага через API.

### Управление субагентами и фоновыми задачами в Dokploy:
* Dokploy реализует **асинхронную модель на базе очередей Inngest**:
  1. Запрос на деплой регистрируется мгновенно с возвратом `jobId` / `serverId`.
  2. Субагент или внешний пайплайн может опрашивать `/jobs?serverId=...` или слушать вебхук завершения `deployment/completed` / `deployment/failed`.
  3. Возможность отмены деплоя: вызов `POST /cancel-deployment` передает сигнал в Inngest, который прерывает активный шаг сборки.
* **Плюс для мультиагентных систем:** Идеально подходит для архитектуры, где один агент-планировщик раздает задачи субагентам-исполнителям, которые асинхронно мониторят выполнение через события.

## 5. Итоговая матрица плюсов и минусов

### Dokku

#### Плюсы:
1. **Максимальная надежность и стабильность:** Проверенная временем архитектура без состояния в БД, которая не может «зависнуть» из-за краша Node.js или нехватки памяти для веб-сервера.
2. **Простота интеграции в CI/CD:** Деплой через `git push` является мировым стандартом, поддерживаемым любыми системами (GitLab CI, GitHub Actions, Bitbucket Pipelines) без сторонних утилит.
3. **Прямой контроль над хостом:** Легкий доступ к контейнерам (`dokku enter`), кастомным конфигам Nginx (`nginx.conf.sigil`) и низкоуровневым опциям Docker (`dokku docker-options`).
4. **Легковесность:** Минимальное потребление RAM (не требует постоянных фоновых тяжелых процессов, работает даже на VPS с 512MB RAM).

#### Минусы:
1. **Отсутствие официального MCP / OpenAPI:** Необходимость выполнения команд через SSH-сессии, что усложняет работу ИИ-агентов без прямого shell-доступа.
2. **Блокирующая модель исполнения:** Синхронные операции затрудняют построение реактивных дашбордов и асинхронного взаимодействия субагентов.
3. **Нет мультисерверного управления из коробки:** Dokku управляет только тем хостом, на котором установлен (за исключением использования k3s плагина).

---

### Dokploy

#### Плюсы:
1. **Нативная совместимость с AI-агентами и MCP:** Автоматическая генерация MCP-сервера и OpenAPI спецификаций обеспечивает бесшовную интеграцию с ИИ-инструментами и фреймворками агентов.
2. **Полноценный API-First подход:** Наличие tRPC, REST API на Hono и генерации SDK для автоматизации любых сценариев управления инфраструктурой.
3. **Асинхронная управляемость:** Очереди задач на Inngest с контролем параллелизма и возможностью отмены долгих операций.
4. **Централизованное управление флотом (Fleet Management):** Возможность из одной точки управлять десятками удаленных серверов по SSH и развертывать Docker Swarm кластеры.
5. **Встроенные сервисы баз данных и S3 бэкапов:** Автоматизация резервного копирования баз данных и томов в облачные хранилища без написания bash-скриптов.

#### Минусы:
1. **Высокий оверхед инфраструктуры:** Требует работы PostgreSQL, Next.js сервера, Hono API, демона мониторинга и Traefik, что требует минимум 2GB+ оперативной памяти на мастер-ноде.
2. **Зависимость от состояния в базе данных:** Сбой PostgreSQL или рассинхронизация записей в БД с реальным состоянием Docker Engine может привести к ошибкам в UI и API.
3. **Сложность отладки низкоуровневых сбоев:** При падении удаленной SSH-сессии или ошибки внутри цепочки Inngest-функций поиск причины требует исследования логов распределенной системы.
