# Отчёт 5: Глубокий анализ универсальности среды opencode (Cloudflare Workers) и подсистемы Memory V2 в grok-build

Настоящий отчёт подготовлен на основе глубокого исследования исходного кода репозиториев `anomalyco/opencode` и `xai-org/grok-build`. В нём подробно раскрываются две ключевые технические темы:
1. Архитектурная универсальность среды исполнения `opencode` с акцентом на запуск в **Cloudflare Edge Workers (workerd / Durable Objects)** и связанные с этим возможности.
2. Внутреннее устройство и математико-алгоритмический аппарат долговременной памяти **Memory V2** в `grok-build`.

---

# ЧАСТЬ I. Универсальность среды выполнения `opencode` и Cloudflare Edge Workers

В кодовой базе `opencode` концепция кроссплатформенности и среды исполнения выведена на фундаментальный уровень благодаря модульной сервисной архитектуре на базе **Effect TS** (`Layer`, `Context.Service`) и бандл-условий (bundle export conditions).

### 1. Единое ядро для четырёх сред исполнения

Один и тот же сервисный граф ядра (`packages/core`) адаптируется под четыре различных сценария без переписывания бизнес-логики:
1. **Интерактивный терминал (CLI & TUI):**
   - Пакеты `packages/cli` и `packages/tui`.
   - Непосредственное взаимодействие с локальной ОС через Node.js / Bun, прямое управление stdin/stdout/raw-mode, отрисовка терминального интерфейса.
2. **Десктопное приложение (Desktop):**
   - Пакет `packages/desktop` и `packages/app`.
   - Локальный процесс ядра запускается как бэкенд, связываясь с фронтендом через локальный IPC/RPC или HTTP-сервер.
3. **Локальный headless HTTP/SSE сервер:**
   - Пакет `packages/server` (`routes.ts`, `event-feed.ts`, `process.ts`).
   - Предоставляет REST API и потоковую передачу событий через Server-Sent Events (SSE). К нему могут подключаться удаленные клиенты, веб-браузеры (`packages/web`) и сторонние расширения.
4. **Cloudflare Edge Workers (`workerd`):**
   - Специализированный профиль запуска ядра в бессерверной среде Cloudflare.

---

### 2. Реализация под Cloudflare Workers (`workerd`) в коде

Поддержка среды Cloudflare Workers реализована через абстракцию `packages/server/src/workerd.ts`, `packages/core/src/database/sqlite.workerd.ts` и условные биндинги файлов `*.workerd.ts`:

#### А. Сборка с бандл-условием `--conditions=workerd`
В конфигурации Bun/TypeScript модули, имеющие специфичные для платформы зависимости, разделены по расширениям:
- `binary.node.ts` / `fff.node.ts` — для классического Node.js.
- `binary.bun.ts` / `fff.bun.ts` — для высокопроизводительного рантайма Bun.
- `binary.workerd.ts` / `fff.workerd.ts` / `sqlite.workerd.ts` — для Cloudflare `workerd`.

При компиляции через `bun build src/workerd.ts --conditions=workerd --target=node` резолвер Bun подменяет нативные бинарные модули на их `workerd`-совместимые заглушки и адаптеры.

#### Б. База данных внутри Cloudflare Durable Object (`sqlite.workerd.ts`)
В обычном окружении `opencode` использует классический локальный файл SQLite через драйвер файловой системы. В среде Cloudflare ядро переключается на **Cloudflare Durable Objects Storage**:
```typescript
// packages/core/src/database/sqlite.workerd.ts
export const supportsTuningPragmas = false;
```
Код явно учитывает специфику SQLite внутри Durable Objects:
- Игнорируются прагмы настройки производительности: `journal_mode`, `synchronous`, `busy_timeout`, `cache_size`, `wal_checkpoint` — в Cloudflare DO SQLite они вызывают исключения (`throw`), так как репликацией и транзакционностью управляет сама платформа Cloudflare.
- Включение внешних ключей (`PRAGMA foreign_keys`) также отклоняется, поскольку `SQLITE_DEFAULT_FOREIGN_KEYS=1` уже включен в Cloudflare на уровне движка. Допускается только `defer_foreign_keys` для проведения миграций схемы Drizzle ORM.
- Сессия агента целиком живет внутри отдельного **Durable Object**, что обеспечивает глобальную консистентность, распределенную изоляцию сессий и персистентность данных прямо на границе сети (at the Edge).

#### В. Адаптация подсистем без локальной ОС (No Execution Plane)
В бессерверном воркере Cloudflare отсутствует локальная файловая система и возможность порождать fork/exec процессы:
- **PTY и терминал:** Модули `packages/core/src/persistent-pty/binary.workerd.ts` и `pty.workerd.ts` подменяют вызовы терминала. Локальный процесс-спавнер переходит в режим `EnvironmentUnavailable`. При попытке локального запуска команд агент получает типизированную ошибку о том, что локальный execution-plane отсутствует.
- **Внешние песочницы (Remote Execution Sandbox):** Архитектура спроектирована так, что при работе в Cloudflare Edge воркер выступает оркестратором (Brain at the Edge), а команды и доступ к файловой системе делегируются удаленным песочницам (remote sandboxes / containers / dev-servers).
- **Конфигурация и плагины:** Конфигурация инжектируется напрямую в виде строки в памяти (`injected as a string`), исключая обращение к локальным `.toml` или `.json` файлам.

---

### 3. Возможности тандема «Opencode + Cloudflare Edge Workers»

1. **Глобально распределенный AI-агент (Agent-as-a-Service):**
   - Возможность запустить серверную часть `opencode` на миллионах edge-узлов Cloudflare по всему миру с минимальной сетевой задержкой к пользователю.
2. **Изоляция сессий в Durable Objects:**
   - Каждый чат, сессия или агент изолированы в собственном Durable Object со встроенной реплицируемой базой SQLite. Состояние не потеряется при рестартах и не требует развертывания отдельного централизованного кластера PostgreSQL/MySQL.
3. **Прямая интеграция с Cloudflare AI:**
   - В `packages/ai` и `packages/core` реализована нативная поддержка:
     - **Cloudflare AI Gateway** (`@opencode/ai/providers/cloudflare-ai-gateway`): кэширование промптов, рейт-лимитинг, аналитика запросов к моделям.
     - **Cloudflare Workers AI** (`cloudflare-workers-ai.ts`): запуск открытых моделей (Llama 3.1, Qwen, DeepSeek) прямо на GPU-инфраструктуре Cloudflare без сторонних API-ключей.
4. **Гибридный запуск (Headless Edge Orchestrator + Remote Workers):**
   - Агент принимает решения, ведет контекст и планирует шаги на Edge, а команды компиляции и тестов отправляет на удаленные машины разработчиков через защищенные туннели или WebSocket-соединения.

# ЧАСТЬ II. Как устроена память MEMORY V2 в `grok-build`

В репозитории `grok-build` подсистема долговременной памяти второго поколения (**Memory V2**) реализована в крейтах `xai-grok-config`, `xai-grok-config-types`, `xai-grok-shell` и `xai-grok-telemetry`. В отличие от тривиальных чат-ботов с плоским сохранением истории сообщений, Memory V2 представляет собой сложный гибридный поисковый движок с алгоритмами консолидации и экспоненциального старения информации.

---

### 1. Архитектурные уровни памяти (Memory Scopes)

Memory V2 разделяет знания на три изолированных пространства:
1. **Global (`global`):** Общесистемные правила, предпочтения разработчика, глобальные паттерны кодирования. Доступны всем сессиям.
2. **Workspace (`workspace`):** Специфика конкретного проекта/репозитория (архитектура, используемые фреймворки, договоренности о стиле кода).
3. **Session (`session`):** Краткосрочные наблюдения и факты, зафиксированные в рамках текущей сессии решения задачи.

---

### 2. Разбиение на чанки и векторные эмбеддинги (`MemoryIndexConfig`, `MemoryEmbeddingConfig`)

- **Чанкирование с перекрытием:**
  - `max_chunk_chars: 1600` (примерно 400 токенов на чанк).
  - `chunk_overlap_chars: 320` (перекрытие в 80 токенов между соседними чанками для сохранения семантической целостности на границах фрагментов).
- **Векторизация:**
  - По умолчанию используются 1024-мерные векторные эмбеддинги (`dimensions: 1024`).
  - Поддерживаются провайдеры `"api"`, `"local"` и режим `"auto"`.

---

### 3. Гибридный алгоритм ранжирования (Hybrid Search)

При каждом обращении к памяти выполняется комбинированный поиск, объединяющий семантику векторов и точное лексическое совпадение ключевых слов:
$$\text{Score}_{\text{base}} = w_{\text{vector}} \cdot \text{Sim}_{\text{cosine}} + w_{\text{text}} \cdot \text{Score}_{\text{BM25}}$$

По умолчанию в коде заданы следующие веса:
- Вес векторной схожести (`vector_weight`): **0.7**
- Вес BM25 текстового поиска (`text_weight`): **0.3**
- Порог отсечения нерелевантных результатов (`min_score`): **0.7**
- Максимальное число извлекаемых результатов (`max_results`): **6**
- Весовые коэффициенты источников (`source_weights`): `workspace: 1.0`, `session: 1.0`, `global: 1.0`.

---

### 4. Экспоненциальный временной спад (Temporal Decay)

В коде `MemorySearchConfig` и `TemporalDecayConfig` реализован учет свежести информации. Экспоненциальный спад применяется исключительно к сессионным чанкам (`session`), предотвращая засорение контекста устаревшими фактами:
$$\text{DecayFactor} = 2^{-\frac{\Delta t}{T_{\text{half\_life}}}}$$
- Где $\Delta t$ — возраст записи, а $T_{\text{half\_life}}$ — период полураспада (задается в конфигурации `temporal_decay`).
- Значение `recency_decay` пересчитывается в период полураспада по формуле:
  $$\text{half\_life} \approx -\frac{1}{\log_2(\text{recency\_decay})}$$

---

### 5. Реранжирование для диверсификации: MMR (Maximal Marginal Relevance)

Чтобы модель не получала 6 одинаковых перефразированных цитат одного и того же куска кода, в пайплайне активирован алгоритм **MMR** (`MmrConfig`):
$$\text{MMR} = \arg\max_{D_i \in R \setminus S} \left[ \lambda \cdot \text{Sim}(D_i, Q) - (1 - \lambda) \cdot \max_{D_j \in S} \text{Sim}(D_i, D_j) \right]$$
- Алгоритм штрафует кандидатов, которые слишком близки к уже выбранным в итоговый набор чанкам $S$, гарантируя разнообразие контекста (diversity).

---

### 6. Пайплайн консолидации памяти: «Dream» (`v2_memory_dream.rs`)

Самая интересная часть реализации Memory V2 — фоновый фоновый процесс консолидации памяти, названный в кодовой базе **Dream** («Сновидение»):
1. **Накопление наблюдений (Observations):** В процессе работы агента все его действия, найденные баги и принятые решения регистрируются в виде черновиков (`pending observations`).
2. **Триггеры консолидации:**
   - Превышение минимального количества накопленных событий: `V2_DREAM_MIN_PENDING_COUNT = 20`.
   - Превышение максимального времени ожидания: `V2_DREAM_MAX_PENDING_AGE = 24 часа`.
   - Ручной вызов оператором или завершение сессии.
3. **Фоновая сессия консолидации:**
   - Запускается специальный таймаут-контролируемый процесс (`V2_DREAM_MODEL_TIMEOUT = 30 мин`, `IDLE_TIMEOUT = 15 мин`).
   - Модель перечитывает сырые наблюдения, удаляет шум, объединяет разрозненные факты в структурированные выводы и генерирует план обновления графа долговременной памяти.
4. **Транзакционное применение (Promotion):**
   - Результаты консолидации атомарно продвигаются в постоянное хранилище с механизмом повторных попыток при конкурентной блокировке (`V2_PROMOTION_MAX_RETRIES = 120`, интервал 30 секунд).
   - Диспозиции выполнения четко типизированы: `Completed`, `Shadow`, `Recovered`, `NoWork`, `Busy`, `Failed`, `Cancelled`, `Disabled`.

---

### 7. Телеметрия и мониторинг памяти (`memory_observation.rs`)

Каждая инъекция памяти в промпт тщательно логируется через `xai_grok_telemetry`:
- `result_count`, `total_snippet_chars`, `top_score`, `configured_min_score`
- `injection_duration_ms`, `injected_bytes`, `estimated_tokens`
- Количество записей из глобального и рабочего пространств (`global_entry_count`, `workspace_entry_count`)
- Флаги повторного использования кэша (`was_reused`) и использования компактного индекса (`compact_index`).

Благодаря этому система точно знает, сколько токенов тратится на долговременную память и насколько извлеченные воспоминания повлияли на финальный результат.
