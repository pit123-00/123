# Отчёт 3: Архитектурное устройство OpenClaw и Pi

В данном отчёте рассматривается архитектура проектов [openclaw/openclaw](https://github.com/openclaw/openclaw) и [earendil-works/pi](https://github.com/earendil-works/pi) с точки зрения структуры системных слоёв, топологии сервисов, сетевых протоколов, межпроцессного взаимодействия (IPC) и распределения ответственности.

---

## 1. Архитектурная топология OpenClaw

OpenClaw построен по принципу **многокомпонентного сервисного хаба (Hub-and-Spoke / Client-Server Daemon Topology)**:

```
                      +--------------------------------------+
                      |      Клиенты и Каналы Ввода          |
                      | (Telegram, Slack, Discord, Web, PTY) |
                      +-------------------+------------------+
                                          |
                                    HTTP / WebSocket
                                          v
+---------------------------------------------------------------------------------+
|                                OPENCLAW GATEWAY                                 |
|                                                                                 |
|  +--------------------+   +-----------------------+   +----------------------+  |
|  | Ingress Controller |-->| Preauth & Rate-Limit  |-->| WS Connection Router |  |
|  +--------------------+   +-----------------------+   +----------+-----------+  |
|                                                                  |              |
|  +-------------------------------------------------------------+ |              |
|  |             Gateway Method Registry (540+ методов)          |<+              |
|  |  [health, channels, config, doctor, exec, sessions, mcp]    |                |
|  +-----------------------------+-------------------------------+                |
|                                |                                                |
|                                v                                                |
|  +-----------------------------+-------------------------------+                |
|  |                 State DB Engine (SQLite WAL)                |                |
|  |   [sessions, transcripts, credentials, device pairings]     |                |
|  +-----------------------------+-------------------------------+                |
+--------------------------------|------------------------------------------------+
                                 | IPC / Tunnels
                                 v
+---------------------------------------------------------------------------------+
|                              NODE-HOST WORKERS                                  |
|                                                                                 |
|  +-----------------------+  +-----------------------+  +---------------------+  |
|  | Worker 1: Agent Turn  |  | Worker 2: Subagents   |  | Worker 3: Sandbox   |  |
|  | Execution Runtime     |  | Tree Management       |  | & Docker Isolation  |  |
|  +-----------------------+  +-----------------------+  +---------------------+  |
+---------------------------------------------------------------------------------+
```

### Ключевые компоненты архитектуры OpenClaw:

### 1.1. Gateway Server и реестр GatewayMethodRegistry (`src/gateway/server-methods.ts`, `core-descriptors.ts`)
- **Сетевое ядро**:
  - Управляет жизненным циклом HTTP и WebSocket серверов (`http-listen.ts`, `ws-connection.ts`).
  - Содержит адаптивную защиту рукопожатия `preauth-connection-budget.ts`, ограничивающую количество неаутентифицированных сокетов в единицу времени, и контроллер `control-plane-rate-limit.ts` (`consumeControlPlaneWriteBudget`), защищающий контрол-плейн от флуда запросами на запись.
- **Архитектура GatewayMethodRegistry**:
  - Центральный реестр методов диспетчеризации насчитывает **более 540 канонических спецификаций методов** (`CORE_GATEWAY_METHOD_SPECS`), управляющих всеми сущностями шлюза.
  - Каждая запись определяет точное имя метода, категорию обработчика, требуемый скоуп доступа оператора и ограничения версий API:
    - **`operator.read`**: мониторинг состояния (`health`, `status`), диагностика стабильности (`diagnostics.stability`), просмотр логов (`logs.tail`), статус каналов связи (`channels.status`), метрики расходов токенов (`usage.status`, `usage.cost`), каталоги TTS (`tts.status`, `tts.providers`, `tts.personas`).
    - **`operator.write`**: динамическое переключение конфигураций (`config.set`, `config.patch`, `config.apply`), сброс и дедупликация памяти (`doctor.memory.resetDreamDiary`, `doctor.memory.dedupeDreamDiary`), переключение голосов и провайдеров озвучки (`tts.setProvider`, `tts.setPersona`).
    - **`operator.admin`**: полное администрирование каналов (`channels.start`, `channels.stop`, `channels.logout`), управление правами выполнения команд и подтверждениями человека (`exec.approvals.set`, `exec.approval.resolve`).
  - **Дескрипторы политик вызова (`core-descriptor-options.ts`)**:
    - `CONTROL_PLANE_WRITE`: выделяет методы, изменяющие конфигурацию ядра с автоматическим списанием лимита бюджета записи.
    - `SESSION_METADATA_READ` и `SESSION_WRITE`: разграничивают права на чтение метаданных и модификацию транскрипта сессии.
    - `PROFILE_DEPENDENT` и `PROFILE_STARTUP`: методы, доступные только после полной загрузки профиля аутентификации.
    - `UNADVERTISED`: скрытые служебные методы для внутреннего межпроцессного взаимодействия.

### 1.2. Подсистема идентификации и туннелей (`src/gateway/openclaw-id/`)
- **Автономная система Identity**:
  - Полный цикл аутентификации и сопряжения распределенных узлов, мобильных клиентов (Android, iOS) и локальных воркеров **без внешних сторонних Identity Providers (IDP)**, таких как Auth0 или Firebase.
- **Криптографическая связка устройств (Device Token Bindings)**:
  - Каждое клиентское устройство при подключении генерирует пару криптографических ключей (`gateway-key.ts`, `device-token-binding.ts`).
  - Для подключения нового узла используется процедура безопасного сопряжения (`node-pairing.ts`) с генерацией одноразовых билетов с ограниченным временем жизни (`node-invites.ts`, `invite-sweep.ts`).
- **Двусторонние защищенные туннели (`tunnel-ipc.ts`, `tunnel-supervisor.ts`)**:
  - `tunnel-supervisor.ts` поддерживает постоянное мультиплексированное сетевое соединение, работающее поверх WebSocket и бинарных фреймов.
  - Туннель обеспечивает прозрачный проброс HTTP/WS вызовов сквозь NAT, корпоративные фаерволы и динамические IP-адреса без необходимости проброса портов на роутере.
  - Позволяет распределенным воркерам и агентам безопасно взаимодействовать с центральной базой данных шлюза и шиной сообщений.

### 1.3. Служба каналов (`src/channels/`)
- **Многоканальный адаптер двусторонней связи**:
  - Включает коннекторы к широкому спектру платформ: Telegram, Discord, Slack, WhatsApp, Signal, iMessage, IRC, Google Chat, Microsoft Teams.
- **Нормализация входящих событий**:
  - Преобразует платформо-зависимые вебхуки и события сокетов в единый стандартизированный формат сообщений `gateway-protocol` (`conversation-binding-route-facts.ts`, `chat-meta.ts`).
  - Автоматически классифицирует контекст взаимодействия: личная переписка (`direct-dm.ts`), цепочки тредов (`thread-bindings-policy.ts`) или публичные каналы с контролем явных упоминаний бота (`mention-pattern-policy.ts`).
- **Композитор промежуточных черновиков (`progress-draft-compositor.ts`)**:
  - Отвечает за реактивную обратную связь с пользователем в реальном времени во время длительных рассуждений модели.
  - Формирует динамически обновляемые черновики сообщений в чате мессенджера, отображая текущий этап работы агента и визуальные глифы выполняемых инструментов (`progress-tool-glyphs.ts`).
- **Очереди и защита от дублирования**:
  - Реализует механизм `inbound-debounce-policy.ts` для подавления повторных запросов вебхуков при сетевых задержках и очереди плавного вывода ответов с учетом rate limits целевых мессенджеров.

### 1.4. Пул воркеров Node-Host (`src/node-host/`)
- Изоляция выполнения кода и моделей. Каждый агентный раунд (agent turn) может запускаться в изолированном дочернем процессе Node.js с контролем выделяемой оперативной памяти (`worker-heap-flag.mjs`).
- При исчерпании лимитов супервизор мягко завершает процесс и производит автоматическое восстановление через `node-runtime-recovery.mjs`.

## 2. Архитектурная топология Pi

Pi построен по принципу **слоистой компонуемой библиотеки (Layered Modular Architecture)**, где каждый уровень является независимым модулем с четким API:

```
+---------------------------------------------------------------------------------+
|                             APPLICATIONS / RUN MODES                            |
|                                                                                 |
|   +--------------------+   +-----------------------+   +---------------------+  |
|   |  Interactive TUI   |   |   Headless RPC Mode   |   |  Direct CLI / Print |  |
|   |  (@pi-tui + Mouse) |   |    (JSONL stdin/out)  |   |    One-shot Runs    |  |
|   +---------+----------+   +-----------+-----------+   +----------+----------+  |
+-------------|--------------------------|--------------------------|-------------+
              |                          |                          |
              +--------------------+     |     +--------------------+
                                   v     v     v
+---------------------------------------------------------------------------------+
|                        @earendil-works/pi-coding-agent                          |
|                                                                                 |
|  +---------------------------------------------------------------------------+  |
|  | AgentSession (Жизненный цикл сессии, ветвление, подписка на события)     |  |
|  +-------------------------------------+-------------------------------------+  |
|                                        |                                        |
|  +--------------------+   +------------v-----------+   +---------------------+  |
|  | Compaction Engine  |   | File Mutation Queue    |   | Extension Runner    |  |
|  | (Сжатие контекста) |   | (Атомарные диффы)      |   | (Jiti Loader)       |  |
|  +--------------------+   +------------+-----------+   +---------------------+  |
+----------------------------------------|----------------------------------------+
                                         |
                                         v
+---------------------------------------------------------------------------------+
|                         @earendil-works/pi-agent-core                           |
|                                                                                 |
|  +---------------------------------------------------------------------------+  |
|  | Agent Loop (Асинхронный цикл рассуждения: Prompt -> Model -> Tools Loop)  |  |
|  +-------------------------------------+-------------------------------------+  |
|                                        |                                        |
|  +--------------------+   +------------v-----------+   +---------------------+  |
|  | Tool Pipeline      |   | Context Interceptors   |   | Stream Function     |  |
|  | (runToolCall)      |   | (before/after hooks)   |   | (streamSimple)      |  |
|  +--------------------+   +------------------------+   +---------------------+  |
+----------------------------------------|----------------------------------------+
                                         |
             +---------------------------+---------------------------+
             v                                                       v
+-----------------------------+                             +---------------------+
|    @earendil-works/pi-ai    |                             |  EXECUTION ENGINES  |
|  - Мультипровайдерный слой  |                             |  - @pi-mcp (Client) |
|  - Retry и стриминг         |                             |  - @pi-codemode     |
|  - Нормализация сообщений   |                             |    (QuickJS WASM)   |
+-----------------------------+                             |  - Native Bash PTY  |
                                                            +---------------------+
```

### Ключевые компоненты архитектуры Pi:
1. **`@earendil-works/pi-agent-core` (Базовое ядро агента)**:
   - Абстрагировано от файловой системы и UI. Реализует чистый конечный автомат `agent-loop.ts`.
   - Запускает стрим модели через `StreamFn`, обнаруживает вызовы инструментов и обрабатывает их через `runToolCall`.
2. **`@earendil-works/pi-coding-agent` (Оркестратор разработки)**:
   - Класс `AgentSession` инкапсулирует состояние, модель, уровень рассуждений (`thinkingLevel`) и ветвление.
   - Механизм `file-mutation-queue.ts` гарантирует бесконфликтное последовательное применение диффов к файлам проекта.
   - Динамический загрузчик расширений на базе `jiti` (`jiti-loader.ts`).
3. **`@earendil-works/pi-codemode` (Песочница QuickJS WebAssembly)**:
   - Выполнение генерируемых скриптов в изолированной WASM-памяти без необходимости запуска контейнеров Docker.

## 3. Сравнительный анализ архитектурных подходов

| Архитектурный аспект | OpenClaw | Pi |
| :--- | :--- | :--- |
| **Связность компонентов (Coupling)** | Тесная вертикальная интеграция вокруг Gateway, SQLite и внутреннего протокола `openclaw-id`. | Слабая связанность (Loose coupling), чистые библиотеки с возможностью автономного использования каждого пакета. |
| **Сетевые интерфейсы** | Центральный WebSocket сервер, HTTP Webhooks, SSH/PTY мосты, внешние сетевые туннели. | JSONL над стандартными потоками ввода-вывода (stdin/stdout) в режиме RPC; отсутствие накладных расходов на сетевые сокеты для локального агента. |
| **Масштабирование** | Горизонтальное подключение внешних нод и воркеров через распределенные туннели шлюза. | Локальный параллелизм через воркеры или распределение через Durable Workers / Cloudflare Workers. |
| **Граница доверия и изоляция** | Жесткая изоляция внешними процессами операционной системы и контейнерами. | Программная изоляция в WASM песочнице (QuickJS) + строгие проверки схем аргументов на TypeBox. |

---

## Резюме третьего отчёта
Архитектура **OpenClaw** — это архитектура **крупного распределенного корпоративного шлюза**, где во главе угла стоят централизованное управление состоянием, надежность сетевых каналов, безопасность доступа и координация фоновых демонов.

Архитектура **Pi** — это архитектура **модульного микроядерного компилятора/рантайма для ИИ-агентов**, где каждый уровень строго изолирован, оптимизирован по скорости и может использоваться независимо — от простого CLI терминала до встроенного ядра в браузере или Cloudflare Workers.
