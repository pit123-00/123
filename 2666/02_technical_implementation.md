# Отчёт 2: Техническая реализация и внутреннее устройство решений

Настоящий отчёт детально разбирает исходный код обоих проектов: организацию многопоточности, сетевые интерфейсы, протоколы MCP, подсистемы хранения, выполнение инструментов и преимущества технической реализации каждой кодовой базы.

## 1. Техническая реализация `grok-build` (xAI)

### 1.1. Архитектура рабочего пространства и крейтов (Crates Layout)
Репозиторий `grok-build` содержит свыше 100 специализированных Rust-крейтов, разбитых на три группы:
1. `crates/codegen/`: функциональные модули агента (`xai-grok-agent`, `xai-grok-config`, `xai-grok-tools`, `xai-grok-mcp`, `xai-grok-sandbox`, `xai-prompt-queue`, `ptyctl` и др.).
2. `crates/common/`: общие низкоуровневые сервисы (`xai-tool-runtime`, `xai-circuit-breaker`, `xai-tool-protocol`, `xai-tracing`).
3. `crates/build/`: билд-скрипты и кодогенераторы protobuf/gRPC (`xai-proto-build`).

### 1.2. Конкурентность и жизненный цикл (Concurrency & Lifecycle)
- **Rust + Tokio:** Вся асинхронная модель построена на Tokio runtime.
- **Изоляция мутаций (Immutability by default):** Структура `Agent` после инициализации в `AgentBuilder::build()` иммутабельна. Состояние инструментов изолировано в `Arc<ToolBridge>`, где конкурентные модификации защищаются внутренними примитивами синхронизации (`tokio::sync::Mutex`, `RwLock`).
- **Пакетная обработка промптов (`xai-prompt-queue`):** При поступлении новых пользовательских запросов во время выполнения текущего хода (turn), очередь промптов применяет правила объединения `can_merge_follower`, предотвращая фрагментацию контекста и лишние сетевые вызовы.
- **Circuit Breaker (`xai-circuit-breaker`):** Защита всех внешних сетевых вызовов (LLM API, внешние интеграции). Реализует протокольно-независимый скользящий автомат состояний:
  $$\text{Trip condition: } \text{sample\_count} \ge \text{min\_samples} \land \frac{\text{error\_count}}{\text{sample\_count}} \ge \text{threshold}$$

### 1.3. Терминальная подсистема `ptyctl`
Вместо использования стандартных скриптов-оберток или простых вызовов `std::process::Command`, `grok-build` включает собственный сервер терминалов:
- Построен на базе библиотеки `alacritty_terminal`.
- Ведет полную эмуляцию виртуального терминала (VT/ANSI) в памяти.
- Предоставляет REST API для взаимодействия с PTY-сессиями.
- Позволяет агенту читать не просто текстовый stdout, а полное состояние виртуального экрана со стилями, цветами и разметкой, а также эмулировать нажатия отдельных клавиш (`ptyctl::keys`).

### 1.4. Ядерная песочница и сетевая фильтрация
- **`xai-grok-sandbox`:** Использует библиотеку `nono`. Активируется на старте процесса:
  - Linux: **Landlock LSM** ограничивает доступ к файловой системе для агента и его потомков; **seccomp** блокирует сетевые сокеты для порождаемых процессов bash/команд.
  - macOS: **Seatbelt (sandbox_init)** накладывает профили системных вызовов.
- **`xai-grok-egress-proxy`:** Локальный HTTP/CONNECT-прокси. Каждому запуску инструмента выдаются уникальные учетные данные в `userinfo` URL-прокси. Прокси перехватывает запросы и проверяет их через `decider`, запрашивая подтверждение у пользователя при попытке доступа к неизвестным хостам.

### 1.5. Протокол инструментов и интеграция MCP
- В крейте `xai-grok-mcp` изолированы версии `rmcp` 2.1 и `reqwest` 0.13, исключая конфликт зависимостей с остальным кодом, использующим `reqwest` 0.12.
- Единый контракт `Tool` в `xai-tool-runtime`:
  ```rust
  pub trait Tool: Send + Sync {
      fn name(&self) -> &str;
      fn description(&self) -> &str;
      fn execute(&self, ctx: ToolCallContext, input: Value) -> ToolStream;
  }
  ```
- Стриминг вывода инструментов через `ToolStream` и явные уведомления `ToolNotification`.

## 2. Техническая реализация `opencode` (Anomaly)

### 2.1. Парадигма Effect TS и архитектура сервисов
`opencode` полностью построен вокруг библиотеки функционального программирования **Effect TS**:
- Каждый модуль оформлен как `Context.Service` (например, `Session.Service`, `Agent.Service`, `Database.Service`, `Job.Service`).
- Внедрение зависимостей управляется через `Layer` и `LayerNode`, гарантируя строго типизированный граф зависимостей и детерминированную очистку ресурсов через `Scope.Scope`.
- Ошибки типизированы на уровне компилятора (`Schema.TaggedError`, отсутствие unhandled rejection).

### 2.2. Управление параллелизмом и планировщик сессий
- **Effect Fibers:** Легковесные зеленые потоки (файберы) вместо тяжелых OS-потоков.
- **`SessionRunCoordinator`:** Управляет выполнением сессий с гарантией взаимного исключения по ключам:
  - Метод `run(key)` стартует выполнение или подписывается на уже активный файбер.
  - Метод `wake(key, scope)` ("дверной звонок") регистрирует поступление новых данных в очередь. Если сессия сейчас активна, она не завершается после текущего шага, а выполняет повторный дренаж инбокса.
  - Метод `interrupt(key)` останавливает файбер сессии без разрушения структуры данных.

### 2.3. Хранилище состояния и событийная модель
- **SQLite + Drizzle ORM / effect-drizzle-sqlite:** Локальная реляционная база данных для персистентности сессий, сообщений, шагов и разрешений.
- **Event Bus (`Bus.Service`):** Центральная шина событий, позволяющая UI, TUI, веб-серверу и плагинам получать real-time обновления состояния (SSE стриминг через `@opencode/server/event-feed`).

### 2.4. Инновация: Code Mode
Вместо классического цикла «модель видит список из 50 инструментов -> выбирает один -> ждет результат -> выбирает второй», `opencode` реализует **Code Mode**:
- LLM генерирует TypeScript/JavaScript-код, использующий типизированный каталог доступных инструментов.
- Код выполняется в изолированном контексте рантайма `CodeModeTool`.
- Инструменты вызываются локально через `CodeModeExecution`, фильтруются и возвращают результат единым батчем (`ExecuteOutput`), экономя до 80% токенов и раундтрипов к LLM.

### 2.5. Мультиплатформенный PTY (`persistent-pty`)
- Демон отслеживания процессов PTY (`PersistentPty`), способный переживать перезапуск основного процесса CLI или веб-интерфейса.
- Механизм передачи дескрипторов и состояния (`Handoff`).
- Кроссплатформенная реализация: биндинги к `node-pty`, биндинги для Bun и поддержка окружений `workerd` (Cloudflare Workers).

## 3. Технические преимущества каждого решения

### Преимущества реализации `grok-build`:
1. **Беспрецедентная системная безопасность:**
   - Настоящая аппаратная и ядерная изоляция через `Landlock`, `Seatbelt`, `seccomp`. Никакой сгенерированный агентом скрипт не сможет выйти за границы рабочей директории на уровне вызовов ядра ОС.
   - Криптографически подписанные политики (Ed25519) и поддержка macOS MDM на уровне системных настроек.
2. **Нулевой runtime-оверхед и стабильность:**
   - Системный язык Rust гарантирует минимальное потребление оперативной памяти, отсутствие пауз сборщика мусора (GC) и высочайшую скорость работы с файловой системой (крейты `xai-fast-worktree`, `xai-fuzzy-file-search`).
3. **Глубокая эмуляция терминала:**
   - Интеграция `alacritty_terminal` дает возможность понимать фактическое состояние экрана консольных утилит (TUI, curses, интерактивные редакторы).
4. **Отказоустойчивость сети:**
   - Встроенный скользящий `CircuitBreaker` с min-sample калибровкой и локальный egress proxy с сессионной авторизацией.

### Преимущества реализации `opencode`:
1. **Элегантная архитектура эффектов (Effect TS):**
   - Композируемость сервисов, абсолютная типизация сайд-эффектов и ошибок, надежное управление жизненным циклом ресурсов через Scopes/Fibers.
2. **Продвинутая модель Code Mode:**
   - Возможность для модели писать код для взаимодействия с инструментами решает проблему раздувания контекста инструментами (tool definition bloat) и минимизирует задержку сложных пайплайнов.
3. **Гибкость и мультипровайдерность:**
   - Прямая интеграция с десятками провайдеров (OpenAI, Anthropic, Bedrock, Groq, Copilot, Ollama) через единый унифицированный слой `@opencode/ai`.
4. **Универсальность среды выполнения:**
   - Один и тот же код может работать в консоли (TUI), в десктопном приложении, в виде локального HTTP/SSE сервера или на Cloudflare edge workers.
