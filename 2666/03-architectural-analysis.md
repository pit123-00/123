# Отчёт 3: Архитектурный анализ Dokku и Dokploy на основе исходного кода

В данном отчёте проводится глубокий анализ архитектуры систем **Dokku** и **Dokploy** исключительно на основе исследования кодовых баз проектов. Рассматриваются архитектурные слои, модели предметной области, шины взаимодействия компонентов, жизненный цикл данных и механизмы безопасности.

---

## 1. Архитектурная топология систем

```
+-----------------------------------------------------------------------------------+
|                                 АРХИТЕКТУРА DOKKU                                 |
+-----------------------------------------------------------------------------------+
|  Пользователь / Git Push / SSH CLI                                                |
|       |                                                                           |
|       v                                                                           |
|  [ /dokku CLI Dispatcher (Bash) ] <--- sudo -u dokku                              |
|       |                                                                           |
|       v                                                                           |
|  [ Plugn Event / Hook Bus ]                                                       |
|       +---> plugins/common (Go)          ---> Локирование, чтение свойств         |
|       +---> plugins/config (Go)          ---> Хранилище переменных в файлах       |
|       +---> plugins/builder-* (Go/Bash)  ---> Сборка OCI-образов                  |
|       +---> plugins/scheduler-* (Go/Bash)---> docker-local (Procfile) / k3s (Helm)|
|       +---> plugins/*-vhosts (Go/Sigil)  ---> nginx / caddy / traefik conf        |
|                                                                                   |
|  Хранилище состояния: Файловая система (/home/dokku/<app>/, /var/lib/dokku/data/) |
+-----------------------------------------------------------------------------------+
```

```
+-----------------------------------------------------------------------------------+
|                                АРХИТЕКТУРА DOKPLOY                                |
+-----------------------------------------------------------------------------------+
|  Пользователь / Браузер / REST Client / AI Агенты                                 |
|       |                                 |                                         |
|       v (HTTP/WebSocket)                v (X-API-Key HTTP)                        |
|  [ Next.js Web Dashboard ]         [ apps/api Service (Hono) ]                    |
|       | (tRPC)                          | (Inngest Event Bus)                     |
|       v                                 v                                         |
|  [ packages/server (Business Logic Layer) ]                                       |
|       +---> Drizzle ORM <-------------> [ Хранилище: PostgreSQL ]                 |
|       +---> Traefik Dynamic Provider -> Маршрутизация трафика и Let's Encrypt     |
|       +---> Monitoring Daemon (Go)   -> Телеметрия CPU/RAM/Net                    |
|       |                                                                           |
|       +---> Local Executor (dockerode / Docker CLI)                               |
|       +---> Remote Executor (SSH Key -> execAsyncRemote -> Target VPS)            |
|       +---> Swarm Manager (Docker Swarm Overlay Network)                          |
+-----------------------------------------------------------------------------------+
```

## 2. Архитектурные уровни и декомпозиция подсистем

### Dokku (Unix-микроядро + плагины):
Кодовая база Dokku построена по принципу расширяемого микроядра с плоской шиной взаимодействия:
1. **Ядро маршрутизации команд (`/dokku`):**
   * Выполняет разбор аргументов командной строки (`parse_args`).
   * Реализует эскалацию/деэскалацию привилегий: большинство команд выполняется от имени непривилегированного системного пользователя `dokku`, а критические операции (установка плагинов, добавление SSH-ключей, инициализация k3s) требуют `root`.
   * Определяет алиасы команд и маршрутизирует вызовы в соответствующие исполняемые файлы в `$PLUGIN_ENABLED_PATH`.
2. **Шина плагинов (`plugn`):**
   * Плагины полностью автономны. Взаимодействие между плагинами происходит через хуки (triggers). Например, когда плагин `git` завершает получение кода, он вызывает триггер `receive-app`, который запускает цепочку:
     `git-build-app-repo` -> `core-post-extract` -> `builder-detect` -> `builder-build` -> `builder-release` -> `scheduler-deploy` -> `core-post-deploy` -> `proxy-build-config`.
   * Ни один плагин не имеет жестких компиляционных зависимостей от другого (loose coupling). Обмен данными осуществляется через аргументы командной строки, потоки STDIN/STDOUT или чтение свойств через `PropertyGet` из общего хранилища.
3. **Слой абстракции планировщика (Scheduler Abstraction):**
   * Dokku отделяет этап сборки артефакта от этапа его запуска. Плагины билдеров отдают готовый Docker Image Tag, а планировщик решает, как его запустить:
     * `scheduler-docker-local`: запускает одиночные контейнеры на том же хосте, конфигурируя локальную docker bridge сеть.
     * `scheduler-k3s`: генерирует K8s манифесты и Helm-релизы, отправляя их в API-сервер Kubernetes.

### Dokploy (Многоуровневый сервисный монолит):
Кодовая база Dokploy следует классической чистой слоистой архитектуре (Clean Architecture / Service-Repository pattern):
1. **Слой представления (Presentation Layer):**
   * Веб-дашборд на React / Next.js (`apps/dokploy/`).
   * REST API сервис на Hono (`apps/api/src/index.ts`).
2. **Слой маршрутизации и валидации (API & Contract Layer):**
   * tRPC роутеры (`apps/dokploy/server/api/routers/`) валидируют типы через Zod-схемы, генерируют OpenAPI спецификацию (`pnpm generate:openapi`) и синхронизируют её в клиентские SDK и MCP-репозиторий.
3. **Слой бизнес-логики (Domain / Service Layer):**
   * Модули в `packages/server/src/services/` изолируют доменную логику: управление сущностями `application`, `compose`, `database`, `destination`, `server`.
   * Изоляция транзакций и работы с базой данных через Drizzle ORM.
4. **Слой асинхронных задач и оркестрации (Job Execution Layer):**
   * Движок Inngest гарантирует надежность выполнения пайплайнов (at-least-once execution, retry policies, cancellation token handling).
5. **Слой инфраструктурных драйверов (Infrastructure Layer):**
   * Прямое управление Docker Engine через библиотеку `dockerode`.
   * Удаленная оркестрация через SSH (`execAsyncRemote`).
   * Драйвер Traefik (`utils/traefik/`): генерация динамических конфигураций маршрутизаторов, сервисов и промежуточных слоев (middlewares).

## 3. Модель домена данных (Data Model Comparison)

### Модель данных Dokku:
* Модель данных децентрализована и хранится на диске:
  * Сущность верхнего уровня — **App** (имя приложения в файловой системе).
  * Параметры приложения хранятся в виде key-value пар в директории плагина:
    `/var/lib/dokku/data/<plugin-name>/<app-name>/<key>`.
  * Переменные окружения хранятся в файле `/home/dokku/<app>/ENV`.
  * Нет сущностей организации, проекта, пользователей или ролей внутри ядра — всё определяется правами доступа к серверу через SSH-ключи.

### Модель данных Dokploy (Схема PostgreSQL):
* Доменная модель строго нормализована и реляционна (`packages/server/src/db/schema/`):
  * **Organization:** Владеет всеми ресурсами, биллингом (Stripe), SSO-настройками и участниками.
  * **User & Member:** Роли `owner`, `admin`, `member`, dynamic access control policies.
  * **Project & Environment:** Проект содержит окружения (Production, Staging, Dev), внутри которых изолируются сервисы. Окружения могут наследовать и переопределять переменные окружения проектов.
  * **Application:** Хранит конфигурацию исходного кода (Git repo, branch, credentials), стратегию сборки (buildType), лимиты ресурсов (CPU, Memory), настройки превью-деплоев.
  * **Compose:** Хранит манифесты docker-compose, флаги изоляции томов (`isolatedDeploymentsVolume`) и правила переименования сервисов для исключения коллизий.
  * **Databases:** Отдельные таблицы для каждого типа БД с полями для подключения, внутренних портов и привязок к расписаниям бэкапов.
  * **Server:** Записи внешних серверов (IP, SSH-порт, приватный ключ) для мультинодового управления.

## 4. Жизненный цикл развертывания (Deployment Lifecycle)

### Сравнительная таблица фаз развертывания:

| Фаза жизненного цикла | Dokku (по коду) | Dokploy (по коду) |
| :--- | :--- | :--- |
| **1. Триггер** | Git push в локальный bare-репозиторий или вызов `dokku git:sync / ps:rebuild`. Блокирует терминал. | Webhook от Git-провайдера, клик в UI или вызов `POST /deploy` с API Key. Асинхронно ставится в Inngest. |
| **2. Блокировка конкурентности** | Блокировка через системные файлы локов: `common.LockDirectory` на директории приложения. | Inngest concurrency group: `{ key: "event.data.serverId", limit: 1 }` — строго один деплой на сервер за раз. |
| **3. Доставка исходников** | Распаковка архива Git дерева во временную папку `/tmp/dokku-...`. | Клонирование репозитория на целевой сервер через Git CLI по SSH или извлечение через API провайдера. |
| **4. Сборка (Build)** | Определение билдера через триггеры `builder-detect` -> сборка Docker-образа в локальный daemon. | Выбор билдера на основе поля `buildType` в БД -> генерация bash-скрипта сборки -> выполнение локально или удаленно. |
| **5. Проверки (Healthchecks)** | `check-deploy`: парсинг `app.json` или файла `CHECKS` -> запуск `docker-container-healthchecker` против порта нового контейнера. | Healthcheck контейнера Docker / Docker Swarm Healthcheck (`docker service inspect`). |
| **6. Переключение трафика** | Атомарная генерация конфигурации Nginx/Caddy -> валидация (`nginx -t`) -> перезагрузка прокси (`nginx -s reload`). | Traefik опрашивает Docker API или считывает динамический YAML; переключение происходит мгновенно в памяти демона без релоада. |
| **7. Очистка старых ревизий** | Отправка `SIGTERM` старым контейнерам, ожидание таймаута `wait-to-retire` (дефолт 60 сек) -> `docker kill`. | Docker Swarm выполняет rolling update автоматически. Для Compose: запуск нового стека с удалением неактуальных контейнеров (`docker compose up -d --remove-orphans`). |

## 5. Архитектура безопасности и изоляции

### Dokku:
1. **Модель привилегий ОС:** Dokku опирается на стандартную модель прав Linux (дискреционный контроль доступа DAC). Все процессы приложений выполняются под изолированными пользователями внутри Docker.
2. **Аутентификация CLI:** Управление ключами через утилиту `sshcommand` (`plugins/ssh-keys`). Команды ограничены вызовом бинарника `/dokku`.
3. **Хранение секретов:** Переменные окружения хранятся в открытом виде на файловой системе хоста с правами `0600` (доступ только пользователю `dokku` и `root`).

### Dokploy:
1. **Комплексная защита на уровне приложения (App-level Security):**
   * Аутентификация через `Better-Auth` с поддержкой MFA (двухфакторная аутентификация), WebAuthn/Passkeys, SSO (SAML/OIDC).
   * Сессии валидируются на каждом запросе к tRPC/Hono.
2. **Криптографическая защита данных:**
   * Все секреты (пароли баз данных, токены GitHub, SSH приватные ключи) перед записью в PostgreSQL шифруются алгоритмом `AES-256-GCM` (`packages/server/src/lib/encryption.ts`).
3. **Изоляция сети:**
   * Для каждого приложения и compose-стека создаются выделенные Docker Networks. Трафик между проектами изолирован, доступ наружу открывается строго через внутреннюю сеть Traefik (`dokploy-network`).

## 6. Резюме архитектурного сравнения

* **Dokku** — образец бессерверного (daemonless) дизайна для PaaS: у него нет фонового управляющего демона, нет центральной базы данных, состояние полностью совпадает с состоянием файлов на хосте, а расширяемость через хуки делает систему практически вечной и не зависящей от версий сторонних фреймворков.
* **Dokploy** — образец современной облачной управляющей платформы (Control Plane): разделение на Control Plane (Next.js/Hono/Postgres) и Data Plane (целевые серверы с Docker/Traefik), асинхронные пайплайны задач и строгие контракты данных позволяют масштабировать платформу на управление целым парком серверов.
