# Отчет 3: Инновационные функции `aif-handoff` и их техническая логика

Репозиторий `aif-handoff` реализует ряд продвинутых инженерных решений, которые редко встречаются в обычных наборах промптов для LLM-агентов. Ниже представлены ключевые инновационные функции и описание того, как они работают "под капотом".

---

## 1. Параллельная реализация через Git Worktrees
**Инновация:** LLM-агенты могут работать над разными частями кода одновременно, не конфликтуя друг с другом.
**Как это работает технически:**
1.  `implement-coordinator` парсит план задачи и строит **Граф Зависимостей (Dependency Graph)**.
2.  Задачи разбиваются на "Слои" (Layers). Все задачи в одном слое независимы друг от друга.
3.  Для каждой задачи в слое координатор спавнит `implement-worker`.
4.  Вместо редактирования одних и тех же файлов, система использует команду `git worktree add`. Каждый `implement-worker` получает свою изолированную копию файловой системы (worktree), привязанную к отдельной ветке.
5.  По завершении работы воркеров, координатор выполняет `git merge`, сводя параллельные изменения в основную рабочую ветку, и переходит к следующему слою зависимостей.

## 2. Model Context Protocol (MCP) для управления состоянием
**Инновация:** Агенты напрямую управляют базой данных и статусами задач в UI, не выходя из сессии LLM.
**Как это работает технически:**
В отличие от классического подхода, где LLM просто генерирует текст, `aif-handoff` предоставляет агентам инструменты MCP (Model Context Protocol), такие как `mcp__handoff__handoff_update_task` или `mcp__handoff__handoff_push_plan`.
1.  Агент решает, что этап завершен.
2.  Он вызывает функцию MCP (tool call).
3.  Сервер Hono (REST API) принимает этот вызов, обновляет статус в БД SQLite.
4.  БД через WebSocket (`/ws`) кидает ивент `task:moved` на фронтенд (React), и карточка визуально перепрыгивает в колонку `Review`.
5.  Это позволяет агенту самостоятельно двигать задачи по Kanban-доске.

## 3. Auto-Mode (Автоматическое исправление после ревью)
**Инновация:** Замкнутый цикл обратной связи без участия человека. Если код плохой, агент сам вернется и перепишет его.
**Как это работает технически:**
1.  Когда `implement-worker` заканчивает код, статус меняется на `review`.
2.  Координатор запускает `review-sidecar` и `security-sidecar`.
3.  Они читают `git diff` и пишут комментарии в БД через MCP.
4.  Если включен флаг `autoMode = true`, фоновый Node.js процесс анализирует эти комментарии. Если найдено критическое замечание, процесс программно переводит статус из `review` обратно в `implementing` (эмулируя нажатие кнопки "Request Changes").
5.  Координатор снова просыпается, видит задачу в `implementing`, читает новые комментарии из базы и снова запускает `implement-worker` на доработку. Цикл продолжается до тех пор, пока сайдекары не выдадут "LGTM" (Looks Good To Me).

## 4. Heartbeat Liveness & Watchdog (Отказоустойчивость)
**Инновация:** Защита от "тихих падений" и галлюцинаций LLM, застрявших в бесконечном цикле.
**Как это работает технически:**
1.  Агенты обязаны посылать пульс (`lastHeartbeatAt`) в БД во время длительных операций.
2.  Фоновый процесс-наблюдатель (Watchdog), работающий через `node-cron`, просыпается каждые 30 секунд.
3.  Он сканирует базу `tasks`. Если задача находится в статусе `implementing` или `planning`, но `lastHeartbeatAt` старше заданного таймаута (например, процесс Claude SDK упал из-за ошибки API), система маркирует задачу как "stale".
4.  Watchdog автоматически переводит задачу в статус `blocked_external` и запускает экспоненциальный бэкофф (`retryAfter`). Через некоторое время координатор попытается перезапустить агента с чистого листа.

## 5. Roadmap Import с генерацией графа (Haiku Agent)
**Инновация:** Мгновенное превращение человеческого текстового роадмапа в набор связанных задач в БД.
**Как это работает технически:**
1.  Пользователь кидает POST запрос на импорт из `.ai-factory/ROADMAP.md`.
2.  Сервер запускает быструю и дешевую модель (`Haiku` через Agent SDK), которая парсит Markdown.
3.  Haiku преобразует текст в структурированный JSON с задачами, связями и тегами (`phase:<N>`, `rm:<alias>`).
4.  Данные проходят строгую валидацию через схемы `Zod`.
5.  Система использует механизм дедупликации (идемпотентность по хешу `normalizedTitle`), чтобы при повторном импорте не плодить дубликаты. Затем WebSocket рассылает команду `agent:wake`, и агенты тут же начинают разбирать созданный бэклог.
