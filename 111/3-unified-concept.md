# Отчет 3: Концепция единой продвинутой системы (Симбиоз)

Данный отчет предлагает концепцию единой системы, которая объединяет лучшие практики из `opencode` (Workflow-based) и `cloude` (Role-based), устраняя их избыточность и сглаживая противоречия.

---

## 1. Фундаментальный конфликт подходов
Перед объединением необходимо разрешить главный конфликт:
**Жесткий линейный конвейер (`opencode`) VS Автономная реактивность агентов (`cloude`).**

В `opencode` процесс управляется **Артефактами** (пока нет файла Плана, код не пишется).
В `cloude` процесс управляется **Ролями** (если есть баг, вызывается Дебаггер, минуя длинные планы).

**Решение:** Внедрение "Двухконтурной системы" (Dual-Track System).
*   **Контур А (Быстрый/Реактивный):** Для багфиксов и мелких задач работает ролевая модель `cloude` (`Debugger` -> `Executor`), без создания тяжеловесных планов.
*   **Контур Б (Медленный/Стратегический):** Для новых фич и рефакторинга работает конвейер `opencode` с жесткими артефактами (Research -> Design -> Plan -> Implement), но внутри каждой фазы работают специализированные агенты из `cloude`.

---

## 2. Что объединить (Симбиоз подходов)

### А. Конвейер как основа, Роли как исполнители
Мы берем пайплайн из `opencode`, но заменяем безликих "subagents" на мощных профильных агентов из `cloude`.
*   **Фаза Research:** Выполняется агентами `Analyst` и `Scientist` (из cloude).
*   **Фаза Design:** Управляется `Planner` и строго ревьюится `Architect` и `Critic` (из cloude, с их multi-perspective подходом).
*   **Фаза Implement:** Оркестрируется `Lead` (из opencode), который раздает задачи `Executor` (из cloude), а проверяют `Test-engineer` и `Security-reviewer`.

### Б. Формула Качества + Ограничения Ролей (Constraints)
*   Берем из `opencode` **Управление контекстом**: Жесткий сброс контекста при переходе между фазами. Никакого переиспользования чатов. Формула качества: `(Correctness + Completeness) / (Size + Noise)`.
*   Берем из `cloude` **Ограничения агентов**: `Architect` остается READ-ONLY. `Critic` использует поиск того, чего "не хватает" (Gap analysis). Обязательное использование протокола `RALPLAN-DR` (консенсус) на фазе Design.

### В. Динамические петли обратной связи (Dynamic Feedback Loops)
Встраиваем в жесткий конвейер `opencode` механику "3-failure circuit breaker" из `cloude`. Если `Executor` на фазе реализации трижды не может пройти тесты, система автоматически вызывает `Architect` для пересмотра Design-документа, создавая контролируемый шаг назад, а не ломая весь процесс.

---

## 3. Что убрать (Избыточное и конфликтующее)

1.  **Удалить генерацию локальных стандартов (opencode Phase 0.5):** Стандарты проекта должны быть глобальными и статичными. Агенты должны их только читать, а не генерировать заново для каждой задачи.
2.  **Убрать зоопарк микро-ревьюеров (cloude):** Слить `code-reviewer`, `code-simplifier`, `verifier` и `qa-tester` в единую роль **Quality Assurance (QA)** или **Critic**. Избыточная фрагментация замедляет работу.
3.  **Убрать жесткое моб-программирование с 5 агентами (opencode):** Использовать динамический спавн ревьюеров только по мере необходимости. Если `Executor` (cloude) отработал с нулевыми ошибками `lsp_diagnostics`, достаточно одного финального ревью, а не консилиума из 4-х агентов.
4.  **Снизить микро-менеджмент артефактов (opencode):** Не сохранять "мысли" агентов (`thoughts/...`) в файловую систему. Сохранять только ключевые вехи: `Design.md` и `Plan.md`.

---

## 4. Резюме единой продвинутой системы
Идеальная система (Hybrid Agent Workflow) — это **"Ленивый Конвейер с Жесткими Ролями"**:
1.  **Триггер:** Пользователь дает задачу.
2.  **Роутинг:** Система определяет сложность (Fast-track или Strategic).
3.  **Исполнение:**
    *   Агенты со строгими ролями (из `cloude`) выполняют задачи.
    *   Передача контекста между ними идет исключительно через утвержденные Markdown-артефакты (из `opencode`), что исключает "глухой телефон" и перегрузку окон контекста LLM.
4.  **Контроль:** Выделенный `Critic` с gap-анализом защищает гейты качества перед написанием кода.
