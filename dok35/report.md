
# Отчет по архитектуре SurrealDB (Технические решения и логика)

В этом отчете подробно рассматривается, как логически и технически работают основные концепции хранения и моделирования данных в SurrealDB: Документное хранилище, Реляционные концепции, Графовая база данных и Spatial/GeoJSON.

---

## 1. Документное хранилище (Document Store)

### Логическая работа
SurrealDB может работать как schema-less (без схемы) или schema-full (со строгой схемой) документная база данных. В режиме без схемы пользователи могут вставлять произвольные JSON-подобные данные. В режиме со схемой можно определять поля (fields) для таблиц.
Основной единицей хранения является запись (Record), которая идентифицируется уникальным `RecordId`. Записи принадлежат таблицам.

### Техническая реализация
SurrealDB написана на Rust и использует абстракцию хранилища (KVS - Key-Value Store) для сохранения данных. В качестве движка KVS под капотом могут использоваться RocksDB (локально) или TiKV/FoundationDB (для распределенных кластеров).

**Схема данных и хранение:**
Каждый документ хранится как пара ключ-значение.
- **Ключ:** Генерируется на основе `RecordId`. `RecordId` состоит из имени таблицы (`Table`) и уникального идентификатора (`RecordIdKey`). Например: `person:john`.
- **Значение:** Данные документа кодируются в бинарный формат (часто с использованием специализированных методов сериализации).
- **Схема:** В файле `surrealdb/core/src/sql/statements/define/table.rs` и `surrealdb/core/src/sql/table_type.rs` видно, что таблица может быть типа `TableType::Normal` (документы) или `TableType::Relation` (ребра графа).

Структура `Value` (из `surrealdb/types/src/value/mod.rs`) описывает все возможные типы данных, которые могут содержаться в документе, включая вложенные массивы (`Array`), объекты (`Object`), строки (`String`), числа (`Number`), даты (`Datetime`) и другие типы.

## 2. Relational Concepts (Реляционные концепции)

### Логическая работа
Хотя SurrealDB является NoSQL/многомодельной БД, она поддерживает реляционные концепции, такие как строгие схемы, ограничения (constraints), и SQL-подобный язык запросов (SurrealQL). Разработчики могут использовать оператор `DEFINE TABLE` для создания строгой структуры таблицы, и `DEFINE FIELD` для определения типов полей, их обязательности и правил валидации (например, `ASSERT`).

### Техническая реализация
- **Определение схемы:** Схема определяется через `DEFINE` выражения (см. `surrealdb/core/src/sql/statements/define/`). Например, можно определить тип поля, значение по умолчанию (через `DefineDefault::Always` или `DefineDefault::Set`), и права доступа.
- **Связи (Record Links):** SurrealDB позволяет хранить `RecordId` напрямую как значение поля. Это позволяет ссылаться на другой документ (как Foreign Key), но без необходимости выполнения классического `JOIN`. При выборке данных SurrealDB может автоматически подтягивать связанные документы с помощью оператора `FETCH`.
- **Индексы:** Поддерживаются различные индексы (уникальные, не уникальные, полнотекстовые) для ускорения поиска. Они реализуются путем создания дополнительных ключей в KVS, которые мапятся на `RecordId`.

## 3. Графовая база данных (Graph Database)

### Логическая работа
В SurrealDB связи между документами (узлами/вершинами) могут быть выражены через "ребра" (edges). Это позволяет преодолеть ограничения реляционных БД (особенно проблему N+1 запросов) при извлечении глубоко вложенных данных. Можно использовать синтаксис обхода графа, например: `SELECT * FROM person->knows->person`.

### Техническая реализация
- **Ребра как таблицы:** Ребра графа в SurrealDB реализованы как специальные таблицы с типом `TableType::Relation`.
- **Структура ребра:** Каждое ребро само по себе является документом (т.е. имеет свой `RecordId` и может хранить свойства/данные). Однако, оно **обязательно** содержит два системных поля: `in` и `out`.
  - `in`: Ссылка на исходящий узел (вершину, откуда начинается связь).
  - `out`: Ссылка на входящий узел (вершину, куда ведет связь).
- **Обход графа:** Как видно из `surrealdb/core/src/exec/operators/scan/graph.rs` (`GraphEdgeScan`), при выполнении запроса движок использует специализированные операторы для сканирования ребер по заданному `RecordId` исходного узла и направлению (in/out/both). Данные извлекаются из KVS по специальным ключам-индексам для связей, что позволяет очень быстро находить все связанные узлы.

## 4. Spatial / GeoJSON

### Логическая работа
SurrealDB нативно поддерживает хранение и запросы пространственных данных (точки, линии, полигоны), которые совместимы со стандартом GeoJSON. Это позволяет выполнять пространственные операции: определение пересечений (intersects), нахождения объектов внутри полигона (inside) и т.д.

### Техническая реализация
- **Типы данных:** Геометрические типы представлены через перечисление `Geometry` (см. `surrealdb/types/src/value/geometry.rs`), которое включает:
  - `Point(Point<f64>)`
  - `Line(LineString<f64>)`
  - `Polygon(Polygon<f64>)`
  - `MultiPoint`, `MultiLine`, `MultiPolygon`, и `Collection`.
  Внутри SurrealDB использует библиотеку `geo` (популярный crate в экосистеме Rust) для представления и математических операций над гео-данными.
- **Хранение и Индексация:** Геометрические объекты сериализуются и хранятся внутри документов как обычные значения (через вариант `Value::Geometry(Geometry)`). Для эффективного поиска по координатам SurrealDB использует пространственные индексы (например, R-Trees или R-Trees поверх KVS), что позволяет быстро отсеивать документы, не попадающие в заданный пространственный запрос.
