# Анализ репозитория: Github-Trends-Aggregator

### 1. Техническая реализация и архитектура
Проект `Github-Trends-Aggregator` представляет собой веб-сервер, написанный на компилируемом языке **Go (Golang)**.
*   **Архитектура:** Это монолитное приложение с четким разделением по пакетам: `api` (HTTP маршрутизация), `fetcher` (сбор данных с GitHub), `store` (хранилище), `scheduler` (планировщик фоновых задач), `ws` (WebSockets), и `email` (отправка уведомлений).
*   **Зависимости:** Используется `github.com/gorilla/mux` для маршрутизации REST API, `github.com/PuerkitoBio/goquery` (порт jQuery для Go) для парсинга HTML DOM, и стандартные пакеты Go (net/http, context).
*   **Среда выполнения:** Приложение контейнеризовано (есть `Dockerfile`) и компилируется в единый бинарный файл.

### 2. Функции и как логически это работает
**Логика работы:**
1.  **Инициализация (main.go):** Запускается HTTP-сервер, загружаются секреты (конфигурация) и инициализируется внутреннее хранилище (`store.NewStore()`).
2.  **Планирование задач (scheduler):** Периодически запускается фоновая задача (cron-подобная реализация), которая вызывает пакет `fetcher`.
3.  **Скрапинг (fetcher.go):** Сервер делает прямой HTTP GET запрос на `https://github.com/trending`. Полученный HTML-ответ парсится с помощью `goquery`. Извлекаются данные о репозиториях: название, автор, количество звезд, форки и язык программирования.
4.  **Уведомления и доставка:** Обновленные данные сохраняются во внутреннее хранилище. Сервер может транслировать эти обновления подключенным клиентам по WebSockets (пакет `ws`) или отправлять сводки по email (пакет `email`). Клиенты также могут запросить данные по REST API.

### 3. Обмен информации, память, потоки данных
**Потоки данных:**
`GitHub HTML -> Go HTTP Client -> io.Reader -> goquery DOM -> Struct models.Repository -> In-memory Store -> HTTP Response (JSON) / WebSocket Message / Email`.
Данные перетекают от сырого HTML в строго типизированные структуры Go.

**Управление памятью:**
*   **Хранение состояния:** Интересной особенностью является использование In-Memory Store (`store.NewStore()`) вместо внешней базы данных вроде PostgreSQL или Redis. Это означает, что спаршенные данные о трендах хранятся прямо в оперативной памяти (в структурах Go, защищенных мьютексами (sync.RWMutex) для безопасного конкурентного доступа).
*   **Сборка мусора (GC):** Go автоматически управляет памятью. При парсинге `goquery` создает множество мелких объектов DOM-дерева в памяти. Как только функция `FetchTrendingRepos` завершается и ссылки на `doc` теряются, GC очищает память.
*   **Горутины:** Вероятно, обработка входящих HTTP-запросов и работа `scheduler` выполняются в отдельных легковесных потоках (goroutines), разделяя общую память сервера, что требует осторожного использования блокировок в пакете `store`.
