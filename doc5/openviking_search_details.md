# Анализ архитектуры OpenViking: Декомпозиция задач, Convergence Detection и Структуры Контекста

## 1. Введение
В данном отчете представлен анализ внутренней логики работы ретривера и разложения задач в OpenViking. Отчет фокусируется на декомпозиции поискового запроса с использованием `TypedQuery`, работе механизма раннего прерывания рекурсивного поиска (Convergence Detection) и формировании структур `MatchedContext`.

## 2. Логическое устройство

### 2.1 Декомпозиция задачи и `TypedQuery`
Когда система получает сложный пользовательский запрос, базовый VLM (`VLMBase`) выступает в роли "анализатора намерений" (Intent Analyzer). Он формирует `QueryPlan` (План запросов).
План запросов разбивается на массив строго типизированных запросов — `TypedQuery`.
Каждый `TypedQuery` содержит:
*   `query` (str): Переписанный, оптимизированный текстовый запрос.
*   `context_type`: Контекстная зона для поиска (например, MEMORY для поиска по фактам пользователя, RESOURCES для поиска по документам, SKILL для поиска инструментов).
*   `intent`: Описание "зачем" нужен этот запрос (используется позже для этапа Re-ranking, чтобы улучшить точность).
*   `priority` (int 1-5): Приоритетность выполнения.
*   `target_directories`: Конкретные пути `viking://`, если LLM смогла их заранее определить.

### 2.2 Детекция сходимости (Convergence Detection)
Поиск в древовидной структуре может стать бесконечным, если директорий слишком много. Чтобы этого избежать, в OpenViking используется механизм Convergence Detection.
Алгоритм отслеживает набор извлекаемых Top-K (самых релевантных) документов на каждой итерации спуска по файловой системе.
Если набор этих документов не изменяется в течение заданного числа раундов (`MAX_CONVERGENCE_ROUNDS = 3`), система считает, что мы "сошлись" (достигли локального максимума релевантности) и досрочно прерывает рекурсию, возвращая текущие результаты. Это колоссально экономит ресурсы.

### 2.3 `MatchedContext` и Связи
После фильтрации и поиска кандидаты преобразуются в массив объектов `MatchedContext`. Эта структура инкапсулирует не просто найденный текст, но и его иерархическую природу.
*   Она содержит сам `uri` файла.
*   В ней хранится тип контекста (`context_type`) и уровень (`level=2` для файлов).
*   Главная особенность: при формировании `MatchedContext`, система обращается к UFS (`viking_fs`) и читает связанные элементы (`get_relations`), подтягивая короткие `abstract` связанных узлов, формируя богатый семантический блок (комбинируя метрику схожести и "горячесть" / "hotness" документа).

## 3. Техническая реализация в коде

*   **Класс `TypedQuery` (`openviking_cli/retrieve/types.py`)**: Представлен в виде датакласса с полями `query`, `context_type`, `intent`, `priority` и `target_directories`.
*   **Константа и Логика Convergence**: В `openviking/retrieve/hierarchical_retriever.py` определена `MAX_CONVERGENCE_ROUNDS = 3`. Во внутреннем цикле `while` (при рекурсивном поиске) ведется счетчик `convergence_rounds`. При каждом обновлении сравниваются множества `prev_topk_uris == current_topk_uris`.
*   **Метод `_convert_to_matched_contexts`**: Там же в `hierarchical_retriever.py`. Он принимает сырые кандидаты, подмешивает к `semantic_score` временной параметр `HOTNESS_ALPHA` (для повышения приоритета свежих данных) и обращается к файловой системе за `relations` для возврата полноценных `MatchedContext`.
*   **`VLMBase` (`openviking/models/vlm/base.py`)**: Абстрактный интерфейс `get_completion`, который в реализациях (OpenAI/LiteLLM) на основе JSON schema заставляет LLM строго возвращать массив объектов, мапящихся на структуру `QueryPlan`.

## 4. Инструкция: Как повторить это в вашем проекте

### Шаг 1: Маршрутизация запросов (Query Routing)
Вместо того чтобы отправлять сырой запрос пользователя (`"Как дела у Васи и как установить Postgres?"`) в векторную БД, используйте LLM для генерации JSON-плана:
```json
{
  "queries": [
    {"query": "Вася состояние дела", "context_type": "MEMORY", "priority": 1},
    {"query": "Установка Postgres инструкция", "context_type": "RESOURCES", "priority": 2}
  ]
}
```
Распарсите JSON в структуры (например, Pydantic модели) и отправляйте их в разные источники (базу данных пользователя и в корпоративную вики соответственно).

### Шаг 2: Внедрение Convergence Detection для графов/деревьев
Если вы ищете по связанным узлам или папкам, напишите простую защиту от переполнения:
```python
max_rounds_unchanged = 3
rounds_unchanged = 0
prev_results = set()

while queue:
    results = search_node(queue.pop())
    current_results = set([r.id for r in get_top_k(results)])

    if current_results == prev_results:
        rounds_unchanged += 1
        if rounds_unchanged >= max_rounds_unchanged:
            break # Прерываем поиск - мы нашли лучшее
    else:
        rounds_unchanged = 0
        prev_results = current_results
```

### Шаг 3: Обогащение результата связанными данными
Не возвращайте в LLM только голый текст из БД. Формируйте объект `MatchedContext`. Если вы нашли документ A, проверьте в БД, есть ли у него связанные документы (например, "Обзорная статья по документу A"). Добавьте краткую выжимку связанных документов в ответ, чтобы LLM лучше поняла контекст происхождения информации.
