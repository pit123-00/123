# Анализ архитектуры OpenViking: Директорийный поиск, ReAct-Оркестратор и Сжатие памяти

## 1. Введение
В данном отчете представлен анализ архитектуры системы OpenViking (`volcengine/OpenViking`). Мы подробно рассмотрим три ключевых аспекта: реализацию парадигмы файловой системы `viking://` с механизмом `_recursive_search`, работу ReAct-оркестратора (`ExtractLoop`) и процесс обновления/сжатия памяти (`Compressor` и `MemoryDeduplicator`).

## 2. Логическое устройство

### 2.1 Файловая парадигма и Директорийный поиск (`viking://` & `_recursive_search`)
OpenViking трактует память и контекст как файловую систему (Uniform File System - UFS) с префиксом `viking://`. Это позволяет оперировать ресурсами через привычные пути (например, `viking://user/memories/preferences/`).
Поиск объединяет семантический и традиционный обход директорий:
*   При вызове `_recursive_search` система использует приоритетную очередь. Она спускается по иерархии папок, опираясь на оценку вложенных узлов (например, файлы L1/L2).
*   Читая метаданные или абстракты (`overview.md`, `abstract.md`), система решает, достаточно ли релевантна текущая директория, чтобы спускаться глубже, что экономит ресурсы на семантическом поиске и улучшает точность выборки контекста.

### 2.2 ReAct-Оркестратор (`ExtractLoop`)
Оркестратор `ExtractLoop` отвечает за финальный анализ сеанса. Он работает по парадигме ReAct (Reasoning and Acting):
1.  **Reasoning (Размышление):** LLM (через интерфейс `VLMBase`) анализирует текущий контекст и решает, нужно ли вызвать какой-то инструмент (например, чтобы докачать контекст из ФС `viking_fs`).
2.  **Acting (Действие):** Если инструмент запрошен, система выполняет его и возвращает результат обратно в LLM.
3.  **Finish:** Если инструментов не требуется, LLM формирует итоговый вывод (сохранение памяти или извлечение фактов) и цикл прерывается (макс. количество итераций по умолчанию задается параметром, чтобы не зацикливаться).

### 2.3 Сжатие и дедупликация памяти (`Compressor` / `Deduplicator`)
При появлении новых фактов в ходе диалога:
1.  **Compressor (`SessionCompressor`)** извлекает новую информацию.
2.  **Deduplicator (`MemoryDeduplicator`)** принимает решение:
    *   Сначала он выполняет быстрый векторный пре-фильтр (SIMILARITY_THRESHOLD), находя Топ-5 (`MAX_PROMPT_SIMILAR_MEMORIES`) похожих фактов.
    *   Затем он передает кандидатов в LLM для принятия решения: создать новый факт (`CREATE`), обновить существующий (`UPDATE`) или пропустить, если информация уже дублируется.
3.  Факты записываются обратно в векторную БД по конкретному URI (категориям), например: `viking://user/memories/preferences/` или `viking://agent/memories/skills/`.

## 3. Техническая реализация в коде

*   **`HierarchicalRetriever._recursive_search`**: Содержит реализацию поиска по директориям. Для каждой папки вычисляется скор, и если он превышает порог, ретривер спускается на уровень файлов (initial_candidates, level 2) или дочерних директорий, избегая полного сканирования всего графа.
*   **`ExtractLoop`**: Находится в `openviking/session/memory/extract_loop.py`. Это класс, который в цикле `while` вызывает модель (`self.vlm`), передает ей доступные инструменты (через `_tool_schemas`), отслеживает прочитанные файлы (чтобы не читать их дважды) и завершает работу, когда модель выдает финальный JSON-ответ.
*   **`MemoryDeduplicator`**: В файле `openviking/session/memory_deduplicator.py` используется логика статического определения категорий (`_USER_CATEGORIES`, `_AGENT_CATEGORIES`), генерация путей `viking://` через `_category_uri_prefix` и многоуровневая дедупликация с привлечением LLM.

## 4. Инструкция: Как повторить это в вашем проекте

### Шаг 1: Имплементация виртуальной файловой системы (URI)
Вместо того чтобы хранить документы просто в базе по ID, присвойте им URI:
- Пользовательские предпочтения: `memory://user_1/preferences/doc_1`
- Рабочие документы: `docs://project_X/technical/doc_2`
При поиске сначала ищите релевантные "папки" (семантический поиск по суммаризациям папок), а затем делайте поиск внутри найденных папок. Это ускорит работу в 10+ раз на больших объемах.

### Шаг 2: Реализация ReAct Цикла (Оркестратора)
Создайте класс-менеджер:
```python
def react_loop(vlm_model, user_input, tools, max_steps=3):
    messages = [{"role": "user", "content": user_input}]
    for _ in range(max_steps):
        response = vlm_model.call(messages, tools=tools)
        if response.wants_to_call_tool:
            result = execute_tool(response.tool_call)
            messages.append({"role": "tool_result", "content": result})
        else:
            return response.final_text
    return "Max steps reached"
```

### Шаг 3: Конвейер сжатия и дедупликации
Когда вы хотите сохранить новый факт ("Пользователь любит пиццу с ананасами"):
1. Сделайте векторный поиск по базе: найдите похожие факты (например, "Клиент предпочитает итальянскую кухню").
2. Передайте новый факт и найденные факты в LLM с промптом: "Стоит ли добавить новый факт, заменить существующий или пропустить?".
3. Если ответ "Добавить", сохраняйте в БД с URI `memory://user_1/preferences/uuid`.
