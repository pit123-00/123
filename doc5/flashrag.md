# Анализ архитектуры и пайплайна FlashRAG (на основе ReasoningPipeline)

## 1. Введение
В данном отчете представлен подробный анализ реализации класса `ReasoningPipeline` из репозитория FlashRAG (`flashrag/pipeline/reasoning_pipeline.py`). Эта архитектура реализует систему типа "Search-R1" или "O2-Searcher", где агент (Ассистент) выполняет итеративный процесс обдумывания (reasoning), поиска информации и формирования финального ответа.

## 2. Логическое устройство
Логика работы пайплайна базируется на использовании специальных токенов-тегов, которые разделяют поток вывода LLM на "мыслительный процесс" и "действия":

*   **<think> ... </think>**: Используется для внутреннего рассуждения модели. Агент обдумывает, хватает ли ему знаний для ответа.
*   **<|begin_of_query|> ... <|end_of_query|>**: (или `<search>...</search>` в `AutoRefinePipeline`). Если знаний не хватает, агент формирует краткий поисковый запрос (в идеале содержащий один факт/тройку).
*   **<|begin_of_documents|> ... <|end_of_documents|>**: (или `<documents>...</documents>`). Система перехватывает поисковый запрос, обращается к ретриверу (поисковому движку), форматирует результаты и подставляет их обратно в контекст агента в виде документов.
*   **<answer> ... </answer>**: Когда агент собирает достаточное количество информации (или исчерпывает лимит шагов), он формирует окончательный ответ.

Процесс зацикливается до тех пор, пока агент не выдаст тег ответа или пока не будет достигнут `max_retrieval_num` (максимальное количество поисков).

## 3. Техническая реализация в коде

### 3.1 Инициализация (`__init__`)
Пайплайн наследуется от `BasicPipeline`. При инициализации задаются:
- `prompt_template` с системным и пользовательским промптами. Пользовательский промпт содержит жесткие инструкции о том, как использовать теги `<think>`, `<|begin_of_query|>`, и `<answer>`.
- `retriever` и `generator`: компоненты для поиска и генерации текста соответственно.
- `max_retrieval_num`: лимит итераций поиска.
- `stop_tokens`: токены остановки генерации (`<|im_end|>`, `<|endoftext|>`, конец запроса, конец ответа). Это ключевой технический момент — генератор прерывает работу, как только агент выдает поисковый запрос или финальный ответ.

### 3.2 Метод `_retrieved_docs_to_string`
Отвечает за форматирование результатов поиска. Берет список словарей документов, извлекает `title` и `text`, убирает лишние пробелы/индексы и оборачивает в теги `<|begin_of_documents|>` и `<|end_of_documents|>`.

### 3.3 Основной цикл (`run`)
Метод `run` обрабатывает батч запросов (датасет):
1.  **Подготовка**: К запросам применяется `prompt_template`, инициализируются флаги завершения (`finish_flag`) и счетчики.
2.  **Итеративный процесс (до `max_retrieval_num + 1` раз)**:
    - Отбираются незаконченные элементы (`finish_flag == False`).
    - Модель генерирует продолжение: `step_outputs = self.generator.generate(exist_prompts, stop=self.stop_tokens)`.
    - **Парсинг вывода**:
        - Если в выводе есть `end_of_answer_token`, извлекается финальный ответ с помощью функции `extract_between`. Элемент помечается как завершенный (`finish_flag = True`).
        - Если в выводе есть `begin_of_query_token`, извлекается запрос. Элемент переходит в статус `search`, а запрос добавляется в список на выполнение.
    - **Поиск и подстановка**:
        - Выполняется пакетный поиск: `retrieved_docs = self.retriever.batch_search([...])`.
        - Результаты форматируются через `_retrieved_docs_to_string` и добавляются к исходному промпту (контексту) элемента.
    - Процесс повторяется, и на следующем шаге LLM видит найденные документы и продолжает генерацию из тега `<think>` или сразу переходит к `<answer>`.

## 4. Инструкция: Как повторить это в вашем проекте

Чтобы внедрить аналогичную архитектуру в ваш проект, выполните следующие шаги:

### Шаг 1: Настройка системного промпта
Создайте промпт, который строго указывает LLM использовать теги.
Пример:
```text
You are a helpful assistant. You must first reason using <think>...</think>.
If you need more info, output <search>your query</search> and STOP.
Once you have the documents provided by the system inside <documents>...</documents>,
continue reasoning or output the final answer inside <answer>...</answer>.
```

### Шаг 2: Настройка генератора (LLM)
Настройте вашу LLM (через API OpenAI, vLLM, HuggingFace) так, чтобы она **обязательно останавливалась** на токенах:
`['</search>', '</answer>']`.
Это позволит вам перехватить управление, когда модель захочет что-то найти.

### Шаг 3: Реализация цикла управления (Control Loop)
Напишите цикл (while loop) со счетчиком итераций:
1. Запустите генерацию с текущим контекстом сообщений.
2. Когда генерация остановится, проанализируйте последний сгенерированный текст.
3. Если текст заканчивается на `</search>` (или содержит его):
   - Распарсите текст между `<search>` и `</search>`.
   - Передайте этот текст в ваш ретривер (векторную БД, BM25, API Google и т.д.).
   - Получите документы, отформатируйте их как строку (например, `Doc 1: ... Doc 2: ...`) и оберните в `<documents>...</documents>`.
   - Добавьте этот блок документов в контекст сообщений (как новое сообщение от системы или ассистента).
   - Продолжите цикл (перейдите к шагу 1).
4. Если текст содержит `</answer>`:
   - Распарсите финальный ответ.
   - Завершите цикл.
5. Задайте `max_steps = 5`, чтобы избежать бесконечных циклов в случае галлюцинаций модели.

### Шаг 4: Форматирование документов
Реализуйте простую функцию подстановки:
```python
def format_docs(docs):
    res = "<documents>\n"
    for i, doc in enumerate(docs):
        res += f"Document {i+1}: {doc['text']}\n"
    res += "</documents>\n"
    return res
```

Такой подход позволит вам создать агента, который будет сам решать, когда ему нужен поиск, и итеративно собирать сложную информацию перед ответом.
