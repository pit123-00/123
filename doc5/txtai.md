# Анализ архитектуры SQL-парсинга и Графов в txtai

## 1. Введение
В данном отчете представлен анализ библиотеки txtai (`neuml/txtai`), а именно механизмов интеграции SQL-поиска (`src/python/txtai/database/sql/base.py`) и построения графовых сетей для возврата подграфов (`src/python/txtai/graph/base.py`). Txtai объединяет возможности семантического, векторного и графового поиска под единым SQL-подобным интерфейсом.

## 2. Логическое устройство
Основная идея txtai заключается в том, чтобы дать пользователю привычный интерфейс (SQL) для выполнения сложных гибридных запросов к неструктурированным данным (тексту) и графам знаний.
*   **SQL-парсинг:** Система перехватывает классический SQL запрос (например, `SELECT id, text, score FROM txtai WHERE similar('query') AND rating > 4`). Она парсит его, выделяя семантическую часть (`similar`) и жесткие фильтры (`rating > 4`). Семантический поиск передается векторному движку, а результаты затем фильтруются через встроенную реляционную БД (обычно SQLite).
*   **Графовый поиск (Subgraphs):** Txtai позволяет строить семантические графы связей между документами. При вызове графового поиска (с параметром `graph=True`) возвращается не просто плоский список найденных документов, но и связи между ними (подграф/subgraph), что позволяет визуализировать кластеры и пути рассуждений.

## 3. Техническая реализация в коде

### 3.1 SQL Парсер (`SQL` класс в `sql/base.py`)
Парсер в txtai реализован легковесно без использования тяжелых AST библиотек, с помощью встроенного модуля `shlex`.
*   **Токенизация (`tokenize`):** Метод разбивает запрос на токены, используя пунктуацию операторов (`=!<>+-*/%|`) в качестве разделителей, игнорируя комментарии.
*   **Идентификация Clauses (Секций):** Парсер проходит по токенам и ищет ключевые слова `SELECT`, `FROM`, `WHERE`, `GROUP BY`, `ORDER BY`, `LIMIT`, записывая их позиции в словарь `positions`.
*   **Обработка `WHERE`:** В секции WHERE парсер выявляет кастомные функции (например, функцию подобия для векторного поиска). Эти функции исполняются на векторной БД, а результат (набор ID документов) подставляется в нативный SQL-запрос для окончательной фильтрации в SQLite.

### 3.2 Графовый интерфейс (`Graph` класс в `graph/base.py`)
Класс `Graph` является базовой абстракцией:
*   Управляет связями (Relationships). Инициализируется конфигурацией `columns`, определяющей, какое поле является текстом (`text`), объектом (`object`) или связью (`relationships`).
*   **Метод `search` и `batchsearch`:** Могут принимать флаг `graph=True`. Если он установлен, бекенд (например, NetworkX или собственная графовая реализация) находит релевантные узлы (документы), а затем извлекает их соседей (edges) для формирования подграфа (отфильтрованного графа).
*   Методы `addnode`, `addnodes`, `attribute` позволяют программно пополнять граф знаниями (например, извлекаемыми через LLM тройками "субъект-предикат-объект").

## 4. Инструкция: Как повторить это в вашем проекте

Чтобы внедрить SQL-интерфейс для гибридного поиска и возвращать графовые связи в вашем проекте, выполните следующие шаги:

### Шаг 1: Хранение данных (Двойная база)
Для реализации паттерна txtai используйте связку из Векторной БД (для `similar()`) и классической реляционной БД (PostgreSQL или SQLite).
Синхронизируйте ID документов:
- Документ "ID_123" лежит в реляционной БД со всеми метаданными (date, author, text).
- Эмбеддинг текста документа "ID_123" лежит в векторной БД с тем же идентификатором "ID_123".

### Шаг 2: Реализация SQL-обертки (Парсер)
Вместо написания своего парсера с нуля, можно использовать библиотеки вроде `sqlglot` или `pyparsing` на Python.
Алгоритм:
1. Получите запрос: `SELECT * FROM docs WHERE similar('AI history', limit=100) AND year > 2020`
2. Перехватите вызов `similar(...)`.
3. Отправьте запрос 'AI history' в Векторную БД. Она вернет список ID: `['ID_1', 'ID_5', 'ID_10']`.
4. Перепишите SQL-запрос для реляционной базы, подставив эти ID: `SELECT * FROM docs WHERE id IN ('ID_1', 'ID_5', 'ID_10') AND year > 2020`.
5. Выполните запрос в Postgres/SQLite и верните результат пользователю.

### Шаг 3: Построение графов и подграфов
Используйте графовую БД (например, Neo4j) или библиотеку NetworkX в памяти (если данных мало).
1. При добавлении документа, если вы извлекаете сущности (Person, Organization), добавляйте узлы (Node) и связи (Edge) в граф.
2. Когда выполняется поиск (Шаг 2), вы получаете список релевантных ID документов.
3. Чтобы вернуть подграф (`graph=True`), сделайте запрос к графовой БД: найти все узлы (и связи между ними), которые прикреплены к найденным документам.
В Neo4j это делается запросом:
`MATCH (d:Document)-[r]-(e:Entity) WHERE d.id IN $doc_ids RETURN d, r, e`
4. Верните полученные связи фронтенду для визуализации в виде графа (например, через библиотеку D3.js, React Flow или Vis.js).
