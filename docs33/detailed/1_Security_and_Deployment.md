# Глубокий технический анализ 1: Безопасность, аутентификация и инфраструктура (X-Brain-Key, RLS, K8s)

## 1. Многоуровневая система аутентификации и контроля доступа

Система OB1 (Open Brain) реализует сложную и гибкую модель безопасности, предназначенную для работы как в локальных, так и в распределенных облачных средах. В отличие от традиционных приложений, где безопасность часто является надстройкой, в OB1 она интегрирована непосредственно в протоколы взаимодействия и ядро базы данных.

### 1.1. X-Brain-Key: Универсальный механизм авторизации
Основным механизмом контроля доступа к серверу Модельного контекстного протокола (MCP) является использование ключа доступа, задаваемого через переменную окружения `MCP_ACCESS_KEY`. В реализации сервера на базе Hono (`server/index.ts`) этот ключ проверяется для каждого входящего запроса.

Особенность реализации заключается в поддержке двух независимых каналов передачи ключа:
1. **Кастомный HTTP-заголовок `x-brain-key`**: Этот метод рекомендуется для десктопных клиентов (например, Claude Desktop) и специализированных инструментов командной строки (Claude Code, Cursor). Он обеспечивает высокий уровень безопасности, так как заголовки обычно не логируются промежуточными прокси-серверами.
2. **Параметр URL `key`**: Этот метод служит резервным для клиентов, которые имеют жесткие ограничения на настройку HTTP-заголовков (например, некоторые облачные веб-интерфейсы или мобильные приложения).

Техническая реализация в коде:
```typescript
const provided = c.req.header("x-brain-key") || new URL(c.req.url).searchParams.get("key");
if (!provided || provided !== MCP_ACCESS_KEY) {
    return c.json({ error: "Invalid or missing access key" }, 401, corsHeaders);
}
```
Такой подход делает OB1 "невидимым" для неавторизованных запросов, эффективно предотвращая атаки методом перебора и несанкционированный доступ к персональной памяти.

### 1.2. Аутентификация через заголовки и управление CORS
Для обеспечения возможности работы современных браузерных клиентов (например, веб-версии Claude.ai или специализированных дашбордов) сервер полностью реализует протокол CORS (Cross-Origin Resource Sharing). Это критически важно, так как MCP-сервер часто работает на другом домене (например, Deno Deploy) относительно клиента ИИ.

Система обрабатывает:
- **Preflight-запросы (OPTIONS)**: Разрешает проверку безопасности браузером перед отправкой реальных данных.
- **Список разрешенных заголовков**: Включает `authorization`, `x-client-info`, `apikey`, `content-type`, `x-brain-key`, `mcp-session-id`, что позволяет передавать сложный контекст сессии.

### 1.3. Патч для Claude Desktop: Инженерное решение проблем совместимости
В процессе разработки было выявлено, что официальный клиент Claude Desktop в определенных режимах не отправляет заголовок `Accept: text/event-stream`, который критически важен для работы транспорта `StreamableHTTPTransport` (основанного на Server-Sent Events).

Чтобы пользователи не сталкивались с необъяснимыми сбоями подключения, в `server/index.ts` интегрирован "защитный" механизм. Если сервер обнаруживает отсутствие нужного заголовка, он на лету создает патченную версию запроса:
```typescript
if (!c.req.header("accept")?.includes("text/event-stream")) {
    const headers = new Headers(c.req.raw.headers);
    headers.set("Accept", "application/json, text/event-stream");
    const patched = new Request(c.req.raw.url, {
        method: c.req.raw.method,
        headers,
        body: c.req.raw.body,
        duplex: "half",
    });
    // Подмена оригинального запроса на пропатченный
}
```
Это пример глубокой технической адаптации под особенности конкретных реализаций протоколов ИИ-клиентами.

## 2. Row Level Security (RLS): Безопасность на уровне ядра PostgreSQL

Одной из самых инновационных частей безопасности OB1 является использование PostgreSQL `Row Level Security`. В отличие от традиционных архитектур, где безопасность проверяется кодом приложения (Node.js/Deno), OB1 делегирует это ядру базы данных.

### 2.1. Изоляция данных в многопользовательской среде
В системе Supabase политики RLS позволяют гарантировать, что один пользователь никогда не увидит данные другого, даже если они хранятся в одной и той же таблице. Это реализуется через проверку идентификатора пользователя из JWT-токена (`auth.uid()`) против столбца `user_id` в таблице.

Преимущества этого подхода:
- **Централизация**: Правила безопасности описаны в SQL-миграциях рядом со схемой данных, а не разбросаны по коду API.
- **Устойчивость к ошибкам в приложении**: Даже если злоумышленник сможет обойти аутентификацию на уровне сервера Deno, база данных физически не вернет ему строки, на которые у него нет прав.
- **Прозрачность**: ИИ-агенты работают в контексте прав пользователя, что предотвращает случайное использование чужих данных при генерации ответов.

### 2.2. Сервисные роли (Service Role Keys)
Для системных операций, таких как фоновый захват данных из Slack или Gmail, используется специальный ключ `service_role`. Этот ключ обладает правами суперпользователя и **полностью игнорирует** все политики RLS.
В архитектуре OB1 это используется для:
- Синхронизации данных между разными источниками.
- Выполнения глобальных задач обслуживания (дедупликация, пересчет эмбеддингов).
Это создает строгую "градуированную" модель доверия: внешние агенты ограничены RLS, внутренние системные процессы — нет.

## 3. Инфраструктура развертывания: Docker и Kubernetes

Для пользователей, стремящихся к полному суверенитету своих данных, OB1 предоставляет инструменты для развертывания вне экосистемы Supabase Cloud (модуль `integrations/kubernetes-deployment`).

### 3.1. Docker-контейнеризация
Файл `Dockerfile` упаковывает среду выполнения Deno вместе со всеми необходимыми библиотеками. Это позволяет запустить Open Brain на любом сервере, в частном облаке или даже на домашнем NAS, обеспечивая полную идентичность среды разработки и эксплуатации.

### 3.2. Kubernetes и масштабируемость
Манифесты в папке `k8s/` описывают промышленный стандарт развертывания:
- **Deployment**: Управляет жизненным циклом подов с сервером Open Brain, обеспечивая автоматический перезапуск при сбоях.
- **Service**: Предоставляет стабильный сетевой адрес внутри кластера.
- **Secrets**: Позволяет безопасно передавать конфиденциальные ключи API (OpenRouter, Supabase) через нативные механизмы K8s.

### 3.3. Standalone PostgreSQL + pgvector
Важной технической деталью является файл `init.sql`. Он содержит полный набор SQL-команд для подготовки **автономного** экземпляра PostgreSQL. Это позволяет пользователю полностью отказаться от Supabase и развернуть базу данных с поддержкой векторов (`pgvector`) на собственном железе. В файл включена реализация функции `match_thoughts` на чистом PL/pgSQL, что делает "мозг" полностью портативным и независимым от конкретного облачного провайдера.

## Заключение
Инфраструктурный слой OB1 — это сочетание современных стандартов (Docker, K8s) и глубоких возможностей PostgreSQL (RLS, pgvector). Сочетание гибких ключей доступа (`X-Brain-Key`), патчей для совместимости и строгой изоляции на уровне БД создает фундамент для действительно надежной и приватной системы персонального искусственного интеллекта.
