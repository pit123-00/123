# Технический анализ: Механизмы безопасности (X-Brain-Key, RLS, Service Role)

## 1. Введение
Система OB1 (Open Brain) реализует эшелонированную систему защиты данных, сочетающую в себе механизмы контроля доступа на уровне приложения и строгую изоляцию на уровне ядра базы данных. Данный документ подробно рассматривает три ключевых компонента безопасности: универсальный ключ доступа, политику разграничения строк (RLS) и роль сервисного администратора.

## 2. X-Brain-Key: Универсальный механизм авторизации
X-Brain-Key является первичным уровнем защиты сервера Модельного контекстного протокола (MCP). Он спроектирован для обеспечения безопасности в условиях, когда сервер доступен через публичный интернет (например, при развертывании на Deno Deploy или Vercel).

### 2.1. Техническая реализация в сервере
Реализация находится в файле `server/index.ts`. Система использует веб-фреймворк Hono для обработки входящих запросов. Логика проверки ключа интегрирована в промежуточное ПО (middleware), которое перехватывает все запросы (`app.all("*", ...)`).

Техническая особенность заключается в гибкости извлечения ключа:
```typescript
const provided = c.req.header("x-brain-key") || new URL(c.req.url).searchParams.get("key");
```
Этот подход позволяет поддерживать два типа клиентов:
1. **Desktop-клиенты** (Claude Desktop, Cursor): Передают ключ в защищенном HTTP-заголовке `x-brain-key`. Это предпочтительный метод, так как заголовки не сохраняются в логах прокси-серверов.
2. **Cloud-клиенты** (веб-версии ChatGPT/Claude): В случаях, когда настройка заголовков невозможна, ключ передается как параметр URL.

Если ключ не совпадает с секретным значением `MCP_ACCESS_KEY`, сервер немедленно прерывает соединение с кодом 401 (Unauthorized), предотвращая любую дальнейшую обработку и защищая ресурсы от атак методом перебора.

## 3. Row Level Security (RLS): Изоляция на уровне БД
RLS — это встроенный механизм PostgreSQL, который позволяет определять права доступа на уровне каждой отдельной строки таблицы. В OB1 это является фундаментом конфиденциальности.

### 3.1. Архитектурный принцип
В отличие от классических систем, где за доступ к данным отвечает программный код (на TypeScript/Python), OB1 переносит эту ответственность в базу данных. Это гарантирует, что даже если в коде сервера будет обнаружена критическая уязвимость, база данных физически не выдаст данные другого пользователя.

### 3.2. Реализация политик
Примитив `primitives/rls` описывает стандартные паттерны:
- **Личный доступ**: Проверка `auth.uid() = user_id`. Система Supabase автоматически прокидывает идентификатор пользователя из JWT-токена в контекст БД.
- **Групповой доступ (Households)**: В расширениях типа `meal-planning` политики становятся более сложными. Они проверяют наличие записи в связующей таблице `household_members`. Если пользователь является членом домохозяйства, ему разрешается просмотр и редактирование общих данных (списки покупок, календарь).

Это позволяет системе быть "многопользовательской из коробки", обеспечивая при этом уровень безопасности, сравнимый с банковскими системами.

## 4. Service Role Keys: Доверенная системная роль
В экосистеме OB1 существует понятие "границы доверия" между внешними клиентами и внутренними функциями.

### 4.1. Обход RLS
Ключ `service_role` обладает правами суперпользователя в контексте PostgreSQL. Он **полностью игнорирует** все политики RLS. Это критически важное техническое решение для выполнения административных задач.

### 4.2. Сценарии использования
OB1 использует `service_role` исключительно в доверенных Edge-функциях (Deno):
1. **Автоматический захват (Ingest)**: Когда сообщение поступает из Slack, система должна записать его в базу. В этот момент у системы нет пользовательского JWT-токена, поэтому она использует `service_role` для записи от имени "системы".
2. **Фоновые процессы**: Задачи дедупликации (фингерпринтинг) или пересчета статистики требуют доступа ко всей таблице `thoughts` для сравнения записей. `service_role` позволяет эффективно выполнять такие операции без ограничений.

### 4.3. Безопасность ключа
Ключ `service_role` никогда не передается клиенту. Он хранится в защищенных переменных окружения Supabase. Это создает архитектурный барьер: внешние ИИ-агенты всегда ограничены своими правами доступа (RLS), в то время как внутренние "операторы" системы имеют полный доступ для поддержания целостности данных.

## 5. Заключение
Сочетание **X-Brain-Key** (внешний периметр), **RLS** (внутренняя изоляция) и **Service Role** (доверенное управление) создает надежную и масштабируемую инфраструктуру безопасности. Система готова к работе в многопользовательских средах, гарантируя пользователю полный контроль над его "цифровым мозгом".
