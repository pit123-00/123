# Технический анализ: Дефрагментация спикеров в транскриптах (Фаза 0.5)

## 1. Введение
При обработке голосовых транскриптов система OB1 (Open Brain) сталкивается с проблемой низкого качества автоматической атрибуции речи. Голосовое ПО часто ошибочно создает десятки меток спикеров (Speaker 1, 2, 3...) там, где реально общаются двое. Для решения этой проблемы в алгоритме `Panning for Gold` реализована "Фаза 0.5: Дефрагментация спикеров". Данный документ анализирует техническую реализацию этого процесса очистки данных.

## 2. Природа проблемы "фрагментации"
Автоматические системы (Otter, Plaud, телефонные записи) переназначают метки спикеров при:
- **Смене акустической среды**: переход из офиса в машину или ресторан.
- **Изменении громкости**: один спикер наклонился к микрофону, а другой отошел.
- **Длительных паузах**: тишина может спровоцировать "сброс" идентификатора.
В результате 2-часовой ланч двух людей может превратиться в транскрипт с 10 "участниками". Это делает дальнейший анализ бессмысленным, так как ИИ не понимает, чья это идея.

## 3. Алгоритм дефрагментации OB1
Процесс очистки данных выполняется перед основным анализом и состоит из четырех технических шагов.

### 3.1. Шаг 1: Поиск "Якорных линий" (Anchor Lines)
Это наиболее интеллектуальная часть алгоритма. Система ищет в тексте фразы, которые однозначно идентифицируют говорящего.
- **Якоря пользователя**: Упоминание членов семьи по именам, специфических внутренних проектов, личной истории карьеры.
- **Якоря собеседника**: Профессиональная лексика ("наши пациенты", "наш бюджет"), личные анекдоты, уникальные для этого человека.
Эти линии становятся "островками правды", на которых строится вся дальнейшая атрибуция.

### 3.2. Шаг 2: Сценарная сегментация (Scene-Based Re-attribution)
Вместо того чтобы доверять меткам ПО, алгоритм разбивает транскрипт на "сцены" по моментам резкого изменения метаданных записи (шум, длинные паузы).
- Внутри каждой сцены система сопоставляет фрагменты с найденными якорями.
- Если в сцене "Спикер 5" произнес якорь пользователя, а "Спикер 2" — якорь собеседника, то во всей этой сцене все реплики Спикера 5 переназначаются пользователю.

### 3.3. Шаг 3: Верификация потока (Flow Verification)
Используя логику диалога ("вопрос-ответ") и типичные речевые обороты, система заполняет пробелы между якорями.
- Каждой атрибуции присваивается уровень уверенности: HIGH, MEDIUM, LOW.
- Реплики с уровнем LOW (короткие междометия, неясные вскрики) помечаются для группового уточнения.

### 3.4. Шаг 4: Групповое уточнение (Batch Clarification)
Система не спрашивает пользователя о каждой реплике. Она формирует список "сомнительных" фрагментов и просит подтверждения одной командой. Это минимизирует трение и позволяет получить чистый транскрипт за считанные секунды.

## 4. Техническая реализация в коде
Логика описана в `panning-for-gold.skill.md`. Агент использует `grep` и поиск по регулярным выражениям для поиска паттернов якорей в сыром тексте. Результатом работы является временный файл `clean-transcript.md`, который становится каноническим источником для всех последующих фаз анализа (инвентаризации и оценки).

## 5. Преимущества для базы знаний
- **Точность связей**: В Open Brain идеи записываются с правильной привязкой к людям.
- **Надежность CRM**: Взаимодействия (interactions) не засоряются "неизвестными спикерами".
- **Качество рассуждений**: ИИ-агент может строить цепочки: "Вы сказали А, а ваш партнер возразил Б", что невозможно при фрагментированных данных.

## 6. Заключение
Фаза 0.5 в OB1 — это образец решения проблем "реального мира" в ИИ-системах. Технический подход, основанный на **семантических якорях** и **сценарном анализе**, позволяет превращать мусорные данные автоматической транскрибации в высококачественный фундамент для персональной базы знаний.
