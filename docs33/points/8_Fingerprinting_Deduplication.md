# Технический анализ: Фингерпринтинг и дедупликация контента

## 1. Введение
В системе OB1 (Open Brain), которая агрегирует данные из множества источников (Slack, Gmail, Obsidian, CLI), проблема дублирования информации стоит особенно остро. Один и тот же текст может быть скопирован в чат, отправлен по почте и сохранен в заметках. Для поддержания чистоты базы знаний и экономии ресурсов на эмбеддинги, реализована система фингерпринтинга (Content Fingerprinting). Данный документ анализирует техническую реализацию этого механизма.

## 2. Алгоритм генерации "отпечатка"
Примитив `content-fingerprint-dedup` (реализованный в различных скриптах импорта и SQL-триггерах) использует криптографическое хеширование для идентификации контента.

### 2.1. Использование SHA-256
Для генерации фингерпринта используется алгоритм SHA-256. Он выбран за его высокую стойкость к коллизиям. Даже минимальное изменение в тексте приведет к генерации совершенно другого хеша.

### 2.2. Этап нормализации (Normalization)
Перед вычислением хеша система выполняет критически важный этап подготовки текста. Если хешировать "сырой" текст, то два идентичных сообщения, отличающиеся только лишним пробелом или переносом строки, будут считаться разными.
Технический процесс нормализации:
1. Удаление начальных и конечных пробелов.
2. Схлопывание множественных пробелов и пустых строк.
3. (Опционально) Приведение к нижнему регистру.
4. Удаление специфических артефактов источника (например, префиксов "Re:" в письмах).

## 3. Механизм дедупликации (Deduplication)
Проверка на дубликаты выполняется на самом раннем этапе конвейера захвата (Ingest Pipeline).

### 3.1. Атомарная проверка "Check-and-Skip"
В коде функций захвата (например, в Edge-функции Slack) присутствует логика:
```typescript
const { data: existing } = await supabase
  .from("thoughts")
  .select("id")
  .eq("content_hash", newHash)
  .limit(1);

if (existing && existing.length > 0) return; // Дубликат найден, пропускаем вставку
```
Это позволяет избежать дорогостоящих вызовов API эмбеддингов и LLM-экстракторов для информации, которая уже есть в системе.

### 3.2. Обновление вместо пропуска (Upsert Pattern)
В некоторых реализациях (например, в `upsert_thought` RPC) используется более сложная логика:
- Если контент совпадает, система не просто игнорирует его, а обновляет метаданные существующей записи.
- Например, к существующей мысли может быть добавлен новый тег источника (`source: ["slack", "email"]`), что позволяет отслеживать цитируемость идеи.

## 4. Оптимизация хранения и поиска
Для того чтобы проверка на дубликаты не замедляла вставку данных, реализованы следующие оптимизации:
- **Уникальный индекс**: На столбец с хешем накладывается индекс `UNIQUE`. Это гарантирует дедупликацию на уровне самой БД (последний рубеж обороны) и делает поиск по хешу мгновенным.
- **Хранение в метаданных**: В некоторых версиях хеш хранится внутри JSONB-столбца. В этом случае используется GIN-индекс для быстрого доступа.

## 5. Преимущества для ИИ-агента
Дедупликация критически важна для качества работы ИИ:
- **Предотвращение повторов**: Агент не будет выдавать один и тот же ответ трижды, если он нашел его в разных источниках.
- **Чистота векторного пространства**: Уменьшается "скученность" векторов в одной области, что повышает точность поиска по смыслу.
- **Экономия токенов**: При формировании контекста для LLM система передает только уникальные "мысли", экономя место в контекстном окне.

## 6. Заключение
Механизм фингерпринтинга в OB1 превращает базу данных из простого хранилища логов в "хранилище уникальных знаний". Использование **криптографического хеширования SHA-256** в сочетании с **предварительной нормализацией** и **уникальными индексами** обеспечивает высочайшую надежность дедупликации, что является необходимым условием для построения качественной персональной памяти.
