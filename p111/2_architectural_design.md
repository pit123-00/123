# Отчёт №2: Архитектурное устройство системы Harness2

## 1. Концептуальная архитектура и принципы проектирования

Система `harness2` спроектирована на основе принципов **гексагональной архитектуры (Ports & Adapters)**, **строгого разделения обязанностей (Separation of Concerns)** и **иммутабельного потока данных на основе файловой системы (Disk-as-State Dataflow)**.

Ключевая архитектурная задача системы — обеспечить оптимизацию окружения агентов (harness) над различными моделями, рантаймами агентов (OpenCode, Codex) и бенчмарками (JobBench, WorkBuddy, LAB) при строгом соблюдении следующих инвариантов:
1. **Метод не знает о бенчмарках (Method Agnosticism)**: ядро оптимизации (`core/`) не содержит условий `if bench == "jobbench"`. Все различия бенчмарков выражены через интерфейсы данных и спецификации.
2. **Бенчмарк не знает о методе оптимизации**: адаптеры бенчмарков реализуют лишь запуск и извлечение артефактов; они не управляют рекурсией или бюджетами.
3. **Answer-Free граница**: модели-оптимизаторы и селекторы никогда не получают судейских инструкций, правильных ответов или результатов тестирования.

```
+-----------------------------------------------------------------------------------+
|                                  CLI & Scheduling                                 |
|                         (run_sweep.py, schedule.py)                               |
+-----------------------------------------+-----------------------------------------+
                                          |
                      +-------------------+-------------------+
                      |                                       |
                      v                                       v
         +-------------------------+             +-------------------------+
         |     Parallel Mode       |             |    Sequential Mode      |
         |    (recursion.agg)      |             |    (recursion.seq)      |
         +------------+------------+             +------------+------------+
                      |                                       |
                      +-------------------+-------------------+
                                          |
                                          v
+-----------------------------------------------------------------------------------+
|                                   Core Engines                                    |
|   Proposer (Model calls) <---> Context (Evidence Tree) <---> Tree (Validation)    |
|   Selection (Blind Choice) <-> Library (Domain Memory) <---> Ledger (Budget)      |
+-----------------------------------------+-----------------------------------------+
                                          |
        +---------------------------------+---------------------------------+
        |                                                                   |
        v                                                                   v
+-------------------------------+                         +-------------------------------+
|       Substrate Port          |                         |     BenchmarkAdapter Port     |
| (opencode.py, codex.py)       |                         | (jobbench.py, workbuddy.py...) |
+---------------+---------------+                         +---------------+---------------+
                |                                                         |
                v                                                         v
    [OpenCode / Codex CLIs]                                    [Task Data & Environments]
```

## 2. Границы абстракций и контракты (Ports & Adapters)

### 2.1. Порт субстрата агента (`Substrate` в `substrate/base.py`)
Субстрат определяет, как конкретный агентный фреймворк запускается и как выглядит его редактируемая поверхность:
- `name: str` — строковый идентификатор рантайма (`opencode`, `codex`).
- `surface() -> SurfaceSpec` — декларативное описание файловой структуры harness: список `always_on` файлов, лимиты символов, пути к навыкам и субагентам, шаблоны триггеров.
- `render_events(path: Path, obs_trunc: int, max_chars: int) -> str` — приведение разнородных логов агента (JSONL-события Codex, телеметрия OpenCode) к единой канонической грамматике траекторий `[ACTION] ... [OBSERVATION] ... [ERROR]`.

### 2.2. Порт бенчмарка (`BenchmarkAdapter` в `core/spec.py`)
Адаптер полностью скрывает детали предметной области и инфраструктуры тестирования:
- `tasks(split) -> list[str]` — стабильный список задач для воспроизводимого порядка.
- `domain_of(task_id) -> str` — группировка задач по профессиональным сферам/доменам.
- `task_prompt(task_id) -> str` — очищенный текст задания без подсказок и критериев оценивания.
- `execute(task_id, harness_dir, run_id) -> Path` — идемпотентный запуск агента с переданным harness на конкретной задаче.
- `delivered(run_dir) -> bool` — проверка физического наличия финального артефакта.
- `deliverable_text(run_dir) -> str` и `deliverable_files(run_dir) -> dict[str, str]` — извлечение чистого содержимого созданных документов.
- `score(run_dir, task_id) -> dict | None` — измерение качества финального решения независимым судейским контуром.

### 2.3. Декларативная конфигурация ячеек (`BenchSpec`)
Вся конфигурация связки (бенчмарк, субстрат) передаётся как неизменяемый объект `BenchSpec`:
- `install_mode`: способ развёртывания (`shared`, `per_task`).
- `prompts`: объект `BenchPrompts`, содержащий доменно-специфичные термины (как называть артефакт: "deliverable", "memo", "spreadsheet"; как называть домен: "field", "practice area", "profession").
- `channels`: словарь `ChannelSpec` для ролей `proposer` и `selector` (модель, температура, глубина рассуждений `effort`, таймаут).
- `leak_globs`: список запрещённых масок путей для предотвращения утечек.

## 3. Топологии рекурсивных пайплайнов: Параллелизм против Последовательности

Архитектура реализует две принципиально различные топологии направленных ациклических графов (DAG) улучшения harness:

### 3.1. Параллельная топология (Ширина, $k$)
Ориентирована на исследование пространства гипотез (Exploration):
1. **Фаза базовых свидетельств**: параллельный запуск $k$ прогонов со стандартным harness ($b_1, \dots, b_k$).
2. **Фаза независимых гипотез**:
   - Параллельный запуск $k$ сессий `INV` (анализ инструментальных ошибок и процедуры исполнения).
   - Параллельный запуск $k$ сессий `DOM` (анализ соответствия стандартам предметной области).
   - Все $2k$ пропоузеров видят только исходные базовые прогоны и независимы друг от друга.
3. **Фаза верификации гипотез**: параллельный прогон каждого из $2k$ предложенных harness на задаче.
4. **Фаза синтеза (Агрегация)**:
   - Модель-агрегатор получает полный кросс-анализ: $k$ базовых прогонов, $2k$ предложенных изменений и $2k$ результатов их тестового запуска.
   - Синтезируются $k$ независимых итоговых сборок (`agg1..aggk`).
5. **Финальный прогон**: каждый `agg_i` прогоняется на задаче, формируя пул для финального выбора.

### 3.2. Последовательная топология (Глубина, $k$)
Ориентирована на пошаговое рафинирование и кумулятивное усложнение (Exploitation):
1. Начинается с $c_0 = \text{base}$.
2. Итеративный цикл по раундам $t = 1 \dots k$:
   - На шаге $t$ относительно текущего чекпоинта $c_{t-1}$ генерируются два взаимодополняющих кандидата: $inv_t$ и $dom_t$.
   - Оба кандидата прогоняются на задаче.
   - Композитор (`COMPOSE`) объединяет лучшее из $inv_t$ и $dom_t$, опираясь на историю всех предыдущих раундов $[1 \dots t-1]$, и формирует чекпоинт $c_t$.
   - Чекпоинт $c_t$ прогоняется на задаче и становится фундаментом для следующего раунда.
3. Финалистами становятся чекпоинты $\{c_1, \dots, c_k\}$.

## 4. Архитектура слепого выбора (Blind Selection)

Критически важный архитектурный узел системы — выбор итогового ответа без использования внешних метрик:
- **Полная изоляция артефактов**: селектор не видит промежуточных рассуждений агента и логов ошибок, если они не запрашивались специально. Он видит условие задачи `task.md`, исходные материалы `source/` и анонимизированные финальные документы кандидатов `candidates/<ID>.md` (плюс отрендеренные таблицы и изображения).
- **Криптографическая анонимизация**:
  Метки прогонов перемешиваются генератором псевдослучайных чисел с детерминированным сидом:
  $\text{seed} = \text{SHA1}(\text{task\_id} \parallel k \parallel \text{mode})$. Кандидаты получают нейтральные буквенные метки ($A, B, C\dots$). Это полностью исключает предвзятость модели к определенным стадиям (например, склонность предпочитать более поздние версии или базовые прогоны).
- **Разделение ролей (Proposer vs Selector)**:
  Архитектура допускает назначение разных моделей и каналов для фазы улучшения harness и фазы выбора лучшего результата (например, `claude_cli` для генерации кода и промптов, а мультимодальная модель через `opencode` для визуального анализа отрендеренных PDF/Excel/PPTX).

## 5. Долгосрочная архитектура памяти и межзадачный опыт (`Library`)

Вместо сложной динамической векторной базы данных в `harness2` реализована **файловая, детерминированная архитектура памяти предметного домена**:
- Каждая задача принадлежит определенному домену (например, `Legal/ContractDrafting`, `Finance/Valuation`, `IT/CodeRefactoring`).
- Если задача решена успешно и выбранный harness отличается от базового, он фиксируется в библиотеке домена:
  1. Полный снапшот файлового дерева принятого harness.
  2. Файл `EXPERIENCE.md`, содержащий формализованный опыт:
     - `cue`: распознаваемый триггер ситуации.
     - `lesson`: передаваемый принцип или правило.
     - `evidence`: фактологическое обоснование на основе траектории.
     - `confidence`: степень уверенности.
- Модуль `Library.rebuild_index()` автоматически компилирует единый markdown-индекс `INDEX.md`.
- При решении последующих задач этого же домена директория библиотеки целиком монтируется в контекст пропоузера (`context/library/`). Это создает архитектурный мост передачи знаний между задачами без модификации весов модели.

## 6. Иерархия управления агентами, субагентами и инструментами

Архитектурная схема компонентов агента построена по принципу минимизации конкуренции за контекстное окно:

```
+-----------------------------------------------------------------------------------+
|                                 Main Agent Context                                |
|  - Always-On Files (systemprompt.md / AGENTS.md, guardrails, memory, tools guide)  |
|  - Strict character budget (< 8k-24k chars)                                       |
+-----------------------------------------+-----------------------------------------+
                                          |
                +-------------------------+-------------------------+
                |                                                   |
                v (Load on Demand)                                  v (Delegate Execution)
+-------------------------------+                         +-------------------------------+
|       Reusable Skills         |                         |      Delegated Subagents      |
|  - Trigger in Always-On text  |                         |  - Isolated context           |
|  - .agents/skills/<name>/     |                         |  - Large Input -> Small Text  |
|  - Frontmatter name & desc    |                         |  - sub_agents/<name>/AGENT.md |
+---------------+---------------+                         +-------------------------------+
                |
                v (Call Execution)
+-------------------------------+
|     Deterministic Scripts     |
|  - scripts/<name>.py          |
|  - Zero LLM overhead          |
+-------------------------------+
```

1. **Always-On Context**: базовый скелет правил и инструкций. Имеет максимальный приоритет, но строго ограничен по размеру (каждый токен конкурирует с генерацией агента).
2. **On-Demand Skills (Навыки)**: специализированные инструкции по сложным процессам. Находятся на диске и загружаются агентом только в момент активации триггера.
3. **Delegated Subagents (Субагенты)**: независимые контексты исполнения. Применяются только для архитектурного паттерна *"Большой вход — Компактный ответ"* (Large Input, Small Output), например, парсинг гигантской базы документов и возврат короткого резюме.
4. **Deterministic Scripts (Скрипты)**: детерминированный код (Python), вызываемый через консоль. Полностью исключает затраты токенов LLM на математические расчеты, форматирование или парсинг таблиц.
