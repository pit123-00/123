# Отчёт 4: Плюсы и минусы, управление агентами, субагентами и пайплайнами

Данный отчёт содержит детальный анализ сильных и слабых сторон проектов [nousresearch/hermes-agent](https://github.com/nousresearch/hermes-agent) и [deepseek-ai/deepseek-harness], с особым фокусом на технических возможностях управления агентами, субагентами, пайплайнами задач и сложными воркфлоу.

---

## 1. Управление агентами, субагентами и пайплайнами

### 1.1. Модель субагентов в hermes-agent

#### Механизм делегирования (`tools/delegate_tool*.py` и `agent/subagent_lifecycle.py`):
* **Создание дочернего агента:**
  - Делегирование вызывается моделью через инструмент `delegate_task`.
  - Родительский агент порождает новый независимый экземпляр `AIAgent` с собственным идентификатором сессии (`task_id`), изолированной историей и отфильтрованным набором доступных инструментов (блокируются инструменты рекурсивного делегирования во избежание бесконечных циклов).
  - Среда исполнения (terminal session, file-ops cache) изолируется в рамках дочерней рабочей директории (`tools/subagent_worktree.py`).
* **Взаимодействие и обмен контекстом:**
  - Модель родительского агента получает **только итоговый результат** работы субагента (`_validate_child_output_schema`). Промежуточные вызовы инструментов и размышления субагента остаются в его собственной истории в базе SQLite и не засоряют контекст родителя.
  - Поддерживается параллельный запуск группы задач (батч-режим) с контролем максимального числа одновременно активных воркеров (`_DEFAULT_MAX_CONCURRENT_CHILDREN`).
* **Управление жизненным циклом:**
  - Реализован явный хартбит (`_start_heartbeat`), тайм-ауты бездействия (`_get_child_timeout`), принудительная остановка при прерывании родителя (`test_stop_ends_background_delegations.py`) и лимиты затрат токенов на субагента (`_delegate_summary_budget.py`).
  - Плагины могут управлять субагентами через публичный контракт `PluginContext.subagent_lifecycle` (`agent/subagent_lifecycle.py`).

#### Пайплайны и воркфлоу:
* Пайплайны в `hermes-agent` реализуются в основном через:
  - Встроенный планировщик задач (`cron/` и `agent/periodic_scheduler.py`).
  - Последовательные сценарии вызовов инструментов и списки дел (`hermes_state_todo.py`, `tools/kanban_tools.py`).
  - Механизм фоновых ревьюеров (`_spawn_background_review`), которые валидируют корректность выполнения задачи перед завершением сессии.

### 1.2. Модель субагентов в deepseek-harness

#### Механизм субагентов (`packages/subagent/*`):
* **Сервисный шов `ctx.subagents`:**
  - В `deepseek-harness` субагенты вынесены в самостоятельную платформенную подсистему (`@deepseek-ai/dsh-subagent`), абстрагированную от конкретного рантайма.
  - Поддерживаются множественные взаимозаменяемые провайдеры запуска:
    1. `subagent-spawn-in-process` — легковесный запуск изолированного дочернего агента в текущем Node-процессе.
    2. `subagent-fork-in-process` — создание форка текущей сессии на основе снимка лога (`buildForkSeed`), сохраняющего предварительный контекст.
    3. `subagent-acp` — делегирование задачи внешнему агенту через протокол ACP (Agent Client Protocol).
    4. `subagent-codex` / `subagent-claude-code` — делегирование специализированным сторонним агентным средам.
* **Управление состоянием и активацией (`manager.ts`):**
  - Класс `SubagentManager` управляет пулом активаций (`ActivationMap`), очередями сообщений и холодным возобновлением (cold resume).
  - Поддерживается активное руление субагентами во время их работы через метод `sendMessage`, без раскрытия того, работает ли субагент локально или на удаленном узле.
* **Управление доступом и политиками:**
  - Глубина вложенности субагентов строго контролируется (`depth.ts`).
  - Дочерние агенты наследуют или переопределяют политики безопасности через `captureDelegatedPolicyOverrides`.

#### Пайплайны и реактивные воркфлоу (`packages/workflow/*`):
* **PTC Workflows (`packages/workflow/workflow-ptc`):**
  - Реализация реактивных пайплайнов, в которых шаги рабочего процесса описываются программно и исполняются в песочнице PTC.
  - Поддерживается координация агентных команд (`packages/team/agent-team`), где несколько субагентов могут совместно решать задачу, обмениваясь структурированными артефактами (`packages/deliverables/`).

## 2. Плюсы и минусы решений

### 2.1. hermes-agent

#### Плюсы:
1. **Простота и доступность для модификации:**
   - Кодовая база написана на привычном для сообщества AI/ML языке Python. Разработчику легко отладить шаг за шагом в стандартном pdb/IDE.
2. **Низкий порог входа для локального использования:**
   - Не требует Node.js, сборщиков проектов, pnpm или фоновых служб. Запуск осуществляется одной командой через CLI или uv.
3. **Продвинутый механизм самообучения (Self-Improving):**
   - Уникальный механизм создания, аудита и сохранения новых навыков (skills) на лету. Агент реально может эволюционировать в процессе решения прикладных задач.
4. **Надёжная изоляция контекста субагентов:**
   - Делегирование полностью скрывает промежуточные шаги дочерних сессий, экономя токены и предотвращая деградацию рассуждений основного агента.
5. **Превосходный терминальный интерфейс:**
   - Интуитивный и эстетичный Rich TUI с выводом дерева задач, расхода бюджета и статусов фоновых воркеров.

#### Минусы:
1. **Монолитное ядро и перегруженность класса `AIAgent`:**
   - Использование множественного наследования 14+ миксинов затрудняет отслеживание связей и приводит к неявным зависимостям между полями `self`.
2. **Ограничения Python по параллелизму (GIL / многопоточность):**
   - Управление множеством параллельных субагентов внутри одного процесса ограничено потоковой моделью Python; требуется спавнить отдельные процессы или обращаться к Docker.
3. **Отсутствие формализованного Event Sourcing:**
   - Состояние изменяется процедурными записями в SQLite. Откат сессии к произвольному промежуточному шагу (time-travel debugging) сложен и требует ручных манипуляций с базой.
4. **Слабая приспособленность для веб-/десктоп-интеграций:**
   - Архитектура исторически заточена под CLI/TUI; создание полноценных веб- или мобильных клиентов требует надстройки внешних адаптеров.

---

### 2.2. deepseek-harness

#### Плюсы:
1. **Промышленная микроядерная архитектура (Cordis IoC):**
   - Идеальная модульность. Любой слой (модель, хранилище, песочница, подсистема субагентов) подключается как независимый плагин без перекомпиляции ядра.
2. **Event Sourcing из коробки:**
   - Полная прозрачность и детерминизм истории сессии. Возможность мгновенно форкать контекст в любой точке, переигрывать ходы и строить сложные аналитические проекции.
3. **Продвинутое программное управление инструментами (PTC):**
   - Модель может писать управляющий скрипт для пакетного выполнения десятков тулов в изолированном воркере, снижая затраты на межсетевое взаимодействие и токенизацию на порядки.
4. **Гибкая и многоуровневая система субагентов:**
   - Поддержка разнородных бэкендов субагентов (локальные форки, изолированные процессы, протокол ACP, внешние тулы вроде Claude Code) в рамках единого интерфейса `ctx.subagents`.
5. **Готовность к любым платформам:**
   - Готовые приложения для CLI, Electron Desktop, браузерного Web UI и headless-режима в Kubernetes.

#### Минусы:
1. **Высокая архитектурная сложность и порог входа:**
   - Десятки абстракций, косвенные вызовы через IoC контейнер Cordis, множество мелких пакетов (более 50 воркспейсов) делают порог входа для рядового разработчика экстремально высоким.
2. **Сложность кастомизации под задачи классического Data Science:**
   - Интеграция нестандартных Python ML-моделей или локальных весов требует создания IPC/RPC-мостов между Node.js рантаймом и Python-окружением.
3. **Тяжеловесный стек сборки:**
   - Зависимость от сборщиков TypeScript (tsdown), pnpm monorepo и специфических плагинов Cordis усложняет быстрые локальные правки и хот-патчинг.
4. **Менее выраженная динамика "самообучения":**
   - Система ориентирована на исполнение предопределённых контрактов и плагинов, в то время как механизмы генерации новых системных навыков агентом выражены слабее, чем в Hermes.

## 3. Сравнительная матрица характеристик

| Критерий | `hermes-agent` | `deepseek-harness` |
| :--- | :--- | :--- |
| **Оркестрация субагентов** | Изолированные дочерние экземпляры `AIAgent` с фильтрацией тулов | Полиморфный реестр провайдеров (`spawn`, `fork`, `acp`, внешние) |
| **Сложные пайплайны** | Скрипты, канбан-очереди, крон и фоновые верификаторы | Реактивные воркфлоу PTC, оркестрация команд (`agent-team`) |
| **Изоляция исполнения** | Docker / Daytona / Modal / Local shell | Sandboxed PTC Worker (RPC) + ACL песочницы |
| **Воспроизводимость сессий** | Чтение строк из SQLite | Строгий Event-Sourced Replay по событиям |
| **Простота кастомизации** | ★★★★★ (Python, легко модифицировать) | ★★☆☆☆ (Сложная типизированная экосистема) |
| **Архитектурная чистота** | ★★★☆☆ (Монолитные миксины) | ★★★★★ (Микроядро, строгие контракты) |
| **Готовность к Enterprise** | ★★★☆☆ (Отлично для локального/CLI использования) | ★★★★★ (Создано для масштабных распределённых систем) |
