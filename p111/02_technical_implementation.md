# Отчёт №2: Техническая реализация и преимущества решений

В данном отчёте детально рассматривается внутренняя программная реализация `ai-proxy` и `EasyCLIProxyAPI` исключительно на базе анализа исходного кода: используемые библиотеки, алгоритмы, модели параллелизма, механизмы ввода-вывода и конкретные технические преимущества каждой реализации.

---

## 1. Техническая реализация `ai-proxy`

### 1.1. Сетевой стек и асинхронный рантайм
* **Ядро сервера**: Построено на `Axum 0.8` поверх `tokio` и `hyper 1.0`. Все входящие HTTP-запросы проходят через глобальный роутер `/{*path}` и `fallback` с привязкой к общему состоянию `Arc<AppState>`.
* **Ограничение частоты запросов (Rate Limiting)**: Реализовано на уровне middleware Axum через библиотеку `governor` (`RateLimiter<NotKeyed, InMemoryState, DefaultClock>`), обеспечивая прямой token-bucket rate limiting на базе `NonZeroU32` с мгновенным возвратом HTTP 429 при превышении RPS.
* **Таймауты и соединения**: `reqwest 0.13` с жестким разделением `connect_timeout` (по умолчанию 10 сек) и `request_timeout` (0 для бесконечного SSE/streaming). Принудительно отключены все автодекодирования сжатия (`no_gzip()`, `no_brotli()`, `no_deflate()`, `no_zstd()`) для сохранения байтовой идентичности тела запроса и ответа.

### 1.2. Реализация MITM и динамического TLS-перехвата (`mitm.rs`)
* **Обработка метода CONNECT**: В функции `handle_connect` запрос туннелирования перехватывается, извлекается запрашиваемый authority, проверяются белые и черные списки (`is_mitm_included_host`, `is_mitm_excluded_host`).
* **Динамическая генерация X.509 сертификатов**: Используется библиотека `rcgen 0.14` с фичами `pem` и `x509-parser`. На старте генерируется или считывается корневой CA (`MitmAuthority`). При первом обращении к новому домену создается виртуальный сертификат с SAN (Subject Alternative Name) для данного домена, подписанный локальным CA.
* **LRU-кэширование TLS-конфигураций**: Реализовано через `tokio_rustls::rustls::ServerConfig`. Сгенерированные сертификаты кэшируются в памяти с настраиваемым лимитом (`mitm_cert_cache_size`), предотвращая ресурсоемкую криптографическую перегенерацию на каждый handshake.
* **Upgrade соединения**: `hyper::upgrade::on(req)` производит апгрейд сокета, поверх которого запускается `TlsAcceptor`, превращающий сокет в расшифрованный TLS-поток, на который вешается внутренний обработчик HTTP/1.1 (`hyper::server::conn::http1::Builder`).

### 1.3. Конвейер сканирования (`ScanPipeline` и middleware)
Конвейер безопасности в `middleware/` объединяет несколько независимых сканеров:
1. **`RegexScanner`**: Компилирует регулярные выражения для поиска AWS ключей (`AKIA...`), GitHub токенов (`ghp_...`, `gho_...`), Anthropic API ключей (`sk-ant-...`), OpenAI ключей (`sk-...`), приватных ключей PEM (`-----BEGIN ... PRIVATE KEY-----`), email и общих секретов в присваиваниях.
2. **`EntropyScanner`**: Вычисляет энтропию Шеннона по формуле:
   $$H = -\sum p_i \log_2(p_i)$$
   Сканирует токены длиной от `min_length` до `max_length`. Оценивает дистанцию до ключевых слов (`key`, `secret`, `token`, `password`, `auth`) в пределах `keyword_proximity` байт. Если энтропия превышает порог (например, 4.5) и рядом есть ключевое слово — строка классифицируется как секрет.
3. **`StructuralScanner`**: Производит синтаксический анализ структур:
   - Детекция JWT (три base64url блока через точку с проверкой валидности заголовка `{"alg":...}`).
   - Детекция URI строк подключения к БД (JDBC, PostgreSQL, MySQL, Redis, MongoDB с логинами и паролями).
   - Детекция блоков конфигурационных файлов и `.env` переменных.
4. **`ModelScanner` & `PrivacyFilterScanner`**:
   - `ModelScanner`: Отправляет фрагменты текста в локальный OpenAI-совместимый LLM (например, Ollama с Llama 3.1) для глубокого семантического анализа PII (имена, телефоны, контекстная конфиденциальность). Поддерживает режимы `direct`, `hybrid` (сначала regex, затем допроверка моделью) и `verify_only`.
   - `PrivacyFilterScanner`: Интеграция с OpenAI Privacy Filter либо через локальный HTTP endpoint (`/scan`), либо через прямой запуск бинарника `opf` с передачей stdin/stdout в формате JSON.
   - Политика сбоя `fail_policy`: настраивается как `regex_only` (продолжить без ML при таймауте) или `fail_closed` (заблокировать запрос).

### 1.4. Контекстная санитизация и восстановление потоковых ответов
* **`Redactor` и `RedactionContext`**:
  - При обнаружении секрета вычисляется его маска в зависимости от длины: частичное маскирование (сохранение первых `prefix_len` и последних `suffix_len` символов) или полная замена.
  - Для обратимых категорий (`restorable_categories`, например email или телефоны) в `RedactionContext` создается уникальный детерминированный плейсхолдер.
* **`StreamingRestore`**:
  - Потоковые ответы модели (SSE чанки `data: ...`) пропускаются через потоковый демультиплексор.
  - Алгоритм скользящего окна (`sliding window`) удерживает буфер размером не менее максимальной длины плейсхолдера (`max_placeholder_len`), чтобы гарантировать, что плейсхолдер, разорванный границей двух сетевых TCP/HTTP-чанков, будет корректно собран и заменен обратно на исходный секрет без рассинхронизации клиентского потока.

### 1.5. Телеметрия и аудит (`telemetry_store.rs`)
* Хранилище на `rusqlite` с многопоточным доступом через `Arc<Mutex<Connection>>`.
* Каждому запросу присваивается ULID (`next_request_id`), гарантирующий хронологическую сортировку.
* Хранятся таблицы: `requests`, `token_usage`, `tool_events`, `content_captures`.
* Захват тела запроса и ответа происходит только после повторной санитизации (`redact_before_store`), исключая утечку секретов в локальную БД телеметрии. Автоматическая фоновая очистка устаревших записей каждые 15 минут по `retention_hours`.

## 2. Техническая реализация `EasyCLIProxyAPI`

### 2.1. Десктопная архитектура Tauri 2 и разделение процессов
* **Гибридный стек**: UI на React 19 / TypeScript, собранный через Vite, исполняется внутри системного WebView (WebView2 на Windows, WebKitGTK на Linux, WKWebView на macOS). Бэкенд написан на Rust 2021 и скомпилирован в бинарник `cpa-gui`.
* **IPC (Inter-Process Communication)**: Взаимодействие фронтенда и Rust-ядра происходит через типизированные команды `#[tauri::command]` (`invokeAgentCommand`), охватывающие сотни эндпоинтов управления.
* **Супервизор процессов (`core_runtime.rs`)**:
  - Управляет жизненным циклом внешнего ядра `cli-proxy-api`.
  - Запуск через системные Job Objects в Windows (`CreateJobObjectW`, `AssignProcessToJobObject`) — гарантирует, что при аварийном падении GUI все дочерние процессы прокси гарантированно уничтожаются операционной системой.
  - На Unix-системах используется отдельный системный поток-спавнер `CORE_PROCESS_SPAWNER` с перехватом сигналов `SIGTERM`/`SIGKILL` и контролем lifetime дочерних процессов.
  - Глобальная блокировка операций над ядром `CORE_OPERATION_LOCK: Mutex<()>` исключает гонки при одновременных перезапусках или обновлениях.

### 2.2. Транзакционный движок модификации конфигураций агентов (`agents/configuration.rs`, `agents/transactions.rs`)
* **Поддержка разнородных форматов**:
  - Парсинг и модификация YAML с сохранением комментариев и исходной структуры через `serde_norway` и `yaml-edit`.
  - Парсинг JSON и JSON5 (поддерживающего комментарии) для файлов конфигураций агентов (`parse_agent_json5_object`).
* **Двухфазные транзакции и резервное копирование (`backups.rs`)**:
  - Перед внесением изменений в конфигурацию любого агента (например, `~/.claude.json` или `~/.codex/config.toml`) создается полный снимок исходного состояния с расчетом SHA-256 хэшей каждого затронутого файла.
  - Реализован механизм валидации состояния `validate_agent_applied_state`.
  - При обнаружении ручных изменений пользователем система детектирует конфликт (`record_conflict_files`) и предлагает безопасное слияние или восстановление (`restore.rs`).

### 2.3. Защитный TLS Reverse Proxy (`reverse_proxy.rs`)
* Реализован на низкоуровневом `hyper 1.0` с коннекторами `hyper_util::rt::TokioIo` и `tokio_rustls`.
* **Функция Hardening (`harden_core_config_document`)**:
  - Автоматически инспектирует YAML-файл конфигурации ядра.
  - Переводит директиву `server.host` в безопасный режим `127.0.0.1`.
  - Прописывает `server.trusted-proxies = ["127.0.0.1"]`.
  - Поднимает TLS-листнер на порту 443 с привязкой к указанным сертификатам и ключам, защищая управляющий порт ядра от несанкционированного доступа по локальной сети.

### 2.4. Аналитика сессий Codex и восстановление SQLite БД (`codex_sessions.rs`, `codex_sessions/context.rs`)
* **Прямая работа с базами данных Codex**: Подключается к `~/.codex/sessions/*.db` с флагами `OpenFlags::SQLITE_OPEN_READ_WRITE` и `SQLITE_BUSY_TIMEOUT` (5 секунд).
* **Сложные реляционные запросы и целостность**: Сканирует 12 связанных таблиц (`threads`, `messages`, `local_thread_catalog`, `automation_runs`, `inbox_items`, `thread_spawn_edges` и др.).
* **Интеллектуальное восстановление (`repair_corrupted_sessions`)**:
  - Обнаруживает битые сессии с поврежденными внешними ключами или незавершенными генерациями.
  - Создает резервную копию базы данных в `backups_state/easy-cli-proxy-api/session-repair`.
  - В транзакции SQLite восстанавливает связность дерева диалога, генерирует события прогресса через Tauri Event Emitter (`codex-session-repair-progress`).
* **Редактор контекста сессий (`CodexSessionContextEditor.tsx`)**: Позволяет удалять или модифицировать системные промпты и внедренные контекстные переменные непосредственно в SQLite-хранилище сессии.

### 2.5. Нативная интеграция с терминалами операционных систем (`agents/launch.rs`)
* Обнаруживает установленные в ОС терминалы и формирует платформозависимые аргументы запуска:
  - **Linux**: `gnome-terminal --`, `konsole -e`, `xfce4-terminal -x`, `mate-terminal --`, `kitty -e`, `alacritty -e`, `ghostty -e`, `xterm -e`.
  - **macOS**: AppleScript команды запуска для `Terminal.app`, `iTerm2`, `Ghostty`.
  - **Windows**: `wt.exe` (Windows Terminal), `powershell.exe`, `cmd.exe` с корректным экранированием через `windows_literal_cli_command`.

### 2.6. Архитектура Go-плагинов
* В директории `plugins/` реализованы автономные плагины на Go:
  - `semantic-router`: Выполняет семантическую оценку пользовательских промптов и направляет их на оптимальные модели.
  - `weekly-reset-priority`: Интеллектуальный планировщик приоритетов аккаунтов на основе недельных лимитов и окон сброса квот провайдеров.

## 3. Сравнительный анализ технических преимуществ

| Направление | Преимущества `ai-proxy` | Преимущества `EasyCLIProxyAPI` |
| :--- | :--- | :--- |
| **Сетевая глубина и перехват** | **Полный TLS MITM и WS-декодирование**. Способен перехватывать трафик программ, не имеющих настроек базового URL, через стандартные переменные `HTTPS_PROXY` и подмену CA. | **Ориентация на стандартный Reverse Proxy**. Не требует установки недоверенного корневого сертификата в систему, что исключает риски компрометации ОС. |
| **DLP и безопасность данных** | **Уникальный 5-уровневый стек санитизации**. Энтропийный анализ, регулярные выражения, парсинг синтаксических структур, локальные LLM и OpenAI Privacy Filter с обратимым потоковым восстановлением секретов. | **Фокус на эксплуатационную безопасность**. Изоляция ядра на loopback, управление ключами доступа, маскирование UI в режиме демонстрации экрана. |
| **Производительность сетевого пути** | **Нулевой оверхед GUI**. Автономный легковесный сервис на Tokio/Axum, потребляющий считанные мегабайты RAM. Минимальные задержки при проксировании больших потоков токенов. | **Многокомпонентный оверхед**. Работает связка React + WebView + Rust бэкенд + дочерний процесс прокси-ядра. Требует значительно больше системных ресурсов. |
| **Интеграция с локальной средой** | Отсутствует. Прокси ничего не знает о файловой системе агентов. | **Беспрецедентная глубина интеграции с хостом**. Поддержка 16+ агентов, прямое манипулирование конфигурационными файлами JSON/YAML/TOML, запуск в нативных терминалах, глубокая работа с SQLite БД сессий. |
| **Надежность файловых операций** | Стандартная запись файлов конфигурации и базы телеметрии. | **Транзакционная файловая система**. Бэкапы перед каждым действием, хэширование SHA-256, проверка конфликтов, блокировка параллельных операций ядра. |
| **Мониторинг и аналитика** | **Аудит сетевых запросов и токенов**. Запись истории вызовов инструментов (tool calls), токенов и санитизированных тел запросов в ULID-базу. | **Финансово-эксплуатационный учёт**. Учёт затрат в долларах по моделям на основе `model_prices.json`, статистика по аккаунтам, графики активности. |
