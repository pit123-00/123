# Отчёт №3: Архитектурное устройство проектов

В данном отчёте приводится детальный архитектурный анализ систем `ai-proxy` и `EasyCLIProxyAPI`: структура подсистем, распределение обязанностей (Separation of Concerns), модели потоков данных (Data Flow) и диаграммы взаимодействия компонентов.

---

## 1. Архитектура `ai-proxy`

Проект `ai-proxy` спроектирован по классической модели **конвейерного шлюза (Pipeline Gateway Pattern)** с глубокой инспекцией пакетов на уровне L7.

### 1.1. Компонентная структура
* **HTTP / TLS Ingress**:
  - `main.rs`: Точка входа, инициализация Tokio рантайма, чтение конфигурации, сборка `ScanPipeline`, биндинг TCP-листнера `axum::serve`.
  - `mitm.rs`: TLS-интерцептор (`MitmAuthority`, LRU кэш `rustls::ServerConfig`). Принимает HTTP CONNECT, генерирует виртуальный сертификат и передает сокет внутреннему серверу.
* **Routing & Dispatcher**:
  - `proxy.rs`: Диспетчеризирует запросы на базе URI и заголовков.
    - Обычный Anthropic поток (`/v1/messages`) -> `anthropic_upstream_url`.
    - OpenAI / Codex поток (`/v1/responses`, `/backend-api/codex/responses`) -> `codex_upstream_url` или `codex_subscription_url` с нормализацией тела (`store: false`).
    - WebSocket Upgrade -> полнодуплексный мост с перехватом кадров.
* **Security & Inspection Layer**:
  - `middleware/mod.rs` (`ScanPipeline`): Менеджер конвейера, последовательно передающий полезную нагрузку через цепочку сканеров.
  - `middleware/regex_scanner.rs`, `entropy_scanner.rs`, `structural_scanner.rs`: Локальные детерминированные синхронные/асинхронные сканеры.
  - `middleware/model_scanner.rs`, `privacy_filter_scanner.rs`: Внешние адаптеры к ML-моделям (Ollama / `opf`).
* **Transformation & De-identification**:
  - `redactor.rs`: Реализует стратегии маскирования данных.
  - `redaction_context.rs`: Хранилище контекста текущего HTTP-запроса (`RedactionContext`), отслеживающее маппинг `placeholder <-> original_secret`.
  - `StreamingRestore`: Демультиплексор потока ответа со скользящим окном, восстанавливающий плейсхолдеры в поток токенов в реальном времени.
* **Observability & Analytics**:
  - `telemetry.rs`: Структуры данных и экстракторы метаданных из JSON (детекция используемой модели, извлечение вызовов инструментов `tool_use`/`tool_calls`).
  - `telemetry_store.rs`: SQLite слой аудита на базе ULID-идентификаторов.
  - `dashboard.rs`: Автономный HTTP-сервер на отдельном порту (по умолчанию 18081) с аутентификацией по токену (`~/.ai-proxy/dashboard.token`), отдающий UI и SSE-стримы телеметрии.

## 2. Архитектура `EasyCLIProxyAPI`

Архитектура `EasyCLIProxyAPI` представляет собой **двухуровневую оркестрационную систему с разделением на Client Shell (Tauri Desktop) и External Proxy Kernel (`cli-proxy-api`)**.

### 2.1. Компонентные уровни
1. **Frontend Presentation & Control Tier (React 19 + TypeScript + Vite)**:
   - Организован по компонентно-страничному принципу (`src/pages/`, `src/components/`, `src/services/`).
   - Содержит специализированные панели управления: `AgentsPage`, `RoutingPage`, `CodexSessionsPanel`, `McpSkillsPage`, `UsageRecordsPage`, `QuotaPage`, `PluginsPage`.
   - Не содержит прямой бизнес-логики работы с сетью и файлами — все вызовы делегируются в Rust через `invokeAgentCommand`.
2. **Desktop Orchestration & Integration Tier (Tauri 2 Core / Rust)**:
   - **`core_runtime.rs`**: Супервизор внешнего процесса ядра. Управляет переменными окружения, дескрипторами процессов, системными Job Objects (в Windows) и сигналами завершения.
   - **`agents/` subsystem**:
     * `discovery.rs`: Автоматический аудит файловой системы и реестра ОС для нахождения путей установки 16+ AI-клиентов.
     * `configuration.rs`: Парсер и генератор конфигурационных файлов клиентов в форматах YAML, JSON, JSON5.
     * `transactions.rs` & `backups.rs`: Двухфазный транзакционный менеджер с SHA-256 валидацией и механизмом атомарного отката при сбоях.
     * `launch.rs`: Адаптер эмуляторов терминалов ОС (macOS Terminal/iTerm2, Windows Terminal/cmd/PowerShell, Linux xterm/kitty/alacritty/gnome-terminal).
   - **`codex_sessions.rs`**: Движок прямого взаимодействия с SQLite базами данных сессий Codex CLI (`~/.codex/sessions/*.db`), включающий транзакционный анализатор повреждений и модуль восстановления связности дерева веток.
   - **`reverse_proxy.rs`**: Защитный контур ядра на базе `hyper 1.0` и `rustls`.
   - **`mcp_servers.rs`**: Локальный реестр Model Context Protocol (MCP) серверов.
3. **Core Proxy Kernel (`cli-proxy-api`)**:
   - Внешний бинарный процесс ядра, компилируемый отдельно или поставляемый в бандле.
   - Осуществляет реальную маршрутизацию запросов между десятками LLM-аккаунтов, ротацию ключей, отслеживание квот и балансировку нагрузки (`round-robin`, `weighted-round-robin`, `fill-first`).
4. **Go Plugin Subsystem (`plugins/`)**:
   - Независимые модули на Go, взаимодействующие с ядром:
     * `plugins/semantic-router`: Высокоскоростная семантическая маршрутизация промптов.
     * `plugins/weekly-reset-priority`: Интеллектуальный балансировщик с учетом графиков сброса квот аккаунтов.

## 3. Сравнительный анализ архитектурных паттернов

| Паттерн / Архитектурный аспект | `ai-proxy` | `EasyCLIProxyAPI` |
| :--- | :--- | :--- |
| **Архитектурный стиль** | **Pipes and Filters / Intercepting Gateway**. Строгая линейная обработка каждого входящего сетевого события через цепочку фильтров. | **Hexagonal / Orchestration Shell**. Ядро системы служит адаптером между UI, локальной ОС (файлы, терминалы, процессы) и внешним демоном маршрутизации. |
| **Управление состоянием (State Management)** | **Минималистичное распределенное состояние**. Состояние инкапсулировано в `AppState` (`Arc<AppState>`), контекст запроса живет строго на время HTTP-соединения (`RedactionContext`), персистентное состояние — только телеметрия в SQLite. | **Сложное многоуровневое состояние**. Состояние распределено между React-состоянием интерфейса, памятью Tauri (State-контейнеры конфигураций), файловой системой хоста (снапшоты бэкапов), SQLite сессиями Codex и файлом `config.yaml` ядра. |
| **Отказоустойчивость и безопасность изоляции** | Отказ любого сканера регулируется `fail_policy` (`fail_closed` или fallback на regex). Процесс полностью изолирован в сети. | **Двухуровневая изоляция процессов**. Падение пользовательского интерфейса или вебвью не убивает ядро прокси (или корректно тушит его через Job Objects). Сбои при редактировании файлов нейтрализуются автоматическим rollback из бэкапа. |
| **Масштабируемость и развертывание** | Идеально подходит для развертывания в виде headless-контейнера в Docker/Kubernetes, системной службы `systemd` или централизованного шлюза в корпоративной сети. | Предназначен строго для локальной рабочей станции разработчика (Desktop Client Workstation), требуя графической среды и доступа к пользовательским директориям хоста. |
