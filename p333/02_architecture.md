# Отчёт №2: Архитектурное устройство системы bb (get-bb/bb)

## 1. Концепция и общая архитектура

Архитектура платформы **bb** спроектирована как распределённая, событийно-ориентированная система (Distributed Event-Driven Architecture) с четким разделением на уровни представления, центральной координации, выполнения на целевых машинах и изоляции провайдеров искусственного интеллекта.

Ключевой архитектурный принцип: **вычислительный процесс агента никогда не выполняется внутри центрального сервера или в браузере пользователя**. Он всегда вынесен на целевой хост (Host Daemon), где изолирован в отдельном процессе операционной системы через адаптер протокола (Bridge).

---

## 2. Архитектурная топология (Tiered Topology)

Система делится на четыре основных уровня:

```
+-------------------------------------------------------------+
|                      Client Layer                           |
|       (React Web App, Desktop Electron App, Mobile App)    |
+-------------------------------------------------------------+
                              |
                     WebSocket / HTTP REST
                              v
+-------------------------------------------------------------+
|                      Server Layer                           |
|      (Hono Framework, SQLite/PostgreSQL, Hub & Queues)      |
+-------------------------------------------------------------+
                              |
                    WebSocket (Daemon Session)
                              v
+-------------------------------------------------------------+
|                   Host Daemon Layer                         |
|  (Local/Remote Machines, Runtime Manager, Workspaces, FS)  |
+-------------------------------------------------------------+
                              |
                    stdio (JSON-RPC 2.0 / Grammar V3)
                              v
+-------------------------------------------------------------+
|                Provider Bridge Child Process                |
|  (Claude Code, Pi, OpenAI Codex, Cursor ACP, OMP, Custom)   |
+-------------------------------------------------------------+
```

### 2.1. Client Layer (Пользовательский интерфейс)
- **Web App (`apps/web`)**: SPA на React, подключающийся к серверу по WebSocket (`hub.ts`) и HTTP REST.
- **Desktop (`apps/desktop`)**: Electron/Tauri-оболочка, объединяющая клиент и возможность локального запуска сервера и хост-демона.
- **Mobile (`apps/mobile`)**: Мобильный клиент, взаимодействующий через Mobile Bridge и центральный сервер.
- **SDK & Client Core (`packages/sdk`, `packages/client-core`)**: Библиотека типизированных клиентов с поддержкой реалтайм-подписок (`realtime-client.ts`), автоматического восстановления связи и буферизации.

### 2.2. Server Layer (Сервер координации)
- Построен на базе **Hono** (`apps/server/src/server.ts`).
- **Ответственность**:
  1. Персистентность потоков, событий, проектов, конфигураций пользователей и плагинов в базе данных (`@bb/db`).
  2. Ведение очередей сообщений (`queued-messages.ts`, `queued-message-dispatch.ts`).
  3. Маршрутизация команд к подключенным демонам по сессионным WebSocket (`daemon-protocol.ts`).
  4. Формирование проекций таймлайна (`services/threads/timeline.ts`) для оптимизированной отдачи клиентам без необходимости отдавать миллионы сырых событий.
  5. Координация перемещения сессий между серверами (`services/server-move`).

### 2.3. Host Daemon Layer (Демон хоста)
- Работает как автономный фоновый сервис на машине разработчика (или в облачном контейнере).
- **Ответственность**:
  1. Поддержание постоянного WebSocket-соединения с сервером с heartbeat (`HEARTBEAT_INTERVAL_MS = 15s`).
  2. Подготовка и изоляция рабочих директорий (`HostWorkspace` в `bb-environment-provider-host`).
  3. Управление жизненным циклом сред (`RuntimeManager` в `apps/host-daemon/src/runtime-manager.ts`).
  4. Подготовка и инжекция скиллов и расширений (`injected-skills.ts`).
  5. Исполнение прямых файловых операций (`hostReadFile`, `hostWriteFile`, `hostListFiles`) и запуск процессов терминалов.

### 2.4. Provider Bridge Layer (Мост провайдера)
- Отдельный дочерний процесс Node.js, запускаемый рантаймом.
- Транслирует внутренний API провайдера (CLI-команды, протокол Claude Agent SDK, протокол ACP Cursor, кастомные стримы) в стандартизованный JSON-RPC протокол дельт `@bb/provider-bridge-protocol`.
- Полностью изолирует нестабильные зависимости вендоров от основного демона.

## 3. Сетевые протоколы и границы абстракции

### 3.1. Server <-> Host Daemon: Двунаправленный WebSocket
- Сессия устанавливается с передачей токена машины (`machine-auth.ts`).
- Сервер отправляет демону команды через строгую типизацию `HostDaemonOnlineRpcCommandSchema`:
  - `thread.start`: запуск нового потока с передачей параметров запуска моста (`bridgeLaunch`), исходных промптов и конфигурации окружения.
  - `turn.submit`: отправка нового хода (режимы: `start`, `auto`, `steer`).
  - `thread.stop`: прерывание текущей генерации или освобождение ресурсов.
  - `interactive.resolve`: передача решения пользователя по запросу подтверждения (approval) или ответу на вопрос (userQuestion).
- Демон отправляет серверу события потоков (`ThreadEvent`), метрики использования ресурсов, обновления статуса инсталляции провайдеров и статусы выполнения задач.

### 3.2. Agent Runtime <-> Provider Bridge: stdio JSON-RPC
- Обмен структурированными сообщениями JSON-RPC 2.0 через стандартный ввод/вывод (`stdin` / `stdout`).
- Версионирование грамматики событий (`ThreadEventGrammar`, текущая версия `THREAD_DELTA_GRAMMAR_V3`).
- Провайдер стримит не готовые сущности базы данных, а дельты (`thread/delta`):
  - `item.open`: открытие сущности (инструмент, команда, сообщение агента, рассуждение, делегирование).
  - `item.textDelta`: посимвольный/построчный стриминг текста ответа или рассуждения (`reasoning`).
  - `item.outputDelta`: потоковый вывод запущенной консольной команды.
  - `item.progress`: обновление промежуточного прогресса выполнения.
  - `item.close`: фиксация финального статуса (`completed`, `failed`).
  - `turn.boundary`: завершение хода с контрольной точкой сессии (`providerCheckpointId`).

## 4. Жизненный цикл окружений и рабочих пространств (Workspaces)

В архитектуре **bb** окружение (`Environment`) является самостоятельной сущностью первого класса:
1. **Provisioning (Подготовка среды)**:
   - Проверяется наличие репозитория Git и текущей рабочей ветки.
   - Запускаются lifecycle-скрипты настройки окружения (`environment-lifecycle-script.ts`).
   - Инициализируется каталог инжектируемых скиллов (`injected-skills.ts`).
2. **Skill Catalog Invalidation**:
   - При изменении набора скиллов вычисляется общий SHA-256 хэш каталога.
   - Если хэш изменился, `RuntimeManager` осуществляет контролируемую замену экземпляра рантайма (`ReplaceEntryForSkillCatalogArgs`), гарантируя консистентность контекста агента.
3. **Execution Isolation (Изоляция сред)**:
   - Каждый поток выполняется строго в своем рабочем каталоге `workspacePath`.
   - Поддерживаются дополнительные каталоги для записи (`additionalWorkspaceWriteRoots`).

## 5. Персистентность, модель событий и проекции (Event Sourcing & Timeline Projections)

Архитектурное решение хранения данных сочетает классическую реляционную модель с принципами **Event Sourcing**:
1. **Событийная модель (Append-Only Event Store)**:
   - Все действия, дельты и сообщения сохраняются в таблицу событий как `stored_thread_events`.
   - События снабжены монотонно возрастающим порядковым номером (`seq`) и скоупом (`threadScope` для общепоточных метаданных, `turnScope` для конкретного хода).
2. **Проекция таймлайна (Timeline Projection)**:
   - Модуль `services/threads/timeline.ts` преобразует сырой поток событий в оптимизированное дерево элементов таймлайна (`ThreadTimelineWindow`).
   - Кэширование проекций (`timeline-cache.ts`, `timeline-selection-memo.ts`): клиенты запрашивают страницы таймлайна, что исключает необходимость рендеринга тысяч событий на клиенте.
   - Механизм сворачивания (Folding) скрывает технические промежуточные шаги рассуждений и длинные терминальные выводы (`timeline-output-shortening.ts`).

## 6. Отказоустойчивость и безопасность (Fault Tolerance & Reliability)

1. **Watchdog-контроль запусков**:
   - `runtime.turn-start-watchdog.ts` отслеживает, подтвердил ли провайдер принятие хода (`input.accepted`) в пределах установленного таймаута. Если провайдер завис, инициируется прерывание и восстановление.
2. **Graceful Stale Recovery**:
   - Если связь с хостом прерывается, поток переходит в статус прерванного с указанием точной причины: `host-connection-lost`, `host-daemon-restarted` или `host-removed`.
3. **Идемпотентность команд**:
   - Каждая отправка хода сопровождается клиентским идентификатором `clientTurnRequestId` (`creq_...`), что предотвращает дублирование ходов при сетевых ретраях.
