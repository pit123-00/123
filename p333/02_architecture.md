# Отчёт 2. Архитектурное устройство системы (Dev Quality Gates)

## Введение и назначение отчёта
Данный архитектурный отчёт посвящен исследованию принципов построения, компонентных связей, потоков данных и архитектурных инвариантов системы `dev-quality-gates`. Анализ выполнен строго на основе архитектуры программных модулей, схем конфигураций (`tools.schema.json`, `hk.pkl`, `mise.toml`), потоков исполнения в CI (`.github/workflows/*`) и паттернов контроля качества кода (`docs/patterns.md`, `docs/adopt.md`).

---

## 1. Архитектурный стиль и базовые принципы

Архитектура системы `dev-quality-gates` объединяет три взаимодополняющих архитектурных стиля:
1. **Schema-First / Metadata-Driven Architecture**: данные о политиках, инструментах и проверках отделены от исполняемого кода и формализованы в виде строгого машиночитаемого контракта.
2. **Three-Tier Quality Gates Pipeline**: разделение жизненного цикла контроля качества на три изолированных барьера с нарастающей строгостью и временем исполнения.
3. **Hermetic & Declarative Toolchain**: исключение неявных системных зависимостей за счет декларативной фиксации инструментов на уровне конфигурации хоста и репозитория.

```
       +-------------------------------------------------------+
       |           tools.json (Single Source of Truth)          |
       +-------------------------------------------------------+
                |                                  |
                v                                  v
     [scripts/check-registry.ts]           [scripts/readme.ts]
      (Ajv Schema Validation)             (Deterministic Render)
                |                                  |
                +-----------------+----------------+
                                  |
                                  v
                    +---------------------------+
                    |  hk.pkl / mise.toml       |
                    |  (Unified Toolchain Execution)
                    +---------------------------+
                                  |
        +-------------------------+-------------------------+
        |                         |                         |
        v                         v                         v
 [Tier 1: Fast Hook]      [Tier 2: Slow Hook]     [Tier 3: CI Gate]
 (Staged files, <2s)      (Pre-push, whole repo)  (Isolated runner, PR)
```

## 2. Трёхуровневая модель контроля качества (Three-Tier Enforcement Architecture)

Ключевой архитектурный паттерн системы — недопущение перегрузки разработчика и агента медленными проверками при сохранении абсолютной строгости в CI.

### 2.1. Уровень 1: Staged-File Hook (Fast Tier)
- **Целевое время исполнения**: < 2 секунд.
- **Область действия**: только измененные (staged) файлы.
- **Изоляция контекста**: `stash = "git"` в `hk.pkl`. Изменения, не добавленные в индекс, временно убираются в stash, предотвращая случайную валидацию «грязного» рабочего дерева.
- **Компоненты**:
  * Сканеры утечки секретов (`betterleaks`).
  * Сверхбыстрые нативные линтеры и форматтеры (`rumdl`, `typos`, `oxlint`).
  * Валидатор синтаксиса и безопасности CI (`jactionlint`).
  * Проверка консистентности реестра метаданных (`check:registry`).
- **Свойство**: `fix = true` — разрешены безопасные автоматические правки на лету.

### 2.2. Уровень 2: Pre-Push Hook (Slow Tier)
- **Целевое время исполнения**: 5–30 секунд.
- **Область действия**: весь локальный репозиторий и граф зависимостей.
- **Компоненты**:
  * Статическая проверка типов компилятором (`tsc`, `ty check`).
  * Полный кросс-модульный линтинг связей и проверка неиспользуемых экспортов (`knip`).
  * Валидация документационных ссылок (`lychee`).
- **Назначение**: отсечь грубые архитектурные поломки до отправки ветки на удаленный сервер.

### 2.3. Уровень 3: CI Gate (Complete & Authoritative Tier)
- **Целевое время исполнения**: до 10–15 минут.
- **Область действия**: полное воспроизводимое окружение на чистой виртуальной машине.
- **Архитектурный инвариант**: *«CI is the only gate that cannot be skipped»*. Локальные git-хуки являются лишь средством оптимизации обратной связи; их пропуск (`--no-verify`) никак не влияет на блокировку слияния в ветку `main`.
- **Компоненты**:
  * Запуск агрегирующей команды `mise run check` (вызывающей `hk check --all`).
  * Мутационное тестирование дельты PR (`stryker run --mutate "$files"`).
  * Сканирование уязвимостей (`osv-scanner`).
  * Проверка соблюдения Conventional Commits (`commitlint`) по диапазону коммитов PR.
  * Верификация отсутствия незакоммиченных изменений через `git status --porcelain`.

## 3. Архитектура Single Source of Truth и генерация артефактов

В репозитории реализован паттерн устранения когнитивного и технического дрифта через жесткую схематизацию данных.

1. **Единый источник метаданных (`tools.json`)**:
   Все свойства инструментов, правила включения, категории, связи с ресерч-документами и ограничения формализованы в едином файле данных.
2. **Валидация до компиляции**:
   `scripts/check-registry.ts` гарантирует, что ни один некорректный инструмент не попадет в систему (проверка схемы Draft-07, уникальность slug ID, уникальность URL репозиториев без учета регистра).
3. **Детерминированный рендеринг (Code/Doc Generation Gate)**:
   Файл `README.md` не пишется человеком вручную в части таблиц инструментов. Скрипт `scripts/readme.ts` читает `tools.json`, сортирует записи в строгом порядке категорий `CATEGORY_ORDER` и встраивает сгенерированный блок между маркерами:
   ```html
   <!-- tools:start -->
   ...
   <!-- tools:end -->
   ```
   В CI запускается проверка:
   ```bash
   pnpm run --silent readme -- --check
   ```
   Если в `README.md` есть хоть один символ ручной правки или рассинхронизации со схемой, сборка завершается аварийно.

## 4. Декларативное управление тулчейном (`mise` + Apple Pkl)

Традиционные подходы к CI страдают от проблемы «двойного описания»: конфигурация инструментов пишется один раз для `.pre-commit-config.yaml` или Husky, и второй раз для GitHub Actions Workflow с отдельными шагами установки.

В архитектуре `dev-quality-gates` эта проблема решена радикально:
1. **Уровень версий бинарников (`mise.toml`)**:
   Инструмент `mise` управляет средами исполнения (Node.js, pnpm, pkl, typos, lychee, rumdl, jactionlint). В GitHub Actions используется официальный экшен `jdx/mise-action`, который считывает ровно тот же `mise.toml`.
2. **Уровень декларации хуков (`hk.pkl`)**:
   Инструмент `hk` использует строго типизированный язык конфигурации Apple Pkl. Это позволяет оперировать объектами `Step`, `Mapping<String, Step>`, маппить glob-маски на шаги и динамически наследовать профили (`all = (fast) { ... }`).
3. **Единая точка входа**:
   Команда `mise run check` вызывает `hk check --all`. И разработчик на рабочей станции, и робот в CI вызывают одну и ту же команду, исключая расхождения в окружении.

## 5. Паттерны контроля деградации (Degradation Control Patterns)

Архитектура системы включает ряд специализированных механизмов, предотвращающих скрытое накопление технического долга.

### 5.1. Управление временными исключениями (Review Dates on Exceptions)
Подавление правил линтеров и сканеров безопасности часто становится «вечным». В архитектуре заложен паттерн **экспирации исключений**:
- Подавление обязано содержать дату планового пересмотра в формате `(review YYYY-MM-DD)` и обоснование.
- Автоматизированный скрипт проверяет валидность даты через парсер календаря и проверяет, что дата еще не наступила.
- При наступлении даты сборка в CI падает, требуя либо устранения дефекта, либо повторного осознанного продления исключения.
- Инструменты со встроенным контролем (например, `osv-scanner` с параметром `ignoreUntil`) используют нативную поддержку.

### 5.2. Двухуровневый барьер покрытия: Line Coverage + PR Mutation Testing
- Традиционный `diff-cover` проверяет только факт исполнения измененных строк (`100% lines executed`).
- Архитектура внедряет **StrykerJS Mutation Gate** на уровне дельты pull request:
  Скрипт вычисляет `git diff --name-only origin/main...HEAD`, фильтрует исходники от тестов и скармливает их во флаг `--mutate`.
  Если добавленный тест не падает при мутации AST (например, содержит пустой или слабый ассерт), мутационный барьер завершается с кодом 1 и блокирует слияние.

### 5.3. Механизм фиксации уровня (Coverage Ratchet)
Базовый уровень покрытия тестами фиксируется в конфигурации как минимальный порог (`floor`). При росте покрытия порог поднимается вверх. Понижение порога блокируется системой контроля версий.

### 5.4. Защита миграций баз данных (Immutable Migrations Gate)
Миграции, уже попавшие в базовую ветку `main`, считаются неизменяемыми. CI-контур вычисляет git diff относительно `main`: любая попытка модификации существующего файла миграции вызывает ошибку сборки. Добавление новых миграций проверяется анализатором `squawk` на предмет блокировок таблиц.
