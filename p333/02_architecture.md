# Отчёт №2: Архитектурное устройство агентной системы и навыков

## 1. Введение и архитектурная концепция

Данный отчёт посвящён архитектуре взаимодействия человека, агента и кодовой базы в рамках репозитория `https://github.com/mokevnin/agentic-coding-design-patterns`.
Архитектура системы построена на парадигме **«Скиллы как пакетированные рабочие процессы» (Skills as Packaged Workflows)**, где сложные инженерные дисциплины (TDD, рефакторинг, ревью кода, триаж задач, дизайн систем, диагностика багов) формализованы в виде исполняемых декларативных инструкций, изолированных стейт-машин и контрактов контекста.

Вместо монолитного раздутого системного промпта (`bloated AGENTS.md`) архитектура использует модульное разделение ответственности, иерархию раскрытия контекста (Progressive Disclosure) и строгие разделительные швы (Seams).

---

## 2. Слои абстракции и модель скиллов

Каждый навык в папке `.agents/skills/<skill-name>/` представляет собой замкнутый модуль с чётким разграничением метаданных, интерфейса запуска и доменной логики.

### 2.1. Метаданные и режим вызова (Invocation Architecture)
Каждый навык начинается с YAML frontmatter:
```yaml
---
name: triage
description: Move issues and external PRs through a state machine of triage roles — categorise, verify, grill if needed, and write agent-ready briefs.
disable-model-invocation: true
---
```
Архитектурно определены два типа навыков (`writing-great-skills`):
1. **Model-invoked skills (вызываемые моделью)**:
   - Флаг `disable-model-invocation` отсутствует.
   - Описание (`description`) оптимизировано под семантический матчинг LLM (содержит точные триггеры, ситуации применения).
   - Агент имеет право запускать их автономно в ходе диалога или из других скиллов.
   - *Архитектурная цена*: описание постоянно занимает место в контекстном окне (Context Load).
2. **User-invoked skills (вызываемые пользователем)**:
   - Установлен флаг `disable-model-invocation: true`.
   - Описание является чисто человекочитаемым кратким резюме.
   - Модель не может вызвать навык самостоятельно; запуск происходит только по прямой команде разработчика (например, `/triage`, `/improve-codebase-architecture`, `/wayfinder`, `/code-review`).
   - *Архитектурная выгода*: нулевая нагрузка на контекст модели в неактивном состоянии. Снижает риск несанкционированного переключения контекста моделью.

## 3. Иерархия контекста и Progressive Disclosure

Архитектура предотвращает деградацию внимания больших языковых моделей (LLM attention drift) путём многоуровневого распределения информации (Information Hierarchy):

1. **Уровень 1: In-skill steps (Шаги первого уровня)**:
   - Располагаются непосредственно в `SKILL.md`.
   - Содержат строгую последовательность фаз с явными критериями завершения (**completion criteria**).
   - Пример: Red-Green-Refactor loop в `tdd/SKILL.md` или фазы `Build feedback loop` -> `Tighten loop` в `diagnosing-bugs/SKILL.md`.
2. **Уровень 2: In-skill reference (Внутренние справочники)**:
   - Определения, статические правила или таблицы решений в `SKILL.md`.
   - Используются по требованию (on-demand), без раздувания управляющей логики.
3. **Уровень 3: External reference & Context Pointers (Внешние ссылки и указатели)**:
   - Детализация вынесена в отдельные файлы рядом с `SKILL.md` (например, `mocking.md`, `tests.md` для TDD; `AGENT-BRIEF.md`, `OUT-OF-SCOPE.md` для Triage; `HTML-REPORT.md` для Архитектуры).
   - Загружаются агентом **только тогда, когда срабатывает контекстный указатель (Context Pointer)**.
   - Пример: если при триаже задача отклоняется как `wontfix`, агент подгружает `OUT-OF-SCOPE.md` для работы с базой отклонённых фич. Если задача берется в работу — подгружается `AGENT-BRIEF.md`.

Такая архитектура снижает объём токенов в базовом цикле на 60–80%, сохраняя доступ к глубокой специфике только при наступлении соответствующей ветки (branching).

## 4. Двухосевая архитектура ревью (Two-Axis Review Architecture)

В навыке `code-review` реализован фундаментальный архитектурный паттерн: **независимый двухосевой аудит через изолированные параллельные агенты**:

```
                  ┌──────────────────────┐
                  │   Команда ревью      │
                  │   git diff + spec    │
                  └──────────┬───────────┘
                             │
            ┌────────────────┴────────────────┐
            ▼                                 ▼
   ┌───────────────────┐             ┌───────────────────┐
   │  Sub-agent 1      │             │  Sub-agent 2      │
   │  Axis: Standards  │             │  Axis: Spec       │
   │  (Стандарты кода, │             │  (Соответствие    │
   │   код-смеллы)     │             │   требованиям ТЗ) │
   └────────┬──────────┘             └────────┬──────────┘
            │                                 │
            └────────────────┬────────────────┘
                             ▼
                  ┌──────────────────────┐
                  │    Агрегатор         │
                  │  (Без смешивания!)   │
                  └──────────────────────┘
```

### Принципы архитектуры:
- **Разделение осей (Standards vs Spec)**:
  - *Ось Standards*: Проверяет форматирование, соответствие стандартам репозитория и каталог из 12 архитектурных «запахов кода» Фаулера (Mysterious Name, Duplicated Code, Feature Envy, Data Clumps, Primitive Obsession, Shotgun Surgery и др.).
  - *Ось Spec*: Проверяет функциональную полноту (что из ТЗ не реализовано), появление несанкционированного кода (scope creep) и расхождения в логике относительно issue/PRD.
- **Изоляция под-агентов (Context Hygiene)**:
  - Проверка запускается в виде двух параллельных вызовов субагентов с типом `general-purpose`.
  - Субагенты не видят рассуждений друг друга, что исключает «эффект ореола» (halo effect), когда красивый код с идеальными типами маскирует отсутствие критической бизнес-логики, или наоборот.
- **Запрет смешивания и ранжирования**:
  - Агрегатор выводит результаты под независимыми заголовками `## Standards` и `## Spec` без общего сквозного ранжирования находок. Это предотвращает вытеснение функциональных багов стилевыми замечаниями.

## 5. Архитектура стейт-машин в процессах разработки

В проекте управление сложными процессами реализовано через формальные конечные автоматы (FSM):

### 5.1. Автомат триажа задач (`triage/SKILL.md`)
Управляет жизненным циклом входящих задач (Issues) и внешних пул-реквестов (PRs treated as issues with attached code):
- **Категории**: `bug`, `enhancement`.
- **Состояния**:
  - `needs-triage` — исходное состояние (требуется первичная оценка);
  - `needs-info` — блокировка в ожидании деталей от автора;
  - `ready-for-agent` — задача полностью специфицирована, составлен долговечный контракт (`AGENT-BRIEF.md`), готова для автономного агента (AFK agent);
  - `ready-for-human` — задача требует решения человека (дизайн, спорные продуктовые решения, мерж PR);
  - `wontfix` — отклонение задачи с обязательной регистрацией в реестре `.out-of-scope/<concept>.md`.

### 5.2. Автомат диагностики и обратной связи (`diagnosing-bugs`)
Диагностический контур строится вокруг принципа «Tight Pass/Fail Signal»:
- Переход к анализу кода запрещён до тех пор, пока не создан узкий автоматизированный feedback loop (тест на граничном шве, curl-скрипт, diff CLI вызова, headless-скрипт Playwright, либо интерактивный shell-скрипт с человеком `hitl-loop.template.sh`).
- Только после фиксации воспроизводимости происходит переход к гипотезам и инструментальной локализации дефекта.

### 5.3. Автомат долгосрочной навигации (`wayfinder`)
Оркестратор долгосрочных задач, превышающих размер одной контекстной сессии:
- Создает общую карту исследования (`wayfinder:map`) в виде родительского issue на трекере задач.
- Декомпозирует задачу на граф дочерних тикетов-решений.
- Работает по принципу «Plan, don't do»: сессия считается успешной, когда устранены неопределённости на границе карты, а не когда сгенерирован незрелый черновой код.

## 6. Абстракция швов и адаптеры трекеров задач

Система полностью абстрагирована от конкретной платформы управления задачами через архитектурный паттерн **Ports & Adapters (Гексагональная архитектура)**:
- Документ `.agents/skills/setup-matt-pocock-skills/` определяет единый порт взаимодействия с трекером.
- Реализованы три адаптера:
  1. **GitHub Issues/PRs Adapter** (`issue-tracker-github.md`) — работа через GitHub CLI (`gh issue list`, `gh pr review`, labels, projects).
  2. **GitLab Issues/MRs Adapter** (`issue-tracker-gitlab.md`) — работа через `glab`.
  3. **Local Markdown Tracker Adapter** (`issue-tracker-local.md`) — локальное хранение задач в виде плоских Markdown-файлов в репозитории (для полной автономности и приватности).

Навыки `triage`, `wayfinder`, `to-tickets`, `code-review` взаимодействуют исключительно со стандартным интерфейсом адаптера, не завися от используемого бэкенда.
