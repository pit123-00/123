# Отчёт: Углубленный технический анализ безопасности, аутентификации и внешних каналов связи

Данный отчёт подготовлен на основе прямого исследования исходного кода подсистем API-шлюза (`backend/app/gateway/auth/`, `backend/app/gateway/csrf_middleware.py`) и диспетчеризации каналов связи (`backend/app/channels/`) платформы **Deer-Flow**.

---

## 1. Безопасность и аутентификация (`backend/app/gateway/auth/`)

Подсистема аутентификации и контроля доступа Deer-Flow решает задачи безопасной идентификации пользователей, защиты от атак полного перебора (brute-force) и утечек секретов.

### 1.1. Версионированное хэширование паролей (`password.py`)
- **Архитектурная проблема**: Классический алгоритм Bcrypt имеет фундаментальное ограничение: входная строка молча обрезается на 72-м байте. Если пользователь задает сложную ключевую фразу длиной 100 символов, последние 28 символов игнорируются, что создает скрытую уязвимость.
- **Инженерное решение Deer-Flow**: Реализован версионированный формат хэша `$dfv<N>$<bcrypt_hash>`:
  - **Версия v1** (legacy): Прямой `bcrypt(password)` для обратной совместимости со старыми установками.
  - **Версия v2** (current production): Композитное хэширование:
    $$	ext{Hash} = 	ext{bcrypt}(	ext{base64}(	ext{sha256}(	ext{password})))$$
    Предварительное хэширование пароля через SHA-256 сжимает строку любой длины в 32 байта (44 символа в представлении Base64). В результате Bcrypt получает строку, которая гарантированно меньше 72 байт, а энтропия всей исходной фразы сохраняется полностью.
  - **Бесшовная миграция**: Функция `verify_password` определяет версию хэша по префиксу. Если хэш соответствует версии v1, но пароль верен, система прозрачно перехэширует его в формат v2 при входе.

### 1.2. Распределенный троттлинг попыток входа (`login_throttle.py`)
- Защита от перебора паролей реализована через абстракцию `LoginThrottleStore`.
- **Бэкенды хранения**:
  - `MemoryLoginThrottleStore`: Локальное кольцевое хранилище для одиночных инстансов.
  - `SqlLoginThrottleStore`: Персистентная реляционная таблица `login_throttle`. При горизонтальном масштабировании Gateway все реплики за балансировщиком нагрузки обращаются к единой таблице, обеспечивая немедленный глобальный lockout атакующего IP-адреса на уровне всей инфраструктуры.
- **Политика блокировки**: Настраиваемое количество попыток, скользящее окно учета неудач и экспоненциальное увеличение задержки.

### 1.3. Корпоративный OIDC / SSO (`oidc.py`)
- Провайдер-агностическая реализация протокола OpenID Connect:
  - Автоматический Discovery конфигурации (`/.well-known/openid-configuration`);
  - Валидация подписей ID Token с динамическим извлечением публичных ключей JWKS (`PyJWKClient`);
  - Защита от Replay-атак: генерация криптографически стойких параметров `state` и `nonce` с обязательной валидацией их совпадения в ответе провайдера;
  - Claim-mapping: автоматическая трансляция корпоративных групп и ролей (claims) в локальные разрешения ролевой модели (RBAC).

### 1.4. Персональные токены доступа (PAT — `pat.py`)
- Токены для программного доступа к REST API:
  - Формат: префикс `dfp_` + 32 байта из CSPRNG (`secrets.token_bytes`), закодированные в base62;
  - Принцип Zero-Knowledge: открытый токен отображается пользователю строго один раз при генерации. В базе данных сохраняется исключительно SHA-256 дайджест;
  - Постоянновременное сравнение: поиск записи осуществляется по хэшу, а верификация выполняется через `hmac.compare_digest` / `constant_time_equals` для предотвращения атак по времени (timing side-channel attacks);
  - Скоупинг: токен может только сужать права пользователя, исключая повышение привилегий.

### 1.5. CSRF-защита и безопасность сессионных cookie (`csrf_middleware.py`, `session_cookie.py`)
- Защита по паттерну Double-Submit Cookie: проверка токена в заголовке `X-CSRF-Token` для методов `POST`, `PUT`, `DELETE`, `PATCH`.
- Куки сессий устанавливаются со свойствами:
  - `HttpOnly`: блокирует доступ к куке из JavaScript, нивелируя последствия XSS;
  - `SameSite=Lax` (или `Strict`): предотвращает передачу сессии при межсайтовых запросах;
  - `Secure`: передача строго по HTTPS;
  - Автоматическая ротация сессии: уничтожение старого идентификатора и выпуск нового при любой смене контекста безопасности.

## 2. Диспетчеризация внешних каналов мессенджеров (`backend/app/channels/`)

Модуль `app/channels/` обеспечивает интеграцию агентной платформы с корпоративными и публичными мессенджерами:

### 2.1. ChannelManager (`manager.py`)
- Служит единым координатором очередей входящих и исходящих сообщений.
- Сопоставляет внешние идентификаторы пользователей и чатов с внутренними изолированными тредами (`thread_id`) в Deer-Flow.
- Осуществляет потоковую трансляцию генерируемого ответа с адаптацией разметки:
  - Feishu Post карточки;
  - Slack Block Kit;
  - Telegram HTML/Markdown;
  - Discord embeds.

### 2.2. Архитектура Outbound-Only (работа без белого IP)
Вместо классических вебхуков, требующих публичного домена, открытых портов наружу и SSL-сертификатов, интеграции Deer-Flow построены на протоколах исходящих постоянных соединений:
- **Feishu / Lark (`feishu.py`)**: Постоянный WebSocket к серверам Lark Open Platform;
- **Slack (`slack.py`)**: Полноценный Socket Mode поверх WebSocket;
- **Telegram (`telegram.py`)**: Длинный опрос (long-polling) с пакетным чтением обновлений;
- **DingTalk (`dingtalk.py`)**: Потоковый протокол DingTalk Stream Client;
- **WeChat / WeCom (`wechat.py`, `wecom.py`)**: Long-polling протокол iLink и авторизация через QR-код (`wechat_qr_login.py`);
- **Discord (`discord.py`)**: Подключение к Discord Gateway по WebSocket.

### 2.3. Координация лидерства и дедупликация (`leadership.py`, `dedupe_store.py`)
- **ChannelLeaderLease**: Механизм распределенной аренды лидерства. При работе нескольких реплик сервиса только одна реплика становится лидером и открывает постоянное соединение с мессенджером. При сбое лидера аренда автоматически перехватывается соседним инстансом.
- **DedupeStore**: Хранилище обработанных ID сообщений, исключающее повторную генерацию ответов при сетевых повторах мессенджеров.
