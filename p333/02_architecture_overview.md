# Отчёт 2: Архитектурное устройство платформы Deer-Flow

Данный отчёт представляет глубокий архитектурный анализ платформы **Deer-Flow** на основе исследования исходного кода репозитория `bytedance/deer-flow`. В отчёте детально рассматриваются топология системы, уровни абстракции, поток управления и данных, конвейер обработки запросов, модель параллелизма и архитектура хранения состояния.

---

## 1. Концептуальная архитектура и топология системы

Архитектура Deer-Flow спроектирована как трехуровневая распределенная система корпоративного класса, разделенная на четкие функциональные слои:

```
[ Frontend (Next.js / React) ]  <---> [ Gateway API (FastAPI / Starlette) ]
                                              |
                        +---------------------+---------------------+
                        |                                           |
             [ Agent Harness (Core SDK) ]               [ Channel Message Bus ]
                        |                           (Slack, Feishu, Discord, Telegram)
        +---------------+---------------+
        |               |               |
[ Middleware Stack ] [ Toolset ] [ Subagent Runtime ]
        |               |               |
[ Model Gateway ] [ Sandboxes ] [ Batch & Background Service ]
        |               |               |
[ LLM Providers ] [ Docker/K8s ] [ Persistence: SQLite / Postgres / Redis ]
```

### 1.1. Слой шлюза (Gateway API Layer — `backend/app/gateway`)
Шлюз выступает точкой входа для клиентских запросов и внешних систем:
- **FastAPI / Starlette App (`gateway/app.py`)**: маршрутизация HTTP/REST запросов и формирование потоков Server-Sent Events (SSE).
- **Безопасность и аутентификация (`gateway/auth/`)**:
  - Поддержка локальной авторизации (пароли с PBKDF2/argon2, дрожжевой троттлинг попыток логина через `login_throttle`);
  - OIDC / OAuth2 провайдеры (SSO корпоративного уровня);
  - Персональные токены доступа (PAT);
  - CSRF-защита (`csrf_middleware.py`) и сессионные куки со строгой ротацией.
- **Диспетчеризация внешних каналов (`app/channels/`)**:
  - Двусторонние мосты для корпоративных мессенджеров (Lark/Feishu, DingTalk, WeChat/WeCom, Slack, Telegram, Discord, QQ);
  - Механизм лидерства и лизинга соединений каналов (`ChannelLeaderLeaseConfig`) для предотвращения дублирования ответов при горизонтальном масштабировании инстансов шлюза.
- **GitHub Triggers & Webhooks (`gateway/github/`)**: автоматическая реакция на Issue, Pull Request и комментарии в репозиториях.

### 1.2. Слой ядра оркестрации (Agent Harness SDK — `backend/packages/harness/deerflow`)
Ядро является полностью отделяемым Python SDK (может работать без FastAPI через CLI или встраиваемый клиент `DeerFlowClient`):
- **Фабрики агентов (`agents/factory.py`, `agents/lead_agent/agent.py`)**: сборка вычислительного графа LangGraph `StateGraph`, регистрация инструментов и связывание middleware.
- **Дескриптор сборки (`AgentAssemblyDescriptor` в `assembly_descriptor.py`)**: уникальный криптографический отпечаток собранного агента (хэши базового промпта, версий инструментов, списка middleware и каталога скиллов), позволяющий контролировать неизменяемость сборки и аудит версий.

## 2. Архитектура конвейера Middleware (The Interceptor Pipeline)

Ключевым архитектурным паттерном Deer-Flow является расширяемый стек middleware (`AgentMiddleware`), перехватывающий жизненный цикл вызова агента:
1. До вызова LLM (`before_model` / `modify_model_request`);
2. После ответа LLM (`after_model` / `process_model_response`);
3. До выполнения инструмента (`before_tool_execution`);
4. После выполнения инструмента (`after_tool_execution`).

Стек собирается в строго детерминированном порядке в `lead_agent/agent.py` и `agents/factory.py`:

```

├────────────────────────────────────────────────────────┤
│ 2. ThreadDataMiddleware                                │ Контекст треда
├────────────────────────────────────────────────────────┤
│ 3. UploadsMiddleware                                   │ Файлы и вложения
├────────────────────────────────────────────────────────┤
│ 4. SandboxMiddleware                                   │ Инициализация песочницы
├────────────────────────────────────────────────────────┤
│ 5. DanglingToolCallMiddleware                          │ Защита от незакрытых tool_call
├────────────────────────────────────────────────────────┤
│ 6. GuardrailMiddleware                                 │ Политики безопасности контента
├────────────────────────────────────────────────────────┤
│ 7. ToolErrorHandlingMiddleware                         │ Преобразование исключений
├────────────────────────────────────────────────────────┤
│ 8. DurableContextMiddleware / DynamicContextMiddleware │ Инъекция даты, системных данных
├────────────────────────────────────────────────────────┤
│ 9. SkillActivationMiddleware                           │ Динамическое подключение скиллов
├────────────────────────────────────────────────────────┤
│ 10. DeferredToolPromotionAudit / DeferredToolFilter    │ Отложенный поиск MCP-инструментов
├────────────────────────────────────────────────────────┤
│ 11. SystemMessageCoalescingMiddleware                  │ Слияние системных сообщений
├────────────────────────────────────────────────────────┤
│ 12. SummarizationMiddleware                            │ Сжатие контекста при переполнении
├────────────────────────────────────────────────────────┤
│ 13. TodoMiddleware                                     │ Управление планом (plan mode)
├────────────────────────────────────────────────────────┤
│ 14. TokenUsageMiddleware / TokenBudgetMiddleware       │ Учет и ограничение токенов
├────────────────────────────────────────────────────────┤
│ 15. TitleMiddleware                                    │ Фоновая генерация заголовка треда
```

Каждый middleware изолирован, имеет строгую схему состояния (`thread_state.py`) и регистрирует свои каналы в графе LangGraph без пересечений.

## 3. Архитектура параллелизма и модель исполнения агентов

В отличие от стандартных фреймворков, где вызовы субагентов блокируют основной тред или засоряют основной EventLoop, в Deer-Flow реализована многоуровневая модель параллелизма:

### 3.1. Изолированный цикл субагентов (`_isolated_subagent_loop`)
- В модуле `subagents/executor.py` создается выделенный поток-демон с собственным циклом событий `asyncio.AbstractEventLoop`.
- Все локальные субагенты, запускаемые через `task_tool` (инструмент делегирования задач), диспетчеризируются на этот изолированный цикл через `run_on_isolated_subagent_loop`.
- **Архитектурный эффект**:
  - Полная изоляция от IO-операций API-шлюза (FastAPI);
  - Гарантированное отсутствие deadlock'ов при синхронных блокировках;
  - Потокобезопасная изоляция ContextVars через глубокое копирование контекста (`_copy_isolated_subagent_context`).

### 3.2. Распределенная пакетная подсистема (`SubagentBatchService`)
Для длительных или массовых задач субагентов используется архитектурный паттерн **Durable Task Queue**:
1. Клиент или агент отправляет `BatchSubmitRequest` через инструмент `batch_task_tool`.
2. Подзадачи сохраняются в репозитории БД в статусе `PENDING`.
3. Фоновый поллер (`subagent-batch-poller`) захватывает задачи с использованием атомарного механизма лизинга (`BatchItemLease`).
4. Если узел падает во время выполнения, срок действия лизинга (`lease_seconds`) истекает, и другой узел безопасно возобновляет выполнение задачи (idempotency key гарантирует отсутствие дублирования эффектов).
5. Результаты выполнения сохраняются в БД, агрегируются и передаются вызывающему агенту.

## 4. Архитектура персистентности, чекпоинтинга и журнала

### 4.1. Чекпоинтинг в LangGraph (`deerflow/runtime/checkpointer`)
Deer-Flow использует расширенную модель чекпоинтинга LangGraph:
- `CachedCheckpointSaver`: декоратор над стандартными чекпоинтерами (Memory, SQLite, PostgreSQL), реализующий **дельта-кеширование**. Чекпоинты считаются математически неизменяемыми узлами в направленном ациклическом графе (DAG). Состояние дельт кешируется в памяти, исключая повторное чтение тяжелых исторических BLOB-объектов из дисковой БД.
- `CheckpointChannelMode`: гибкая схема каналов, позволяющая сохранять состояние треда компактно либо в расширенном аудит-режиме.

### 4.2. Журнал событий выполнения (`RunJournal` и `RunEventStore`)
Вместо сохранения неструктурированных текстовых логов архитектура Deer-Flow опирается на **Event-Sourced Journal**:
- Перехват через LangChain Callbacks в `deerflow/runtime/journal.py`:
  - `on_chat_model_start` фиксирует входные данные;
  - `on_llm_end` сохраняет полные структурированные сообщения;
  - Вызовы инструментов фиксируются с метаданными выполнения и квитанциями.
- Хранилища событий (`RunEventStore`):
  - `MemoryRunEventStore` — для тестирования и легковесных агентов;
  - `DbRunEventStore` — персистентное реляционное хранение для аудита и воспроизведения;
  - `JsonlRunEventStore` — высокоскоростной аппенд-лог на диске для аналитики.

## 5. Архитектура интеграции с окружением: Sandboxes и MCP

### 5.1. Подсистема песочниц (Sandbox Abstraction)
- Унифицированный контракт песочницы `BaseSandbox` инкапсулирует операции: `exec_command`, `read_file`, `write_file`, `list_dir`, `download_file`.
- Провайдеры песочниц:
  - `LocalSandbox`: локальная песочница с жестким разделением директорий и проверкой путей (chroot-like guardrails);
  - `Docker / Kubernetes Sandbox`: изолированные контейнеры с динамическим монтированием томов;
  - Внешние облачные песочницы (Modal, E2B).
- **Сетевой фаервол**: контроль сетевого трафика через выделенный sidecar-прокси (`SandboxNetworkProxy`), фильтрующий исходящие HTTP(S) запросы согласно белому списку `allow_domains`.

### 5.2. Архитектура поддержки MCP (Model Context Protocol)
- Пул сессий MCP (`SessionPool` в `deerflow/mcp/session_pool.py`): переиспользование запущенных stdio/SSE процессов MCP-серверов.
- Отложенное обнаружение (`Tool Search & Deferred Tools`): при наличии сотен инструментов они не загружаются целиком в промпт модели, а регистрируются в каталоге поиска (`tool_search`). Модель видит только легковесные дескрипторы и активирует нужные инструменты динамически по мере необходимости.

## 6. Резюме архитектурного устройства

Архитектура Deer-Flow спроектирована по принципам **Zero Trust**, **высокого параллелизма** и **строгой воспроизводимости**:
- Четкое разделение протокола шлюза, логики сборки агента и среды исполнения инструментов;
- Двухуровневый планировщик задач: быстрые легковесные субагенты на изолированном loop и долгоживущие пакетные задачи с лизингом в БД;
- Многоуровневый middleware-конвейер, гарантирующий безопасность, учет квот и отказоустойчивость каждого шага LLM.
