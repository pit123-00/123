# Аналитический отчёт: Плюсы, минусы, необычные инженерные решения и оркестрация агентов в WorkflowBuilder

## 1. Введение
В данном отчёте систематизированы достоинства, архитектурные ограничения (минусы), нестандартные инженерные приёмы, а также особенности управления агентами, субагентами и пайплайнами в кодовой базе **WorkflowBuilder**.

---

## 2. Сильные стороны (Плюсы) реализации

### 2.1. Истинный Durable Execution без оверхеда
* Большинство AI-оркестраторов (например, классический LangChain, AutoGen или простые скрипты на FastAPI) хранят состояние пайплайна в памяти процесса. Падение процесса или перезапуск пода Kubernetes приводит к потере контекста и необходимости начинать цепочку дорогих LLM-вызовов сначала.
* WorkflowBuilder делегирует управление состоянием **Temporal**. При падении воркера Temporal автоматически восстанавливает исполнение воркфлоу с последнего детерминированного состояния без повторного вызова уже завершившихся LLM-активностей.

### 2.2. Чистая топологическая модель (DAG-first) с поддержкой параллелизма
* Волновой планировщик в `packages/execution-core/src/graph-runner.ts` естественным образом исполняет независимые узлы графа параллельно (`Promise.allSettled`).
* Если граф разветвляется на три независимых агента (например, Researcher, Fact-Checker, Stylist), они стартуют в одной волне, отправляя параллельные запросы в LLM или внешние API.

### 2.3. Надежный Human-in-the-Loop без поллинга
* Вместо самодельных таблиц ожидания в PostgreSQL со сложным поллингом, пауза пайплайна реализована через нативный механизм `await condition(...)` внутри Temporal Workflow. Пайплайн может ждать решения человека часами или днями, не потребляя процессорных ресурсов.

### 2.4. Строгая типизация и Generic Core
* Ядро `execution-core` параметризовано универсальным дженериком `TNode extends BaseNode`. Это позволяет легко расширять платформу новыми типами узлов (например, Bash-скрипты, SQL-запросы, отправка в Slack) без модификации кода планировщика и Temporal-плагина.

---

## 3. Слабые стороны и архитектурные ограничения (Минусы)

### 3.1. Ограниченная гибкость циклов (Looping) и динамического ветвления
* Ядро `execution-core` жестко ориентировано на ациклические графы (DAG). В коде есть прямая проверка на наличие циклов (`detectCycle`), которая аварийно прерывает выполнение, если граф содержит обратные связи.
* Реализовать циклы вида «агент переписывает текст, пока критик не одобрит» в рамках одного графа невозможно — для этого приходится прятать цикл внутрь одного узла (как это сделано в `MAX_TOOL_STEPS` для AI Agent) либо перезапускать граф целиком.

### 3.2. Крупнозернистый Activity-контейнер для агента
* В `apps/execution-worker/src/activities/ai-agent.ts` весь цикл работы агента с инструментами (до 4 шагов поиска через Tavily) упакован в **одну** Temporal Activity.
* *Следствие:* Если на 4-м шаге произойдет сбой сети, Temporal Activity перезапустится с первой попытки, повторяя все предыдущие шаги и вызовы LLM, что приводит к дополнительным финансовым затратам на токены API.

### 3.3. Отсутствие прямого стриминга токенов в реальном времени
* События эмитятся на уровне жизненного цикла узла (`node_started`, `node_completed`).
* Генерация текста через LLM внутри воркера происходит блочно: результат вызова `generateText` отдается целиком после завершения генерации. В системе отсутствует потоковый вывод посимвольных токенов (token streaming) через SSE в браузер пользователя во время генерации ответа моделью.

## 4. Необычные и нетривиальные инженерные решения

### 4.1. Волновой планировщик с итеративным dynamic skip propagation
* **Проблема:** В графах с ветвлением (Decision) отсечение неактивной ветки может оставить зависимые узлы в вечном ожидании (они ждут выполнения предшественника, который никогда не запустится).
* **Решение:** В функции `propagate` реализован счетчик `pendingPredecessors` и `liveIncoming`. Когда узел завершается, он передает статус ребер. Если к узлу больше нет живых входящих связей, он помечается `skipped` с указанием точной причины (`branch_not_taken` или `error_route_not_taken`), и через итеративную очередь (без риска переполнения стека рекурсией) пропуск лавинообразно каскадируется по всем дочерним поддеревьям.

### 4.2. Human-in-the-Loop через Temporal Updates с in-flight валидатором
* Большинство интеграций с Temporal используют Signals. Сигналы являются асинхронными ("fire-and-forget"): сервер принимает сигнал 200 OK, даже если воркфлоу уже завершился или узел не ожидает решения, что затрудняет обработку ошибок на клиенте.
* В WorkflowBuilder применен **Temporal Update** (`resolveNodeUpdate`). Он имеет фазу синхронного валидатора `validateVerdict()`:
  * Если передано решение для узла, который еще не перешел в состояние ожидания или уже был разрешен, Update отклоняется синхронно на стороне кластера Temporal до фиксации в журнале истории.
  * Бэкенд возвращает клиенту четкий HTTP 409 Conflict.

### 4.3. Принудительное подавление инструментов на финальном шаге цикла агента
* В `apps/execution-worker/src/activities/ai-agent.ts` функция `prepareStep` динамически переопределяет настройки вызова LLM:
  ```typescript
  stopWhen: stepCountIs(MAX_TOOL_STEPS),
  prepareStep: ({ stepNumber }) =>
    stepNumber === MAX_TOOL_STEPS - 1 ? { toolChoice: 'none' as const } : undefined
  ```
  Это гарантирует, что на последней итерации агент будет вынужден синтезировать текстовый ответ на основе уже собранных данных, а не упадет по таймауту или лимиту шагов с очередным незавершенным `tool_call`.

### 4.4. Двухуровневая классификация ошибок (Permanent vs Transient)
* `PermanentNodeExecutionError` и `TransientNodeExecutionError` предотвращают «застревание» воркеров. Ошибки, вызванные некорректным шаблоном `{{...}}`, синтаксической ошибкой или отсутствием ключей API, сразу прерывают выполнение с ясным статусом и кодом ошибки, исключая бесполезные повторные попытки (retries).

## 5. Управление агентами, субагентами и пайплайнами

### 5.1. Парадигма оркестрации: Graph Workflow vs Chat Agent
В отличие от библиотек типа AutoGen или CrewAI, где агенты свободно общаются друг с другом через групповой чат (что трудно прогнозировать и контролировать), WorkflowBuilder исповедует **детерминированный пайплайн-подход**:
* Взаимодействие агентов строго регламентировано ребрами направленного графа.
* Выход предыдущего агента становится входом следующего через контекст `context.nodeOutputs`.
* Каждый агент решает узкую специализированную задачу в рамках выделенного узла.

### 5.2. Пайплайны субагентов и паттерны композиции
1. **Паттерн «Генератор — Критик — Человек» (Draft-Review-Approval):**
   * `Trigger` -> `AI Agent (Draft Writer)` -> `AI Agent (Fact Checker / Critique)` -> `Human Decision (Approval)` -> `Visualize / Publish`.
2. **Паттерн параллельного ансамбля (Fan-out / Fan-in):**
   * Входной узел запускает одновременно несколько агентов с разными системными промптами (например, перевод на разные языки или анализ с разных точек зрения), после чего узел Decision или узел-сводка агрегирует результаты.
3. **Паттерн контролируемого ветвления:**
   * Агент классифицирует входящий запрос и возвращает структурированный JSON с категорией (`support`, `sales`, `bug`).
   * Узел `Decision` сопоставляет поля и направляет выполнение специализированному субагенту нужного домена.

### 5.3. Итоговое резюме
WorkflowBuilder представляет собой надежное инженерное решение промышленного уровня для задач, где во главу угла ставятся **детерминизм, аудит, надежность (durable execution) и предсказуемость расходов**, успешно совмещая визуальный no-code интерфейс с мощью распределенного движка Temporal.
