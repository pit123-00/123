# Отчёт 1. Техническая реализация системы управления качеством (Dev Quality Gates)

## Введение и назначение отчёта
Данный технический отчёт составлен на основе глубокого исследования исходного кода, контрактов схем данных, конфигураций инструментария, автоматизационных скриптов и исследовательских тестовых стендов (fixtures) репозитория `dev-quality-gates`. Анализ сфокусирован исключительно на исходном коде и программных артефактах, исключая рекламный или обзорный текст README.

Цель отчёта — детально разобрать:
1. Как технически реализован программный слой управления качеством.
2. Архитектуру и схему данных реестра (`tools.json` / `tools.schema.json`).
3. Логику работы скриптов верификации, мониторинга свежести и кодогенерации (`scripts/*.ts`).
4. Конфигурацию низкоуровневых проверок, тулчейна и git-хуков (`mise.toml`, `hk.pkl`, `.rumdl.toml`, `_typos.toml`, `lychee.toml`).
5. Глубокие технические настройки ключевых анализаторов, линтеров и сканеров из 70 зарегистрированных инструментов.
6. Ключевые преимущества принятой технической реализации.

## 1. Схема данных и типизация реестра инструментов

Ядром системы является реляционно-подобная документная база инструментов, хранящаяся в `tools.json` и строго валидируемая схемой `tools.schema.json` (JSON Schema Draft-07).

### 1.1. Контракт схемы (`tools.schema.json`)
Схема определяет строгие структурные ограничения:
- `tools`: массив объектов, где `additionalProperties: false` гарантирует отсутствие невалидированных полей.
- Обязательные поля (`required`): `["id", "name", "repo", "category", "last_reviewed", "sources", "rationale", "limitations"]`.
- Валидация форматов по регулярным выражениям:
  * `id`: `^[a-z0-9][a-z0-9-]*$` — slug-идентификатор в kebab-case.
  * `repo`: `^[\\w.-]+/[\\w.-]+$` — канонический формат GitHub-репозитория (`owner/repo`).
  * `last_reviewed`: `^\\d{4}-\\d{2}-\\d{2}$` — дата в формате ISO 8601 (YYYY-MM-DD).
  * `sources`: непустой массив строк (`minItems: 1`), содержащий URL или пути к локальным отчётам ресерча.
- Опциональные поля:
  * `details`: путь к расширенному файлу исследования в `research/`.
  * `stable_exception`: булево значение (`true`/`false`), указывающее на зрелый инструмент со стабильным API и редкими релизами (отключает алерты по времени последнего релиза/коммита).

### 1.2. Программный интерфейс (`scripts/registry.ts`)
В коде TypeScript (`scripts/registry.ts`) контракт выражен через интерфейс `Tool`:
```typescript
export interface Tool {
  id: string
  name: string
  repo: string
  category: string
  last_reviewed: string
  sources: string[]
  rationale: string
  limitations: string
  details?: string
  stable_exception?: boolean
}

export function readTools(path = 'tools.json'): Tool[] {
  const registry = JSON.parse(readFileSync(path, 'utf8')) as { tools: Tool[] }
  return registry.tools
}
```
Функция `readTools` обеспечивает типобезопасный доступ к реестру без внешних зависимостей в рантайме чтения.

## 2. Реализация проверочного конвейера (`scripts/check-registry.ts`)

Скрипт `scripts/check-registry.ts` отвечает за валидацию целостности базы данных инструментов и предотвращение рассинхронизации.

### 2.1. Механизм многоуровневой проверки
1. **Валидация схемы через Ajv**:
   Используется компилятор `new Ajv({ allErrors: true })`. При наличии несоответствий собираются все ошибки с путями (`instancePath`) и описаниями.
2. **Проверка уникальности (Uniqueness constraints)**:
   Поддерживаются две структуры `Set<string>`:
   - `ids`: проверяет уникальность `tool.id`.
   - `repos`: нормализует репозитории к нижнему регистру (`tool.repo.toLowerCase()`) и блокирует дубликаты.
3. **Проверка детерминированной генерации документации**:
   Скрипт вызывает функцию `update(readme, tools)` из `scripts/readme.ts` и сравнивает строковое значение результата с исходным файлом `README.md`. Если результат не совпадает с дисковым состоянием, скрипт выбрасывает ошибку:
   `README.md is out of date: run pnpm run readme and commit the result.`
4. **Управление кодами завершения (Exit Codes)**:
   При любых ошибках скрипт печатает их список в `stderr` и завершается с `process.exit(1)`. При успехе выводится `tools.json: N tools OK, README.md up to date` с кодом 0.

## 3. Мониторинг актуальности и интеграция с GitHub API (`scripts/freshness.ts`)

Скрипт `scripts/freshness.ts` реализует механизм телеметрии жизненного цикла используемых зависимостей.

### 3.1. Эвристические константы старения
В коде зафиксированы жесткие пороги проверки:
- `PUSH_DAYS = 90` (3 месяца без коммитов в upstream — триггер флага заброшенности).
- `RELEASE_DAYS = 365` (1 год без новых релизов — триггер флага стагнации версий).
- `REVIEW_DAYS = 180` (6 месяцев без ревью внутренней команды — требование аудита).

### 3.2. Алгоритм инспекции API
Скрипт асинхронно опрашивает GitHub REST API:
1. `GET /repos/${tool.repo}`:
   - Проверяется `repo.archived` -> добавляется флаг `ARCHIVED`.
   - Проверяется переименование репозитория (`repo.full_name.toLowerCase() !== tool.repo.toLowerCase()`).
   - Если `stable_exception !== true`, проверяется `days(repo.pushed_at) > PUSH_DAYS`.
2. `GET /repos/${tool.repo}/releases?per_page=1`:
   - Выбирается самый свежий релиз (включая `prerelease`, чтобы проекты с ветками 2.0-rc не помечались как мертвые).
   - Если `stable_exception !== true`, проверяется `days(release.published_at) > RELEASE_DAYS`.
3. Локальная проверка `days(tool.last_reviewed) > REVIEW_DAYS`.

### 3.3. Автоматизированное управление жизненным циклом Issue (Tracking Issue Lifecycle)
Скрипт не просто выдает лог в терминал, но управляет состоянием инцидентов в GitHub Issues:
- Заголовок задачи: `Tool freshness report`.
- Через GitHub API ищется открытый issue с таким заголовком (`issues?state=open&per_page=100`).
- Если есть флаги (`flagged.length > 0`):
  * При наличии существующего issue выполняется `PATCH /repos/.../issues/{number}` с обновленным отчетом.
  * При отсутствии — создается новый issue через `POST /repos/.../issues`.
- Если проблемных инструментов нет (`flagged.length === 0`), но issue открыт:
  * Выполняется `PATCH` со статусом `state: "closed", state_reason: "completed"`.
- Скрипт пишет отчет в `$GITHUB_STEP_SUMMARY` и завершается с кодом 1, если есть флаги, что прерывает CI шаг.

## 4. Декларативная конфигурация тулчейна и Git-хуков

Вся инфраструктура проекта базируется на связке инструментов `mise` и `hk` с типизированным языком конфигурации Apple Pkl.

### 4.1. Декларация окружения (`mise.toml`)
`mise.toml` фиксирует точные версии компиляторов и CLI-утилит для обеспечения воспроизводимости между разработчиками и CI:
```toml
min_version = "2026.11.3"

[tools]
node = "26"
pnpm = "12.18.0"
hk = { version = "2.11.1", workflow = "release.yml" }
pkl = "0.33.0"
rumdl = "0.3.2"
typos = "1.52.0"
lychee = "0.24.2"
jactionlint = { version = "2.5.0", workflow = "release.yaml" }

[tasks.setup]
run = ["pnpm install --frozen-lockfile", "hk install"]

[tasks.check]
run = "hk check --all"

[tasks.fix]
run = "hk fix --all"
```

### 4.2. Конфигурация Git-хуков в Pkl (`hk.pkl`)
`hk.pkl` расширяет стандартную библиотеку `Config.pkl` и `Builtins.pkl`.
На техническом уровне проверки разделены на профили с фильтрацией по glob-паттернам:
- **Быстрый локальный шаг (`fast`)**:
  * `rumdl`: нативный Rust-линтер и форматтер Markdown.
  * `typos`: проверка опечаток в исходном коде.
  * `jactionlint`: валидация воркфлоу GitHub Actions.
  * `registry`: запуск `pnpm run --silent check:registry && pnpm run --silent readme -- --check` при модификации файлов `tools.json`, `tools.schema.json`, `README.md`, `scripts/*.ts`, `package.json`.
  * `typecheck`: `tsc` по паттерну `scripts/*.ts`, `tsconfig.json`.
- **Полный профиль (`all`)**:
  * Включает `fast` + `lychee` (сетевой валидатор ссылок по `**/*.md` с конфигом `lychee.toml`).
- **Связывание хуков**:
  * `pre-commit`: `fix = true`, `stash = "git"`, `steps = fast`. Автоматически изолирует стейдж через stash и применяет автоисправления.
  * `pre-push`: `steps = all`.
  * `check`: `steps = all`.
  * `fix`: `fix = true`, `steps = all`.

## 5. Глубокий технический разбор категорий инструментов и их настроек

Реестр насчитывает 70 инструментов, каждый из которых исследован на предмет exit-кодов, флагов командной строки, ограничений и режимов работы.

### 5.1. Категория: Инфраструктурные CI/CD проверки
- **jactionlint** (`jdx/jactionlint`):
  * *Назначение*: Единый бинарник на Rust, форк actionlint, полностью интегрирующий проверки zizmor.
  * *Флаги и поведение*:
    - `--fix`: автоматически устраняет механические дефекты.
    - `--online`: подключается к GitHub API и автоматически пинит сторонние action-теги на полные commit SHA с сохранением комментария с версией (`unpinned-uses`).
    - `--diff`: выводит diff исправлений.
    - Профили: `correctness`, `default`, `pedantic`.
    - Выходные форматы: `text`, `json`, `jsonl`, `sarif`, `github`. Exit code 1 при ошибках уровня `error`.
- **plumber** (`getplumber/plumber`):
  * Сканер безопасности для GitLab CI (`.gitlab-ci.yml`), резолвит инклуды и проверяет параметры защиты веток. Форматы: terminal, JSON, SARIF, GitLab SAST.

### 5.2. Категория: Анализ кода и кастомные правила
- **ast-grep** (`ast-grep/ast-grep`):
  * *Глубокая настройка*: Скрипт `research/fixtures/ast-grep/run.py` демонстрирует работу движка:
    - `ast-grep test`: прогоняет снапшотные тесты правил из директории `rule-tests/`. При расхождении со снапшотом в `__snapshots__/` завершается с exit code 4.
    - `ast-grep scan`: сканирует AST проекта. Если сработало правило с `severity: warning`, завершается с кодом 0; если `severity: error` — завершается с кодом 1.
    - `ast-grep scan --format sarif`: генерирует уровни severity в структуре SARIF.
    - Поддержка автофиксов через блок `fix:` в YAML-правилах.
- **easement** (`mokevnin/easement`):
  * Проверка архитектурных границ и зависимостей между модулями на основе правил импорта.

### 5.3. Категория: Python
- **Ruff** (`astral-sh/ruff`):
  * Заменяет Flake8, isort, pyupgrade, Black, Bandit (правила серии `S`), pydocstyle (серия `D`), radon/xenon (метрика сложности `C901`).
  * Высокая производительность за счет Rust; нативные флаги `--fix`, `--check`.
- **ty** (`astral-sh/ty`):
  * Новый типизатор от Astral на Rust. Эксперимент в `research/mypy-plugins.md` выявил критическую особенность: `ty check` на текущем этапе не поддерживает плагины mypy (`pydantic.mypy`, `mypy-protobuf`), что требует явного пиннинга и осознанного применения.
- **deptry** (`osprey-oss/deptry`):
  * Детекция неиспользуемых, отсутствующих и транзитивных зависимостей в `pyproject.toml`.
- **import-linter** (`seddonym/import-linter`):
  * Контроль контрактов слоев (grimp), предотвращение циклических импортов между пакетами.

### 5.4. Категория: JavaScript / TypeScript
- **oxlint** (`oxc-project/oxc`):
  * Линтер на Rust со скоростью выполнения в 50-100 раз выше ESLint.
  * *Важная техническая деталь*: по умолчанию oxlint завершается с кодом 0 даже при наличии warnings. Для превращения его в ворота качества (Quality Gate) в CI обязательно передаются флаги `--deny-warnings` или `-D <category>` (что переводит нарушения в разряд ошибок с exit code 1).
  * Интеграция с TypeScript 7 через движок `tsgolint` для type-aware правил.
- **knip** (`webpro-nl/knip`):
  * Поиск мертвого кода: неиспользуемые файлы, экспорты, типы, зависимости в `package.json`.
- **stryker-js** (`stryker-mutator/stryker-js`):
  * *Мутационное тестирование*: исследование в `research/fixtures/stryker/run.py` и `stryker.md` доказало, что diff-cover дает ложное чувство безопасности при 100% покрытии строк (слабый ассерт вида `toBeTypeOf("number")`).
  * Stryker мутирует AST и ожидает падения тестов. Настройка порога: `thresholds.break: 80`. Запуск исключительно на файлах дельты PR через `--mutate "$files"` занимает 6-11 секунд вместо минут полного прогона.

### 5.5. Категория: Безопасность и секреты
- **betterleaks** (`betterleaks/betterleaks`):
  * Высокопроизводительный поиск утёкших API-токенов, приватных ключей и паролей в git-коммитах.
- **osv-scanner** (`google/osv-scanner`):
  * Сканирование зависимостей по базе данных Google OSV.
  * Поддержка директивы `ignoreUntil` в конфигурации: подавление уязвимости автоматически прекращается по наступлении указанной даты (защита от забытых исключений).

### 5.6. Категория: Базы данных и миграции
- **squawk** (`sbdchd/squawk`):
  * Статический анализ миграций PostgreSQL: предотвращение блокировок таблиц (`ACCESS EXCLUSIVE`), опасных изменений типов столбцов и добавления индексов без `CONCURRENTLY`.
- **database-consistency** и **schemalens**:
  * Валидация консистентности внешних ключей, индексов и ограничений между кодом моделей и реальной схемой БД.

## 6. Преимущества выбранной технической реализации

1. **Абсолютная воспроизводимость окружения (Hermetic Toolchains)**:
   Благодаря `mise.toml` и `pnpm-lock.yaml` полностью исключена проблема «работает на машине разработчика, но ломается в CI». Любой агент или инженер одной командой получает идентичный набор бинарников с точными версиями.
2. **Многоуровневый параллелизм и защита от зависаний**:
   Хуки используют stash-изоляцию (`stash = "git"` в `hk.pkl`), автоисправления на лету (`fix = true`) и разделение проверок по глоб-паттернам измененных файлов, что сокращает время обратной связи до сотен миллисекунд.
3. **Строгая статическая типизация и контрактное тестирование**:
   Связка JSON Schema Draft-07 + Ajv в `scripts/check-registry.ts` с TypeScript 7 гарантирует корректность метаданных инструментов. Любая ошибка в именовании категории или формата ссылки приводит к падению сборки.
4. **Автоматический контроль дрифта документации**:
   Документация и таблицы рекомендаций не пишутся вручную, а компилируются скриптом `scripts/readme.ts` из единого источника правды (`tools.json`). Флаг `--check` предотвращает ручное редактирование сгенерированных блоков.
5. **Телеметрия деградации зависимостей без вмешательства человека**:
   Автоматизированный мониторинг свежести (`scripts/freshness.ts`) с автосозданием и автозакрытием issue снимает с команды рутину по отслеживанию заброшенных библиотек.
