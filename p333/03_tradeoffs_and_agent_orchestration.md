# Отчёт 3. Анализ компромиссов, нестандартных решений и управление AI-агентами (Dev Quality Gates)

## Введение и назначение отчёта
Данный аналитический отчёт исследует инженерные компромиссы (плюсы и минусы), необычные технические решения и специализированную методологию управления автономными AI-агентами, субагентами и проверочными пайплайнами в системе `dev-quality-gates`. Анализ базируется на коде и конфигурациях репозитория (`scripts/*`, `hk.pkl`, `mise.toml`, `research/*`, `docs/*`) и принципах агентного управления (`AGENT_WORKFLOW_FRAMEWORK_RU.md`).

---

## 1. Плюсы и минусы технической и архитектурной реализации

### 1.1. Преимущества (Плюсы)
1. **Экстремальная скорость обратной связи (High Performance Sub-Second Gates)**:
   Переход на современные нативные инструменты на Rust/Go (`rumdl` вместо `markdownlint`, `typos` вместо `cspell`, `oxlint` вместо `eslint`, `jactionlint` вместо комбинации `actionlint` + `zizmor`) сокращает время выполнения локальных хуков с десятков секунд до 200–500 мс. Это исключает соблазн разработчиков и агентов отключать хуки через `--no-verify`.
2. **Нулевой дрифт окружения (Zero Environment Drift)**:
   Использование декларативного менеджера тулчейнов `mise` в паре с `hk` устраняет классический класс багов «у меня локально проходит, а в GitHub Actions падает». Локальная машина и облачный раннер исполняют строго бинарно идентичные версии инструментов.
3. **Строгая верификация контрактов (Schema-Driven Integrity)**:
   Ajv и JSON Schema Draft-07 предотвращают появление невалидных метаданных еще до запуска основного кода. Никакой невалидный инструмент или битая ссылка не могут проникнуть в реестр.
4. **Непрерывный самоконтроль свежести зависимостей**:
   Скрипт `scripts/freshness.ts` переводит отслеживание заброшенных репозиториев (90 дней без коммитов, 365 дней без релизов, 180 дней без аудита) из ручного процесса в автоматический фоновый мониторинг с управлением жизненным циклом issue.
5. **Защита от фиктивного тестового покрытия**:
   Интеграция мутационного тестирования Stryker на уровне дельты PR вскрывает слабые тесты, проходящие 100% строковое покрытие `diff-cover`.

### 1.2. Недостатки и компромиссы (Минусы)
1. **Высокая зависимость от молодых инструментов (Bleeding Edge & Bus Factor Risk)**:
   Такие ключевые инструменты, как `jactionlint` (создан в октябре 2026), `ty` (версия 0.0.x), `rumdl` и `hk`, имеют крайне небольшую историю и часто поддерживаются единственным мейнтейнером (высокий фактор автобуса).
2. **Ограниченная экосистема плагинов у нативных альтернатив**:
   Хотя `oxlint` и `ty` работают в десятки раз быстрее ESLint и mypy, они не поддерживают сложные экосистемные плагины (например, `pydantic.mypy`, `mypy-protobuf` или специфические правила шаблонов Vue/Svelte в oxlint), что вынуждает сохранять старые компиляторы для глубокого анализа.
3. **Потенциальная хрупкость GitHub API Rate Limits в freshness**:
   Скрипт `scripts/freshness.ts` делает последовательные вызовы API без кеширования ответов. Без переменной `GITHUB_TOKEN` скрипт быстро упирается в лимит 60 запросов/час при 70 инструментах в реестре.
4. **Сложность кастомизации Pkl**:
   Использование языка Apple Pkl (`hk.pkl`) требует от инженеров изучения нового синтаксиса и наличия специфического бинарника `pkl` в тулчейне.

## 2. Нестандартные и оригинальные инженерные решения

В кодовой базе реализован ряд нетривиальных инженерных решений:

1. **Мутационное тестирование среза `git diff` (Delta Mutation Gate)**:
   Мутационное тестирование традиционно считается слишком «тяжелым» для CI (часы прогона). В репозитории найдено элегантное решение:
   ```bash
   git diff --name-only --diff-filter=AM origin/main...HEAD -- 'src/*.ts' ... > changed.txt
   files=$(paste -sd, - < changed.txt)
   [ -z "$files" ] || npx stryker run --mutate "$files"
   ```
   Мутируются только измененные в PR файлы, сокращая время выполнения до 6–11 секунд и обеспечивая абсолютную защиту от фиктивных тестов.
2. **Автоматический жизненный цикл одного Issue без спама (Single Living Issue Lifecycle)**:
   Вместо создания сотен шумных уведомлений или падений сборки на каждый релиз, `scripts/freshness.ts` держит в репозитории **ровно один issue** с заголовком `Tool freshness report`. Скрипт обновляет его через `PATCH`, если есть проблемы, и автоматически закрывает (`state: closed, state_reason: completed`), когда проблемы устранены.
3. **Маркерная детерминированная кодогенерация без шаблонных файлов**:
   Вместо тяжелых шаблонизаторов скрипт `scripts/readme.ts` находит в теле `README.md` текстовые маркеры `<!-- tools:start -->` и `<!-- tools:end -->`, заменяя только середину. При флаге `--check` скрипт сравнивает сгенерированную строку с файлом, превращая `readme.ts` в линтер консистентности документации.
4. **Временные исключения с обязательной экспирацией (Expiring Suppressions)**:
   Вместо бессрочных `# noqa` или `eslint-disable`, архитектура требует формат `(review YYYY-MM-DD)` с проверкой календаря. Дата, наступившая по календарю, ломает CI даже при отсутствии изменений в коде правила.

## 3. Управление агентами, субагентами и пайплайнами

Изучение кода и документации выявило целостную парадигму взаимодействия с AI-агентами и оркестрации субагентов.

```
                  +-----------------------------------+
                  |         Главный Оркестратор       |
                  |  (Читает метаданные: ID, пути,    |
                  |   хеши, стейты; НЕ читает контент)|
                  +-----------------------------------+
                                    |
            +-----------------------+-----------------------+
            | Назначение задачи                             | Выдача контракта
            v                                               v
+-----------------------+                       +-----------------------+
|  Субагент 1: АВТОР    |                       |  Субагент 2: АУДИТОР  |
| - fork_turns="none"   |                       | - Изолированный контекст|
| - Управляемое чтение  |                       | - Снимок кандидата    |
|   порциями (12KB)     |                       | - Независимая оценка  |
| - Пишет только        |                       | - Выдает structured   |
|   в /candidates/      |                       |   findings (JSON)     |
+-----------------------+                       +-----------------------+
            |                                               |
            v                                               v
+-----------------------------------------------------------------------+
|                       Программный слой (Scripts)                      |
| - registry.py: атомарный переход стейт-машины (PREPARED->BOUND->...)  |
| - patch.py: строгое наложение патчей по секциям                       |
| - validate.py: запуск проверок (Exit Code != 0 блокирует переход)    |
| - flock: защита от ресурсного голодания при параллельных агентах      |
+-----------------------------------------------------------------------+
```

### 3.1. Принцип изоляции контекста и точной области записи
- **Минимальный достаточный контекст**: субагент не должен получать всю историю главного чата. При порождении субагента задается `fork_turns="none"`. Передача всей истории раскрывает избыточные данные и провоцирует галлюцинации.
- **Управляемое чтение (Reading Protocol)**:
  Агент не обходит файловую систему свободным `find/grep`. Программный скрипт формирует структурированный манифест чтения. Материал подается чанками (лимит ~12 000 байт в UTF-8) с маркерами `PART <id>` и `END_PART <id>`. Следующая порция выдается только после подтверждения предыдущей.
- **Строгое разграничение прав (Read/Evaluate/Write Bounds)**:
  В контракте задания (`assignment.json`) разделены три списка путей:
  * `inputs`: пути и хеши файлов, доступных для чтения.
  * `allowed_sections`: смысловые секции, подлежащие анализу.
  * `allowed_write_paths`: изолированные пути, куда разрешена запись (например, `outputs/.workflow/runs/<run_id>/candidates/result.md`). Попытка записи в другие файлы блокируется программным слоем.

### 3.2. Машиночитаемые контракты и управление через стейт-машину
- **Стейт-машина жизненного цикла**:
  Процесс выражен цепочкой строго детерминированных состояний:
  `PREPARED → BOUND → READING → WORKING → CHECKING → COMPLETED` (с петлей исправления `CHECKING → REPAIR → CHECKING`).
- **Идемпотентность и квитанции**:
  Оркестратор не парсит свободный текст ответа субагента для принятия решений. Каждая операция возвращает машиночитаемый JSON с точной следующей операцией (`READ`, `WRITE_RESULT`, `CHECK`, `REPAIR_THEN_RETRY`, `FINISH`). Повторный вызов одной и той же команды возвращает сохраненную квитанцию без повторного продвижения этапа.
- **Атомарность сохранения состояния**:
  Реестр состояния обновляется атомарно через запись во временный файл в каталоге запуска с последующим `rename` и защитой файловыми блокировками.

### 3.3. Разделение ролей: Автор и Независимый Аудитор
- Автор и Аудитор обязаны быть разными агентами с изолированными промптами и личностями.
- Автор генерирует кандидат (`candidate`), запускает проверки и передает результат.
- Аудитор получает фиксированный снимок (`snapshot`) кандидата автора и применимый свод правил. Аудитор **не имеет права редактировать текст автора** — он возвращает строго структурированный JSON с замечаниями:
  * Точная цитата и номер строки.
  * Идентификатор нарушенного требования (`rule_id`).
  * Причина дефекта и конкретный критерий приёмки.
- Программный слой преобразует замечания аудитора в контракт режима `PATCH`, где автору выдаются только те секции, которые требуют исправления, защищая остальной документ от несанкционированных правок.

### 3.4. Защита ресурсов хоста: Паттерн `flock`
При одновременной работе нескольких агентов на одной машине тяжелые команды (компиляция, проверка типов `tsc`, мутационное тестирование) приводят к исчерпанию памяти (OOM) и взаимной блокировке CPU.
В коде заложен паттерн **машинного семафора**:
- Тяжелые задачи запускаются через обертку, удерживающую один из нескольких слотов файловой блокировки `flock` операционной системы.
- В CI очередь `flock` отключается, так как раннер изначально изолирован.
- Вложенные вызовы тяжелых команд внутри уже захваченного слота исполняются немедленно, предотвращая deadlock.

### 3.5. Инструменты контроля за агентами
- **agnix** (`agent-sh/agnix`): специализированный линтер для конфигураций агентов (`CLAUDE.md`, `AGENTS.md`, `SKILL.md`, правил MCP). Предотвращает синтаксические и логические ошибки в инструкциях, которые иначе приводили бы к тихому отказу агентов.
- **skylos**: специализированный аудит веток агентов, выявляющий попытки удаления тестов, снижение порогов покрытия или ослабление CI-пайплайнов ради фиктивного прохождения задачи.

---

## Заключение
Архитектура `dev-quality-gates` демонстрирует переход от разрозненных рекомендаций по линтингу к целостной инженерной платформе. В ней качество обеспечивается не доверием к агенту или разработчику, а математически строгими барьерами: неизменяемостью метаданных, воспроизводимостью тулчейна через `mise`/`hk`, контрактной изоляцией контекста субагентов и автоматической детекцией фиктивных проверок через дельта-мутационное тестирование.
