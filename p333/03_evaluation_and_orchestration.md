# Отчёт №3: Плюсы, минусы, необычные решения и управление агентами, субагентами и пайплайнами в bb

## 1. Введение

В данном отчёте анализируются сильные и слабые стороны платформы **bb** (`get-bb/bb`), выявленные в ходе анализа кода инженерные паттерны, а также реализованные механизмы оркестрации автономных агентов, субагентов, иерархий потоков (parent-child threads) и пайплайнов обработки сообщений.

---

## 2. Оркестрация агентов, субагентов и иерархий потоков (Agent & Subagent Orchestration)

Архитектура системы реализует поддержку многоагентных сценариев на нескольких уровнях: на уровне протокола дельт провайдеров, на уровне рантайма и на уровне доменных сущностей сервера.

### 2.1. Иерархия родительских и дочерних потоков (Parent-Child Thread Tree)
Файлы: `apps/server/src/services/threads/thread-parent.ts`, `child-thread-notifications.ts`, `packages/domain/src/thread-parent-notifications.ts`.

1. **Строгое ограничение глубины дерева**:
   - `MAX_THREAD_HIERARCHY_DEPTH = 4`.
   - При попытке создания дочернего потока функция `resolveParentDepth` обходит цепочку предков вверх, проверяя:
     - `self`: дочерний поток не может быть своим же родителем.
     - `cycle`: защита от циклических ссылок.
     - `too_deep`: глубина родителя + максимальная глубина поддерева потомков не может превышать 4 уровня.
2. **Политика уведомления родителя (`ThreadParentNotifications`)**:
   - `auto`: родительский поток автоматически уведомляется о любом исходе дочернего потока (успех, ошибка, прерывание).
   - `stuck`: родитель уведомляется только в случае, если дочерний агент застрял или упал (`outcome !== "completed"`).
   - `off`: уведомления отключены.
3. **Механизм объединения и доставки уведомлений (Batching & Coalescing)**:
   - Дочерние потоки не спамят родителя одиночными вызовами. В модуле `child-thread-notifications.ts` настроено окно агрегации:
     `CHILD_THREAD_TURN_NOTIFICATION_BATCH_DELAY_MS = 2_000` (2 секунды).
   - Уведомления группируются по ключу `child-outcomes`. Если несколько субагентов завершили работу одновременно, родитель получает одно сводное системное сообщение (`postCoalescedSystemNotice`).
   - Финальный вывод дочернего агента извлекается через `getTurnFinalOutput`, усекается до лимита `CHILD_THREAD_TERMINAL_OUTPUT_EXCERPT_CHAR_LIMIT = 4_000` символов и оформляется как структурированное упоминание со слотом `__BB_CHILD_THREAD_MENTION__`.
   - Если у субагента ещё остаются активные фоновые воркфлоу, родителю передаётся предупреждение: *"A workflow it started is still running, so this output is not its final result"*.

### 2.2. Модель делегирования и субагентов внутри провайдера (Delegation & Background Tasks)
Файлы: `packages/provider-bridge-protocol/src/thread-delta.ts`, `packages/provider-bridge-protocol/src/assembler/delta-assembler.ts`, `packages/provider-bridge-acp/src/dialect.ts`.

1. **Элемент типа `delegation`**:
   - Схема `deltaDelegationShapeSchema`: `{ type: "delegation", childRef, label, background, summary }`.
   - Применяется при вызове субагентов (например, Cursor ACP `task` / `cursor/task`, Codex `spawnAgent`, Claude Code `Agent`).
2. **Иерархическая привязка через `parentRef` / `parentToolCallId`**:
   - В `delta-assembler.ts` каждый элемент потока может иметь `key.parentRef`.
   - Ассемблер преобразует `parentRef` (внешний ID провайдера) во внутренний `bbItemId` через реестр `state.bbItemIdByProviderItemId`.
   - Все команды, вызовы инструментов или сообщения, порождённые субагентом, автоматически получают поле `parentToolCallId`. В UI и логах это позволяет строить древовидное отображение хода работы субагента без смешивания с главным контекстом.
3. **Фоновые задачи (`backgroundTask`)**:
   - Поддерживают жизненный цикл: `pending` -> `running` -> `completed` / `failed`.
   - Содержат отдельную статистику использования токенов `usage: { totalTokens, toolUses, durationMs }` и ссылку на выходной файл `outputFile`.

## 3. Оркестрация пайплайнов сообщений и очереди диспетчеризации (Queued Messages Pipeline)

Файлы: `packages/domain/src/queued-message.ts`, `queued-message-lifecycle.ts`, `apps/server/src/services/threads/queued-messages.ts`, `queued-message-dispatch.ts`.

Когда пользователь или родительский агент отправляет сообщение в поток, оно не сразу передается провайдеру, а проходит через конечный автомат проверки готовности:

1. **Причины ожидания (`queuedMessageWaitingOnKindValues`)**:
   - `time`: отложенная отправка по времени (`sendAt`).
   - `thread-busy`: поток выполняет текущий turn, а новое сообщение не помечено как steer-сообщение.
   - `stopping`: пользователь запросил остановку потока, и остановка еще фиксируется.
   - `provisioning`: рабочее пространство потока находится в процессе настройки.
   - `host-offline`: целевой хост временно отключен от сети или находится в процессе гибернации/пробуждения.
   - `interaction`: на потоке висит неразрешённый запрос подтверждения (approval) или интерактивный вопрос агента.
   - `plugin`: плагин выставил gate-блокировку с явной причиной.
   - `superseded`: устаревшее сообщение, вытесненное более свежим ходом.
2. **Режимы выполнения: Auto vs Steer**:
   - `TurnSubmitTarget`:
     - `start`: инициализация первого хода потока.
     - `auto`: стандартное продолжение диалога; если поток занят, сообщение встаёт в очередь `thread-busy`.
     - `steer`: прерывание или корректировка на лету текущего выполняющегося хода агента (`expectedTurnId`), позволяя вмешаться в ход генерации без полной остановки сессии.

## 4. Необычные инженерные решения в коде

1. **Dialect Adapter Pattern в ACP (`packages/provider-bridge-acp/src/dialect.ts`)**:
   - Вместо монолитного адаптера сделан реестр диалектов (`AcpDialect`): Cursor, OMP, Grok, OpenCode, Generic.
   - Каждый диалект имеет собственные функции классификации (`classifyToolCall`), перехвата клиентских методов (`handleClientRequest`), нормализации вывода терминала (`ompCommandResult` с вырезанием служебных нотисов о времени и коде выхода) и парсинга контекстного окна из метаданных.
2. **Векторная дельта-сборка (`DeltaAssembler`) со скользящим окном дедупликации**:
   - Хранит кольцевые буферы открытых элементов с автоматическим вытеснением старых (`trimOldestEntries`, `MAX_THREAD_STATES = 256`, `MAX_ID_MAP_ENTRIES = 1024`).
   - Функция `diffCumulativeText` распознает как инкрементальный стриминг, так и полную перезапись буфера (reset-сценарии некоторых LLM-провайдеров).
3. **Изоляция мутаций хоста через `SerialLane`**:
   - Реализация асинхронного мьютекса с промис-очередью в `serial-lane.ts`. Гарантирует, что файловые операции клонирования, переключения веток и сборки скиллов в одном воркспейсе никогда не будут выполняться параллельно.
4. **Контроль задержки Event Loop (`event-loop-stall-monitor.ts`)**:
   - Хост-демон непрерывно отслеживает лаги event loop Node.js (`event-loop-stall-monitor`). Если демон начинает испытывать лаги из-за тяжёлых вычислений, это регистрируется в телеметрии для предотвращения ложных таймаутов провайдера.
5. **Хэш-верификация каталога скиллов (`EMPTY_SKILL_CATALOG_HASH`)**:
   - Скиллы монтируются через генерацию промежуточных симлинков/директорий с проверкой контентного хэша, исключая устаревание кэша в рантайме.

## 5. Плюсы и минусы технической реализации

### Плюсы (Преимущества)

1. **Высочайшая надежность изоляции процессов**:
   - Никакой сторонний код CLI-агентов не выполняется в основном процессе. Сбои процессов изолированы на уровне ОС (`child_process`).
2. **Унифицированный контракт поверх разнородных агентов**:
   - Платформа одинаково гладко работает с Claude Code, OpenAI Codex, инструментами ACP Cursor и локальными консольными утилитами, сводя их к единому протоколу дельт `ThreadDelta`.
3. **Безупречная типобезопасность**:
   - Полная интеграция Zod от сетевых запросов и веб-сокетов до хранения в БД исключает ошибки формата данных при апгрейдах.
4. **Продуманная многоагентная иерархия**:
   - Встроенный контроль глубины вложенности, агрегация уведомлений от субагентов и сохранение связей `parentToolCallId` делают систему готовой для построения сложных иерархических роевых систем.
5. **Масштабируемая топология**:
   - Сервер координации легко отделяется от хост-машин, позволяя запускать агентов на мощных удалённых серверах разработчиков или в GPU-кластерах, управляя ими из одного интерфейса.

### Минусы (Недостатки и узкие места)

1. **Высокая архитектурная сложность и накладные расходы (Overhead)**:
   - Сообщение проходит путь: `Client UI -> Server Hono -> Server Queues -> Host Daemon WS -> Agent Runtime -> Provider Bridge stdio -> CLI Provider`.
   - Сериализация и десериализация JSON-RPC на каждом узле создает накладные расходы по CPU и миллисекундные задержки.
2. **Сложность отладки асинхронных цепочек**:
   - Из-за множества слоев адаптеров и ассемблеров поиск причин потерянного события или рассинхронизации идентификаторов требует анализа многослойных логов (сервер, демон, мост).
3. **Ограничение глубины иерархии субагентов**:
   - Жесткий лимит `MAX_THREAD_HIERARCHY_DEPTH = 4` предотвращает рекурсию, однако может ограничивать узкоспециализированные многоуровневые агентные графы.
4. **Зависимость от состояния хост-демона**:
   - Если host-daemon теряет связь или перезапускается, выполнение активных turn-ов прерывается (`host-connection-lost`), а возобновление требует сложной логики `restart-resume.ts`.
