# Отчет 5: Анализ проекта google-research/harness2

## 1. Архитектура и кодовая база проекта
Проект **google-research/harness2** — это исследовательский фреймворк на **Python** от Google Research, посвященный автоматическому итеративному улучшению конфигураций агентов (инструкций, памяти, инструментов, скиллов) через параллельную и последовательную рекурсию с независимым судейством.

Ключевые модули ядра (`harness2/core/`):
- `runmark.py`:
  - Механизм строгой фиксации идентичности запуска (`Trial identity`) и квитанции завершения (`.adapt_complete`).
  - Рассчитывает составной хеш (fingerprint) от дерева конфигурации (промпты, правила, память) и входных данных задачи (`input_version`).
  - При любом изменении зависимостей (исходников, правил, входов) сохраненный результат объявляется устаревшим (`stale`) и исключается из повторного использования.
  - Наличие выходного файла само по себе не считается успехом: завершение фиксируется только доверенным кодом среды запуска (`RunMark.write`).
- `tree.py`:
  - Компонентное дерево конфигурации агента (`c1..c8`), параметризованное через `SurfaceSpec` (поддерживает поверхности OpenCode и Codex/Claude).
  - Реализует принцип **"omitted-is-inherited"**: предложение изменений содержит только то, что реально меняется. Валидирует структуру файлов, исключает служебные скрипты и артефакты сборки.
- `proposer.py`:
  - Выполнение сессий генерации/улучшения в строго **изолированных временных рабочих каталогах** (`tempfile.mkdtemp`).
  - Субагент-пропоузер получает только свой контекст, входы подаются через `stdin`, а результаты валидируются перед принятием.
- `judge.py`:
  - Механизм **независимого судейства (LLM-as-a-Judge + программные проверки)**.
  - Оценивает артефакты отдельно от автора. Ошибка судьи (`None`) строго отделяется от провала задачи (`0 / N`), что исключает искажение знаменателя метрик.
- `ledger.py` и `recursion.py`:
  - Строгий учет бюджетов вызовов ($R = 4k$ запусков, $P = 3k$ стадий улучшения).
  - Управление параллельными и последовательными графами улучшения с поддержкой повторных попыток (`retry`) при невалидных предложениях.

## 2. Чем и как этот проект полезен для `AGENT_WORKFLOW_FRAMEWORK_RU.md`

Из всех проанализированных репозиториев `google-research/harness2` содержит решения, которые **на 100% концептуально и технически закрывают ключевые пункты вашего документа**:

### 1. Детерминированная проверка актуальности и квитанции (`runmark.py` -> Разделы 4.5, 4.6, 7.7, 10.1, 10.5)
- **Требование фреймворка:** «При изменении зависимости отклоняйте устаревшее задание. Свяжите результат с хешами снимков, инструкций, правил... До очистки сохраните отдельную квитанцию выдачи».
- **Что взять из `harness2`:** Готовый модуль `runmark.py`. Он вычисляет `sha256` каждого файла конфигурации, генерирует метаданные `.adapt_complete` с `fingerprint`, `inputs_fingerprint` и временем завершения. Функция `is_reusable` моментально проверяет, актуален ли существующий кандидат, или требуется перезапуск.

### 2. Принцип ограниченных правок и неизменяемости (`tree.py` -> Раздел 9: "Исправляйте только назначенные части")
- **Требование фреймворка:** «Сохраняйте принятие неизмененных независимых блоков. Исполнитель сохраняет замены... Служебные поля и границы сохраняет программный слой».
- **Что взять из `harness2`:** Механизм патчинга компонентов из `tree.py`. Изменения передаются как дельта (`diff`), а программный слой накладывает их на базовое дерево, гарантируя, что защищенные системные компоненты не были стерты или подменены.

### 3. Изоляция рабочего пространства исполнителя (`proposer.py` -> Разделы 6.2, 8.3)
- **Требование фреймворка:** «Для строгого ограничения создавайте отдельную рабочую среду исполнителя. Помещайте в неё только разрешенные снимки и нужные инструменты».
- **Что взять из `harness2`:** Реализацию создания изолированных песочниц в `proposer.py` (`contextlib.contextmanager _isolated_dir`), где субагенту монтируются только необходимые снимки входов, а после работы каталог очищается.

### 4. Независимый аудит и разделение статусов (`judge.py` -> Раздел 8.1, 8.2)
- **Требование фреймворка:** «Различайте PASS, FAIL, BLOCKED и технический ERROR... Автор не принимает собственный аудит».
- **Что взять из `harness2`:** Класс `Judge` и функции градаций оценок. Реализует строгое разграничение: техническая ошибка выполнения скрипта проверки (`ERROR`) не смешивается с содержательным провалом проверки (`FAIL`).

### 5. Учет бюджета шагов и конечный автомат (`ledger.py` -> Раздел 1.1, 7.1)
- **Требование фреймворка:** «Общая инструкция проекта задает предел числа активных субагентов... Задайте конечный набор состояний».
- **Что взять из `harness2`:** Структуру `Ledger` для отслеживания лимита шагов, числа исправлений и переходов.

## 3. Технические плюсы и минусы `google-research/harness2`

### Плюсы:
- **Язык Python:** Полная совместимость с вашей архитектурой скриптов (`runner.py`, `registry.py`, `validate.py`).
- **Готовая логика валидации кэша и зависимостей:** `runmark.py` решает одну из самых сложных задач фреймворка — детерминированную инвалидацию результатов при изменении исходников или правил.
- **Проверенная интеграция с несколькими рантаймами:** В каталоге `substrate/` уже реализованы адаптеры под Claude CLI и OpenCode, что позволяет использовать готовые мосты запуска агентов.
- **Исключительная академическая строгость:** Чистый, отлично протестированный код (покрытие тестами `tests/test_runmark...`, `test_tree...`, `test_judge...`).

### Минусы:
- `harness2` проектировался для задач бенчмаркинга и оптимизации промптов/скиллов ("meta-harness"), поэтому в нем нет встроенного CLI для пошагового чтения порциями по 12 Кб (курсор чтения из раздела 5 вашего фреймворка нужно реализовать самостоятельно или взять алгоритм курсора).
- В `harness2` нет системы квитанций вызовов инструментов вида `[r1]` с проверкой цитирования (этот компонент лучше взять из `deer-flow`).

## 4. Итоговая рекомендация по синергии проектов

Идеальная реализация вашего фреймворка получается путем соединения лучших решений:
1. **Ядро версионирования, снимков, квитанций завершения и изоляции каталогов:** взять из **`google-research/harness2`** (`runmark.py`, `tree.py`, изоляция песочниц из `proposer.py`).
2. **Слой квитанций вызовов инструментов и верификации цитат:** взять из **`bytedance/deer-flow`** (`tool_receipt.py`, `receipt_verification.py`, `read_before_write_middleware.py`).
3. **Модель проверок путей и прав доступа:** взять паттерн проверки путей из **`anomalyco/opencode`** (`file-access.ts`).
4. **Конвертация и генерация пресетов:** взять утилиту **`xisnn/harness2-dsh`** (`yaml_emit.py` для чистого YAML без PyYAML).
