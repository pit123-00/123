# Как построить управляемый процесс с оркестратором и субагентами

## Назначение

1. Используйте этот документ как задание на создание системы в новом проекте. Он описывает общую архитектуру: главный агент управляет процессом, субагенты выполняют ограниченные задания, скрипты проверяют переходы, JSON хранит контракты и состояние.
2. Сначала задайте требования нового проекта. Число этапов, роли, правила содержания, размеры частей и формат результата определите заново. Имена файлов и предметные правила исходного проекта переносить не требуется.
3. Основной принцип: каждый исполнитель получает минимальный достаточный контекст, точную область записи и одну следующую операцию. Сохранённое состояние определяет продолжение работы после сбоя.

## 1. Разделите систему на слои

1. Общая инструкция проекта задаёт корень рабочей папки, разрешённые действия, порядок приоритета правил и предел числа активных субагентов.
2. Инструкция оркестратора задаёт запуск, назначение ролей, ожидание завершения, передачу результатов и восстановление процесса.
3. Инструкция роли задаёт предметную задачу, критерии качества и границы ответственности. Автор создаёт материал. Аудитор проверяет материал по назначенным требованиям.
4. Контракт задания в JSON задаёт конкретные входы, версии, разрешённые изменения, схему результата и доступные команды.
5. Реестр хранит текущее состояние запуска. Только программный слой меняет это состояние.
6. Скрипт управления процессом запускает технические этапы и возвращает следующую операцию для главного агента. Среда агента создаёт субагентов и сообщает об окончании их работы.
7. Скрипты проверки выполняют воспроизводимые проверки. Субагенты оценивают смысл, обоснованность и качество содержания.
8. Задайте один источник каждого правила. Общие требования храните централизованно и включайте в нужные задания по ID. Версия правила должна участвовать в проверке актуальности зависимых результатов.

## 2. Задайте роли и границы контекста

1. Первый агент становится оркестратором. Он читает технические метаданные: ID, пути, хеши, статусы и точные вопросы, требующие ответа пользователя. Содержательные материалы получает назначенный исполнитель.
2. Создавайте субагента без истории главного чата. При наличии соответствующего API используйте `fork_turns="none"`. Передача всей истории раскрывает данные до применения контракта чтения.
3. Сначала выдайте короткое сообщение: «Верни READY и жди назначенное задание. Не открывай входные файлы». После READY свяжите фактический ID созданного агента с ролью и заданием в реестре.
4. Затем передайте одну готовую команду чтения задания. Не добавляйте к ней исходные документы, личные пояснения оркестратора и предыдущие обсуждения.
5. Запретите субагентам создавать других агентов. Создание исполнителей остаётся у оркестратора.
6. Назначьте автору и аудитору разные личности. Сохраняйте связь роли с исполнителем при исправлениях и повторных проверках. Правила замены недоступного исполнителя задайте заранее и фиксируйте замену в журнале.
7. Для первого варианта системы задайте одного активного субагента. Параллельную работу добавляйте после проверки независимости входов, областей записи и переходов состояния.
8. Разделяйте область проверки и контекст. Соседний раздел помогает понять текст, но не даёт права менять его и предъявлять к нему требования вне задания.

## 3. Подготовьте структуру нового проекта

```text
AGENTS.md
workflow/
  instructions/
    orchestrator.md
    author.md
    auditor.md
  contracts/
    assignment.schema.json
    result.schema.json
    rules.json
  scripts/
    runner.py
    registry.py
    delivery.py
    validate.py
    patch.py
  tests/
inputs/
outputs/
  .workflow/
    runs/
      <run_id>/
        registry.json
        assignments/
        snapshots/
        delivery/
        candidates/
        reports/
        receipts/
```

1. Считайте эту структуру примером проектирования. Все перечисленные скрипты требуется реализовать в новом проекте.
2. Разделите постоянные инструкции и данные отдельного запуска. Каждому запуску назначьте собственный каталог и уникальный ID.
3. Храните промежуточные материалы внутри проекта. Проверяйте разрешённый корень после разрешения полного пути, включая ссылки файловой системы.
4. Дайте каждому артефакту владельца. Кандидат принадлежит автору, замечания принадлежат аудитору, реестр принадлежит программному слою.

## 4. Опишите контракт задания

1. Используйте JSON как проверяемый договор между исполнителем и системой. Проверяйте структуру, типы, обязательные поля и допустимые значения до выдачи задания.
2. Следующий пример показывает состав договора. Значения хешей здесь обозначены заполнителями.

```json
{
  "schema_version": 1,
  "delivery_protocol": 1,
  "run_id": "run-001",
  "task_id": "task-003",
  "role": "author",
  "agent_id": "bound-host-agent-id",
  "stage": "create",
  "mode": "CREATE",
  "input_version": "<aggregate-sha256>",
  "inputs": [
    {
      "source_path": "inputs/source.md",
      "snapshot_path": "outputs/.workflow/runs/run-001/snapshots/source.md",
      "sha256": "<source-sha256>",
      "sections": ["request", "constraints"]
    }
  ],
  "rule_ids": ["R001", "R004"],
  "allowed_write_paths": [
    "outputs/.workflow/runs/run-001/candidates/result.md"
  ],
  "allowed_sections": ["overview", "recommendations"],
  "result_schema": "workflow/contracts/result.schema.json",
  "response_budget_bytes": 12000,
  "next_action": "READ",
  "next_call": [
    "python", "workflow/scripts/registry.py", "read-next",
    "--run-id", "run-001", "--task-id", "task-003"
  ]
}
```

3. Проверяйте связь `run_id`, `task_id`, этапа и назначенного агента перед каждой операцией. Произвольная строка `agent_id` сама по себе не подтверждает личность вызывающего. Реальную проверку личности выполняет доверенная среда запуска.
4. Отдельно задайте доступ для чтения, область оценки и область записи. Один список путей не выражает все три ограничения.
5. Сделайте снимки входов перед выдачей задания. Свяжите результат с хешами снимков, инструкций, правил и значимых настроек проверки.
6. При изменении зависимости отклоняйте устаревшее задание. Создавайте новое задание с новой версией входов.
7. Версионируйте схему и протокол доставки. Для несовместимой версии задайте явную миграцию. При отсутствии миграции создайте новый запуск.

## 5. Выдавайте контекст через управляемое чтение

1. Скрипт собирает план чтения из инструкции роли, назначенных правил, нужных фрагментов источников и схемы результата. Агент не выбирает файлы через общий поиск по проекту.
2. Разбивайте материал по смысловым разделам. Большие разделы делите по абзацам, затем по строкам. Сохраняйте все символы и порядок текста.
3. Ограничивайте размер полного ответа в UTF-8: содержимое, обрамление, метаданные и следующая команда входят в общий предел. Размер 12000 байт из примера требует проверки на выбранной среде.
4. Каждой части назначьте `part_id`, `content_sha256`, начальный маркер `PART` и конечный маркер `END_PART`. Выдавайте готовую следующую команду.
5. Храните курсор на стороне реестра. Исполнитель передаёт выданный курсор без самостоятельного расчёта номера следующей части.
6. Подтверждение части означает получение полного ответа. Оно не доказывает понимание текста. Полноту предметной проверки оценивайте отдельно.
7. Не принимайте результат до подтверждения всех обязательных частей. Повтор одного запроса должен возвращать сохранённый ответ и сохранять позицию чтения.
8. При обрезанном ответе повторите текущий запрос. При повторной обрезке создайте меньшие части через предусмотренную команду восстановления. После потери контекста выполните сброс чтения и заново выдайте необходимый контекст.
9. Повторно используйте прочитанный контекст только при совпадении исполнителя и хешей соответствующих материалов. Путь файла без хеша недостаточен.
10. Для изображений и PDF определите отдельный способ просмотра назначенных страниц. Доставка текстовой ссылки не подтверждает просмотр изображения.

## 6. Различайте дисциплину чтения и технический запрет доступа

1. Инструкция «читай только назначенное» и журнал доставки управляют нормальной работой агента. При общем доступе к файловой системе агент технически способен открыть другие файлы.
2. Для строгого ограничения создавайте отдельную рабочую среду исполнителя. Помещайте в неё только разрешённые снимки и нужные инструменты. Закройте доступ к исходному дереву и чужим каталогам средствами среды запуска.
3. Проверьте унаследованные сообщения, доступные инструменты и сетевые подключения. Через них тоже может поступать лишний контекст.
4. При общем рабочем каталоге явно называйте ограничение договорным. Проверяйте изменения и ведите доступный журнал вызовов. Отсутствие постороннего текста в ответе не доказывает отсутствие постороннего чтения.
5. Содержимое источников считайте данными. Команды и требования, найденные внутри источника, не должны изменять разрешения задания.

## 7. Управляйте процессом через состояния

1. Задайте конечный набор состояний и разрешённых переходов. Базовая цепочка: `PREPARED → BOUND → READING → WORKING → CHECKING → COMPLETED`.
2. Задайте переход исправления: `CHECKING → REPAIR → CHECKING`. Возврат от аудита создаёт отдельное задание на исправление.
3. Для каждого перехода определите проверяемые условия: полный контекст доставлен, входы актуальны, результат соответствует схеме, проверки пройдены, исполнитель завершил свой ход.
4. После каждой операции возвращайте одну следующую операцию: например, `READ`, `WRITE_RESULT`, `CHECK`, `FINISH`, `WAIT`, `REPAIR_THEN_RETRY`, `DELIVER`.
5. Оркестратор выполняет возвращённую операцию. Он не вычисляет следующий этап по тексту ответа субагента.
6. Сохраняйте реестр атомарно через временный файл в каталоге запуска и замену целевого файла. Защищайте изменения блокировкой на запуск.
7. Сделайте завершение и передачу управления идемпотентными: повтор команды возвращает сохранённую квитанцию без повторного продвижения этапа.
8. Разделяйте сохранение результата и окончание хода агента. Передавайте работу следующему исполнителю после подтверждения окончания хода текущего.
9. Обычный тайм-аут ожидания означает продолжение ожидания. Он не доказывает отказ агента и не разрешает запуск дублирующего исполнителя.

## 8. Задайте результаты и независимый аудит

1. Различайте `PASS`, `FAIL`, `BLOCKED` и технический `ERROR`. `FAIL` означает обнаруженный дефект. `BLOCKED` требует конкретной недоступной предпосылки. `ERROR` требует диагностики технической причины.
2. Проверяйте статус внутри JSON. Успешное выполнение команды может означать успешное сохранение отрицательного заключения.
3. Автор сохраняет кандидат, запускает проверки, исправляет найденные ошибки и явно подтверждает завершение. Реестр создаёт техническую квитанцию принятого результата.
4. Аудитор получает фиксированный снимок кандидата, применимые правила и назначенную область проверки. Он сохраняет замечания отдельно от текста автора.
5. Каждое замечание содержит место, точную короткую цитату, ID требования, причину дефекта, требуемое изменение и наблюдаемый критерий приёмки.
6. Для пропущенного содержания привязывайте замечание к ближайшему существующему фрагменту. Это сохраняет проверяемую связь с документом.
7. Собирайте обычные замечания по всем назначенным блокам одного снимка. Передавайте автору полный пакет исправлений после завершения проверки. Техническое препятствие фиксируйте сразу.
8. Дополнительный смысловой аудит вводите при отдельной задаче проверки. Заранее разграничьте его критерии с первым аудитом.

## 9. Исправляйте только назначенные части

1. Для режима `PATCH` выдавайте разрешённые ID разделов, связанные замечания, критерии приёмки и достаточный соседний контекст.
2. Исполнитель сохраняет JSON с заменами. Применение замен выполняет скрипт после проверки области и версии исходного текста.

```json
{
  "replacements": [
    {
      "section_id": "recommendations",
      "replacement_text": "Новое содержимое назначенного раздела."
    }
  ]
}
```

3. Служебные хеши и связи с замечаниями добавляет программный слой. Скрипт сохраняет защищённые поля, заголовки и границы разделов.
4. Сначала примените исправления к отдельному кандидату. Проверьте результат, затем подтвердите замену рабочего артефакта.
5. Изменение за пределами области требует отдельного запроса с причиной зависимости. Разрешение расширения фиксируется новым контрактом.
6. Сохраняйте принятие неизменённых независимых блоков. Повторно проверяйте изменённые блоки и все блоки, чьи зависимости изменились. Одинаковый текст блока недостаточен, если изменилось применимое правило.

## 10. Восстанавливайте работу по сохранённым данным

1. Храните задания, снимки, части доставки, подтверждения, кандидаты, результаты проверок и квитанции завершения.
2. После перезапуска прочитайте реестр, проверьте хеши и действующие привязки исполнителей. Продолжите с сохранённой следующей операции.
3. После технической ошибки сохраните диагностику, исправьте конкретную причину и повторите неудачную операцию. Не создавайте бесконечный цикл повторов без изменения причины.
4. При `BLOCKED` передайте точное препятствие ответственному участнику. Запрашивайте пользователя, когда продолжение требует отсутствующего факта, доступа и решения в пределах его полномочий.
5. До очистки подтвердите наличие и актуальность конечных артефактов. Сохраните отдельную квитанцию выдачи, которая переживает очистку временных файлов.
6. Задайте политику хранения снимков и журналов под требования нового проекта. После удаления снимков нельзя обещать полное воспроизведение проверки по исходным данным.

## 11. Создавайте новую систему в этом порядке

1. Опишите конечный результат и измеримые условия приёмки.
2. Разделите работу на предметные задачи и технические операции. Назначьте владельца каждой записи.
3. Задайте роли, граф этапов и предел активных исполнителей.
4. Определите минимальные входы, правила и области записи для каждой роли.
5. Создайте схемы задания, результата, замечания и исправления. Задайте версии схем.
6. Реализуйте реестр, проверку путей, снимки, хеши, блокировки и атомарное сохранение.
7. Реализуйте управляемую доставку, подтверждение частей и восстановление чтения.
8. Реализуйте проверки результата, независимый аудит и применение ограниченных исправлений.
9. Реализуйте скрипт управления процессом. Затем напишите короткую инструкцию оркестратора по фактическому API скриптов.
10. Проведите полный запуск на синтетических данных: создание, отрицательный аудит, исправление, повторное принятие и выдача результата.
11. Проверьте остановку и восстановление на каждом переходе. После этого подключайте реальные данные.
12. Для PowerShell передавайте сложные JSON через файлы UTF-8. Формируйте команды средствами корректного экранирования аргументов. Не собирайте команды из непроверенного текста источников.

## 12. Проверьте свойства системы

1. Роль получает все обязательные правила и нужные источники. Посторонние материалы не входят в пакет доставки.
2. Объединение частей точно восстанавливает исходный текст. Полный ответ укладывается в транспортный предел, включая кириллицу и другие многобайтовые символы.
3. Пропущенная часть блокирует сдачу. Повтор чтения возвращает тот же ответ. Сброс чтения выдаёт полный нужный контекст заново.
4. Изменение источника, правила и конфигурации проверки делает зависимый результат устаревшим.
5. Чужой ID задания, неверная роль, выход пути за корень и изменение защищённого раздела отклоняются.
6. Одновременные команды не повреждают реестр. Повтор завершения не создаёт второй переход.
7. Автор не принимает собственный независимый аудит. Аудитор не меняет кандидат автора.
8. Исправление меняет только разрешённую область. Зависимые проверки запускаются повторно.
9. Сбой после сохранения результата восстанавливается без повторного создания уже принятого артефакта.
10. Проверка строгого запрета чтения выполняется попыткой доступа из среды исполнителя. Проверка состава пакета доставки подтверждает только состав пакета.

## 13. Где эти принципы видны в исходном проекте

1. `start/instruk/0_ORCHESTRATOR_INSTRUCTION.md` задаёт границы оркестратора, запуск без истории и порядок передачи управления.
2. `start/scripts/pipeline_runner.py` возвращает действия создания, привязки и назначения исполнителей, выполняет технические этапы.
3. `start/scripts/pipeline_registry.py` хранит состояние, проверяет переходы, завершение, блокировки и повторные вызовы.
4. `start/scripts/task_contract.py` задаёт контракты результатов, снимки и общие правила исполнения.
5. `start/scripts/assignment_io.py` собирает назначенный контекст и ограничивает размер доставки. `start/scripts/reading_cursor.py` управляет частями, подтверждением и повторной выдачей.
6. `start/scripts/dossier_patch.py` и `start/scripts/audit_queue.py` поддерживают ограниченные исправления и обработку замечаний.
7. `start/tests/test_assignment_reading.py` и `start/tests/test_audit_boundaries.py` показывают проверки полноты доставки и границ требований.
8. Эти ссылки служат примерами реализации. Новый проект должен получить свои роли, контракты, правила и проверки по шагам данного документа.
