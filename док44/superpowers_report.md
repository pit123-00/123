# Подробный аналитический отчет по методологии Superpowers

## 1. Введение в Superpowers

Superpowers — это комплексная методология разработки программного обеспечения, специально разработанная для ИИ-агентов. Она построена на наборе «навыков» (skills) — модульных инструкций, которые направляют агента через все этапы жизненного цикла разработки: от первоначального мозгового штурма до слияния готового кода в основную ветку.

Основная философия Superpowers заключается в приоритете процесса над интуицией. Вместо того чтобы сразу приступать к написанию кода, агент должен сначала полностью понять намерения пользователя, спроектировать решение, составить детальный план и только потом приступать к реализации, используя строгий подход TDD (Test-Driven Development).

## 2. Карта навыков (Skill Map)

Система Superpowers состоит из 14 ключевых навыков, которые можно разделить на несколько функциональных групп:

### Группа А: Проектирование и планирование
1. **brainstorming** — преобразование идей в детальный дизайн-документ.
2. **writing-plans** — декомпозиция утвержденного дизайна на конкретные, проверяемые задачи.

### Группа Б: Управление рабочим пространством
3. **using-git-worktrees** — создание изолированных сред для разработки на отдельных ветках.
4. **finishing-a-development-branch** — завершение работы, выбор способа интеграции (merge, PR) и очистка окружения.

### Группа В: Реализация и качество
5. **subagent-driven-development** — исполнение плана через делегирование задач специализированным субагентам.
6. **executing-plans** — альтернативный метод исполнения плана в текущей сессии с контрольными точками.
7. **test-driven-development (TDD)** — цикл «Красный-Зеленый-Рефакторинг», гарантирующий корректность кода.
8. **verification-before-completion** — обязательная проверка доказательств работоспособности перед заявлением об успехе.

### Группа Г: Отладка
9. **systematic-debugging** — четырехфазный процесс поиска первопричины перед внесением исправлений.
10. **dispatching-parallel-agents** — параллельное исследование независимых проблем несколькими агентами.

### Группа Д: Взаимодействие и код-ревью
11. **requesting-code-review** — запрос проверки кода субагентом для выявления ошибок на ранних стадиях.
12. **receiving-code-review** — методология обработки обратной связи с упором на техническую аргументацию.

### Группа Е: Мета-навыки
13. **using-superpowers** — входная точка системы, определяющая правила выбора и активации навыков.
14. **writing-skills** — методология создания новых навыков с использованием принципов TDD.

## 3. Детальное описание каждого навыка

### 3.1. Brainstorming
**Описание:** Используется перед любой творческой работой. Помогает превратить сырые идеи в спецификации через сократический диалог.
**Процесс:** Исследование контекста -> Уточняющие вопросы -> Предложение 2-3 подходов -> Представление дизайна по секциям -> Написание дизайн-дока.
**Зависимости:** Обязательно переходит к `writing-plans`.

### 3.2. Writing Plans
**Описание:** Создание детальных планов реализации. План должен быть настолько четким, чтобы его мог выполнить «энтузиаст-джуниор без контекста».
**Правила:** Задачи по 2-5 минут. Полный код тестов и реализации прямо в плане. Никаких TBD.
**Зависимости:** Получает вход от `brainstorming`. Используется `subagent-driven-development` для выполнения.

### 3.3. Test-Driven Development (TDD)
**Описание:** «Железный закон»: нет кода без падающего теста.
**Цикл:** RED (написать тест, увидеть падение) -> GREEN (написать минимальный код) -> REFACTOR (улучшить структуру).
**Важно:** Код, написанный до теста, подлежит удалению.

### 3.4. Systematic Debugging
**Описание:** Процесс поиска первопричины (Root Cause) из 4 фаз. Запрещает «случайные» исправления симптомов.
**Инновация:** Если 3 исправления не помогли, необходимо поставить под сомнение саму архитектуру.

### 3.5. Subagent-Driven Development
**Описание:** Делегирование каждой задачи плана отдельному «чистому» субагенту.
**Контроль:** Двухстадийное ревью каждой задачи (соответствие спеке и качество кода).
**Связи:** Интегрируется с `using-git-worktrees` и `requesting-code-review`.

### 3.6. Verification Before Completion
**Описание:** Запрет на пустые заявления об успехе. Требует предъявления свежих доказательств (логов тестов, билдов) в текущем сообщении.

### 3.7. Using Git Worktrees
**Описание:** Механизм изоляции рабочего пространства. Создает отдельную папку для каждой фичи/ветки, предотвращая загрязнение основного репозитория.

### 3.8. Finishing a Development Branch
**Описание:** Стандартизированный финал работы. Проверка тестов перед предложением мержа, PR или удаления ветки.

### 3.9. Dispatching Parallel Agents
**Описание:** Позволяет распараллеливать независимые задачи (например, фикс трех разных багов в разных файлах) между несколькими агентами.

### 3.10. Requesting Code Review
**Описание:** Протокол вызова агента-ревьюера. Передается только необходимый контекст изменений (diff) и план, чтобы ревьюер не отвлекался на процесс размышлений основного агента.

### 3.11. Receiving Code Review
**Описание:** Отношение к правкам как к техническим требованиям. Запрещает «соглашательство» (выражения благодарности), требует технической верификации предложенных изменений.

### 3.12. Writing Skills
**Описание:** TDD для документации. Создание нового навыка начинается с описания сценария, где агент ошибается, и написания инструкции, которая исправляет это поведение.

### 3.13. Using Superpowers
**Описание:** Корневой навык. Устанавливает приоритет: инструкции пользователя > навыки Superpowers > системный промпт. Обязывает проверять наличие навыков перед любым действием.

### 3.14. Executing Plans
**Описание:** Режим исполнения плана в текущей сессии (без субагентов) с человеческими чекпоинтами.

## 4. Анализ зависимостей и жизненный цикл

Типичный поток (Workflow) в системе:
1. `using-superpowers` активирует `brainstorming`.
2. `brainstorming` (Спецификация) -> `writing-plans` (План).
3. `writing-plans` -> `using-git-worktrees` (Среда).
4. `using-git-worktrees` -> `subagent-driven-development` (Исполнение).
5. Внутри каждой задачи: `test-driven-development` -> `verification-before-completion` -> `requesting-code-review`.
6. Ошибки в процессе: `systematic-debugging` (может задействовать `dispatching-parallel-agents`).
7. Финал: `finishing-a-development-branch`.

## 5. Философия и принципы эффективности

- **Масштабируемость через декомпозицию:** План разбивается на шаги по 2-5 минут, что позволяет ИИ сохранять фокус и не ошибаться в деталях.
- **Изоляция контекста:** Использование субагентов для конкретных задач предотвращает накопление «шума» в основной сессии.
- **Доказательная база:** Верификация обязательна на каждом этапе. Успех — это не слово агента, а лог терминала.
- **Самокоррекция:** Ревью встроено в цикл разработки каждой маленькой задачи.

## 6. Резюме

Superpowers превращает ненадежный процесс генерации кода в предсказуемый инженерный конвейер. Главная ценность — жесткие ограничения (Guardrails), которые не дают ИИ «срезать углы», забывать о тестах или внедрять непроверенные решения. Методология позволяет достигать высокого качества кода даже на больших проектах, выходящих за рамки контекстного окна одной модели.
