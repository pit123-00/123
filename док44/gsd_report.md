# Аналитический отчет по системе агентов Get Shit Done (GSD)

## 1. Введение в экосистему GSD

Система Get Shit Done (GSD) представляет собой сложную многоагентную среду, предназначенную для автоматизации полного цикла разработки программного обеспечения. В отличие от простых чат-ботов, агенты GSD обладают узкой специализацией, четко определенными ролями и строгими протоколами взаимодействия через промежуточные артефакты (Markdown-файлы в директории `.planning/`).

Основная концепция GSD — «Solo Developer + Claude Workflow», где пользователь выступает в роли визионера и владельца продукта, а специализированные агенты берут на себя роли архитекторов, планировщиков, исполнителей и аудиторов.

## 2. Карта агентов (Agent Map)

Агентов GSD можно классифицировать по фазам жизненного цикла проекта:

### Группа 1: Инициация и Роадмап
1. **gsd-roadmapper** — создание глобального плана проекта (ROADMAP.md) на основе требований.
2. **gsd-codebase-mapper** — исследование существующего кода и создание документации (STACK.md, ARCHITECTURE.md, CONVENTIONS.md).

### Группа 2: Исследование и Дизайн
3. **gsd-phase-researcher** — техническое исследование предметной области конкретной фазы (RESEARCH.md).
4. **gsd-ai-researcher** — специализированное исследование ИИ-фреймворков и паттернов (AI-SPEC.md).
5. **gsd-assumptions-analyzer** — анализ неявных предположений и рисков в коде перед планированием.
6. **gsd-advisor-researcher** — поиск экспертных советов по конкретным библиотекам.

### Группа 3: Планирование
7. **gsd-planner** — декомпозиция фаз на атомарные, проверяемые планы (PLAN.md).
8. **gsd-eval-planner** — создание планов для оценки качества (evals) ИИ-систем.
9. **gsd-plan-checker** — верификация планов на соответствие правилам GSD.

### Группа 4: Реализация (Исполнение)
10. **gsd-executor** — основной агент, выполняющий задачи из планов с атомарными коммитами.
11. **gsd-debugger** — системная отладка багов с использованием научного метода.
12. **gsd-code-fixer** — специализированный агент для быстрого применения исправлений.
13. **gsd-debug-session-manager** — управление состоянием длительных сессий отладки.

### Группа 5: Верификация и Аудит
14. **gsd-verifier** — проверка достижения целей фазы («Task completion ≠ Goal achievement»).
15. **gsd-code-reviewer** — глубокий технический аудит кода ( bugs, security, quality).
16. **gsd-ui-auditor** — визуальный аудит интерфейса по 6 столпам дизайна.
17. **gsd-security-auditor** — проверка реализации мер по защите от угроз (Threat Model).
18. **gsd-ui-checker** — автоматизированная проверка UI через скриншоты.
19. **gsd-integration-checker** — проверка связей между компонентами.
20. **gsd-eval-auditor** — анализ результатов прогона евалов.

### Группа 6: Документация и Интеллект
21. **gsd-doc-writer** — генерация и обновление технической документации.
22. **gsd-doc-verifier** — проверка соответствия документации реальному коду.
23. **gsd-doc-classifier** — автоматическая классификация документов.
24. **gsd-doc-synthesizer** — объединение разрозненных данных в единые гайды.
25. **gsd-intel-updater** — обновление базы знаний проекта (Project Memory).

### Группа 7: Прочее
26. **gsd-user-profiler** — настройка поведения агентов под стиль пользователя.
27. **gsd-project-researcher** — глубокое изучение контекста всего проекта.
28. **gsd-domain-researcher** — поиск информации по бизнес-домену.

## 3. Подробное описание ключевых ролей

### 3.1. GSD Planner
Это «мозг» тактического уровня. Planner получает на вход цели из Роадмапа и контекст из исследований.
- **Задача:** Создать набор файлов `PLAN.md`, которые Executor сможет выполнить без интерпретации.
- **Метод:** Goal-Backward (идем от желаемого состояния системы назад).
- **Nyquist Rule:** Каждая задача должна содержать команду автоматизированной проверки.

### 3.2. GSD Executor
Основной агент реализации. Его работа атомарна.
- **Задача:** Выполнение задач типа `auto`, `tdd` или `checkpoint`.
- **Deviation Rules:** Имеет право сам фиксить баги, найденные в процессе, но обязан сообщать об архитектурных отклонениях.

### 3.3. GSD Verifier
Критический аудитор. Проверяет не «сделаны ли задачи», а «достигнута ли цель».
- **Метод:** Трехуровневая проверка: 1. Наличие файлов. 2. Субстантивность кода. 3. Рабочая проводка (wiring) — импортирован ли код в систему.

### 3.4. GSD Debugger
Дисциплинированный следователь.
- **Задача:** Найти первопричину через цикл: Гипотеза -> Эксперимент -> Улика -> Вывод.
- **Память:** Ведет файл сессии отладки, который позволяет продолжать работу даже после сброса контекста модели.

## 4. Схема взаимодействия и зависимости

1.  **ROADMAPPER** (Цели) -> **PLANNER** (Задачи).
2.  **CODEBASE MAPPER** (Контекст кода) -> **PLANNER** & **EXECUTOR**.
3.  **PLANNER** -> **EXECUTOR** (Исполнение).
4.  **EXECUTOR** -> **VERIFIER** (Проверка результата).
5.  **VERIFIER** (если ошибки) -> **PLANNER** (режим gap-closure) -> **EXECUTOR**.
6.  **EXECUTOR** -> **CODE REVIEWER** (Проверка качества).

---

## 5. Уникальные инженерные принципы GSD

- **Adversarial Stance:** Аудиторы ОБЯЗАНЫ предполагать, что код сломан, пока не доказано обратное.
- **Context window management:** Планы строятся так, чтобы модель не теряла фокус (не более 50% окна контекста на план).
- **Automation First:** Если что-то можно проверить скриптом, агент обязан это сделать сам, не беспокоя пользователя.

## 6. Заключение

GSD — это не просто чат-бот, это «операционная система» для агентской разработки. Ее сила в жесткой типизации задач и строгом разделении ответственности. Это позволяет масштабировать ИИ на огромные проекты, с которыми одна модель не справится из-за лимита контекста.
