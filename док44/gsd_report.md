# Аналитический отчет по системе агентов Get Shit Done (GSD)

## 1. Введение в экосистему GSD

Система Get Shit Done (GSD) представляет собой сложную многоагентную среду, предназначенную для автоматизации полного цикла разработки программного обеспечения. В отличие от простых чат-ботов, агенты GSD обладают узкой специализацией, четко определенными ролями и строгими протоколами взаимодействия через промежуточные артефакты (Markdown-файлы в директории `.planning/`).

Основная концепция GSD — «Solo Developer + Claude Workflow», где пользователь выступает в роли визионера и владельца продукта, а специализированные агенты берут на себя роли архитекторов, планировщиков, исполнителей и аудиторов.

## 2. Карта агентов (Agent Map)

Агентов GSD можно классифицировать по фазам жизненного цикла проекта:

### Фаза А: Инициация и Роадмап
1. **gsd-roadmapper** — создание глобального плана проекта (ROADMAP.md) на основе требований.
2. **gsd-codebase-mapper** — исследование существующего кода и создание документации по стеку, архитектуре и конвенциям.

### Фаза Б: Исследование и Дизайн
3. **gsd-phase-researcher** — техническое исследование предметной области конкретной фазы.
4. **gsd-ai-researcher** — специализированное исследование ИИ-фреймворков и паттернов.
5. **gsd-assumptions-analyzer** — анализ неявных предположений и рисков в коде перед планированием.

### Фаза В: Планирование
6. **gsd-planner** — декомпозиция фаз на атомарные, проверяемые планы (PLAN.md).
7. **gsd-eval-planner** — создание планов для оценки качества (evals) ИИ-систем.

### Фаза Г: Реализация (Исполнение)
8. **gsd-executor** — «рабочая лошадка», выполняющая задачи из планов с атомарными коммитами.
9. **gsd-debugger** — системная отладка багов с использованием научного метода.

### Фаза Д: Верификация и Аудит
10. **gsd-verifier** — проверка достижения целей фазы («Task completion ≠ Goal achievement»).
11. **gsd-code-reviewer** — глубокий технический аудит кода на наличие багов и уязвимостей.
12. **gsd-ui-auditor** — визуальный аудит интерфейса по 6 столпам дизайна.
13. **gsd-security-auditor** — проверка реализации мер по защите от угроз (Threat Model).

### Фаза Е: Документация
14. **gsd-doc-writer** — генерация и обновление проектной документации.
15. **gsd-doc-verifier** — проверка соответствия документации реальному коду.

## 3. Подробное описание ключевых ролей и взаимодействий

### 3.1 GSD Planner (Планировщик)
Это «мозг» тактического уровня. Planner получает на вход цели из Роадмапа и контекст из исследований.
- **Задача:** Создать набор файлов `PLAN.md`, которые Executor сможет выполнить без лишних вопросов.
- **Методология:** Goal-Backward (идем от желаемого состояния системы назад к необходимым действиям).
- **Зависимости:** Зависит от `gsd-roadmapper` (цели) и `gsd-phase-researcher` (технические решения).

### 3.2 GSD Executor (Исполнитель)
Основной агент реализации. Он не принимает стратегических решений, а строго следует плану.
- **Задача:** Выполнение задач типа `auto` или `tdd`, создание коммитов, ведение лога отклонений.
- **Инновация:** Deviation Rules (правила отклонений). Executor может сам фиксить мелкие баги (Rule 1) или добавлять критическую функциональность (Rule 2), но обязан останавливаться при архитектурных изменениях (Rule 4).
- **Зависимости:** Получает инструкции от `gsd-planner`. Передает результат `gsd-verifier`.

### 3.3 GSD Verifier (Верификатор)
Критически настроенный аудитор. Его девиз: «Не верь утверждениям в SUMMARY.md».
- **Задача:** Убедиться, что цель фазы РЕАЛЬНО достигнута в коде, а не просто задачи отмечены галочками.
- **Метод:** Проверка трех уровней: 1. Существование файлов. 2. Субстантивность (не заглушка ли это). 3. Связанность (wired) — импортирован и используется ли код.
- **Зависимости:** Проверяет работу `gsd-executor` против критериев успеха из `gsd-roadmapper`.

### 3.4 GSD Debugger (Отладчик)
Агент для решения сложных проблем.
- **Задача:** Поиск первопричины через фальсифицируемые гипотезы.
- **Инновация:** Ведение файла сессии отладки, который выживает после очистки контекста ИИ. Это «внешняя память» процесса расследования.

## 4. Схема взаимодействия и потоки данных

Взаимодействие агентов в GSD построено на передаче артефактов:

1.  **Поток Инициализации:**
    `gsd-roadmapper` -> (ROADMAP.md) -> `gsd-planner`.
2.  **Поток Подготовки:**
    `gsd-codebase-mapper` -> (STACK.md, ARCH.md) -> `gsd-planner` & `gsd-executor`.
3.  **Поток Планирования:**
    `gsd-phase-researcher` -> (RESEARCH.md) -> `gsd-planner` -> (PLAN.md) -> `gsd-executor`.
4.  **Поток Исполнения:**
    `gsd-executor` -> (Code + SUMMARY.md) -> `gsd-verifier` & `gsd-code-reviewer`.
5.  **Поток Обратной Связи:**
    `gsd-verifier` (если найдены пробелы) -> `gsd-planner` (режим gap-closure) -> Новый PLAN.md.

## 5. Уникальные особенности и «Железные правила»

- **Nyquist Rule:** Каждая верификация задачи должна содержать автоматизированную команду проверки. Если теста нет, «Нулевая волна» (Wave 0) плана должна его создать.
- **Adversarial Stance (Состязательная позиция):** Аудиторы (`gsd-verifier`, `gsd-code-reviewer`) ОБЯЗАНЫ предполагать, что работа сделана плохо или не сделана вовсе, пока не будет доказано обратное.
- **Context Budgeting:** Система жестко следит за потреблением контекстного окна ИИ. Планы составляются так, чтобы занимать не более 50% окна, гарантируя сохранение «интеллектуальных способностей» модели до конца задачи.
- **Prescriptive vs Descriptive:** Документация и инструкции должны быть предписывающими («Используй X»), а не просто описательными («Здесь используется X»).

## 6. Заключение

GSD — это высокоструктурированная фабрика программного обеспечения, где ИИ-агенты заменяют не просто программистов, но и всю вертикаль управления проектом. Разделение на «Планировщика» (думает) и «Исполнителя» (делает) позволяет обходить ограничения моделей по длине контекста и склонность к упрощению задач. Строгая система перекрестных аудитов гарантирует, что итоговый продукт будет соответствовать не только букве плана, но и духу инженерного качества.
