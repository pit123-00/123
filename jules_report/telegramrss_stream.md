# 1. Техническая реализация и архитектура
Проект `TelegramRSS` (написанный на PHP с использованием фреймворка Amphp) предоставляет возможность прямого доступа к медиафайлам Telegram через свои прокси-эндпоинты (например, `/media/...`). Архитектура решает проблему исчерпания оперативной памяти сервера (OOM) при загрузке больших видеофайлов из Telegram. Вместо загрузки файла целиком в RAM, используется асинхронный компонент `amphp/byte-stream`, который позволяет читать медиаконтент из Telegram API потоками чанков (chunks) и сразу же отдавать их клиенту в HTTP ответ.

# 2. Функции и логическая работа
Ключевая логика находится в `MediaController.php` и клиенте `TgClient.php`.
- При HTTP GET запросе к `/media/{channel}/{message_id}`, `MediaController` формирует запрос к `TgClient`.
- Метод `downloadToResponse` в `TgClient` использует библиотеку MadelineProto или HTTP-адаптер для инициации скачивания медиа.
- С помощью `amphp/byte-stream`, сервер открывает поток. В отличие от стандартного `file_get_contents`, который ждет завершения скачивания, возвращаемый объект `HttpResponse` привязывается к байтовому потоку.
- По мере того как куски файла (chunks) поступают от серверов Telegram на сервер `TelegramRSS`, они мгновенно перенаправляются (pipe) в выходной буфер ответа веб-сервера (клиенту).

# 3. Информационный обмен, память и потоки данных
Поток данных "проксируется" без сохранения состояния:
1. HTTP-клиент (например, браузер) запрашивает видео.
2. PHP-сервер устанавливает соединение с Telegram API.
3. Данные из сокета Telegram читаются небольшими буферами (например, по 8KB - 64KB).
4. Эти же буферы пишутся в TCP-сокет HTTP-клиента.
Память сервера: потребление RAM остается строго константным, равным размеру буфера (chunk_size), независимо от того, весит ли скачиваемое видео 10 МБ или 2 ГБ. Это критически важное архитектурное решение для высоконагруженных или публичных прокси-серверов.
