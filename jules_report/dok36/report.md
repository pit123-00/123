# Отчет по архитектуре и логике работы LetterFeed (для интеграции в PostgreSQL проект)

Этот отчет описывает логическую и техническую реализацию проекта [LetterFeed](https://github.com/LeonMusCoden/LetterFeed) на основе анализа его исходного кода, как запрошено для дальнейшей адаптации в вашем проекте на PostgreSQL.

## 1. Техническая реализация и архитектура

LetterFeed представляет собой full-stack приложение, цель которого — конвертация email-рассылок в форматы RSS/Atom для удобного чтения.

**Бэкенд:**
- **Фреймворк:** FastAPI (Python). Обеспечивает высокую производительность и автоматическую генерацию OpenAPI документации.
- **База данных:** Реляционная СУБД (поддерживается любая через SQLAlchemy, в том числе PostgreSQL, что идеально подходит для вашей задачи).
- **Фоновые задачи:** Библиотека `APScheduler` (`BackgroundScheduler`) используется для периодического запуска задачи `process_emails` внутри того же процесса (без необходимости воркеров вроде Celery, что упрощает деплой, но менее масштабируемо).
- **Миграции:** `Alembic` используется для управления схемой БД.
- **Генерация фидов:** Библиотека `feedgen` используется для создания валидных XML-документов (Atom).
- **Парсинг писем:** Стандартные библиотеки `imaplib` (для работы с почтовым сервером) и `email` (для парсинга MIME-структуры). Для очистки HTML и извлечения полезного контента используются `readability-lxml` (аналог режима чтения в браузерах) и `nh3` (для безопасной очистки от вредоносных тегов).

**Фронтенд:**
- **Фреймворк:** Судя по структуре директорий (`frontend/src/app`, `middleware.ts`), используется **Next.js** с App Router.
- **Связь с бэкендом:** Классический REST API посредством стандартных HTTP-запросов (с настроенным CORS в FastAPI).

## 2. Функции и как логически это работает

Основная логика сосредоточена в сервисах бэкенда: `app/services/email_processor.py` и `app/services/feed_generator.py`.

### 2.1 Планировщик и старт (`app/core/scheduler.py` & `main.py`)
При запуске FastAPI приложения (в блоке `lifespan`) инициализируется `BackgroundScheduler`. Он настраивается на периодический запуск (интервал задается в настройках, по умолчанию каждые 15 минут) функции `process_emails(db)`.

### 2.2 Обработка входящей почты (`email_processor.py`)
1. **Группировка:** Функция `process_emails` извлекает все активные подписки (`Newsletter`) из базы данных и группирует их по `search_folder` (IMAP-папка для поиска, обычно "INBOX").
2. **Подключение к IMAP:** Для каждой папки создается IMAP-подключение (`_connect_to_imap`).
3. **Поиск писем:** Выполняется поиск непрочитанных сообщений (`_fetch_unread_email_ids`).
4. **Обработка отдельного письма (`_process_single_email`):**
    - Письмо скачивается и парсится (`email.message_from_bytes`).
    - Проверяется `Message-ID`. Если письмо с таким ID уже есть в БД (в таблице `entries`), оно пропускается. Это механизм дедупликации.
    - Извлекается адрес отправителя. Бэкенд ищет совпадение в списке отправителей (`Sender`), привязанных к рассылкам (`Newsletter`).
    - Если отправитель не найден, но включена опция `auto_add_new_senders`, автоматически создается новая рассылка (`_auto_add_newsletter`).
    - Из письма извлекаются тема, дата получения и тело (HTML).
    - Если в настройках рассылки включена опция `extract_content`, HTML пропускается через `readability` (для выделения основной статьи и отсечения футеров/меню) и `nh3` (для очистки).
    - Создается новая запись в БД (`Entry`), связанная с `Newsletter`.
5. **Постобработка:** В зависимости от настроек, письмо либо помечается как прочитанное (`+FLAGS \Seen`), либо перемещается в архивную папку (`move_to_folder`) и помечается на удаление, после чего может быть вызван `expunge` (очистка).

### 2.3 Генерация RSS/Atom фидов (`feed_generator.py`)
- Запрос фида (например, `/feeds/{slug}`) вызывает функцию `generate_feed`.
- Функция извлекает `Newsletter` по его идентификатору и все связанные с ним `Entry` (посты).
- Инициализируется `FeedGenerator`.
- В цикле записи добавляются в фид (`fg.add_entry()`), маппинг: тема $\rightarrow$ `<title>`, HTML-тело $\rightarrow$ `<content>`, дата получения $\rightarrow$ `<published>` / `<updated>`.
- Формируется и возвращается XML-строка. Также есть `/feeds/all` (master feed), который объединяет посты из всех рассылок.

## 3. Как происходит обмен информации, память, потоки данных

### Потоки данных (Data Flow)
1. **IMAP Server $\rightarrow$ Backend:** Планировщик инициирует IMAP-запрос, почтовый сервер возвращает сырые байты писем (MIME).
2. **Backend (Память) $\rightarrow$ Database:** Бэкенд парсит байты в объекты Python (`email.message.Message`). Извлекает текст, очищает его. Затем с помощью ORM (SQLAlchemy) формирует объекты моделей и выполняет `INSERT` запросы в базу данных.
3. **Frontend $\rightarrow$ Backend:** Пользователь через UI (Next.js) отправляет REST запросы (GET, POST, PUT) для добавления/редактирования подписок (`newsletters`), привязки email-адресов (`senders`) и изменения общих настроек.
4. **RSS Reader $\rightarrow$ Backend:** Сторонняя программа (RSS-клиент) делает HTTP GET запрос на эндпоинт `/feeds/...`. Бэкенд делает `SELECT` из базы данных, "на лету" (in-memory) формирует XML с помощью `feedgen` и отдает его как ответ (`application/atom+xml`).

### Память и Хранение
- **Персистентное хранение (БД):** Данные надежно хранятся в реляционной базе. В вашем случае это будет **PostgreSQL**.
- **Оперативная память (RAM):** Используется временно. При парсинге IMAP в памяти создаются DOM-деревья HTML (при использовании lxml/BeautifulSoup). При генерации фидов загружаются последние N записей из БД и формируется строка XML.
- **Схема данных (Data Schema):**
    Ключевые таблицы в базе данных (идеально ложатся на реляционную модель PostgreSQL):
    1. **`newsletters` (Рассылки):**
        - `id` (String/UUID, PK)
        - `slug` (String, Unique) — для красивых URL фидов.
        - `name` (String) — название рассылки.
        - `search_folder`, `move_to_folder` (String) — настройки папок.
        - `extract_content` (Boolean) — флаг очистки HTML.
    2. **`senders` (Отправители):**
        - `id` (String/UUID, PK)
        - `email` (String, Unique) — адрес отправителя (например, `hello@substack.com`).
        - `newsletter_id` (String, FK) — связь многие-к-одному с таблицей `newsletters`. Это позволяет объединять письма с разных адресов в один фид.
    3. **`entries` (Письма/Посты):**
        - `id` (String/UUID, PK)
        - `newsletter_id` (String, FK)
        - `message_id` (String, Unique) — уникальный ID письма из заголовков (важно для идемпотентности, чтобы не скачивать дважды).
        - `subject` (String) — тема.
        - `body` (Text) — очищенное HTML-содержимое.
        - `received_at` (DateTime) — дата получения письма.

### Рекомендации для реализации на PostgreSQL:
В вашем проекте на PostgreSQL схему можно немного оптимизировать:
- Вместо `String` для ID использовать `UUID`.
- Для поля `body` в таблице `entries` можно рассмотреть тип `JSONB`, если планируется извлекать не только сырой HTML, но и структурированные данные (например, ссылки, изображения, метаданные).
- Дедупликация по `message_id` отлично реализуется через PostgreSQL constraint `UNIQUE` и конструкцию `INSERT ... ON CONFLICT DO NOTHING`.
