# 1. Техническая реализация и архитектура
Библиотека `reader` построена вокруг монолитного ядра (`core.py`), которое выступает в роли координатора между парсерами (чтение данных из сети) и хранилищем (сохранение в базу данных). Архитектура использует абстракцию `Reader`, которая инкапсулирует логику управления подписками. Для работы с подписками используется класс `Storage` и методы вроде `add_feed`, `update_feed`, а также `get_feeds`.
Для оптимизации сетевых запросов и дедупликации активно применяются механизмы HTTP-кэширования: ETag и Last-Modified. При вызове обновления фида (через `update_feed`), ядро извлекает сохраненные ранее HTTP-заголовки из базы данных и передает их в `_parser.py`.

# 2. Функции и логическая работа
Основной метод для работы с фидом — `update_feed()`. Он выполняет следующие шаги:
- Извлекает из базы данных текущую информацию о фиде (URL, ETag, Last-Modified, хэш содержимого).
- Вызывает парсер `_parser.py`, передавая ему эти данные. Если сервер отвечает статусом `304 Not Modified` (на основе ETag), парсинг завершается без загрузки тела ответа.
- Если данные изменились, парсер возвращает новый список записей (entries).
- Далее ядро выполняет дедупликацию. Оно проверяет наличие каждой записи в БД по её уникальному идентификатору (`id` записи в RSS/Atom). Если запись с таким `id` уже существует, проверяется изменение её содержимого. Если хэш/содержимое не изменилось, запись игнорируется (дедупликация). Если изменилось — обновляется. Новые записи вставляются в БД.

# 3. Информационный обмен, память и потоки данных
Поток данных начинается с вызова пользователем функции обновления. Ядро читает метаданные (ETag) из базы данных SQLite, формирует запрос через парсер, который отправляет HTTP GET запрос к серверу источника.
Ответ сервера (HTTP заголовки + XML/JSON тело) парсится во внутреннюю модель данных `EntryData` и `FeedData`.
Затем эти данные передаются обратно в ядро, где сравниваются с существующим состоянием в хранилище (памяти БД). Если обнаруживаются новые элементы, они сериализуются и сохраняются в таблицы БД (например, `entries` и `feeds`). ETag и Last-Modified фида обновляются в таблице `feeds`, чтобы следующий запрос был оптимизирован. Таким образом, состояние кэша жестко привязано к записям в БД, обеспечивая эффективный сетевой обмен.
