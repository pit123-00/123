# Сбор и хранение данных в базе данных (Все типы данных)

## 1. Техническая реализация и архитектура
Архитектура хранения данных NodeRSSBot опирается на SQL-реляционную базу данных (SQLite по умолчанию, либо PostgreSQL через Knex.js). Управление схемой базы данных осуществляется через миграции (папка `source/migrations`).

Вся система хранения минимизирована: база данных спроектирована **не для архивирования** контента (самих постов, текстов, медиафайлов), а исключительно для **отслеживания состояния подписок** и **отслеживания уже отправленных обновлений**.

## 2. Функции и логическая работа
База данных хранит три основные сущности (таблицы):

**Таблица `rss_feed` (Каналы):**
Содержит информацию о самих фидах.
- `feed_id` (BigInt/PK): Уникальный идентификатор фида.
- `url` (Text): Декодированный URL-адрес RSS-канала. Индексируется как уникальный ключ (`unique`).
- `feed_title` (Text): Название фида (полученное при парсинге тега `<title>`).
- `recent_hash_list` (Text/JSON): Массив идентификаторов или хэшей недавних постов в формате JSON-строки. Это необходимо для определения новых элементов: при каждом `fetch`-цикле новые посты сравниваются с этим списком.
- `error_count` (Integer): Счетчик ошибок. Если бот несколько раз подряд не может скачать фид (таймауты, 404), счетчик увеличивается. При достижении лимита бот может отписать пользователей или уведомить их об ошибке (`handleErr` в `source/utils/fetch.ts`).
- `next_fetch_time` (Timestamp): Время следующего запланированного опроса фида.
- `last_modified_header` (Text): Значение HTTP-заголовка `Last-Modified` для поддержки HTTP Caching.
- `etag_header` (Text): Значение HTTP-заголовка `ETag` для поддержки HTTP Caching (если возвращается 304 Not Modified, фид не парсится).
- `ttl` (Integer): Time-to-Live фида в минутах.

**Таблица `users` (Пользователи):**
Сохраняет настройки пользователей, взаимодействующих с ботом.
- `user_id` (BigInt/PK): Telegram Chat ID (ID пользователя, группы или канала).
- `lang` (Text): Выбранный пользователем язык интерфейса (I18N).

**Таблица `subscribes` (Подписки):**
Связующая таблица для реализации связи M:N (многие-ко-многим).
- `subscribe_id` (BigInt/PK): Внутренний ID.
- `feed_id` (BigInt/FK): Внешний ключ на таблицу `rss_feed` (с `ON DELETE CASCADE`).
- `user_id` (BigInt): Telegram Chat ID пользователя.
Имеет уникальный индекс на связку `[feed_id, user_id]`, что предотвращает дублирование подписок.

## 3. Обмен информацией, память и потоки данных
- **Фоновый цикл:** Функция `fetchAll()` запускается по расписанию (node-schedule), делает запрос в БД (`getAllFeeds`), выбирая фиды, у которых `next_fetch_time < NOW()`.
- **Процесс фильтрации:** При загрузке фида, парсер формирует массив `FeedItem[]`. Функция `getNewItems(oldHashList, fetchedItems)` сравнивает ID и ссылки новых постов с полем `recent_hash_list` из памяти БД.
- **Обновление памяти:** После успешной отправки сообщений в Telegram, поле `recent_hash_list` перезаписывается новым списком хэшей (функция `updateHashList`), а счетчик `error_count` сбрасывается в 0. Устанавливается новое `next_fetch_time` на основе заголовков или TTL (например, текущее время + `config.fetch_gap`).
- Данные о самих постах (текст, изображения) передаются "на лету" из HTTP-запроса прямо в Telegram API. Они существуют в оперативной памяти (в очереди `fastQueue`) лишь на время обработки и в БД на диск **не сохраняются**.
