# Отчет: Анализ Nitter (Архитектура проксирования и кеширования медиа)

Источник данных:
* Nitter: https://github.com/zedeus/nitter

## 1. Алгоритм `getPicUrl` / `getVidUrl` (Подмена оригинальных ссылок)
Вся архитектура Nitter строится на том, чтобы отдавать фронтенд без прямого обращения клиента к серверам Twitter. Это предотвращает трекинг.

Логика (файл `src/utils.nim`):
*   В зависимости от конфигурации (`base64Media`), все ссылки на изображения (вида `pbs.twimg.com/...`) кодируются.
    *   **Base64:** `/pic/enc/{base64(url)}` (защищает URL от блокировок провайдерами).
    *   **URL Encode:** `/pic/{encodeUrl(url)}`.
*   **HMAC Подпись для видео (`getVidUrl`):** Для видео-потоков (m3u8/mp4) используется криптографическая подпись для предотвращения злоупотреблений прокси-сервером Nitter (чтобы чужие сайты не использовали Nitter как бесплатный CDN для своих видео).
    *   `hmacKey` берется из конфига (`nitter.example.conf: hmacKey = "secretkey"`).
    *   `sig = HMAC(sha256, hmacKey, url)[0..12]` — берется подпись и усекается до 12 символов.
    *   Итоговый путь: `/video/{sig}/{encode(url)}`.

## 2. Логика обработки ETag и If-None-Match (HTTP 304)
В `src/routes/media.nim` реализован умный прокси, который не только пересылает данные, но и значительно экономит трафик при повторных запросах пользователя (повторный просмотр аватарок и картинок).

Алгоритм (`proxyMedia`):
1.  **Получение оригинальной ссылки:** Роутер перехватывает `/pic/{url}`. Исходная ссылка декодируется.
2.  **Валидация:** Проверка `isTwitterUrl(uri)` гарантирует, что прокси не используется для атаки SSRF на внутренние сервисы (разрешены только домены `twimg.com`, `video.twimg.com`, и т.д.).
3.  **Генерация ETag:** Идентификатором версии картинки служит хэш от её оригинального URL: `hashed = $hash(url)`.
4.  **Проверка кэша клиента:**
    ```nim
    if request.headers.getOrDefault("If-None-Match") == hashed:
        return Http304  # Not Modified
    ```
    Если браузер пользователя уже имеет эту картинку, сервер не скачивает её с Twitter и не отдает клиенту, а просто возвращает код `304`.
5.  **Потоковая отдача (Streaming):**
    Если файла в кэше браузера нет, открывается асинхронный HTTP клиент к Twitter:
    *   Устанавливаются заголовки `Content-Type`, `Content-Length`, `ETag: {hashed}` и кэширование на неделю `Cache-Control: max-age=604800`.
    *   Данные читаются чанками через `res.bodyStream.read()` и сразу отправляются клиенту `request.client.send(data)`. Это позволяет проксировать видео и большие картинки без загрузки их целиком в оперативную память сервера.

## Итог для Cherry-picking
Для реализации безопасного и быстрого прокси медиафайлов:
1.  Создать функцию-генератор, которая принимает URL картинки, и возвращает локальный URL-путь: `/media/proxy/{base64(url)}`. Для видео добавить проверку подписи `/video/proxy/{hmac(url)}/{base64(url)}`.
2.  Написать эндпоинт, который принимает эти пути, декодирует URL, проверяет домен по "белому списку" (чтобы избежать SSRF).
3.  Вычислить `ETag` (например, MD5 или просто хэш от URL).
4.  Проверить заголовок `If-None-Match`. Если совпадает — вернуть пустой ответ `304 Not Modified`.
5.  Если не совпадает, открыть стрим с целевого сервера и через пайплайн передавать байты клиенту (stream proxying).
