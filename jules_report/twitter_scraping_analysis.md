# Анализ скрапинга Twitter / X

Ссылки на репозитории:
* twscrape: https://github.com/vladkens/twscrape
* twitter-rss: https://github.com/book000/twitter-rss

## 1. Техническая реализация и архитектура
Скрапинг Twitter (платформы X) использует приватное GraphQL API (`api.x.com/graphql`) вместо закрытого публичного API v1.1/v2.

**twscrape** использует SQLite базу данных для хранения пула аккаунтов. Каждый аккаунт (`Account` объект) хранит логин, пароль, email, настройки HTTP-заголовков (User-Agent) и сохраненные cookies. Для каждого аккаунта создается асинхронный клиент `httpx.AsyncClient` с привязкой конкретного прокси. Библиотека содержит жестко зашитый Bearer токен `TOKEN`, который является публичным ключом клиентского приложения Twitter Web.

**twitter-rss** - это TypeScript/Node.js проект, который использует внешний инструмент (`twitter-openapi-typescript` / `cycle-tls`) или Playwright-подобную логику (`twitter-scraper`) для входа и поддержания сессии. Основной механизм работы также опирается на GraphQL API с эмуляцией заголовков браузера.

## 2. Функции и логика работы
**Обход авторизации и управление сессионными cookies**:
В `twscrape` (файл `login.py`) эмулируется пошаговый процесс входа (flow `login` на эндпоинт `/1.1/onboarding/task.json`).
- Отправляется запрос на активацию гостевого токена (guest token) на `/1.1/guest/activate.json`.
- Отправляется серия подзадач в `task.json`: `LoginEnterUserIdentifierSSO`, `LoginEnterPassword`, обработка 2FA (TOTP) или `LoginAcid` (запрос кода на почту, причем `twscrape` умеет подключаться к IMAP для автоматического извлечения кода).
- При успешном завершении flow, сервер отдает cookie `auth_token` (токен авторизации пользователя) и `ct0` (CSRF-токен).
- При последующих запросах к GraphQL API клиент обязательно отправляет заголовок `x-csrf-token`, значение которого берется из cookie `ct0`.

**Обход "Cursor Pagination" (из GraphQL API)**:
GraphQL API Twitter не использует смещение (offset/limit), а использует курсоры. В `twscrape` (файл `api.py`) функция `_gql_items` рекурсивно или циклично запрашивает новые страницы. Из ответа API (JSON дерева) ищется объект, у которого `cursorType` равен `Bottom` (для прокрутки вниз, загрузки более старых элементов) или `Top` (для загрузки новых). Найденный текстовый идентификатор курсора подставляется в переменные (variables) следующего GraphQL-запроса. Если `cursorType: Bottom` отсутствует или не изменяется, пагинация прекращается. Дополнительно используются курсоры типа `ShowMoreThreads` при сборе ответов на твиты.

**Архитектура пула аккаунтов (twscrape)**:
В `twscrape` реализован механизм распределения нагрузки. Каждый аккаунт имеет поля `stats` (счетчик запросов), `locks` (отметки времени блокировок) и `error_msg`. При возникновении ошибки 429 (Rate Limit) или других блокировок, аккаунт помечается заблокированным (в `locks` записывается время, до которого аккаунт "отдыхает", либо флаг `active=False` при перманентном бане). Система ротирует запросы между активными аккаунтами (и их прокси), что позволяет обходить лимиты на массовый сбор.

**Фильтрация рекламных твитов и санитаризация текста (XSS)**:
В `twitter-rss` (файл `main.ts`) после получения списка твитов из GraphQL API (`getSearchTimeline`) происходит фильтрация: отбрасываются элементы, у которых присутствует поле `promotedMetadata` (реклама).
Для предотвращения XSS-атак при формировании XML/HTML ленты используется строгая санитаризация (функция `escapeHtml`). Символы `&`, `<`, `>`, `"`, `'` заменяются на соответствующие HTML-сущности (например, `&lt;`). Все текстовые данные (`fullText`) и ссылки на медиа (`mediaUrls`) прогоняются через этот фильтр перед подстановкой в выходной XML-документ (RSS 2.0).

## 3. Информационный обмен, память и потоки данных
**Поток данных**:
1. Система извлекает аккаунт из пула (БД SQLite в `twscrape` или из JSON файлов/environment переменных в `twitter-rss`).
2. При отсутствии валидных cookies (`auth_token` и `ct0`), запускается Flow авторизации, по завершению которого cookies сохраняются в БД.
3. Формируется GraphQL запрос (например, поиск `SearchTimeline`, профиль пользователя, подписчики). Для запроса формируется JSON-словарь `variables` и `features`, куда подставляются ID пользователя или поисковый запрос, а также `cursor` (если это не первая страница).
4. Запрос отправляется на `https://api.x.com/graphql/<query_id>/<query_name>` с обязательными заголовками: `authorization` (Bearer токен Twitter Web), `x-csrf-token` (`ct0`), `x-guest-token`.
5. Сервер возвращает глубоко вложенный JSON.
6. Парсер (например, функция `parse_tweets` или `parse_users` в `twscrape`) обходит дерево инструкций (`TimelineAddEntries`) и извлекает объекты `legacy` (для твитов - текст, дата, медиа; для пользователей - screen_name, followers_count). При этом извлекаются курсоры (`Bottom`, `Top`).
7. Сформированные данные нормализуются и сохраняются в целевой формат (JSON, БД или XML-RSS). Память используется циклично: при переходе на новую страницу курсора предыдущий JSON-ответ может быть удален из памяти во избежание утечек. В `twscrape` используется асинхронный генератор `yield`, выдающий элементы по мере их поступления и парсинга, что минимизирует пиковое потребление RAM.
