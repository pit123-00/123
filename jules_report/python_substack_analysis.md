# Анализ API Substack

Ссылка на репозиторий:
* python-substack: https://github.com/ma2za/python-substack

## 1. Техническая реализация и архитектура
Substack не предоставляет официального публичного API для создания и управления постами сторонними приложениями. Репозиторий `python-substack` использует технику обратного инжиниринга (reverse-engineering) внутреннего (непубличного) REST API, которое использует сам веб-интерфейс Substack.
Основной клиент `Api` (в `api.py`) построен поверх `requests.Session`, что обеспечивает автоматическое сохранение и передачу сессионных cookies между запросами. Клиент настраивается базовыми URL-адресами `https://substack.com/api/v1` (для глобальных запросов) и `https://<publication_name>.substack.com/api/v1` (для запросов в рамках конкретного блога).

## 2. Функции и логика работы
**Механизм логина и получения cookie `substack.sid`**:
Логика аутентификации работает напрямую с эндпоинтом `/api/v1/login`. В функцию логина передается `email` и `password`. После успешного POST-запроса сервер Substack отвечает заголовком `Set-Cookie`, который содержит сессионный идентификатор `substack.sid` (и другие служебные куки). Объект `requests.Session` автоматически перехватывает эти куки и подставляет во все последующие защищенные запросы. Это обходит базовую защиту, так как запросы эмулируют браузер администратора.

**Взаимодействие с непубличным внутренним API**:
- **`/api/v1/reader/posts`**: Метод `get_posts` выполняет GET запрос к этому эндпоинту (глобальный `base_url`). Он возвращает JSON-ленту постов, доступных для чтения аккаунту (лента подписок пользователя). Это позволяет собирать контент как агрегатор.
- **`/api/v1/publication_launch_checklist`**: Метод `get_subscriber_count` использует этот эндпоинт (на уровне конкретной публикации `publication_url`) для извлечения статистики. В возвращаемом JSON находится поле `subscriberCount`, которое парсится и возвращается. Это обходной путь для получения количества подписчиков, так как специального эндпоинта для статистики в открытом доступе нет.
- Дополнительно реализованы эндпоинты для управления черновиками (`/drafts`), публикации постов (`/publish`), загрузки изображений (с кодированием в base64 и отправкой на `/image`) и работы с тегами.

**Абстракция Post**:
В проекте реализована концепция абстракции `Post` для формирования постов перед их отправкой. В коде библиотеки под капотом формируется JSON payload с метаданными. Черновик (draft) инициализируется базовыми параметрами (заголовок, подзаголовок, тело). Тело поста должно быть представлено в виде валидного HTML или внутреннего формата Substack (ProseMirror JSON). При публикации метаданные (дата публикации, отправка на email (`send`), автоматическая публикация в соцсети (`share_automatically`)) упаковываются в JSON и отправляются методом POST на `/api/v1/drafts/{draft_id}/publish`.

## 3. Информационный обмен, память и потоки данных
**Процесс инициализации и авторизации**:
1. Инициализация объекта `Api` с указанием email, пароля и имени публикации.
2. Выполняется запрос логина. В ответ `requests.Session` сохраняет в своей памяти (cookie jar) токен `substack.sid`.
3. Состояние сессии держится в памяти экземпляра `Api` на протяжении работы скрипта.

**Поток получения данных (Reader Posts / Статистика)**:
1. Выполняется GET запрос к целевому эндпоинту с прикрепленным `substack.sid`.
2. Сервер Substack валидирует cookie и возвращает JSON ответ.
3. Библиотека парсит ответ в Python словари (dict). Отсутствуют сложные ORM модели (как Pydantic), данные передаются в сыром виде (raw dict).

**Поток создания поста (Drafting & Publishing)**:
1. Пользователь передает контент (тег, текст, изображения).
2. Изображения кодируются в base64 и загружаются на сервер (эндпоинт `/image`), сервер возвращает URL загруженной картинки.
3. Формируется payload черновика (включая замену локальных изображений на полученные URL), который отправляется через POST на `/drafts`.
4. Сервер возвращает JSON с назначенным `draft_id`.
5. Позже этот `draft_id` используется для вызова метода `publish_draft` (POST запрос, который меняет состояние черновика на опубликованный пост).
Вся память для хранения промежуточных состояний (URL изображений, ID черновиков) находится на стороне вызывающего клиентского скрипта.
