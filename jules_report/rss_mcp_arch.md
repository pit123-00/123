# 1. Техническая реализация и архитектура
Архитектура `rss-mcp` представляет собой серверное приложение на базе спецификации Model Context Protocol (MCP), реализованное на TypeScript (Node.js). MCP-сервер абстрагирует доступ к внешним источникам данных (в данном случае RSS-фидам) и предоставляет унифицированный интерфейс для LLM через механизм "инструментов" (Tools).
При адаптации данной архитектуры поверх PostgreSQL (как требуется в проекте), MCP-сервер будет выступать в качестве слоя бизнес-логики (middleware). Он будет регистрировать инструменты (например, `get_stored_feeds`, `search_knowledge_graph`), которые вместо парсинга внешних URL (как в `rss-mcp`) будут выполнять SQL-запросы или вызывать хранимые процедуры базы данных PostgreSQL.

# 2. Функции и логическая работа
Ключевые механизмы архитектуры:
- **Инициализация сервера**: Создание экземпляра `McpServer` с определением имени и версии.
- **Регистрация инструментов (Tools)**: Вызов метода `server.registerTool(...)`. В этом методе описывается:
  - Имя инструмента (например, `get_feed`).
  - Описание (для LLM, чтобы нейросеть понимала, когда вызывать инструмент).
  - Схема входных данных, определяемая с помощью Zod (строгая валидация типов параметров).
  - Асинхронный коллбэк (handler), который исполняет бизнес-логику при вызове инструмента.
- Для PostgreSQL-адаптации в handler'е инструмента вместо HTTP-вызовов (axios) будет инициализироваться подключение к БД (например, через `pg` или `asyncpg`), валидироваться входные параметры от LLM, выполняться запрос к таблицам/JSONB-полям и формироваться ответ.

# 3. Информационный обмен, память и потоки данных
Информационный обмен базируется на стандартном транспорте MCP (чаще всего `StdioServerTransport` для локальных процессов или SSE для сети).
Поток данных:
1. LLM определяет необходимость получения данных и формирует JSON-RPC запрос с аргументами, соответствующими Zod-схеме инструмента.
2. MCP-сервер читает запрос из `stdin`, валидирует аргументы.
3. Сервер выполняет внутреннюю логику (в контексте PostgreSQL — выполняет запрос в БД, считывает данные из `pgvector` или реляционных таблиц).
4. Полученные данные агрегируются в строгий JSON объект (в памяти создаются DTO).
5. Результат сериализуется и отправляется обратно LLM через `stdout`.
Этот подход гарантирует изоляцию базы данных от прямого доступа нейросети, обеспечивая безопасность и строгую типизацию информационного обмена.
