# Отчет по анализу репозитория feed2json

Вводная ремарка: в запросе упоминаются функции `struct_time_to_rfc3339` и `gfnn`, которые характерны для библиотеки Python `feedparser`. Анализируемый репозиторий [feed2json](https://github.com/earthboundkid/feed2json) написан на Go и выполняет аналогичную задачу (маппинг XML RSS/Atom в JSON Feed), используя библиотеку `gofeed` для разбора и структуру `feeds.JSONFeed` для формирования ответа. Тем не менее, логика fallback'ов и нормализации, заложенная в этот проект, крайне полезна для архитектуры коннекторов (слой Ingestion) в PBD.

Ниже представлен детальный анализ реализации в контексте адаптации для Python/Pydantic пайплайна.

## 1. Техническая реализация и архитектура

Архитектура `feed2json` построена на строгом разделении ответственности между парсингом входящих данных и их сериализацией.
Процесс можно разбить на два слоя (подобно слою L1_raw в PBD):
1.  **Слой чтения и нормализации:** Использование внешней библиотеки (`github.com/mmcdole/gofeed`), которая инкапсулирует в себе всю грязь работы с различными диалектами RSS и Atom. Парсер приводит все фиды к единой внутренней структуре `gofeed.Feed`.
2.  **Слой сериализации (Маппинг):** Собственная логика маппинга нормализованной структуры в стандарт JSON Feed 1.1 (используя `github.com/gorilla/feeds` в качестве базы).

**Применимость для PBD:** Для Python коннекторов аналогичным паттерном будет использование `feedparser` (или более современной обертки) с последующей строгой валидацией через `Pydantic` модель (Universal Atom), которая гарантирует JSON Feed 1.1 контракт.

## 2. Функции и логическая работа (Fallback логика)

Основная логика маппинга сосредоточена в функции `convertObject` (файл `convert.go`). В ней реализованы важные механизмы fallback'ов, которые следует перенести в Python-коннекторы:

*   **Fallback для контента (Content vs Description):**
    В RSS часто путают теги `<content:encoded>` и `<description>`. Функция проверяет наличие `item.Content`. Если он пуст, она применяет эвристику для определения типа данных в `item.Description`:
    ```go
    // Detects if <tag> or &code; is in text to guess if it's HTML
    var htmlishRe = regexp.MustCompile(`<\w.*?>|&\w+;`)

    if item.Content == "" {
        if htmlishRe.MatchString(item.Description) {
            jsonItem.ContentHTML = item.Description // Если есть теги - это HTML
        } else {
            jsonItem.ContentText = item.Description // Иначе - простой текст
        }
    } else {
        jsonItem.ContentHTML = item.Content
        jsonItem.Summary = item.Description
    }
    ```
    *Адаптация в PBD:* Функция `gfnn` (get first not null) в связке с регулярным выражением `htmlishRe` может быть реализована в Pydantic `model_validator` (или `@field_validator`) для автоматической диспетчеризации контента в поля `content_html` или `content_text` в Универсальном Атоме.

*   **Конвертация и маппинг дат:**
    В Go версии разбор дат инкапсулирован внутри `gofeed` (который внутри парсит множество форматов). Поля `PublishedParsed` и `UpdatedParsed` напрямую маппятся в структуры времени.
    *Адаптация в PBD:* Функция `struct_time_to_rfc3339` необходима в Python, так как `feedparser` возвращает даты в формате `time.struct_time`. В коннекторе нужно реализовать утилиту, которая переводит этот кортеж в стандарт RFC 3339 (например, `2023-10-25T14:30:00Z`), который ожидает Pydantic для полей типа `datetime`.

*   **Обработка вложений (Enclosures):**
    Массив вложений итеративно маппится в структуру `JSONAttachment` с сохранением URL и MIME-типа.

## 3. Обмен информацией, память и потоки данных

Поток данных (Data Flow) в `feed2json` строго однонаправленный и работает в памяти без сохранения состояния (stateless), что идеально для коннекторов-сборщиков:

1.  **Вход (Source):** Функция `Convert` принимает сырой поток XML (байты) в виде `*bytes.Buffer`.
2.  **Трансформация (In-memory state):** Парсер `gofeed` читает поток и создает структуру `xmlfeed` (`*gofeed.Feed`).
3.  **Маппинг (Conversion):** Функция `convertObject` преобразует `xmlfeed` в `jsonfeed` (`*feeds.JSONFeed`).
4.  **Выход (Sink):** JSON Encoder сериализует структуру обратно в буфер `to *bytes.Buffer` (с отключенным экранированием HTML: `enc.SetEscapeHTML(false)`).

**Значение для Ingestion Layer PBD:** Коннекторы (Fetchers) должны быть чистыми функциями. Они принимают на вход URL или сырой payload (из RabbitMQ/Hatchet), скачивают его, применяют Fallback-логику (как `htmlishRe`) и маппинг в RFC 3339, и отдают строго типизированный Pydantic объект (JSON Feed 1.1) без каких-либо побочных эффектов или прямого общения с базой данных PostgreSQL. База данных (вставка и дедупликация по UUIDv7) — это задача следующего слоя (Emitter).
