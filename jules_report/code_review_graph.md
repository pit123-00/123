# Глубокий технический анализ и логика: code-review-graph
*Архитектура высокопроизводительного структурного анализа кода для ИИ-ассистентов*

## 1. Графовое хранилище на SQLite: выбор и оптимизация
Выбор SQLite в качестве основы для хранения графа знаний о коде — это стратегическое решение, обеспечивающее идеальный баланс между производительностью и портативностью. В отличие от серверных решений (Neo4j, PostgreSQL), SQLite работает локально, не требует настройки и обеспечивает мгновенный доступ к данным через файловую систему.

### 1.1 Обоснование локальности
Инструмент для код-ревью должен работать на машине разработчика или в среде CI максимально быстро. SQLite исключает сетевые задержки при запросах ИИ. В контексте ИИ-ассистентов (например, Claude Code или Cursor), которые выполняют десятки мелких запросов к базе в процессе одной итерации ревью, задержка в 1-2 мс против 50-100 мс у сетевой базы становится решающим фактором.

### 1.2 Схема базы данных и индексация
БД спроектирована для поддержки сложных графовых обходов (`traversal`) средствами реляционных запросов.
- **Таблица `nodes`:** Хранит сущности кода. Ключевые поля: `kind` (File, Class, Function, Test), `qualified_name` (глобальный уникальный ID), `signature` (декларация без реализации).
- **Таблица `edges`:** Хранит направленные связи. Поля: `source_qualified`, `target_qualified`, `kind` (CALLS, INHERITS и т.д.).
- **Оптимизация индексами:**
    - `idx_nodes_qualified` (UNIQUE): Позволяет мгновенно найти метаданные функции по её имени.
    - `idx_edges_source` и `idx_edges_target`: Эти два индекса превращают SQLite в эффективный графовый движок. Они позволяют системе мгновенно отвечать на вопросы "кто вызывает эту функцию?" и "кого вызывает эта функция?", выполняя эффективный поиск по индексу вместо полного сканирования таблицы.
- **FTS5 (Полнотекстовый поиск):** Виртуальная таблица `nodes_fts` позволяет ИИ выполнять семантически близкие текстовые запросы по именам и путям файлов, используя морфологический анализ SQLite.

### 1.3 Конкурентный доступ: режим WAL
Проект использует режим **Write-Ahead Logging (WAL)**. Это критично для интеграции с IDE. Когда пользователь сохраняет файл, срабатывает хук обновления графа (запись). В этот же момент ИИ-ассистент может анализировать код (чтение). В обычном режиме SQLite это вызвало бы блокировку `database is locked`. Режим WAL позволяет писателю и читателям работать одновременно, обеспечивая непрерывность рабочего процесса.

## 2. Экстракция сущностей: магия Tree-sitter
Проект использует Tree-sitter — современный инкрементальный парсер, который строит полноценное абстрактное синтаксическое дерево (AST) для каждого файла.

### 2.1 Логика построения AST
В отличие от анализа через регулярные выражения, Tree-sitter понимает контекст. Он отличает вызов функции от её определения, понимает области видимости (scope) и вложенность. Для каждого из 19+ языков в проекте реализован специфический маппер, который переводит низкоуровневые токены AST в высокоуровневые узлы графа.

### 2.2 Qualified Names (Уникальные идентификаторы)
Генерация квалифицированных имен — это фундамент точности системы. Имя генерируется по шаблону:
`file_path::[EnclosingClass.]EntityName`
Пример: `/app/auth/logic.py::AuthManager.verify_token`.
Такой подход гарантирует, что даже если в проекте 100 функций с названием `verify`, в графе каждая из них будет представлена уникальным узлом, связанным с конкретным файлом и классом. Это позволяет ИИ прослеживать зависимости через границы модулей без риска ложных срабатываний.

## 3. Генерация связей: многослойный анализ
После извлечения узлов система строит сеть отношений, используя несколько стратегий:
- **`CALLS` (Вызовы):** Парсер анализирует тела функций, находя обращения к другим именам. Если цель вызова определена в том же файле, связь устанавливается сразу. Если нет — она помечается как внешняя и разрешается на этапе пост-обработки.
- **`IMPORTS_FROM`:** Анализирует зависимости на уровне файлов. Это база для инкрементальных обновлений.
- **`INHERITS` / `IMPLEMENTS`:** Отслеживает иерархию классов и интерфейсов, позволяя ИИ понимать полиморфные связи.
- **`TESTED_BY`:** Инновационный тип связи. Система находит соответствия между рабочим кодом и тестами (по именам и вызовам), создавая обратные ребра. Это позволяет ИИ отвечать на вопрос: "Какие тесты мне нужно запустить, если я изменю этот метод?".

## 4. Инкрементальность: «Сердце» проекта
Инкрементальность обеспечивает актуальность графа без необходимости полной переиндексации проекта на каждый чих.

### 4.1 Алгоритм Git-driven Update
1. **Обнаружение изменений:** При вызове обновления (`code-review-graph update`) система выполняет `git diff --name-only HEAD~1`. Это дает список измененных файлов за миллисекунды.
2. **Impact Propagation (Распространение влияния):** Система запрашивает SQLite: "Какие файлы импортируют эти измененные файлы?". Все найденные "потребители" также помечаются как требующие перепарсинга, так как изменения в экспортируемом API могут изменить граф вызовов в импортирующем коде.
3. **Хеширование SHA-256:** Прежде чем запустить парсер Tree-sitter, система вычисляет хеш контента файла и сравнивает его с сохраненным в базе. Если хеши совпадают (например, файл был затронут git-операцией без изменения кода), парсинг пропускается.
4. **Скорость:** Благодаря этим оптимизациям, обновление графа на проекте из 3000+ файлов занимает менее 2 секунд. Это позволяет встроить обновление графа в `post-commit` хук или в процесс сохранения файла в IDE.

## 5. Вывод
`code-review-graph` — это инженерный шедевр в области инструментов для ИИ-разработки. Его сила не в сложности LLM-промптов, а в глубине понимания структуры кода. Объединение классического компиляторного анализа (AST) с эффективными методами хранения данных (SQLite + WAL) и интеграция с инструментами контроля версий (Git) создают уникальный фундамент для ИИ-ассистентов, позволяя им работать с кодом на уровне опытного системного архитектора.
