# Анализ архитектуры Nitter

Ссылка на репозиторий:
* Nitter: https://github.com/zedeus/nitter

## 1. Техническая реализация и архитектура
Nitter — это альтернативный frontend для Twitter, написанный на языке Nim, созданный с упором на конфиденциальность и производительность. Его архитектура не использует клиентский JavaScript, а выполняет полный Server-Side Rendering (SSR).
Существенной частью архитектуры Nitter является встроенная система проксирования медиафайлов (картинок, видео) через собственный backend. Это делается для сокрытия IP-адресов пользователей от серверов Twitter (чтобы предотвратить трекинг) и для обхода блокировок контента. Маршрутизация построена на базе веб-фреймворка `jester`.

## 2. Функции и логика работы
**Проксирование медиафайлов и функция `getPicUrl`**:
Вместо того чтобы отдавать пользователю оригинальные ссылки на изображения (например, `https://pbs.twimg.com/media/XYZ.jpg`), парсер Nitter заменяет их при рендеринге HTML/RSS с помощью функции `getPicUrl` (находится в `src/utils.nim`).
Алгоритм `getPicUrl`:
1. Принимает оригинальный URL изображения.
2. Кодирует URL с помощью `encodeUrl` (или `encode(link, safe=true)` при включенном режиме `base64Media`).
3. Добавляет префикс маршрутизатора `/pic/` или `/pic/enc/`.
Для видео (функция `getVidUrl`) процесс сложнее: генерируется криптографическая подпись (HMAC-SHA256) оригинальной ссылки, чтобы злоумышленники не могли использовать сервер Nitter как открытый прокси для произвольных видеофайлов. `getHmac(link)` возвращает срез хэша (`[0 .. 12]`), который добавляется в URL (`/video/{sig}/{encodeUrl(link)}`).

**Логика быстрого кеша и HTTP-заголовков (If-None-Match, ETag)**:
Сам процесс скачивания и отдачи медиа происходит в файле `src/routes/media.nim` (функция `proxyMedia`).
Для экономии трафика как самого сервера Nitter, так и клиентов, реализована строгая логика HTTP-кэширования:
1. При поступлении запроса на `/pic/...`, сервер Nitter скачивает заголовок/изображение с `pbs.twimg.com`.
2. Вычисляется хэш от оригинального URL (`let hashed = $hash(url)`).
3. Проверяется входящий заголовок от браузера пользователя: `if request.headers.getOrDefault("If-None-Match") == hashed:`.
4. Если хэши совпадают, значит картинка у пользователя в кэше браузера уже есть. Сервер моментально отвечает `Http304` (Not Modified) с пустым телом, обрывая загрузку и экономя полосу пропускания.
5. Если картинки в кэше нет, Nitter загружает ее и отдает клиенту со следующими заголовками:
   - `content-type`: оригинальный MIME тип
   - `cache-control: max-age=604800` (кэширование на неделю)
   - `etag: hashed` (для последующих запросов)
Тело файла отдается потоково (стриминг): `await res.bodyStream.read() -> await request.client.send(data)`.

## 3. Информационный обмен, память и потоки данных
**Поток данных при рендеринге страницы (Timeline/RSS)**:
1. Парсер собирает данные твита из внутреннего API (GraphQL/Legacy).
2. При формировании структуры твита (например, в представлениях `views/tweet.nim` или `views/rss.nimf`), оригинальные URL медиа-вложений пропускаются через функцию `getPicUrl`.
3. В итоговый HTML/XML вставляется локальная ссылка, например `<img src="/pic/enc/YXNkZg...">`.

**Поток данных при загрузке медиа (Proxying)**:
1. Браузер пользователя выполняет HTTP GET запрос на маршрут `/pic/enc/...`.
2. Роутер (`jester`) в `media.nim` перехватывает запрос.
3. Извлекается закодированная часть (`decoded(request, 1)`), декодируется (Base64 или URL Decode) и нормализуется (добавление префикса `https://pbs.twimg.com/`, если нужно).
4. Проверяется ETag (`If-None-Match`).
5. Если требуется загрузка, создается `AsyncHttpClient`.
6. Отправляется GET запрос на серверы Twitter.
7. Данные скачиваются из потока Twitter и **параллельно** транслируются (chunked streaming) в сокет клиента пользователя (`await request.client.send(data)`).
Таким образом, Nitter почти не использует локальную оперативную память или дисковое пространство для длительного хранения картинок — он выступает потоковым мостом (Stream Proxy) между Twitter и пользователем, перекладывая долгосрочное кэширование на браузер клиента (посредством ETag и Cache-Control).
