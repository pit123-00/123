# Отчет по telegram-to-rss

## 1. Техническая реализация и архитектура
Проект реализован на Python и использует библиотеку `Telethon` (MTProto клиент) для взаимодействия с API Telegram от лица пользователя (userbot). Для работы с базой данных (SQLite) используется асинхронный ORM `Tortoise`.
Сервис имеет фоновый процесс поллинга (`telegram_to_rss.poll_telegram.TelegramPoller`), который регулярно опрашивает API Telegram на предмет новых сообщений в каналах/чатах пользователя, скачивает медиафайлы и сохраняет текстовые данные и метаданные в базу.

## 2. Функции и логическая работа
- **Фоновое прослушивание каналов через Telethon:**
  Класс `TelegramPoller` реализует логику синхронизации:
  1. `fetch_dialogs()` запрашивает через Telethon список диалогов и сравнивает их с сохраненными в БД `Feed`. Определяются каналы для создания, обновления или удаления.
  2. `update_feed(dialog)` получает последнее сохраненное сообщение (`FeedEntry`) для канала и делает запрос к Telethon (`get_dialog_messages(min_message_id=...)`), скачивая только новые сообщения.
  3. `_process_new_dialog_messages` фильтрует сообщения, объединяет сгруппированные сообщения (альбомы/медиагруппы) на основе `grouped_id` из Telethon, скачивает медиа (фото, видео, документы), учитывая ограничения на размер файла.
- **Маппинг данных Telegram в универсальный формат (models/feed_entry.py):**
  Данные сохраняются в реляционную структуру (Tortoise ORM):
  - Модель `Feed` (id, name, last_update) представляет собой RSS-ленту, мапится 1-к-1 с `dialog.id` в Telegram.
  - Модель `FeedEntry` мапится на отдельные сообщения (`custom.Message` из Telethon).
    Она содержит:
    - `id`: составной ключ формата `{channel_id}--{message_id}` (генерируется в `to_feed_entry_id`).
    - `feed`: связь с родительским `Feed`.
    - `message`: текст сообщения (`dialog_message.text`).
    - `date`: дата публикации.
    - `media`: JSON-массив с путями к скачанным медиафайлам.
    - `has_unsupported_media`: флаг наличия неподдерживаемых медиа-вложений.
  Для очистки файловой системы при удалении записей в `feed_entry.py` используется хук Tortoise ORM `@post_delete`, который удаляет скачанные медиафайлы с диска.

## 3. Обмен информацией, память и потоки данных
- Клиент (Telethon) по таймеру или запросу устанавливает TCP-соединение (по MTProto) с серверами Telegram.
- Через RPC-запросы загружаются списки диалогов и история сообщений.
- Медиафайлы скачиваются асинхронно потоками (`dialog_message.download_media`) и сохраняются в статическую директорию на диске. В БД сохраняются только относительные пути.
- Если сообщение является частью альбома (медиагруппы), `grouped_id` позволяет связать несколько медиафайлов с одним текстом (последним или самым длинным из группы).
- Впоследствии эти данные из БД извлекаются и рендерятся в стандартные RSS (XML) файлы, к которым пользователь обращается через веб-сервер.
