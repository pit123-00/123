# Отчет по анализу репозитория FeedCord

Проект [FeedCord](https://github.com/Qolors/FeedCord) (C#/.NET) демонстрирует великолепную архитектуру изоляции адаптеров (Dependency Injection), которая является эталонным примером того, как следует проектировать слой Ingestion в PBD.

Ниже представлен детальный анализ архитектурной концепции строгих интерфейсов.

## 1. Техническая реализация и архитектура (Изоляция адаптеров)

Архитектура FeedCord построена на принципах **Чистой Архитектуры (Clean Architecture)** и инверсии зависимостей. Вместо того чтобы бизнес-логика (воркеры, менеджеры фидов) напрямую вызывала конкретные классы парсеров, она оперирует исключительно абстракциями (интерфейсами).

Вся магия сборки приложения происходит в `Startup.cs`, используя стандартный `Microsoft.Extensions.DependencyInjection`:
*   Определение абстракций: `IRssParsingService`, `INotifier`, `IFeedManager`, `IYoutubeParsingService`.
*   Регистрация конкретных реализаций (Адаптеров): `services.AddTransient<IRssParsingService, RssParsingService>();`
*   Использование фабрик для сложных объектов (например, фоновых сервисов, привязанных к конфигурации): `IFeedWorkerFactory`.

**Применимость для PBD:** Коннекторы (Fetchers) в PBD должны быть реализованы как самодостаточные скрипты (классы/модули), которые реализуют единый интерфейс (например, `BaseFetcher`). Слой бизнес-логики (Hatchet worker) не должен знать, парсит он IMAP, RSS или Telegram. Он должен лишь вызывать метод `fetch_updates() -> List[UniversalAtom]` у переданного ему интерфейса.

## 2. Функции и логическая работа (DI & Фабрики)

Ключевую роль в изоляции играют интерфейсы, определенные в директории `src/Services/Interfaces/`.
Например, парсер RSS ничего не знает о том, как будут отправляться данные (в Discord), а модуль отправки (Notifier) ничего не знает о парсинге.

*   `IRssParsingService` имеет строгий контракт: `Task<List<Post?>> ParseRssFeedAsync(string xmlContent, int trim)`. Он принимает сырую строку (не URL) и возвращает нормализованный список моделей. Это делает парсер чистым и легко тестируемым.
*   `INotifier` имеет контракт `Task SendNotificationsAsync(List<Post> newPosts)`.
*   Связывание (Orchestration) происходит через фабрики (`FeedWorkerFactory`), которые конструируют фоновый воркер (`IHostedService`), внедряя в него нужные менеджеры и нотификаторы.

**Применимость для PBD:** Для каждого источника создается свой адаптер. В PBD каждый адаптер (RSSFetcher, TelegramFetcher) — это чистая функция, "не знающая про базу". Она принимает конфигурацию источника, скачивает данные, нормализует их в `Universal Atom` (аналог модели `Post` в FeedCord) и возвращает список атомов.

## 3. Обмен информацией, память и потоки данных

В FeedCord поток данных (Data Flow) организован через конвейер независимых сервисов:
1.  **Триггер (Background Worker):** Циклически вызывает `IFeedManager.CheckForNewPostsAsync()`.
2.  **Сбор (HTTP/Parsers):** `IFeedManager` использует внедренный `IRssParsingService` для преобразования ответа в объекты `Post`.
3.  **Состояние (In-Memory State):** Менеджер фидов (`FeedManager`) хранит текущее состояние (например, последние прочитанные URL) в памяти/словарях, сверяя новые посты со старыми.
4.  **Отправка (Notifier):** Если найден новый пост, вызывается `INotifier.SendNotificationsAsync(newPosts)`.

**Значение для Ingestion Layer PBD:** В архитектуре PBD (через Celery/Hatchet) поток данных должен быть схожим:
*   Hatchet Worker (Оркестратор) триггерится по расписанию.
*   Он берет из базы конфигурацию источника (URL).
*   Он инстанциирует нужный изолированный адаптер (Fetcher), передавая ему URL (и, возможно, курсор/last_date).
*   Адаптер делает HTTP-запрос, парсит, маппит в Pydantic `Universal Atom` и возвращает список.
*   Оркестратор (а не адаптер!) берет этот список и отправляет его в Emitter (слой сохранения), который отвечает за дедупликацию по UUIDv7 и вставку в PostgreSQL. Таким образом достигается полная изоляция адаптеров от базы данных.
