# Анализ архитектуры Instagrapi

Ссылка на репозиторий:
* instagrapi: https://github.com/subzeroid/instagrapi

## 1. Техническая реализация и архитектура
`instagrapi` — это продвинутая библиотека на Python для работы с недокументированным Private API Instagram (мобильным приложением Android).
Главная архитектурная особенность библиотеки — использование паттерна **Mixin** (модульных примесей).
Главный класс `Client` (определенный в `__init__.py`) сам по себе почти пустой и создается путем множественного наследования десятков небольших классов-миксинов (`LoginMixin`, `ShareMixin`, `UploadVideoMixin`, `StoryMixin` и др.). Это позволяет избежать превращения кода в гигантский, монолитный, нечитаемый спагетти-класс "God Object" и логически разделить функционал (авторизация, профили, сторис, комментарии) по разным файлам в директории `mixins/`.

## 2. Функции и логика работы
**Модульный подход на миксинах (Mixins)**:
В файле `mixins/auth.py` реализованы базовые классы: `PreLoginFlowMixin`, `PostLoginFlowMixin`, и сам `LoginMixin`, который наследует их оба. В `mixins/video.py` находятся классы `DownloadVideoMixin` и `UploadVideoMixin`. Главный `Client` просто агрегирует их: `class Client(PublicRequestMixin, LoginMixin, UploadVideoMixin, ...):`. Внутри миксинов функции имеют доступ к общему состоянию клиента (например `self.private_request` или `self.device_settings`), так как предполагается, что в рантайме они будут частью единого инстанса `Client`.

**Эмуляция мобильных устройств и конфигурации "железа"**:
Instagram строго проверяет подлинность устройств. В `mixins/auth.py` (и конфигурационном файле `config.py`) происходит генерация "цифрового отпечатка" смартфона. Функция `set_device` подгружает данные из констант (например `android_version: 26`, `dpi: 480dpi`, `model: OnePlus`), а также генерируются уникальные UUID и `android_device_id` (базируется на SHA256 хэше времени `hashlib.sha256(str(time.time()).encode()).hexdigest()[:16]`). При входе эти параметры (`android_device_id`, `phone_id`, `device_id`) отправляются в API. Сохраненная конфигурация (жестко привязанная к аккаунту) используется для генерации заголовка `User-Agent`.

**Логика шифрования пароля (RSA + AES-GCM)**:
В `mixins/password.py` реализована криптографическая подготовка payload'а для авторизации. Instagram не принимает пароли в чистом виде (Plain Text).
Алгоритм шифрования `password_encrypt`:
1. Запрашивается публичный ключ RSA с эндпоинта `/api/v1/qe/sync/` (извлекается `ig-set-password-encryption-pub-key` и `ig-set-password-encryption-key-id`).
2. Генерируется случайный сессионный ключ 32 байта (`session_key`) и вектор инициализации 12 байт (`iv`).
3. Берется текущий Timestamp.
4. `session_key` шифруется публичным ключом RSA (с помощью `PKCS1_v1_5`).
5. Пароль пользователя шифруется алгоритмом AES (режим GCM) с использованием `session_key` и `iv`, добавляя `Timestamp` в качестве Authentication Data.
6. Полученные байты (ID ключа, IV, длина, зашифрованный AES, тег AES, зашифрованный RSA) склеиваются и кодируются в Base64.
7. Формируется строка вида `#PWD_INSTAGRAM:4:<timestamp>:<base64_payload>`, которая и отправляется на сервер как поле `enc_password`.

**Алгоритм rupload для загрузки медиа**:
Загрузка фотографий, видео и сторис реализована через внутренний сервис Instagram `rupload_igvideo` и `rupload_igphoto` (файлы `mixins/video.py`, `mixins/photo.py`).
Алгоритм загрузки (chunked upload) видео:
1. Вычисляется длина, ширина, длительность видео (через `moviepy` в `analyze_video`). Генерируется миниатюра (thumbnail).
2. Формируются параметры `rupload_params` (JSON объект с `retry_context`, `media_type`, `upload_id`).
3. Генерируется уникальный `upload_id`.
4. URL формируется как `https://i.instagram.com/rupload_igvideo/{name}` (где `name` содержит `upload_id`).
5. Для видео выполняется поэтапная загрузка (Upload Phase): файл отправляется потоково с заголовком `X-Instagram-Rupload-Params`.
6. После загрузки видео, отдельно загружается миниатюра (thumbnail) с тем же `upload_id` на эндпоинт `rupload_igphoto`.
7. Завершающий этап (Configure Phase): Вызывается эндпоинт `/api/v1/media/configure/` (или `configure_to_story`), куда передается `upload_id`. Сервер Instagram на своей стороне "собирает" ранее загруженные куски видео и миниатюру в финальный пост.

## 3. Информационный обмен, память и потоки данных
**Жизненный цикл сессии**:
1. Разработчик инициализирует `Client` и передает (или генерирует) объект настроек `settings`, который содержит UUID устройства и куки.
2. При вызове `client.login()` происходит процесс шифрования пароля и отправка POST-запроса авторизации.
3. Сервер возвращает JSON и сессионные куки (в том числе `sessionid`, `csrftoken`). Объекты сохраняются в `requests.Session`. Авторизация завершена.
4. Настройки "железа" и куки можно выгрузить (`client.get_settings()`) и сохранить в JSON файл, чтобы при следующем запуске выполнить вход без логина/пароля (просто восстановив сессионные токены).

**Поток создания видео-поста (IGTV / Reels / Feed)**:
1. Вызов метода `video_upload`.
2. Локальный видеофайл анализируется в памяти.
3. Поток загрузки файла (`rupload`): данные читаются с диска и отправляются по сети. Память не забивается всем видео-файлом, так как используется потоковая отправка (`requests` позволяет отправлять файл стримом).
4. Обмен статусами: сервер отвечает кодом 201/200 или 202 (Transcode not finished yet). При 202 скрипт засыпает (`time.sleep`) и повторяет запрос статуса.
5. Завершение: Отправка JSON-конфигурации (текст поста, теги, геолокация). Сервер возвращает объект созданного медиа, который парсится в ORM-подобный класс `Media` (используя `pydantic.BaseModel`).
Сложные вложенные данные (ответы GraphQL или REST) преобразуются в строго типизированные Python-объекты (классы из `types.py`, например `DirectMessage`, `UserShort`, `Story`), что гарантирует безопасность типов при дальнейшей работе.
