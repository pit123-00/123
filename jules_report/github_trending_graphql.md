# 1. Техническая реализация и архитектура
Компонент `GitHubGraphQLManager` (написанный на Swift) реализует абстракцию для доступа к GitHub GraphQL API `https://api.github.com/graphql`. Архитектура спроектирована для минимизации количества сетевых вызовов, чтобы избежать исчерпания Rate Limit. Вместо отправки отдельного REST-запроса на каждый репозиторий, менеджер динамически генерирует объединенный GraphQL-запрос с использованием механизма GraphQL Aliases, чтобы получить информацию о десятках репозиториев за одну транзакцию.

# 2. Функции и логическая работа
Ключевая функция — `fetchRepositoriesOGImages`, которая запрашивает URL Open Graph изображений для переданного массива кортежей `(owner: String, name: String)`.
Она использует функцию-помощник `buildBatchQuery`. Логика сборки:
- В цикле по всем переданным репозиториям формируется строковый блок для каждого репозитория.
- Каждому блоку назначается уникальный alias (например, `repo_0`, `repo_1`).
- Запрашиваются поля `openGraphImageUrl`, `usesCustomOpenGraphImage` и `id`.
Затем эта гигантская строка оборачивается в JSON-объект `{"query": "..."}` и отправляется методом HTTP POST на GraphQL эндпоинт. После загрузки ответ (JSON) декодируется встроенным механизмом Swift `JSONDecoder` в модель `GraphQLResponse`.

# 3. Информационный обмен, память и потоки данных
Поток данных ориентирован на батчинг (batching).
Вместо множественных аллокаций памяти под N сетевых запросов, приложение собирает данные в одну строку. Сетевой обмен представляет собой одно POST-соединение, что сильно экономит ресурсы процессора и задержку сети.
Ответ сервера возвращается как единый JSON-документ, который загружается в память в виде структуры `[String: RepositoryNode]`.
Ключами словаря являются алиасы (`repo_0`, `repo_1`), а значениями — извлеченные метаданные. После этого функция может вернуть эти данные, и они связываются с оригинальными репозиториями. Ошибки GraphQL (если какие-то репозитории не найдены) парсятся и пробрасываются как исключения `Error.graphQLError`.
