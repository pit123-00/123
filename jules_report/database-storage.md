# Сбор и хранение данных в базе данных (Folo)

Технический анализ организации хранения данных, типов контента и архитектуры базы данных в проекте Folo. Отчет основан на анализе Drizzle-схем.

## 1. Техническая реализация и архитектура

Проект Folo использует SQLite в качестве базы данных (на стороне клиента/локально) с использованием ORM Drizzle (`drizzle-orm/sqlite-core`). Архитектура БД спроектирована по принципу "плоских" таблиц с активным использованием колонок типа JSON (`{ mode: "json" }`) для хранения вложенных и динамических структур данных.

Основные сущности и таблицы:
- **`feedsTable` (Ленты/Источники):** Хранит метаданные об RSS/JSON источниках (URL, название, описание, частота обновлений).
- **`entriesTable` (Записи/Статьи):** Главная таблица контента. Хранит все типы записей, скачанных из источников.
- **`subscriptionsTable` (Подписки) и `listsTable` (Списки):** Управляют тем, как пользователи организуют и просматривают источники.
- **`aiChatTable` и `aiChatMessagesTable`:** Сохраняют историю взаимодействия пользователя с встроенным AI-ассистентом.
- **Таблицы-дополнения:** `imagesTable` (цветовые профили картинок), `summariesTable` (AI-саммари), `translationsTable` (AI-переводы).

## 2. Функции и логическая работа (Типы сохраняемых данных)

Folo сохраняет "все типы доступных данных" из фидов благодаря гибкой структуре таблицы `entries`:

- **Текстовый контент:**
  - `content` (оригинальный HTML).
  - `readabilityContent` (очищенный от мусора HTML-текст для удобного чтения, парсится через библиотеку Readability).
  - `description` (краткое описание из RSS).
- **Медиа-файлы (Изображения/Видео):**
  Хранятся в массиве JSON-объектов `MediaModel` (колонка `media`), содержащем `url`, тип `type: "photo" | "video"`, `preview_image_url`, размеры и `blurhash` для генерации превью-заглушки перед загрузкой картинки.
- **Вложения (Аудио/Подкасты):**
  Хранятся в колонке `attachments` (`AttachmentsModel[]`), которая сохраняет `mime_type`, размер файла в байтах и `duration_in_seconds`. Это позволяет реализовать нативный аудиоплеер.
- **Экстра-данные и Метаданные:**
  - `categories` - JSON-массив тегов фида (строки).
  - `extra` (`ExtraModel`) - сохраняет дополнительные ссылки (например, на источник оригинального поста) и title_keyword.
  - `settings` - персональные настройки для конкретной записи (состояние прочтения, закладки и т.д.).

## 3. Обмен информацией, память и потоки данных

Поток данных между БД и приложением:

1. **Нормализация при записи (Insert):** Парсер (работающий локально или получающий данные с бэкенда) получает сырой RSS/JSON, извлекает все найденные картинки (`<img>`, `<enclosure type="image/*">`) и видео/аудио (`<enclosure type="video/*">`) и складывает их в типизированные JSON-массивы.
2. **Индексирование и поиск:** Таблицы оптимизированы для быстрых выборок (например, поиск уникальных переводов по комбинации `entryId` и `language` через `uniqueIndex("translation-unique-index")`).
3. **Обновление состояния (Readability / AI):**
   - Когда пользователь запрашивает перевод статьи, он асинхронно сохраняется в `translationsTable` и связывается с записью по `entryId`.
   - То же самое касается AI-сводок новостей (таблица `summariesTable`).
4. **Синхронизация:** Идентификаторы генерируются как текстовые UUID или строковые хэши (`id: text("id").primaryKey()`), что упрощает оффлайн-первую синхронизацию базы данных между устройствами.
