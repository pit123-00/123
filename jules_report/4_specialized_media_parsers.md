# Анализ механизма: Специализированные медиа-парсеры (из FeedCord)

## 1. Техническая реализация и архитектура
В проекте `FeedCord` реализована архитектура разделения ответственности: базовый парсинг структуры RSS вынесен отдельно от узкоспециализированной логики извлечения медиаконтента (превью, картинок, видео-ссылок). Это реализовано через специализированные сервисы `YoutubeParsingService` и `ImageParserService`.

- **`YoutubeParsingService`:** Анализирует XML-структуру лент YouTube (namespace `http://search.yahoo.com/mrss/`). Если стандартный тег `link` указывает на видео, сервис специально ищет теги `media:group` -> `media:thumbnail`, чтобы извлечь прямую ссылку на превью видеоролика, игнорируя стандартные текстовые описания.
- **`ImageParserService`:** Работает по принципу фоллбэка (многоуровневого поиска). Сначала он пытается извлечь картинку прямо из XML ленты (проверяет `enclosure`, `media:content`, `itunes:image`, а также парсит HTML внутри `description` или `content:encoded` с помощью `HtmlAgilityPack` в поисках тега `<img>`). Если картинки в XML нет, сервис делает отдельный HTTP-запрос (ScrapeImageFromWebpage) по ссылке на сам пост и извлекает картинки из OpenGraph тегов (`og:image`, `twitter:image`) или из DOM-дерева страницы (`<img data-src>`, `image_src`).

## 2. Функции и логическая работа
Ключевые элементы:
- Сервисы инкапсулируют сложную логику регулярных выражений, парсинга HTML-дерева (XPath) и проверок на валидность URL-адресов.
- Изолированная обработка исключений и логирование. Если не удалось достать картинку, сервис возвращает пустую строку, не ломая общий флоу получения текста поста.
- Динамическое формирование абсолютных URL из относительных ссылок с помощью `Uri.TryCreate`.

## 3. Информационный обмен, память и потоки данных (Интеграция в PBD)
В системе PBD этот подход "фабрики медиа-экстракторов" следует применить на этапе обработки атомов L1_raw, но вынести в отдельный фоновый сервис, чтобы не замедлять текстовую нормализацию (L2).

- **Информационный обмен:** Парсинг текста (NormalizerService) и извлечение картинок строго разделены. Когда IngestionLayer сохраняет сырой JSON Feed в L1_raw, запускается независимый `MediaExtractorService`.
- **Потоки данных:** Фабрика экстракторов (`YoutubeExtractor`, `OpenGraphExtractor`, `HTMLImageExtractor` и т.д.) пробегается по контенту `L1_raw` (или по ссылкам, найденным внутри него).
- Как и в FeedCord, экстракторы пытаются выдернуть превьюшки (например, YouTube обложки или og:image из статей).
- Найденные медиафайлы скачиваются, чтобы избежать проблем с CORS и битыми ссылками на фронтенде, и складываются в S3-бакет `awareness-thumbnails`.
- В метаданные атома (в базу данных PBD) записывается уже абсолютный публичный HTTPS URL из нашего S3 (Minio), который затем используется фронтендом (Reflex/Canvas API) для отображения карточек в графе знаний.
