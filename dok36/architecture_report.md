# Отчет по архитектуре: Сбор данных, Обработка и Хранение (Анализ auto-news)

Настоящий отчет основан на анализе исходного кода репозитория `auto-news` и описывает техническую реализацию конвейера обработки данных (от сбора до хранения), а также предлагает способы реализации подобной архитектуры в PostgreSQL. Отчет разделен на 3 части согласно требованиям к техническому анализу.

---

## 1. Техническая реализация и архитектура

В репозитории `auto-news` четко прослеживается микросервисный и пайплайновый подход к обработке данных.

* **Оркестрация (Airflow DAGs):**
  Управление потоками осуществляется через Apache Airflow (папка `dags/`). Например, даг `news_pulling.py` запускается по cron-расписанию (каждые 15 минут) и имеет строгую последовательность задач: `start -> prepare -> pull -> save -> finish`. Каждая задача запускает соответствующий Python-скрипт (например, `af_pull.py` или `af_save.py`) как bash-команду.
* **Слой операторов (Operators):**
  В директории `src/` реализованы специализированные классы-операторы для каждого источника (`ops_twitter.py`, `ops_reddit.py`, `ops_youtube.py`, `ops_article.py` и т.д.). Они инкапсулируют логику подключения к API, скачивания и первичной трансформации данных. Для загрузки также используются механизмы LangChain (например, `WebBaseLoader`, `YoutubeLoader`).
* **Векторные хранилища (ChromaDB / Milvus):**
  Для поиска по эмбеддингам и хранения векторов используются ChromaDB (`chromadb_cli.py`) и Milvus (`ops_milvus.py`, `milvus_cli.py`). В модуле `llama_index_cli.py` происходит интеграция LLM, ChromaDB и `llama_index` для реализации механизма Retrieval-Augmented Generation (RAG).
* **Слой хранения результатов (Notion):**
  Итоговые результаты пушатся в базы данных Notion через `notion.py` и `ops_notion.py`, где они становятся доступны пользователю.

**Проекция на PostgreSQL (Ваш проект):**
Вместо Airflow можно использовать асинхронное фоновое планирование задач (asynchronous background task scheduling), реализованное в вашем проекте (например, через Celery, Graphile Worker или планировщики на основе графов). Векторные БД ChromaDB и Milvus полностью заменяются расширением `pgvector`.

## 2. Функции и логическая работа

Конвейер обработки данных разбит на две основные фазы, вызываемые скриптами `af_pull.py` и `af_save.py`.

1. **Сбор данных (Pull - `af_pull.py`):**
   * Скрипт последовательно обращается к источникам через операторы.
   * Данные скачиваются и сохраняются в сыром виде в локальные JSON-файлы (в папке `data/news/` с уникальным `run_id`). Это обеспечивает отказоустойчивость: если следующая фаза упадет, сырые данные не придется скачивать заново.
2. **Обработка и Дедупликация (Process & Dedup - `af_save.py`):**
   * Данные загружаются из локальных JSON.
   * **Дедупликация:** Вызывается метод `op.dedup()`, который проверяет, не были ли эти элементы уже обработаны (через проверку Redis-кешей или существующих записей).
3. **Оценка кандидатов (Scoring):**
   * Для больших потоков данных (Twitter, Reddit) применяется алгоритм скоринга. Текст превращается в векторный эмбеддинг, после чего выполняется поиск ближайших соседей (K-Means / similarity search в Milvus/ChromaDB).
   * Вычисляется средний балл (score) на основе исторических пользовательских оценок (`user_rating` в Notion, где балл варьируется от 1 до 5).
4. **Фильтрация и Ранжирование (Filtering & Ranking):**
   * Метод `op.filter()` отсекает элементы со score < 4.
   * Оставшиеся элементы пропускаются через LLM Agent (`llm_agent.py`) для суммаризации (`op.summarize()`) и финального ранжирования (`op.rank()`).
5. **Сохранение (Push):**
   * Отфильтрованные и обработанные статьи отправляются в Notion (и/или сохраняются в индекс векторной БД).

**Проекция на PostgreSQL (Ваш проект):**
Сырые данные (вместо локальных JSON-файлов) можно временно сохранять в таблицы staging-слоя с полем `JSONB`. Дедупликация реализуется на уровне базы данных (уникальные индексы, ограничения `UNIQUE` + `ON CONFLICT DO NOTHING`). Оценка кандидатов (Scoring) решается путем вычисления косинусного расстояния с помощью оператора `<=>` из `pgvector` в комбинации с SQL-агрегациями для расчета среднего рейтинга похожих записей.

## 3. Обмен информацией, память и потоки данных

Поток данных движется от API источников в локальные JSON (состояние "в процессе"), затем трансформируется, векторизуется и отправляется в Notion и ChromaDB (итоговое состояние).

**Схема данных и метаданных в ChromaDB (`chromadb_cli.py`):**
Когда данные помещаются в ChromaDB (метод `add` класса `ChromaDB`), они разбиваются на чанки (используется `RecursiveCharacterTextSplitter`).
Структура хранения в ChromaDB:
* `documents`: Массив строк с самим текстом (чанком).
* `ids`: В качестве уникального идентификатора используется MD5-хэш от текста чанка (`utils.hashcode_md5(doc.page_content.encode('utf-8'))`).
* `metadatas`: Словарь `dict` с метаданными.

В коде используются различные метаданные в зависимости от источника. Например:
* **YouTube (`ops_youtube.py`):** `title`, `description`, `thumbnail_url`, `publish_date`, `author`, `view_count`, `length`.
* **Общее (из LangChain/LlamaIndex):** `uuid`, `url`, `source`, `category`.
* **Пользовательские метрики (`data_model.py`):** Могут включать `user_rating`, `distance`, `last_edited_time`.

**Проекция на PostgreSQL (Ваш проект):**
Схема данных ChromaDB идеально ложится на таблицу PostgreSQL следующей структуры:

```sql
CREATE TABLE document_embeddings (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    content_hash VARCHAR(32) NOT NULL, -- Замена для MD5 ID из Chroma
    chunk_text TEXT NOT NULL,          -- Текст чанка (documents)
    embedding VECTOR(1536),            -- Эмбеддинг текста (pgvector)
    metadata JSONB NOT NULL,           -- Динамические метаданные (metadatas)
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- Индекс для быстрого поиска по метаданным (GIN)
CREATE INDEX idx_document_embeddings_metadata ON document_embeddings USING GIN (metadata);

-- Векторный индекс для HNSW-поиска (из pgvector)
CREATE INDEX idx_document_embeddings_vector ON document_embeddings USING hnsw (embedding vector_cosine_ops);
```

Такой подход позволяет объединить мощь реляционных запросов, гибкость JSON-схем для разнородных метаданных из разных источников (новостей, видео, статей) и эффективный гибридный поиск (графы + векторы), что полностью соответствует целям вашего мультимодельного проекта.
