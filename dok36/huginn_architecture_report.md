# Анализ архитектуры и схемы данных системы Huginn (в разрезе создания агентов и обработки событий)

Данный отчет содержит подробный разбор того, как логически и технически работает считывание данных из интернета, цепочки агентов, настройка их конфигурации и поток обработки данных в проекте Huginn, строго основываясь на анализе исходного кода репозитория. Эти концепции могут быть перенесены в реализацию на базе PostgreSQL.

## 1. Техническая реализация и архитектура

Архитектура Huginn построена на базе паттерна MVC с использованием Ruby on Rails, где основное состояние системы сохраняется в реляционных таблицах. Ниже приведено описание ключевых таблиц, основанное на анализе миграций (`db/migrate/*.rb`) и моделей проекта:

### Таблица `users`
Представляет пользователей (tenants) в системе.
- `id`: Уникальный идентификатор.
- `email`, `encrypted_password` и т.д.
Обеспечивает multi-tenant архитектуру, так как агенты и события привязаны к конкретному `user_id`.

### Таблица `agents`
Хранит настройки экземпляров агентов, созданных пользователями.
- `id`: Первичный ключ.
- `user_id` (integer): ID владельца-пользователя (multi-tenant изоляция).
- `type` (string): STI (Single Table Inheritance) в Rails. Определяет конкретный подкласс агента (например, `WebsiteAgent`, `EmailAgent`).
- `name` (string): Человекочитаемое имя агента.
- `schedule` (string): Расписание запуска агента (например, `every_10m`, `midnight`), используемое планировщиком.
- `options` (text): Сериализованный JSON, хранящий специфичные настройки агента (например, URL для парсинга, CSS-селекторы).
- `memory` (text): Сериализованный JSON, хранящий внутреннее состояние агента (например, ID последнего обработанного твита, хеши уже виденных статей).
- `last_check_at` (datetime): Время последней успешной проверки (вызова метода `check`).
- `last_receive_at` (datetime): Время последнего получения событий (вызова метода `receive`).
- `last_checked_event_id` (integer): ID последнего события из таблицы `events`, которое этот агент обработал. Используется для оптимизации выборки новых событий для данного агента-получателя.

### Таблица `events`
Хранит события, сгенерированные агентами. События передают данные по графу агентов.
- `id`: Первичный ключ.
- `user_id` (integer): Привязка к пользователю (безопасность).
- `agent_id` (integer): ID агента-генератора (источника), создавшего это событие.
- `payload` (text): Основная полезная нагрузка. Сериализованный JSON с данными события (например, заголовок и URL статьи, текст твита).
- `created_at` (datetime): Время создания события.
*(В Huginn реализован механизм очистки старых событий через фоновые задачи, опираясь на глобальные настройки или специфичные для агента, например `keep_events_for`).*

### Таблица `links`
Определяет ребра графа — направленные связи (цепочки) между агентами.
- `id`: Первичный ключ.
- `source_id` (integer): ID агента-отправителя (тот, кто генерирует событие).
- `receiver_id` (integer): ID агента-получателя (тот, кто будет обрабатывать событие).
- `event_id_at_creation` (integer): Используется для того, чтобы новый получатель не обрабатывал старые события источника, которые были сгенерированы до создания этой связи.

## 2. Функции и логическое функционирование

Архитектура построена вокруг асинхронного выполнения задач с использованием фоновой очереди (`delayed_job`). Логика системы разделена на сбор данных, генерацию событий и их обработку по цепочке.

### Считывание данных из интернета (метод `check`)
1. **Планировщик:** Демон `bin/schedule.rb` вызывает метод `Agent.run_schedule(schedule)`.
2. **Очередь:** Для всех агентов, чье расписание совпадает с текущим, создается фоновая задача (job) на проверку — вызывается `Agent.async_check(agent_id)`.
3. **Выполнение (Worker):** Воркер берет задачу из очереди `delayed_jobs`, загружает объект `Agent` из БД по ID и вызывает на нем метод `check`.
4. **Сбор данных:** Внутри метода `check` конкретный подкласс агента (например, `WebsiteAgent`) выполняет действия (например, HTTP-запрос по URL из своего поля `options`, парсит HTML и находит новые элементы).
5. **Генерация событий:** Для каждого нового элемента агент может обновить свою колонку `memory` (чтобы не обрабатывать этот элемент в будущем) и вызывает метод `create_event(event)` из базового класса `Agent`. Этот метод проверяет `can_create_events?`, строит событие (`build_event`) и сохраняет его (`event.save!`), что приводит к вставке новой записи в таблицу `events`.

### Веб-интерфейс и настройка опций
Пользователь управляет всей этой системой через стандартный веб-интерфейс (MVC контроллеры, такие как `AgentsController`).
- При создании агента пользователь выбирает тип агента (подкласс).
- В форме он заполняет `options` — JSON объект. Для удобства Huginn предоставляет формы, которые сериализуются в JSON, или прямые текстовые редакторы JSON.
- Пользователь задает связи: в интерфейсе он выбирает источники или получателей из списка других своих агентов. При сохранении эти связи записываются как строки в таблицу `links`.
- Все запросы контроллера скоупятся по `current_user.agents`, обеспечивая строгую изоляцию (как видно из связей `belongs_to :user`).

## 3. Обмен информации, память, потоки данных

Поток данных (Data Flow) в Huginn реализован как ориентированный граф, где агенты - это узлы, а события - данные, передаваемые по ребрам (`links`). Обмен информацией происходит асинхронно через БД.

### Цепочки агентов и обработка событий (метод `receive!`)
Агенты образуют граф благодаря таблице `links`. Обработка потока событий реализована асинхронно через bulk-опрос базы данных.

1. **Генерация событий:** Агент-источник сохранил новые записи в таблицу `events`.
2. **Поиск получателей:** Планировщик периодически вызывает метод класса `Agent.receive!`.
3. **SQL Запрос (Ключевой момент):** Метод `Agent.receive!` в `app/models/agent.rb` выполняет сложный JOIN-запрос к БД:
   - Объединяет `agents` (как получателей), `links` и `agents` (как источники).
   - Объединяет с `events`, где `events.agent_id = sources.id AND events.id > links.event_id_at_creation`.
   - **Условие новизны:** Фильтрует события так, чтобы `events.id > agents.last_checked_event_id` (или если оно NULL) и агенты не были отключены (`NOT agents.disabled AND NOT agents.deactivated`).
   - Этот запрос возвращает список получателей и новые события: `[receiver_agent_id, source_agent_type, receiver_agent_type, event_id]`.
4. **Группировка и обновление:**
   - Для каждого `receiver_agent_id` собирается массив уникальных новых `event_id` (`agents_to_events[receiver_agent_id.to_i] << event_id`).
   - В БД обновляется поле `last_checked_event_id` у агента-получателя на максимальный `event_id` из массива (`agent.update_attribute :last_checked_event_id, event_ids.max`).
5. **Постановка в очередь:** Для каждого агента-получателя ставится задача в очередь — `Agent.async_receive(agent.id, event_ids)`. Это ставит в очередь `AgentReceiveJob`.
6. **Выполнение получателя (Worker):**
   - Как видно в `app/jobs/agent_receive_job.rb`, воркер извлекает `AgentReceiveJob` (`perform(agent_id, event_ids)`).
   - Загружает агента (`agent_id`) и события (`event_ids`) из БД.
   - Вызывает инстанс-метод `agent.receive(Event.where(:id => event_ids).order(:id))`.
   - Конкретный агент-получатель перебирает массив событий, может форматировать `payload` с помощью шаблонизатора на основе своих `options`, и выполняет конечное действие.
   - После успешного выполнения воркер обновляет поле `last_receive_at` у агента (`agent.last_receive_at = Time.now; agent.save!`).

### Рекомендации для реализации на PostgreSQL

При переносе этой архитектуры на PostgreSQL в вашем проекте:
1. **Структура хранения:** Используйте тип `jsonb` для колонок `options`, `memory` в таблице агентов и `payload` в таблице событий. В Huginn используется просто `text`, но `jsonb` позволит эффективно индексировать и фильтровать настройки и данные.
2. **Очереди задач:** Для реализации воркеров и замены `delayed_job` можно использовать встроенную блокировку Postgres `FOR UPDATE SKIP LOCKED`.
3. **Рекурсивные запросы для графа:** Так как ваш проект использует графовые подходы ('postgres-graph-rag'), связи (`links`) и потоки событий можно анализировать через `WITH RECURSIVE` для сквозного трейсинга данных по цепочке агентов.
4. **Событийно-ориентированный подход:** Вместо периодического вызова `receive!` (polling из базы как делает Huginn), можно использовать триггеры (`AFTER INSERT ON events`) в комбинации с функцией `pg_notify` для мгновенного запуска воркеров.
