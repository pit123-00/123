# Отчет по анализу репозитория Letta

## 1. Техническая реализация и архитектура
Проект **Letta** (ранее известный как MemGPT) — это фреймворк и серверная платформа для создания ИИ-агентов с расширенной (долгосрочной) памятью, способных обучаться и самосовершенствоваться.
- **Язык:** Python.
- **Основа (Фреймворк):**
  - **Сервер/API:** Используется FastAPI для создания REST API (`letta/server/`).
  - **ОРМ и БД:** Используется SQLAlchemy (`letta/orm/`) вместе с Alembic для миграций. По умолчанию работает с PostgreSQL, поддерживает векторные расширения (pgvector) для семантического поиска.
  - **Инфраструктура:** Проект имеет обширную поддержку Docker (`Dockerfile`, `compose.yaml`, конфигурации для vLLM), а также интеграцию с OpenTelemetry (`otel/`) для распределенной трассировки и ClickHouse для логов.
  - **Клиенты:** Есть готовые SDK для TypeScript (`@letta-ai/letta-client`) и Python (`letta-client`).
- **Архитектура:**
  - `letta/agent.py` — ядро. Описывает класс `Agent`, который инкапсулирует логику управления LLM, промптами, вызовом инструментов (tools) и памятью (пагинация контекстного окна).
  - `letta/server/` — бэкенд (FastAPI), который управляет пулом агентов, их состоянием (State), источниками данных (Data Sources) и пользователями. Управляет REST-эндпоинтами.
  - `letta/memory/` и `letta/schemas/memory.py` — структуры, описывающие блоки памяти агента (Memory Blocks).
  - `letta/services/` — сервисный слой для работы с БД, инструментами (ToolManager), шагами агента (StepManager) и провайдерами LLM.
  - `letta/llm_api/` — слой абстракции для работы с различными провайдерами моделей (OpenAI, Anthropic, Azure, Local LLM/vLLM).

## 2. Функции и как логически это работает
Основная проблема, которую решает Letta — это ограниченный размер контекстного окна у современных LLM (Context Window). Letta предоставляет агентам виртуальную ОС, где память разделена на "оперативную" (Core Memory, всегда в контексте) и "постоянную" (Archival Memory, БД/Векторная база, выгружена на диск).

**Логика работы:**
1. При создании агента ему выделяется структура `Memory`, состоящая из блоков (например, "о пользователе", "о себе", "текущая задача").
2. Когда пользователь отправляет сообщение (`step`), оно добавляется в очередь.
3. Менеджер формирует промпт. Если история сообщений или объем памяти превышают лимиты токенов (Token Limits), Letta использует алгоритмы *усечения (truncation)* или *суммаризации (summarization)*, оставляя только самое важное.
4. LLM генерирует ответ. Если LLM понимает, что ей нужно что-то запомнить или вспомнить, она генерирует вызов функции (Function Calling/Tool Call), например `core_memory_append` или `archival_memory_search`.
5. Слой `ToolManager` и песочница (`ToolExecutionSandbox`) выполняют эти системные функции (модифицируя таблицы в PostgreSQL).
6. Затем LLM генерирует финальное сообщение для пользователя (используя `send_message`).
7. Фреймворк поддерживает многоагентные системы, где агенты могут делегировать задачи друг другу (subagents). Поддерживается интеграция с Composio и MCP (Model Context Protocol).

## 3. Обмен информации, память, потоки данных
- **Память (Ключевая фича):**
  - *Core Memory:* JSON-блоки, которые всегда инжектятся в System Prompt. Агент может сам их редактировать.
  - *Archival/Recall Memory:* Внешнее хранилище. Поиск по нему осуществляется через семантический поиск (Embeddings) или SQL/keyword поиск.
- **Потоки данных (Data Flow):**
  1. `HTTP POST /agents/{id}/messages` -> `FastAPI Router`.
  2. `Server` извлекает `AgentState` из PostgreSQL.
  3. Инициализируется класс `Agent`.
  4. Сообщение пользователя добавляется в `MessageManager` (сохраняется в БД).
  5. Запускается цикл `step()`:
     - Оценивается размер контекста (`count_tokens`).
     - Если нужно — старые сообщения пакуются в Summary (`summarize_messages`).
     - LLMClient делает запрос к API (например, OpenAI или Anthropic) -> `ChatCompletionResponse`.
  6. Если ответ содержит `tool_calls` (например, агент просит записать файл или выполнить поиск в памяти):
     - Инструмент выполняется локально в Python (или в защищенной песочнице, например Modal Sandbox).
     - Результат (`ToolReturn`) добавляется обратно в контекст.
     - Делается еще один проход к LLM (внутренний цикл "мыслей").
  7. Когда агент вызывает `send_message_to_user`, поток завершается.
  8. Все стейты (обновленная Core Memory, история) синхронизируются с базой данных (PostgreSQL).
  9. Ответ (включая внутренние мысли, если разрешено) стримится или возвращается единым JSON-ом клиенту.
- **Observability:** Каждый шаг (`step`), использование токенов (`LettaUsageStatistics`) и ошибки тщательно логируются и могут быть отправлены в ClickHouse через OpenTelemetry (OTel) для построения дашбордов.
