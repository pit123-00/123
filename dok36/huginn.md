# Отчет по анализу репозитория Huginn

## 1. Техническая реализация и архитектура
Проект **Huginn** — это система для создания агентов, которые выполняют автоматизированные задачи в интернете для пользователя (аналог Yahoo! Pipes, IFTTT или Zapier).
- **Язык и фреймворк:** Ruby (на базе фреймворка Ruby on Rails).
- **СУБД:** По умолчанию поддерживает MySQL и PostgreSQL. Для фоновых задач (Background Jobs) используется база данных и механизм `delayed_job`.
- **Архитектура:** Классическое монолитное приложение Ruby on Rails (MVC):
  - `app/models/` — ядро бизнес-логики. Ключевая модель — `Agent.rb`. В системе существуют десятки подклассов (конкретных агентов), которые наследуются от `Agent`.
  - `app/controllers/` — HTTP контроллеры (например, `AgentsController.rb`), которые управляют агентами через веб-интерфейс, CRUD операции.
  - `app/views/` — HTML/ERB шаблоны пользовательского интерфейса.
  - `app/jobs/` — Фоновые задачи (ActiveJob), такие как получение данных (Receive), проверка агентов (Check) или рассылка email.
- **Инфраструктура:** Проект имеет продвинутую поддержку Docker (как single-process, так и multi-process архитектуры), скрипты для деплоя на Heroku, скрипты для Capistrano, а также поддерживает платформу Cloud Foundry. Присутствуют `Procfile` для запуска различных воркеров и веб-сервера (Puma) через foreman.

## 2. Функции и как логически это работает
Главная задача Huginn — считывать интернет (RSS, веб-страницы, API, email), анализировать данные и выполнять действия (отправлять SMS, делать HTTP POST, сохранять в файлы).

**Логика работы (на основе Agent.rb):**
1. В системе регистрируются **Агенты (Agents)**. У агента есть расписание (`schedule`), по которому он запускается.
2. Агенты могут быть соединены в цепочки (граф): одни агенты генерируют **События (Events)** (например, `WebsiteAgent` парсит сайт и находит новую статью), другие агенты получают эти события и обрабатывают их.
3. У базового класса `Agent` есть ключевые методы:
   - `check` (запускается по таймеру, проверяет источник).
   - `receive(events)` (вызывается, когда агент получает событие от другого агента).
   - `create_event(payload)` (создание нового события, чтобы передать его дальше).
4. Пользователь через веб-интерфейс (через `AgentsController`) создает агентов, настраивает их опции (часто используя формат JSON) и связи друг с другом.
5. Huginn содержит планировщик (демон, который запускает `bin/schedule.rb`). Этот планировщик периодически вызывает метод `Agent.receive!` и `Agent.run_schedule(schedule)`, которые через ActiveJob (попадая в таблицу `delayed_jobs`) асинхронно активируют нужных агентов.
6. В агентах можно использовать шаблонизатор **Liquid**, чтобы динамически форматировать текст событий (например, превращать JSON-объект в красивое тело email сообщения).

## 3. Обмен информации, память, потоки данных
- **Память и Данные:** Все состояние хранится в реляционной БД.
  - `users` — пользователи системы.
  - `agents` — настроенные экземпляры агентов. Они хранят свои настройки в колонке `options` (обычно сериализованный JSON) и могут сохранять внутреннее состояние (например, ID последнего увиденного твита) в колонке `memory`.
  - `events` — сгенерированные события. События имеют `payload` (полезную нагрузку в виде JSON) и могут автоматически удаляться по истечении времени (`expires_at`, `keep_events_for`).
  - `links` — таблица связей между агентами (source_id, receiver_id).
- **Потоки данных (Data Flow):**
  1. `Scheduler` (отдельный процесс) каждую минуту проверяет расписания.
  2. Если пора, `Scheduler` вызывает `Agent.async_check(agent_id)` -> помещает задачу `AgentCheckJob` в очередь.
  3. Процесс-воркер (`delayed_job`) забирает задачу, инстанцирует модель Агента и вызывает метод `#check`.
  4. Агент идет в интернет (HTTP запрос), парсит данные, обновляет свою `memory` и вызывает `create_event(payload)`.
  5. Событие пишется в таблицу `events`.
  6. Срабатывает `Agent.receive!`: база данных опрашивается на предмет новых событий. Для всех агентов-получателей (`receiver_id`) в очередь ставится `AgentReceiveJob`.
  7. Воркер берет `AgentReceiveJob`, находит агента и передает ему массив новых событий (метод `#receive(events)`).
  8. Агент-получатель выполняет действие (например, шлет email).
- **Многопользовательская безопасность:** Система спроектирована как multi-tenant. Агенты жестко привязаны к `user_id`. Контроллеры используют `current_user.agents` для авторизации запросов, чтобы пользователи не видели данные друг друга.
