# Технический отчет по AgensGraph

## 1. Техническая реализация и архитектура

### Совместное хранение реляционных и графовых данных
AgensGraph является форком PostgreSQL, который глубоко интегрирован на уровне ядра, что позволяет хранить как реляционные, так и графовые данные в одной и той же базе данных. Эта многомодельная структура достигается за счет использования существующих структур данных PostgreSQL:
- Графы представлены как логическое пространство имен (namespace), аналогично схемам в PostgreSQL. Системный каталог `ag_graph` связывает идентификатор графа (`graphid`) с идентификатором схемы (`nspid`).
- Узлы (вершины) и связи (ребра) логически группируются с помощью "меток" (Labels), которые на уровне хранения являются обычными таблицами PostgreSQL.
- Системный каталог `ag_label` отслеживает эти метки, связывая их с конкретным графом и указывая базовую таблицу (`relid`), в которой хранятся данные.
- Иерархия меток (наследование) реализуется с помощью механизма наследования таблиц PostgreSQL (`INHERITS`).

### Структура данных (схема)
Структура хранения узлов и ребер определена в системных каталогах `ag_vertex` и `ag_edge` соответственно:

**Схема вершин (узлов) - `ag_vertex`:**
- `id` (graphid): Уникальный идентификатор узла внутри графа (состоит из ID метки и ID элемента).
- `properties` (jsonb): Все свойства (атрибуты) узла хранятся в бинарном формате JSON (JSONB), обеспечивая бессхемное хранение данных (schemaless).
- `tid`: Tuple Identifier, внутренний идентификатор строки PostgreSQL (CTID).

**Схема ребер (связей) - `ag_edge`:**
- `id` (graphid): Уникальный идентификатор ребра.
- `start` (graphid): Идентификатор начального узла.
- `end` (graphid): Идентификатор конечного узла.
- `properties` (jsonb): Свойства ребра в формате JSONB.
- `tid`: Tuple Identifier.

Обе сущности используют специальный составной тип `graphid`, который кодирует 16-битный ID метки и 48-битный ID самого элемента, что позволяет эффективно определять тип сущности без дополнительных объединений (JOIN).

## 2. Функции и логическая работа

### Гибридные запросы (SQL + Cypher)
AgensGraph модифицирует парсер и планировщик запросов PostgreSQL для понимания как SQL, так и Cypher (язык запросов к графам).
- **Парсер:** В каталог `src/backend/parser` добавлены модули (например, `parse_cypher_expr.c`), которые могут разбирать синтаксис Cypher. Язык Cypher поддерживается внутри специального предложения `MATCH` (или других Cypher-конструкций).
- **Выполнение запросов:** Когда парсер встречает гибридный запрос, он преобразует Cypher-выражения во внутреннее дерево разбора (Parse Tree), которое затем преобразуется в дерево запроса PostgreSQL (Query Tree), в котором обход графа (pattern matching) моделируется через серию соединений (JOIN) между таблицами меток (ребер и вершин).
- Передача данных между SQL и Cypher осуществляется бесшовно. Например, вы можете выбрать данные из реляционной таблицы, используя стандартный SQL `SELECT ... FROM table WHERE ...`, а затем передать результат этого фильтра в конструкцию `MATCH (v:Label) WHERE v.id = table.id`.
- Движок может использовать индексы PostgreSQL (B-Tree, GIN, GiST) для ускорения поиска как по идентификаторам, так и по свойствам, хранящимся в формате JSONB.

## 3. Информационный обмен, память и потоки данных

### Драйверы и потоки данных (JDBC, Python)
Поскольку AgensGraph возвращает данные, которые могут одновременно содержать плоские реляционные столбцы и вложенные графовые структуры (узлы с внутренними JSON-свойствами, пути графа), стандартные драйверы PostgreSQL не могут их корректно интерпретировать "из коробки".
- **Интерфейсы драйверов:** В `src/interfaces` находятся драйверы (например, libpq, jdbc, python), которые были расширены или специально написаны для парсинга и сериализации/десериализации специфических для AgensGraph типов данных (таких как `graphid`, `agtype` или `jsonb` в контексте узлов/ребер).
- **Сериализация:** При отправке данных клиенту графовые объекты сериализуются в строковый формат (обычно основанный на JSON, часто называемый `agtype`), который драйвер на стороне клиента парсит и превращает в объекты (Node, Edge, Path), с которыми разработчик может взаимодействовать программно (например, `node.getProperties()`).
- Это позволяет клиентскому приложению получать единый набор результатов, в котором одна колонка может быть целым числом из реляционной таблицы, а другая - полноценным графовым объектом-путем (содержащим массив узлов и ребер) из Cypher-запроса.
