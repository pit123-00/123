# Анализ репозитория: feeds.fun

## 1. Техническая реализация и архитектура
Feeds.fun — это self-hosted RSS ридер нового поколения, акцентирующий внимание на автоматическом тегировании статей с помощью ИИ.
- **Бэкенд:** Написан на Python. Представляет собой ASGI-приложение на базе FastAPI (запускается через `uvicorn`), которое предоставляет только HTTP API для доступа к данным и настройкам пользователя. Вся тяжелая логика вынесена в воркеры (cli команда `ffun workers`).
- **Фронтенд:** Реализован на TypeScript (предположительно Vue или React), компилируется через NPM (`feeds-fun` package) и представляет собой SPA (Single Page Application).
- **База данных:** Используется реляционная база PostgreSQL, к которой бэкенд обращается (вероятно, асинхронно через asyncpg или SQLAlchemy). Дополнительно применяются механизмы миграций БД (инструмент `yoyo`).

## 2. Функции и как логически это работает
Ключевая особенность проекта — отсутствие ручной сортировки. Система автоматически назначает теги новостям, а пользователь создает правила (rules) для фильтрации и скоринга новостей на основе этих тегов.
Основные функции:
- **Loader:** Отдельный воркер, который скачивает и парсит RSS-фиды. Поддерживает работу через HTTP-прокси.
- **Librarian:** Интеллектуальный воркер, анализирующий скачанные статьи и присваивающий им теги. Имеет плагиную систему Tag Processors:
  - `domain` (извлекает домены), `native_tags` (использует теги из самого RSS).
  - `llm_general` (основная фича) — использует ChatGPT (OpenAI) или Gemini (Google) для интеллектуального определения смысловых тегов из текста статьи.
- **Tag Normalizers:** Система нормализации "сырых" тегов, сгенерированных ИИ (например, удаление артиклей "the", "a", разбиение сложных тегов "apple-vs-microsoft" на отдельные), чтобы фильтрация работала корректно.
- **Изоляция конфигурации:** Предусмотрен гибкий механизм конфигурации через переменные окружения и TOML файлы, позволяющий подключать кастомные LLM-модели (с API, совместимыми с OpenAI или Gemini).

## 3. Как происходит обмен информации память потоки данных
- **Разделение API и фоновой обработки:** API-сервер (FastAPI) работает синхронно с клиентом (SPA), быстро отдавая отфильтрованные данные из PostgreSQL.
- **Потоки данных при обновлении фидов:**
  1. Воркер `Loader` просыпается по расписанию, скачивает XML фиды, парсит их и кладет новые записи (сырой контент) в базу данных.
  2. Воркер `Librarian` забирает новые, еще не размеченные статьи из базы.
  3. Контент прогоняется через цепочку Tag Processors. Если задействован LLM-процессор, текст (опционально разбитый на чанки с подсчетом токенов `tiktoken`) отправляется по сети к провайдеру ИИ (OpenAI/Gemini).
  4. Полученные "сырые" теги пропускаются через пайплайн Tag Normalizers (очистка, замена, сплиттинг).
  5. Финализированные теги сохраняются в PostgreSQL и связываются с конкретной статьей.
- **Чтение:** Когда пользователь открывает фронтенд, приложение запрашивает API. Бэкенд делает запрос к PostgreSQL, который "на лету" (или по заранее посчитанным индексам) применяет пользовательские правила скоринга к тегам и возвращает отсортированный массив новостей (первыми идут статьи с наивысшим score по нужным тегам).
- **Память:** Система stateless для API. Воркеры держат в памяти NLP-модели (например, загружается модель `en_core_web_lg` из SpaCy, если используются дефолтные локальные процессоры), что требует достаточного объема оперативной памяти при работе Librarian.
