# Анализ репозитория: auto-news

### 1. Техническая реализация и архитектура
Репозиторий `auto-news` представляет собой сложное агрегационное приложение, построенное на **Python**. Архитектура системы включает:
*   **Слой данных и интеграций (src/):** Большое количество файлов, отвечающих за интеграцию с различными платформами (Notion через `notion.py`, Reddit через `reddit_agent.py`, RSS).
*   **Оркестрация (dags/):** Использование Apache Airflow (`news_pulling.py`, `collect_weekly.py`) для управления фоновыми задачами и периодического сбора данных.
*   **Интеграция с LLM (src/llm_agent.py):** В проекте активно используется `langchain` для построения пайплайнов обработки естественного языка. Поддерживаются интеграции с ChatOpenAI, ChatOllama и ChatGoogleGenerativeAI, а также используются различные "loader-ы" (WebBaseLoader, YoutubeLoader) для получения сырого контента.
*   **Контейнеризация и деплой:** Проект поставляется с полной поддержкой развертывания (Docker, Helm, ArgoCD).

Архитектура четко разделяет сбор данных (Airflow DAGs), извлечение признаков/суммаризацию (LLM Agents) и хранение результатов (Notion/ChromaDB).

### 2. Функции и логическая работа в базе (Как работают пункты и Схема данных)

**Логика работы системы:**
1.  **Сбор данных (Ingestion):** По расписанию (определенному в Airflow DAG `news_pulling.py` или подобных) запускаются процессы загрузки данных из внешних источников (Twitter, Reddit, статьи, транскрипты YouTube видео, RSS). Процесс сбора разделен на этапы (start, prepare, pull, save, finish) через Airflow.
2.  **Обработка и Дедупликация (Processing & Deduplication):** В фазе `save` (вызывается скрипт `af_save.py`) скачанные данные дедуплицируются с помощью соответствующих операторов (OperatorTwitter, OperatorReddit, и т.д.).
3.  **Оценка (Scoring):** Для больших потоков данных (например, Twitter, Reddit, RSS) применяется алгоритм на основе эмбеддингов для вычисления кандидатов и их фильтрации. Система вычисляет "score" (рейтинг) для новых элементов, сравнивая их с историей или эталонными эмбеддингами.
4.  **Фильтрация (Filtering):** Оставляются элементы со score >= 4 (где score от 1 до 5).
5.  **Суммаризация (Summarization):** Для таких источников как Статьи, YouTube и отфильтрованных постов Reddit/RSS, запускается LLM для создания краткого изложения (summary).
6.  **Ранжирование (Ranking):** LLM ранжирует отфильтрованные/суммаризированные данные, чтобы определить наиболее важные.
7.  **Публикация (Pushing):** Отранжированные данные отправляются в хранилище, в первую очередь в Notion (для визуализации), а также сохраняются в векторную базу данных для будущего семантического поиска.

**Схема данных и хранение в ChromaDB:**
Для сохранения векторных представлений (эмбеддингов) используется **ChromaDB**. В проекте описан клиент `ChromaDB` (`src/chromadb_cli.py`), который управляет коллекциями.

*   **Инициализация:** ChromaDB работает в режиме `PersistentClient` (данные сохраняются на диск по указанному пути, по умолчанию `./test.vdb`). Создается коллекция по имени (например, `default`). Эмбеддинги по умолчанию генерируются с помощью OpenAI (модель `text-embedding-ada-002`, если не указан другой провайдер, хотя поддерживаются также HuggingFace и Ollama через `embedding_agent.py`).
*   **Формат хранения в ChromaDB:**
    Когда данные добавляются в ChromaDB (метод `add` в `chromadb_cli.py`), они разбиваются на фрагменты (chunks) с помощью `RecursiveCharacterTextSplitter` (по умолчанию chunk_size=1024, chunk_overlap=128).
*   **Сохраняемые поля (для каждого chunk-а):**
    *   **documents:** Текстовое содержимое фрагмента (`doc.page_content`).
    *   **ids:** Уникальный идентификатор фрагмента, который генерируется как MD5-хэш от содержимого фрагмента (`utils.hashcode_md5(doc.page_content.encode('utf-8'))`).
    *   **metadatas:** Метаданные (передаются как словарь `dict`).
*   **Метаданные (Metadata):**
    Метаданные, которые прикрепляются к каждому документу, зависят от источника, но обычно включают:
    *   `uuid` или уникальный ID исходного документа.
    *   `url` или ссылка на источник (твит, статья, видео).
    *   `title` или заголовок документа.
    *   Другие специфичные для источника поля (например, автор, дата).
*   **Поиск (Querying):** При поиске (`query` или `query_result`) система вычисляет эмбеддинг для запроса и ищет `n_results` ближайших документов. Дополнительно применяется фильтрация по `max_distance` (максимальному расстоянию), отсеивая результаты, у которых дистанция (расстояние) больше заданного порога (например, 0.5), что означает низкую релевантность.

### 3. Информационный обмен, память и потоки данных
*   **Airflow DAGs -> Python Scripts:** Airflow вызывает bash-команды, которые запускают Python скрипты из папки `src` (`af_pull.py`, `af_save.py` и др.), передавая им параметры через аргументы командной строки (даты, пути к данным).
*   **Источники -> Локальное хранилище (JSON):** Скрипты `af_pull.py` загружают сырые данные из источников и сохраняют их в локальные JSON-файлы в папке `data/news/`.
*   **JSON -> Обработчики -> Внешние системы (Notion/ChromaDB):** Скрипт `af_save.py` считывает JSON-файлы. Далее `Ops_*.py` классы (например, `ops_twitter.py`) обрабатывают данные (дедупликация, скоринг через LLM или эмбеддинги, суммаризация) и отправляют отфильтрованный результат в Notion (через Notion API) и/или векторную базу.
*   **Взаимодействие с LLM:** Для оценки (scoring) и суммаризации (summarize) вызывается `llm_agent.py`, который формирует промпты (определенные в `llm_prompts.py`) и обращается к выбранному провайдеру (OpenAI, Ollama и др.).
*   **Память и состояние:**
    *   **Notion:** Выступает в роли долгосрочной памяти для пользователя и интерфейса для чтения новостей.
    *   **Redis/MySQL/Локальные файлы:** В проекте есть скрипты для работы с Redis (`redis_cli.py`) и MySQL (`mysql_cli.py`), которые могут использоваться для кеширования состояний (дедупликация, чтобы не обрабатывать одни и те же новости дважды) или хранения промежуточных метаданных.
    *   **ChromaDB/Milvus:** Векторные базы данных используются для семантического поиска. Они позволяют системе сравнивать новые поступающие новости с уже обработанными или с профилем интересов пользователя, чтобы вычислять релевантность (score).

### Применение в PostgreSQL (Postgres-Graph-RAG)
Для реализации подобной логики в вашем проекте на PostgreSQL:
1.  **Airflow/Оркестрация:** Можно использовать `pg_cron` или внешний планировщик для запуска функций сбора данных.
2.  **Хранилище сырых данных (JSON):** В PostgreSQL можно использовать колонки типа `JSONB` для хранения сырых данных из различных источников, аналогично тому, как они сохраняются в файлы.
3.  **Векторная база данных (замена ChromaDB):** Использовать расширение `pgvector`.
    *   Тексты разбиваются на чанки (как `RecursiveCharacterTextSplitter`).
    *   Создается таблица `chunks` с колонкой `embedding vector(1536)` (для OpenAI ada-002).
    *   Вместо отдельного словаря метаданных (как в Chroma), метаданные (url, title, source_id) можно хранить в отдельных колонках этой же таблицы или как `JSONB` поле `metadata`.
4.  **Дедупликация и поиск:** Запросы на семантическую близость (аналог `collection.query` с `max_distance`) в Postgres реализуются через операторы `<->` (Евклидово расстояние) или `<=>` (Косинусное расстояние) с установкой порога отсечения `WHERE vector <-> query_embedding < 0.5`.
5.  **Графовая составляющая:** Метаданные (author, topic, category) можно связать в графовую структуру (используя реляционные связи или рекурсивные CTE), что позволит делать гибридные запросы: "найти семантически похожие новости (pgvector), написанные тем же автором (graph/relational)".
