# Отчет об архитектуре и обработке фидов: NewsBlur

В данном отчете представлен подробный анализ логической и технической работы системы обработки фидов на базе архитектуры проекта NewsBlur. Отчет разбит на три ключевые части и предназначен для последующей реализации аналогичной системы в проекте на PostgreSQL.

## 1. Техническая реализация и архитектура

Архитектура платформы строится на подходе **Polyglot Persistence**, где различные типы баз данных используются для тех задач, с которыми они справляются лучше всего.

### Слой маршрутизации и балансировки
*   **Nginx и HAProxy:** Выполняют роль балансировщиков нагрузки и обратных прокси-серверов. Они принимают входящие запросы от веб-клиента (Single-page application на Backbone.js) и маршрутизируют их на соответствующие бекенд-узлы (Django/Python или Node.js).
*   **Imageproxy:** Отдельный микросервис для проксирования, кэширования и масштабирования изображений (в первую очередь favicons и картинок из статей), чтобы избежать проблем с блокировками смешанного контента (HTTP/HTTPS) и снизить нагрузку.

### Инфраструктура хранилищ (Polyglot Persistence)
*   **PostgreSQL:** Служит основным реляционным (ACID) хранилищем. Здесь хранятся критичные данные: профили пользователей (`User`), метаданные фидов (`Feed`), подписки пользователей (`UserSubscription`), биллинг и статистика.
*   **MongoDB:** Документо-ориентированная база данных, используемая для хранения объемного контента. Главная сущность — `MStory` (сама статья, текст которой сжимается с помощью `zlib`), а также классификаторы для машинного обучения, социальные данные и ответы AI.
*   **Redis:** Выполняет несколько критически важных ролей:
    *   **Брокер сообщений для Celery:** Хранит очереди задач для фоновой обработки фидов (`queued_feeds`, `tasked_feeds`, `scheduled_updates`).
    *   **Шина Pub/Sub:** Обеспечивает работу веб-сокетов (через Node.js и Socket.io) для обновления счетчиков непрочитанных в реальном времени.
    *   **Кэш и хранилище состояния:** Хранит хэши прочитанных статей (например, сеты `RS:{user_id}` и `RS:{user_id}:{feed_id}`), чтобы быстро определять прочитанные элементы, не нагружая основные базы. В продакшене используются разные пулы (например, `REDIS_FEED_UPDATE_POOL`, `REDIS_PUBSUB_POOL`, `REDIS_STORY_HASH_POOL`).
*   **Elasticsearch:** Обеспечивает функционал полнотекстового поиска по всем статьям и векторного поиска для рекомендаций (discovery).

### Фоновые задачи
*   **Celery:** Фреймворк для асинхронных задач. Рабочие процессы (Celery Workers) занимаются скачиванием RSS-фидов, парсингом текста, извлечением изображений, обучением классификаторов, рассылкой push-уведомлений и обновлением агрегированной статистики.

## 2. Функции и логическая работа

В этом разделе описано, как система обрабатывает запросы пользователя и как работают фоновые процессы обновления фидов.

### Запрос статей пользователем
1.  **Маршрутизация:** Пользователь запрашивает статьи из папки или списка фидов через веб-интерфейс. API-запрос (например, `load_single_feed` или `refresh_feeds`) обрабатывается бэкендом на Django.
2.  **Сбор метаданных (PostgreSQL):** Бэкенд запрашивает `UserSubscription` и `Feed` в PostgreSQL для проверки прав пользователя, получения ID фидов, проверки состояния фида (активен, заблокирован) и счетчиков непрочитанных (`unread_count_neutral`, `unread_count_positive`).
3.  **Запрос контента (MongoDB):** Бэкенд формирует запрос в MongoDB к коллекции `stories` (`MStory`), фильтруя по `story_feed_id` и дате.
4.  **Сборка ответа:** Метаданные из реляционной БД и сжатый (затем распакованный) контент из MongoDB объединяются, после чего к ним применяются обученные AI-классификаторы. Готовый JSON отправляется клиенту.

### Процесс планирования и обработки фидов (Celery)
Процесс обновления фидов непрерывен и управляется через **Celery Beat** и очереди в **Redis**.

1.  **Очереди задач (`TaskFeeds`):**
    *   Каждую минуту `Celery Beat` инициирует выполнение `TaskFeeds`.
    *   Эта функция сканирует Sorted Sets в Redis (например, `scheduled_updates`), находя фиды, которые подошли к времени обновления.
    *   Она формирует список фидов, переносит их в сет `queued_feeds` и создает задачи для воркеров, используя `UpdateFeeds.apply_async`.
2.  **Скачивание и парсинг (`UpdateFeeds`):**
    *   Свободный воркер берет задачу и загружает RSS/Atom XML фида.
    *   Затем он парсит XML (используя `feedparser` или собственный парсер), извлекает текст, авторов, теги и URL-адреса изображений.
3.  **Сжатие и сохранение:**
    *   Тело статьи сжимается алгоритмом `zlib` для экономии места в БД и RAM (поля `story_content_z`, `story_original_content_z`).
    *   Новые истории сохраняются в **MongoDB** (`MStory`).
    *   Хэши новых статей записываются в **Redis**, чтобы отслеживать дубликаты.
4.  **Обновление счетчиков (PostgreSQL):**
    *   Если статья новая, бэкенд обновляет кэшированные счетчики `unread_count_*` в `UserSubscription` для каждого подписчика фида.
    *   Генерируется событие Pub/Sub через Redis, которое перехватывается Node.js-сервером и по веб-сокету отправляет клиенту команду обновить счетчики в UI.

### Протокол PubSubHubbub
Чтобы минимизировать интервалы опроса (polling), NewsBlur поддерживает протокол PubSubHubbub.
*   Приложение `push` управляет подписками (`PushSubscription`).
*   Бэкенд сообщает хабу (Hub) фида свой callback-адрес.
*   Когда автор публикует новую статью, хаб почти моментально отправляет POST-запрос с содержимым статьи на вебхук приложения `push`.
*   NewsBlur немедленно сохраняет статью и инициирует обновление счетчиков в браузере.

## 3. Обмен информацией, память и потоки данных (Схемы данных)

Ключевые данные распределены между PostgreSQL и MongoDB. Ниже приведены основные схемы (модели).

### Модель Feed (PostgreSQL)
Хранит общую информацию о RSS-ленте, общую для всех пользователей.
*   `id`: Первичный ключ (int).
*   `feed_address`: URL RSS-файла (URLField).
*   `feed_link`: URL самого сайта (URLField).
*   `feed_title`: Название блога/сайта.
*   `active_subscribers`: Количество активных пользователей, подписанных на фид. Это поле помогает приоритизировать частоту парсинга `TaskFeeds`.
*   `last_update`, `next_scheduled_update`: Временные метки (timestamps), используемые Celery для планирования.
*   `fetched_once`, `has_feed_exception`: Флаги состояния.

### Модель UserSubscription (PostgreSQL)
Связывает пользователя с фидом и хранит персонализированные данные: счетчики и метки.
*   `user_id`: Внешний ключ на таблицу User.
*   `feed_id`: Внешний ключ на таблицу Feed.
*   `user_title`: Персональное название фида, если пользователь его переименовал.
*   `last_read_date`: Дата последней активности в фиде.
*   `unread_count_neutral`, `unread_count_positive`, `unread_count_negative`: Агрегированные счетчики непрочитанных статей, разделенные по оценкам классификатора (Intelligence Trainer).
*   `needs_unread_recalc`: Булево поле-флаг, сигнализирующее о том, что счетчики устарели и фоновый воркер должен пересчитать их.

### Модель MStory (MongoDB)
Хранит контент самой истории. Документы в коллекции `stories` имеют сложные индексы (составной индекс по `story_feed_id` и убывающей дате `-story_date` для быстрой выборки новостей из фида).
*   `story_feed_id`: ID фида из PostgreSQL (IntField).
*   `story_date`: Дата публикации.
*   `story_hash`: Уникальный хэш истории (используется как ID для отслеживания прочитанных состояний в Redis).
*   `story_title`, `story_author_name`, `story_permalink`: Текстовые метаданные.
*   `story_content_z`: Бинарное поле (BinaryField), содержащее текущий HTML-контент статьи, сжатый библиотекой `zlib`.
*   `story_original_content_z`: Оригинальный контент, также сжатый `zlib`.
*   `image_urls`, `story_tags`: Списки строк, хранящие извлеченные ссылки на картинки и теги.

### Поток данных при чтении статьи (Mark as Read)
1.  Клиент отправляет POST-запрос с массивом `story_hash`.
2.  Функция `mark_story_hashes_as_read` обращается к пулу **Redis** (Story Hash Pool).
3.  Хэш добавляется в два множества Redis (Sets):
    *   Глобальное множество пользователя: `RS:{user_id}`
    *   Множество фида: `RS:{user_id}:{feed_id}`
4.  В `UserSubscription` выставляется флаг `needs_unread_recalc = True`.
5.  Сообщение отправляется в шину Pub/Sub для синхронизации вкладок пользователя.
