# Отчёт 3: Плюсы, минусы и необычные решения (Агенты, Субагенты, Пайплайны)

## 1. Управление агентами, субагентами и пайплайнами

В проекте `treg` реализована самобытная и глубоко продуманная концепция взаимодействия с AI-агентами, организации составных цепочек вызовов (пайплайнов) и управления мульти-агентными рабочими процессами (модули `src/treg/application/hub/*`, `src/treg/domain/hub/*`, `src/treg/mcp.py`, `skills/`, `plugins/`).

### 1.1. Hub Manifests и оркестрация DAG (JSON Road)
Вместо использования тяжеловесных фреймворков для оркестрации (типа Celery, Airflow или Temporal), конвейеры инструментов в `treg` определяются декларативными манифестами (`recipe.json`):
- **Синтаксис контракта:** Декларируются входные параметры (`inputs`), используемые инструменты (`uses`), лимиты (`limits`: шаги, время, стоимость в USD) и последовательность шагов (`steps`).
- **Построение DAG и волновой параллелизм (Wave-based concurrency):**
  - Модуль `src/treg/domain/hub/graph.py` строит направленный ациклический граф зависимостей между шагами конвейера.
  - Шаги группируются в «волны» (waves). Независимые шаги внутри одной волны выполняются параллельно с ограничением `MAX_PARALLEL = 4` через семафор `asyncio.Semaphore(4)`.
  - Поддерживается цикл по коллекции (`for_each`) с динамическим разворачиванием подшагов.
- **Условные переходы и отказоустойчивость шагов:**
  - `skip_if_empty`: пропуск шага, если результат предыдущего вызова пуст (например, не найдены кандидаты).
  - `allow_fail: true`: продолжение выполнения пайплайна даже в случае падения отдельного инструмента.
- **Изоляция контекстов и двойное владение (Maker vs Caller):**
  - В одном пайплайне встречаются две стороны: **Caller** (клиентский агент, оплачивающий запуск и предоставляющий входные данные) и **Maker** (автор рецепта хаба, предоставивший логику или приватный инструмент).
  - Если шаг вызывает публичный инструмент каталога — он выполняется от лица Caller (с его баланса и с его API-ключами, если они настроены).
  - Если шаг вызывает приватный инструмент автора рецепта (`target in own_tools`) — он выполняется от лица Maker под его авторизацией. Клиентский агент **никогда не получает доступ к ключам автора рецепта**, но получает результат их работы.

### 1.2. Протокол MCP (Model Context Protocol) и защита контекстного окна LLM
При интеграции с агентами LLM критически важен расход контекстного окна. В каталоге `treg` находится более 2600 конечных точек API. Если зарегистрировать каждую точку как отдельную MCP-функцию:
1. Модель потратит десятки тысяч токенов только на системный промпт со схемами функций.
2. Вероятность галлюцинаций и ошибочного выбора инструмента возрастет экспоненциально.

**Решение в treg:** Принцип **«Каталог как данные»**:
- Для LLM экспонируется всего 3 ключевых мета-инструмента:
  - `catalog_search(query)` — агент формулирует естественным языком, какую задачу нужно решить, и получает 3–5 релевантных инструментов.
  - `catalog_get(endpoint_id)` — агент запрашивает детальную JSON-схему аргументов выбранного инструмента.
  - `call(endpoint_id, arguments)` — агент выполняет вызов.
- Это сохраняет контекст модели чистым и позволяет масштабировать каталог до десятков тысяч инструментов без деградации рассуждений агента.

## 2. Необычные и оригинальные технические решения

### 2.1. Локальный Transparent MITM Proxy для агентов (`localproxy.py`)
Автономные кодогенераторы (например, агент в терминале, пишущий скрипт на Python с использованием библиотеки `requests` или `stripe-python`) не умеют «из коробки» вызывать специфические CLI-команды `treg call`. Они генерируют прямой сетевой код к `https://api.stripe.com/...`.
- `treg` решает эту проблему гениальным способом: поднимается локальный демон-прокси (`127.0.0.1:18791`).
- Для подпроцесса агента устанавливаются переменные `HTTPS_PROXY` и `NODE_EXTRA_CA_CERTS`/`SSL_CERT_FILE`.
- Прокси перехватывает исходящий HTTPS-запрос агента, на лету подписывает локальным CA и перенаправляет запрос на сервер `treg`.
- Сервер внедряет корпоративный API-ключ в заголовок и передает запрос в реальный Stripe.
- **Агент уверен, что работает с внешним API напрямую, не имея локального ключа!** При этом трафик к LLM-провайдерам (`api.anthropic.com`) не расшифровывается, а передается вслепую (HTTP CONNECT tunneling).

### 2.2. Серверная песочница QuickJS без Node.js и Docker (`hub_sandbox.py`)
Большинство платформ запуска пользовательских скриптов используют тяжелые контейнеры Docker/Firecracker или огромный рантайм Node.js.
- `treg` использует встраиваемый C-движок **QuickJS** через Python-биндинг.
- Старт процесса занимает считанные миллисекунды (в отличие от секунд для Docker/Node.js).
- Движок наглухо изолирован: вырезаны сокеты, файлы, `eval`, системные вызовы.
- Ограничение памяти — 64 МБ, CPU — секунды.
- Мост между Python и QuickJS реализован как IPC по `stdin`/`stdout` через структурированные JSON-строки.

### 2.3. Целочисленный микродолларовый биллинг (`micro-USD`) и Two-Phase Commit
Отказ от чисел с плавающей точкой в пользу `BigInteger` микродолларов (`1 USD = 1 000 000 µ$`) с двухфазным резервированием (`Reserve -> Execute -> Settle / Release`):
- Защита от накопления погрешности при списании $0.0006 за вызов.
- Гарантия отсутствия ситуации «деньги списали, а провайдер упал с 500 ошибкой». При падении провайдера холд автоматически разблокируется на полную сумму.

### 2.4. Smart Archive с продажей кэша за 10% стоимости
Если агент повторно запрашивает детерминированные неизменяемые данные (например, данные профиля компании или технический аудит сайта), ответ выдается из архива:
- Клиенту возвращается заголовок `X-Treg-Served-By: archive`.
- Стоимость вызова составляет всего **10%** от тарифа прямого вызова API (`archive_hit_repeat_price_percent = 10`).
- Это мотивирует агентов экономить баланс и снижает нагрузку на лимиты вендоров.

### 2.5. Декларативные адаптеры ответов и нормализация контрактов
Провайдеры обогащения данных (например, Apollo, Hunter, ContactOut, Clearbit) возвращают JSON с совершенно разной структурой. В `treg` разработана система YAML-адаптеров (`routing/contracts.py`), которая на лету преобразует разные вендорские ответы в единый контракт поля в поле (`standardized schema`). Для агента замена одного поставщика на другого происходит абсолютно прозрачно.

## 3. Анализ преимуществ (Плюсы)

1. **Идеальное сопряжение с природой AI-агентов:**
   - Агенту не нужно учиться аутентификации в сотнях API — для него весь мир представлен единым шлюзом с предсказуемыми форматами ошибок.
   - Мета-инструменты MCP экономят контекст и бюджет токенов.
2. **Абсолютная безопасность секретов:**
   - Ни один внешний API-ключ не попадает в контекст языковой модели и на диск машины разработчика. Утечка промпта или взлом машины агента не скомпрометирует ключи от Stripe, OpenAI или баз данных.
3. **Беспрецедентный контроль расходов и квот:**
   - Многоуровневые лимиты: на пользователя, на организацию, на конвейер (`X-Treg-Run-Max-Cost`), суточные лимиты на всю платформу.
   - Защита от зацикливания агентов (runaway loops), способных обнулить кредитную карту за несколько минут.
4. **Легковесность и автономность рантайма:**
   - Быстрый старт, минимальные накладные расходы благодаря чистой архитектуре FastAPI + AsyncIO + QuickJS без тяжелых контейнеров.
5. **Высокая отказоустойчивость:**
   - Автоматический Waterfall/Failover: падение одного провайдера незаметно для агента компенсируется другим.

## 4. Анализ недостатков, рисков и ограничений (Минусы)

1. **Ограниченность скриптового окружения QuickJS:**
   - Песочница поддерживает чистый стандарт ECMAScript, но не имеет доступа к NPM-пакетам. Нельзя использовать популярные библиотеки вроде `axios`, `cheerio` или `lodash` без предварительной сборки/бандлинга кода в один файл.
   - Ограничение по памяти в 64 МБ делает невозможной тяжелую аналитику больших массивов данных прямо внутри скрипта шага.
2. **Единая точка отказа (Single Point of Failure):**
   - Централизованный прокси-сервер становится критическим узлом инфраструктуры. При сетевых задержках или сбое инстанса `treg` останавливается работа всех зависимых агентов.
3. **Сложность распределенной отладки:**
   - Из-за многослойности (Local Proxy -> REST /call -> Waterfall Router -> Upstream Relay -> Provider) при возникновении нетривиальных ошибок (например, искажение специфических multipart/form-data заголовков) поиск первопричины требует глубокого анализа логов аудита и трассировок нескольких уровней.
4. **Специфика поддержки WebSocket и длительного стриминга:**
   - Архитектура с двухфазным биллингом (`reserve` / `settle`) и анализом тел ответов идеально приспособлена для HTTP Request-Response моделей, но создает значительные технические сложности при работе с постоянными WebSocket-соединениями или бесконечными SSE-потоками без четких границ завершения сообщений.
5. **Потенциальные коллизии локального сертификата:**
   - Хотя `localproxy` настраивает CA только для дочерних процессов, некоторые языковые среды (например, определенные версии компилированных Go-бинарей или изолированные Docker-контейнеры внутри хоста) игнорируют переменные `SSL_CERT_FILE` и требуют дополнительной ручной настройки доверенных сертификатов.
