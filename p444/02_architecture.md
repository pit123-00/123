# Отчёт 2: Архитектурное устройство системы treg

## 1. Концепция и архитектурная парадигма

Архитектура `treg` построена в соответствии с принципами **Domain-Driven Design (DDD)**, **Чистой архитектуры (Clean / Hexagonal Architecture)** и модели **Zero-Trust Security**.

Вся система разделена на четко разграниченные слои с однонаправленным потоком зависимостей:
1. **Domain (`src/treg/domain/`)** — чистая бизнес-логика, инварианты предметной области, правила валидации манифестов, графы зависимостей, финансовые операции над балансом без побочных эффектов ввода-вывода.
2. **Application (`src/treg/application/`)** — сценарии использования (Use Cases): оркестрация жизненного цикла вызова (`call/service.py`), построение планов маршрутизации (`call/route.py`), исполнение рецептов хаба (`hub/runner.py`), аутентификация и биллинг.
3. **Infrastructure (`src/treg/infra/`)** — взаимодействие с внешним миром: адаптеры баз данных (PostgreSQL, SQLite через SQLAlchemy/SQLModel), распределенный кэш/координация (Redis KV), облачные хранилища (Cloudflare R2, S3), платежные шлюзы (Stripe) и сетевой транспорт (HTTPX Relay).
4. **Interfaces / Routers (`src/treg/routers/`, `src/treg/mcp.py`, `cli/`)** — точки входа: REST API (FastAPI), протокол MCP (Model Context Protocol), интерфейс командной строки (Go/Python CLI) и локальный MITM-прокси.

## 2. Модель данных и сущности предметной области (`src/treg/models.py`)

Модель данных спроектирована по принципу строгой изоляции арендаторов (Multi-tenancy):

```
+-------------------------------------------------------+
|                         User                          |
|         (глобальная учетная запись разработчика)       |
+-------------------------------------------------------+
                           | 1
                           |
                           | N
+-------------------------------------------------------+
|                      Membership                       |
|   (токен доступа treg-..., роль: owner/admin/member)  |
+-------------------------------------------------------+
                           | N
                           |
                           | 1
+-------------------------------------------------------+
|                         Org                           |
|  (изолированный арендатор: баланс micro-USD, квоты)   |
+-------------------------------------------------------+
    | 1              | 1               | 1          | 1
    |                |                 |            |
    | N              | N               | N          | N
+--------+      +---------+      +-----------+   +----------+
|  Tool  |      | Secret  |      | Credit    |   | HubTool  |
| (API)  |      | (ключи) |      | Block     |   | (рецепты)|
+--------+      +---------+      +-----------+   +----------+
                                       |              |
                                       | N            | N
                                 +-----------+   +----------+
                                 |   Hold    |   |  HubRun  |
                                 | & Ledger  |   | (запуски)|
                                 +-----------+   +----------+
```

### 2.1. Иерархия идентификации и владения
- **`Org` (Организация):** Главный корень агрегации (Tenant Root). Владеет финансовым балансом (`balance_micro`), пользовательскими инструментами, секретами и ограничениями расходов.
- **`User`:** Глобальная учетная запись человека или сервисного агента.
- **`Membership`:** Связующая сущность между пользователем и организацией. Именно на уровне Membership выпускается постоянный или временный токен авторизации (`treg-...`). Токен однозначно адресует пару `(user_id, org_id)` с определенной ролью (`owner`, `admin`, `member`).

### 2.2. Финансовые сущности (Micro-USD Ledger)
Финансовый модуль `src/treg/domain/money/` гарантирует неизменяемость и двойную запись:
- **`CreditBlock`:** Блок средств на балансе. Имеет тип: грант (`promo`), купленные средства (`stripe`), бонус или корректировка. Хранит начальную сумму, текущий неизрасходованный остаток и дату экспирации.
- **`Hold`:** Временная блокировка средств под выполнение асинхронного или длительного вызова. Открывается перед сетевым запросом к провайдеру на оценочную максимальную стоимость (`reserve`) и закрывается (`settle` или `release`) по фактическому результату.
- **`LedgerEntry`:** Неизменяемая бухгалтерская проводка фактического списания средств. Содержит точный идентификатор вызова (`call_ref`), сумму в micro-USD и ссылку на использованный `CreditBlock`.

### 2.3. Инструменты и исполнение
- **`Tool`:** Зарегистрированный собственный инструмент организации с базовым URL, маппингом параметров и правами доступа.
- **`Secret`:** Зашифрованные учетные данные (API-ключи, токены), связанные с Tool или внешним провайдером.
- **`CallRecord`:** Детализированная запись аудита каждого запроса: время выполнения в миллисекундах (`duration_ms`, `provider_ms`), статус ответа, размер данных, биллинг и идентификаторы трассировки.
- **`HubTool` & `HubRun`:** Метаданные составных пайплайнов хаба и история их выполнений со статусом, графом шагов и затратами.

## 3. Ключевые архитектурные паттерны

### 3.1. Паттерн In-Process Loopback через `httpx.ASGITransport`
Для исключения дублирования логики проверок авторизации, биллинга, квот и аудита все внешние протокольные адаптеры (в частности, MCP-сервер в `src/treg/mcp.py`) обращаются к основному API шлюза **внутри одного процесса**:
```
[MCP Client: Claude / Cursor]
             │ (JSON-RPC)
             ▼
   [src/treg/mcp.py]
             │
             │ httpx.ASGITransport (in-memory, без сетевого сокета)
             ▼
 [FastAPI Router: /call/...]
             │ (Единая точка применения правил: ACL, Hold, Settle, Audit)
             ▼
   [Target API / Upstream]
```
Это гарантирует, что какие бы интерфейсы ни добавлялись в будущем (CLI, MCP, Web, SDK), правила безопасности и тарификации никогда не разойдутся.

### 3.2. Паттерн «Маршрутизация с водопадом» (Waterfall / Routed Capabilities)
Архитектурный компонент `src/treg/application/call/route.py` реализует виртуальные конечные точки платформы (формата `treg.<capability>`, например `treg.company-enrich`):
- Запрос поступает на виртуальную возможность.
- Система строит план вызова (`Plan`), состоящий из цепочки кандидатов (`Candidate`), отсортированных по качеству, стоимости и доступности квот.
- Исполнение первого кандидата происходит как полноценный дочерний вызов с контекстом `f"{parent_ref}:r1"`.
- При получении 429 (Too Many Requests), 5xx или объявленного `miss` (отсутствие данных) маршрутизатор плавно переключается на следующего кандидата в цепочке.
- Ответ автоматически нормализуется адаптером (`Adapter`) к единому контракту платформы, скрывая различия форматов вендоров от агента.

### 3.3. Паттерн двухфазного биллинга (Two-Phase Reserve / Settle)
В распределенных AI-системах стоимость вызова API заранее неизвестна (она зависит от объема генерации токенов, количества найденных результатов или внутренних кредитов вендора).
Архитектура решает эту проблему разделением фаз:
1. **Фаза Reserve:** Оценка максимальной стоимости (`ceiling`). Блокировка суммы в micro-USD на балансе организации через запись `Hold`. Если баланса недостаточно — мгновенный отказ со статусом 402 Payment Required без обращения к провайдеру.
2. **Сетевой вызов к Upstream:** Передача запроса с инжекцией ключа.
3. **Фаза Settle:** Извлечение фактической стоимости из заголовков ответа или тела ответа через декларативные правила адаптера, фиксация списания в `LedgerEntry` и освобождение `Hold` с возвратом неиспользованного остатка. При системном сбое холд снимается полностью (`release`).

### 3.4. Фоновые демоны и распределенный воркер (`src/treg/worker.py`)
Тяжелые агрегационные и очистительные задачи вынесены из критического пути обработки HTTP-запросов в отдельный компонент `treg-worker`:
- Периодический сброс и агрегация статистики использования инструментов (`catalog stats`).
- Суточное свертывание расходов по ключам и участникам (`spend rollup`, `usage rollup`).
- Фоновая очистка неиспользуемых медиафайлов и устаревших архивных тел (`archive prune`, `media sweep`).
- Проверка доступности резервных маршрутов и агрегаторов (`overflow sync`, `overflow verify`).

## 4. Архитектурные границы и принципы изоляции

| Граница | Механизм изоляции | Гарантии |
| :--- | :--- | :--- |
| **Тенант vs Тенант** | `org_id` в ORM-запросах + внешние ключи | Полная невозможность доступа к чужим инструментам, ключам, логам и балансу |
| **Агент vs Секреты** | Серверное внедрение в `relay.py` | Агент видит только публичные контракты; API-ключи провайдеров никогда не возвращаются в CLI/MCP |
| **Пользовательский код vs Сервер** | QuickJS Sandbox + POSIX rlimits | Запрет прямого доступа к сокетам, файлам и окружению хоста; связь только по JSON-line мосту |
| **Клиентский трафик vs Внутренние сети** | SSRF Check (`proxy_ssrf_check`) | Запрет вызова loopback-адресов, Link-Local и приватных подсетей (10.x, 192.168.x) |
| **Трафик агента vs LLM трафик** | White-list проксирование в `localproxy` | Запросы к моделям (OpenAI/Anthropic) туннелируются без MITM; перехватываются только зарегистрированные инструменты |
