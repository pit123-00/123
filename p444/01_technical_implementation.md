# Отчёт 1: Техническая реализация treg (Tools Registry)

## 1. Введение и назначение проекта
Проект `treg` (`tools-registry`) представляет собой высокопроизводительный шлюз (credential-injecting proxy) и реестр инструментов для AI-агентов, командных скриптов и внешних платформ. Основная техническая задача системы — преобразовать разрозненные внешние API (более 2600 конечных точек провайдеров) и пользовательские скрипты в стандартизированные, безопасные и тарифицируемые инструменты, с которыми автономные агенты могут взаимодействовать через CLI, REST API, локальный прозрачный прокси или протокол MCP (Model Context Protocol), не получая прямого доступа к секретным API-ключам третьих сторон.

## 2. Архитектура конфигурации и параметры глубокой настройки (Deep Configuration)

Конфигурация системы сосредоточена в модуле `src/treg/config.py` на базе `pydantic_settings.BaseSettings`. Настройки загружаются из переменных окружения и `.env`-файлов со строгой типизацией и валидацией.

### 2.1. Финансовые параметры и микродолларовый биллинг (Micro-USD)
Все денежные расчеты в системе выполняются исключительно в целочисленных микродолларах (`1 USD = 1 000 000 micro-USD`). Это исключает ошибки округления чисел с плавающей точкой (`float`) при миллионах микротранзакций:
- `promo_grant_micro: int = 1_000_000` — размер стартового гранта для новых организаций при регистрации ($1.00 = 1,000,000 µ$).
- `platform_margin: float = 0.0` — маржинальная наценка платформы на стоимость вызовов провайдеров. При расчете сразу преобразуется в целочисленные микродоллары (`with_margin`).
- `platform_daily_cap_usd: float = 0.0` — глобальный суточный лимит расходов всей платформы для защиты от утечек и аномальных всплесков.
- `topup_min_usd: int = 10` — минимальная сумма пополнения баланса.
- `topup_default_usd: int = 10`, `topup_presets: list[int] = [10, 50, 100, 200]` — пресеты пополнения через Stripe.
- `topup_bonus_tiers: dict[int, int] = {10: 0, 50: 5, 100: 10, 200: 15}` — система бонусов при пополнении баланса на определенные суммы.
- `autotopup_default_threshold_usd: int = 5`, `autotopup_default_amount_usd: int = 20`, `autotopup_cooldown_s: int = 3600`, `autotopup_max_attempts: int = 3` — параметры автоматического пополнения баланса при снижении ниже порогового значения.

### 2.2. Защита конкурентности и управление доступом к деньгам (Money Admission)
Модуль `src/treg/infra/money_admission.py` реализует распределенный механизм предварительного получения аренд (lease) на проведение финансовых операций для снижения нагрузки на базу данных PostgreSQL:
- `money_admission_enabled: bool = False` — включение предварительной аренды через Redis/KV.
- `money_admission_org_ids: list[PositiveInt] = []` — список ID организаций, для которых применяется механизм.
- `money_admission_wait_s: float = 5.0` (допустимый диапазон `(0, 120]`) — тайм-аут ожидания получения аренды на операцию с балансом.
- `money_admission_lease_s: float = 15.0` (диапазон `[3, 300]`) — время жизни выданной аренды в Redis.
- `money_admission_retry_after_s: int = 2` — рекомендация клиенту в заголовке `Retry-After` при исчерпании лимита ожидания.
- `holdless_free_org_ids: list[PositiveInt] = []` — организации с правом выполнения бесплатных вызовов без создания блокировок (`Hold`).

### 2.3. Контроль потока (Flow Control), квоты и троттлинг
- `org_endpoint_quota_enabled: bool = False`, `org_endpoint_quota_redis_url: str = ""` — распределенный учет квот конечных точек организаций.
- `org_flow_control_enabled: bool = False`, `org_flow_control_refresh_s: float = 2.0` (диапазон `[0.2, 10]`) — фоновое обновление правил троттлинга организаций.
- `provider_rate_mode: Literal["off", "observe"] = "off"` — режим отслеживания лимитов провайдеров (`observe` — мониторинг без блокировки вызовов).
- `provider_rate_enforce: str = ""` — список провайдеров/бакетов, для которых лимиты жестко блокируют запросы (`refuses`) на основе распределенных Sliding Windows в Redis.
- `fair_share_wait_s: float = 2.0` (диапазон `[0, 30]`) — допустимое время ожидания в очереди честного распределения ресурсов между клиентами.

### 2.4. Тайминги вызовов и отказоустойчивость
- `call_timeout_s: int = 180` — максимальное время выполнения вызова к целевому API провайдера.
- `hold_grace_s: int = 60` — grace-период перед принудительным снятием зависшего холда (`Hold`).
- `run_cpu_seconds: int = 300` — лимит CPU времени на выполнение серверного процесса.
- `run_fsize_mb: int = 100` — лимит на размер файла, создаваемого серверным процессом (защита от переполнения диска).
- `spool_dir: str = ""`, `spool_max_bytes: int = 64 MB`, `spool_budget_bytes: int = 512 MB`, `spool_parse_concurrency: int = 2` — параметры буферизации больших ответов на диске (spooling) с потоковой обработкой.

### 2.5. Семантический поиск и Discovery (AI-поиск по каталогу)
- `find_engine: str = "v1"` — механизм семантического сопоставления задач с инструментами.
- `find_candidates: int = 60`, `find_jobs: int = 25`, `find_delta: int = 10`, `find_raw: int = 10`.
- `find_platform_seats: int = 8`, `find_gap_min: float = 0.5`, `find_name_min: float = 0.8`.
- `find_embed_model: str = "voyageai/voyage-4-lite"`, `find_embed_url: str = "https://openrouter.ai/api/v1/embeddings"`, `find_embed_timeout_s: float = 0.8`.
- `typesafe_model: str = "jev-latest"`, `typesafe_url: str = "https://api.typesafe.ai/v1/systemone"`, `typesafe_timeout_s: float = 2.5` — обращение к LLM-судье (Jev) для оценки релевантности найденных инструментов пользовательскому запросу.
- `search_judge_keep: float = 0.4`, `search_judge_high: float = 0.7` — пороговые значения скоринга релевантности.

### 2.6. Кэширование и архивирование ответов (Archive & Cache Subsystem)
- `archive_mode: str = "off"` — общий режим архивации (`off`, `read`, `write`, `both`).
- `archive_body_write: Literal["db", "both", "r2"] = "db"` — целевое хранилище тел ответов (PostgreSQL, Cloudflare R2 или оба параллельно).
- `archive_body_read_lookup: Literal["db", "r2-first"] = "db"`.
- `archive_r2_upload_concurrency: int = 8`, `archive_r2_max_pending: int = 256`, `archive_r2_max_pending_bytes: int = 128 MB`.
- `archive_serve_percent: int = 100`, `archive_hit_repeat_price_percent: int = 10` — предоставление архивного ответа со скидкой (всего 10% от стандартной стоимости прямого вызова API).
- `archive_max_body_bytes: int = 2_000_000` (2 МБ) — лимит на сохранение тела ответа в архив.
- `archive_prune_interval_s: int = 3600`, `archive_prune_batch: int = 500`, `archive_prune_keep_versions: int = 2`, `archive_prune_min_age_days: int = 7` — параметры циклической очистки устаревших архивных тел ответов.

## 3. Техническая реализация ключевых подсистем

### 3.1. Ядро проксирования и инжекции учетных данных (`src/treg/application/call/service.py`)
Проксирование запросов в `treg` построено как строгий многофазный пайплайн с нулевым доверием (Zero-Trust):
1. **Идентификация и проверка безопасности (SSRF Guard):** Валидация целевого хоста. Запрещены приватные подсети, loopback-адреса и облачные метаданные (`169.254.169.254`).
2. **Разрешение сущности (Target Resolution):**
   - Проверяется принадлежность конечной точки: пользовательский инструмент организации (`Tool`), каталог платформы (`Catalog`) или составной рецепт хаба (`HubTool`).
   - Определение учетной записи (собственный ключ организации или общий пул платформы).
3. **Идемпотентность (Idempotency Claim):**
   - Обработка заголовка `Idempotency-Key` с распределенной блокировкой. Повторный вызов не создает дублирующих списаний и мгновенно возвращает кэшированный результат.
4. **Финансовая резервация (`reserve`):**
   - Вызов `_platform_reserve`: блокировка суммы в micro-USD на балансе организации. Создается запись `Hold`.
5. **Внедрение аутентификации (Relay Injection):**
   - Запрос перенаправляется через модуль `src/treg/infra/upstream/relay.py`.
   - В зависимости от спецификации провайдера инжектируются заголовки: `Authorization: Bearer <token>`, `X-API-Key`, пользовательские токены сессий или Basic Auth. Клиентский агент никогда не видит и не получает в ответе секретные ключи.
6. **Потоковое чтение и тарификация (`settle`):**
   - Чтение ответа провайдера. При ошибке провайдера (5xx) или сетевом сбое выполняется автоматический `release` (разблокировка средств).
   - При успешном завершении вызывается `settle`: точный подсчет стоимости по правилам каталога (на основе статус-кода, количества возвращенных записей или заголовков расхода кредитов, например `X-Credits-Charged`), фиксация списания в `LedgerEntry` и возврат сдачи.

### 3.2. Локальный перехватывающий прокси (`src/treg/localproxy.py`)
Инновационное решение для автономных агентов, которые генерируют произвольный код (Python, Node.js, cURL) и пытаются напрямую обращаться к внешним API (например, `api.stripe.com`, `api.github.com`):
- Поднимается локальный HTTP/HTTPS-прокси (`127.0.0.1:18791`).
- Генерируется эфемерный локальный CA-сертификат (срок действия 730 дней, права доступа `0600`), переменные среды подменяются только для дочернего дерева процессов агента (`SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS`, `HTTPS_PROXY`).
- Система **не трогает** системное хранилище ОС.
- Перехватываются **только** хосты из доверенного белого списка зарегистрированных инструментов (`Allow-List`). Запросы к LLM (например, `api.anthropic.com` или `api.openai.com`) проходят как глухой сквозной туннель (`blind tunnel`) без MITM-расшифровки.
- Перехваченный HTTPS-запрос заворачивается в вызов `/call/` на сервер `treg`, где сервер подставляет нужный ключ.

### 3.3. Изолированная песочница исполнения скриптов (`src/treg/application/hub/sandbox.py` и `src/treg/hub_sandbox.py`)
Для выполнения кастомной логики агентов и конвейеров на стороне сервера используется изолированная среда QuickJS:
- Выделенный короткоживущий дочерний процесс операционной системы (`python -m treg.hub_sandbox`).
- Очистка переменных окружения (`scrubbed environment`), временный пустой каталог `HOME`, собственная группа процессов (`process group`).
- Ограничения POSIX rlimits (`resource.setrlimit`): лимит памяти процесса 512 МБ (куча QuickJS ограничена 64 МБ), ограничение CPU времени, запрет создания файлов.
- Внутри среды QuickJS **полностью отсутствуют** доступ к файловой системе, сеть, функции `require` или `process`.
- Единственный канал связи с внешним миром — мост IPC по протоколу JSON-lines через стандартный ввод/вывод (`stdin`/`stdout`). Функция `ctx.call(tool_id, args)` передает команду родительскому процессу, который исполняет её через стандартный защищенный `execute_call` со всеми проверками квот и баланса.

### 3.4. Шлюз протокола MCP (`src/treg/mcp.py`)
Реализация сервера Model Context Protocol для бесшовного подключения агентов из сред вроде Claude Desktop, ChatGPT Actions и Cursor:
- **Архитектурный принцип «Каталог как данные»**: вместо экспорта всех 2600+ конечных точек каталога в виде отдельных MCP-инструментов (что привело бы к переполнению контекстного окна модели и галлюцинациям), шлюз экспортирует компактный мета-набор инструментов:
  - `catalog_search` — поиск инструментов по текстовому описанию задачи.
  - `catalog_get` — получение схемы и цен конкретного инструмента.
  - `call` — исполнение вызова выбранного инструмента с валидацией аргументов.
  - `balance` — проверка текущего баланса организации.
  - `my_tools` — список собственных подключенных инструментов команды.
- **Безопасность исполнения:** вызовы инструментов через MCP не дублируют логику проверки прав и денег, а внутри процесса направляются через `httpx.ASGITransport` на собственный HTTP-эндпоинт `/call/`, проходя полный цикл валидации, ACL, резервации и аудита.

## 4. Преимущества технической реализации

1. **Гарантированная финансовая консистентность:**
   - Строгий двухфазный протокол резервирования и урегулирования (`Reserve-Hold-Settle`). Баланс списывается только после фактического подтверждения успеха внешнего вызова.
   - Использование целочисленной арифметики микродолларов (`micro-USD`) предотвращает накопление погрешностей при микроплатежах.
2. **Многоуровневая эшелонированная безопасность (Defense in Depth):**
   - Учетные данные внешних сервисов хранятся в зашифрованном виде (Fernet/Cryptography) в БД и никогда не передаются на сторону клиента или LLM-агента.
   - Двойная изоляция исполнения пользовательского кода: POSIX rlimits + QuickJS без сетевых сокетов.
   - Защита от SSRF и сканирования внутренней инфраструктуры.
3. **Высокая отказоустойчивость и маршрутизация с водопадом (Waterfall / Failover):**
   - Автоматический переход на альтернативных провайдеров (`overflow_route`) при получении 429 (Rate Limit) или 5xx от основного провайдера.
   - Встроенная пауза на основе заголовка `Retry-After` поставщика с повторной попыткой перед переключением на fallback.
4. **Оптимизация расходов и сетевого трафика (Smart Archive):**
   - Кэширование детерминированных результатов API с возможностью отдачи архивного ответа за 10% стоимости прямого запроса.
   - Разделение хранения метаданных в PostgreSQL и тяжелых тел ответов в объектном хранилище S3/Cloudflare R2.
5. **Прозрачность и непрерывный аудит:**
   - Полная фиксация каждого вызова в таблице `call_record`: время ответа поставщика (`provider_ms`), накладные расходы платформы, размер переданных данных, статус, биллинговая информация и отпечаток ошибки.
