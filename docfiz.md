# Архитектурный синтез: Оптимальная реализация управляемого процесса (Симбиоз OpenCode + Google Harness2 + Deer-Flow без LangGraph)

Этот документ описывает самый простой, надежный и архитектурно выверенный способ реализовать требования спецификации `AGENT_WORKFLOW_FRAMEWORK_RU.md`.

Мы исключаем избыточный оверхед тяжелых графовых фреймворков (таких как LangGraph) и строим архитектуру как **симбиоз трех проверенных в коде слоев**:
1. **Интерфейс, хост сессий и оркестратор:** `opencode` (Node/TypeScript/CLI/TUI).
2. **Идентичность запусков, версионирование деревьев и изоляция сред:** `google-research/harness2` (Python).
3. **Детерминированные квитанции, верификация цитат и шлюз Read-Before-Write:** `bytedance/deer-flow` (чистая Python-логика без LangChain/LangGraph зависимостей).
4. **Программный слой управления:** легкие CLI-скрипты на стандартной библиотеке Python (`workflow/scripts/`).

## 2. Что конкретно взять из каждого проекта

### А. Из `opencode`: Слой хоста оркестратора и субагентов
1. **Запуск субагента без истории диалога (`fork_turns="none"`):**
   - В `opencode/packages/core/src/tool/plugin/subagent.ts` и `session/subagent-job.ts` субагент запускается как полностью изолированная сессия (`childSessionID`).
   - Оркестратор в OpenCode не передает субагенту свои рассуждения и прошлые сообщения.
2. **Строгая проверка границ файловой системы (`file-access.ts`):**
   - Субагенту передаются только разрешенные лексические пути. Попытки выхода за границы рабочего каталога (`../`) пресекаются на уровне системных вызовов.
3. **Очередь и сериализация (`run-coordinator.ts`):**
   - Оркестратор ждет окончания работы текущего субагента (`awaitIdle`), исключая параллельные гонки в одном запуске.

### Б. Из `google-research/harness2`: Идентичность запусков и компонентная модель
1. **Фиксация идентичности и проверка актуальности (`harness2/core/runmark.py`):**
   - Наличие файлов в папке не означает завершение работы! Завершение подтверждается только созданием маркерного файла `.adapt_complete` с вычислением суммарного отпечатка (`fingerprint` от промпта, правил и снимка входных файлов `inputs_fingerprint`).
   - Если входные файлы или правила изменились, `is_reusable()` вернет `False`, и старый результат автоматически аннулируется.
2. **Компонентное дерево и принцип "omitted-is-inherited" (`harness2/core/tree.py`):**
   - Конфигурации и отчеты бьются на компоненты. При исправлении замечаний (`REPAIR`) субагент присылает только измененные секции (патч), а программный слой накладывает их на базовый артефакт.
3. **Изолированное рабочее пространство (`harness2/core/proposer.py`):**
   - Код создания временной изолированной папки под сессию субагента (`mkdtemp` + копирование только разрешенных снапшотов).

### В. Из `bytedance/deer-flow`: Слой детерминированных квитанций (БЕЗ LangGraph)
Вместо того чтобы тянуть LangGraph, мы извлекаем из `deer-flow` чистые математические функции:
1. **Генератор квитанций вызова инструментов (`deerflow/agents/middlewares/tool_receipt.py`):**
   - При вызове любого инструмента (скрипт, запись, чтение) штампуется неизменяемая квитанция:
     `{"id": "r1", "tool_name": "bash", "output_sha256": "...", "timestamp": "..."}`.
2. **Проверка цитирования в отчете (`deerflow/agents/middlewares/receipt_verification.py`):**
   - Чистая функция `verify_receipt_citations(report_text, receipts)` на Python без участия LLM проверяет: если субагент в отчете написал "Я проверил тесты и они прошли", он **обязан** сослаться на квитанцию `[r1]` или `[r1 bash]`. Если ссылка отсутствует или ссылается на несуществующую квитанцию — отчет отклоняется со статусом `FAIL`.
3. **Шлюз Read-Before-Write (`deerflow/agents/middlewares/read_before_write_middleware.py`):**
   - Защита от слепой перезаписи: субагент не имеет права перезаписать или пропатчить файл, если в рамках этой сессии он предварительно не выполнил чтение этого файла с получением его актуального `sha256`.

## 3. Как это работает на практике: Сквозной сценарий работы

### Шаг 1. Оркестратор в OpenCode инициирует запуск
1. Оркестратор получает задачу от пользователя в интерфейсе OpenCode.
2. Оркестратор запускает технический скрипт:
   ```bash
   python workflow/scripts/runner.py init --input inputs/request.md
   ```
3. Скрипт:
   - Генерирует уникальный `run_id` (например, `run-001`).
   - Делает неизменяемый снимок `inputs/request.md` в `outputs/.workflow/runs/run-001/snapshots/request.md`.
   - Вычисляет `sha256` снимка и правил.
   - Инициализирует `registry.json` в состоянии `PREPARED`.
   - Возвращает оркестратору следующую операцию: `SPAWN_AUTHOR`.

### Шаг 2. Запуск субагента Автора (Автор в режиме изоляции)
1. Оркестратор через инструмент `subagent` в OpenCode порождает нового агента с параметром `fork_turns="none"`.
2. Оркестратор отправляет субагенту **только одну команду**:
   ```text
   Верни READY и жди назначенное задание. Не открывай входные файлы.
   ```
3. После получения `READY` оркестратор вызывает `runner.py bind --role author --agent-id <id>` и передает субагенту команду на чтение первой порции задания:
   ```bash
   python workflow/scripts/delivery.py read-next --run-id run-001 --task-id task-author
   ```

### Шаг 3. Управляемая доставка контекста (Chunked Reading Cursor)
1. Субагент вызывает `delivery.py read-next`.
2. Скрипт выдает порцию текста (не более 12000 байт в UTF-8), обрамленную маркерами:
   ```text
   === PART 1/3 [sha256: e3b0c442...] ===
   Инструкция роли и входные требования...
   === END_PART 1/3 ===
   Следующая команда: python workflow/scripts/delivery.py ack --run-id run-001 --part 1
   ```
3. Субагент подтверждает получение части (`ack`). Курсор в реестре сдвигается на 2-ю часть.
4. До тех пор пока все части не подтверждены, `registry.py` физически заблокирует прием кандидатного отчета (`BLOCKED_READING_INCOMPLETE`).

### Шаг 4. Выполнение работы и сдача результата с квитанциями
1. Автор выполняет задачу в песочнице (пишет код, запускает генерацию).
2. Каждый вызов инструмента логируется в `receipts.json` запуска с фиксацией `output_sha256`.
3. Автор формирует отчет и сохраняет его в `outputs/.workflow/runs/run-001/candidates/candidate_v1.md`.
4. В отчете Автор обязательно приводит цитаты квитанций (`[r1]`, `[r2]`).
5. Автор вызывает:
   ```bash
   python workflow/scripts/runner.py submit-candidate --run-id run-001 --file candidate_v1.md
   ```
6. Скрипт `validate.py`:
   - Проверяет Read-Before-Write шлюз (читал ли автор исходник перед записью).
   - Вызывает `receipt_verification.py` (все ли цитаты квитанций сходятся с реальными вызовами).
   - Если проверка успешна, реестр переходит в статус `CHECKING`.
   - `runner.py` возвращает оркестратору команду: `SPAWN_AUDITOR`.

### Шаг 5. Независимый аудит (Аудитор)
1. Оркестратор создает **нового, независимого субагента** (Аудитора) с другой системной ролью и опять без истории чата Автора.
2. Аудитор получает фиксированный снимок `candidate_v1.md` и чек-лист правил проверки.
3. Аудитор **не имеет права редактировать текст Автора** (запрет в `allowed_write_paths`). Он может писать только в `reports/audit_report.json`.
4. Формат замечания строго структурирован (по JSON Schema):
   ```json
   {
     "verdict": "FAIL",
     "issues": [
       {
         "section_id": "recommendations",
         "quote": "короткая точная цитата",
         "rule_id": "R004",
         "reason": "Отсутствует обоснование затрат",
         "required_change": "Добавить расчет бюджета",
         "acceptance_criterion": "Присутствует таблица с цифрами"
       }
     ]
   }
   ```
5. Аудитор сдает отчет через `runner.py submit-audit`.
6. Если вердикт `FAIL`, состояние реестра переключается в `REPAIR`.
   `runner.py` сообщает оркестратору: `REPAIR_WITH_AUTHOR`.

### Шаг 6. Точечный ремонт (Patch / Omitted-is-Inherited)
1. Оркестратор возобновляет сессию Автора.
2. Автору передается **только список замечаний аудитора** и разрешенный к правке `section_id` ("recommendations").
3. Автор генерирует JSON-патч:
   ```json
   {
     "replacements": [
       {
         "section_id": "recommendations",
         "replacement_text": "Обновленный раздел с расчетом бюджета..."
       }
     ]
   }
   ```
4. Скрипт `patch.py` (на базе компонентной логики `tree.py` из Harness2):
   - Проверяет, что патч затрагивает **только** разрешенный `section_id`.
   - Накладывает патч на `candidate_v1.md`, создавая `candidate_v2.md`.
5. Повторный аудит проверяет **только измененный раздел**, экономя контекст и токены.
6. При получении `PASS` от аудитора скрипт `runmark.py` штампует финальную квитанцию `.adapt_complete` с хэшами всех артефактов.
7. Процесс завершается (`COMPLETED`), оркестратор отдает итоговый артефакт пользователю в интерфейс OpenCode.

## 4. Архитектура скриптового слоя (Workflow Scripts на Python)

Создается чистая, компактная структура внутри вашего репозитория без внешних зависимостей (только стандартная библиотека Python `hashlib`, `json`, `os`, `sys`, `pathlib`, `re`):

```text
workflow/
  contracts/
    assignment.schema.json      <- JSON Schema задания
    result.schema.json          <- JSON Schema отчета и кандидата
    audit.schema.json           <- JSON Schema замечаний аудита
    patch.schema.json           <- JSON Schema точечных правок
  scripts/
    registry.py                 <- Управление registry.json, FSM переходов, локи
    delivery.py                 <- Порционная выдача контекста (пагинатор 12 Кб, sha256)
    runmark.py                  <- Извлечен из harness2 (trial identity, квитанция .adapt_complete)
    receipts.py                 <- Извлечен из deer-flow (ToolReceipt + receipt_verification)
    patch.py                    <- Безопасное наложение замен по section_id
    runner.py                   <- Единая точка входа для оркестратора (next_action)
```

### Почему именно такая схема оптимальна?
1. **Никакого LangGraph:** Никаких циклических графов в памяти, тяжелых зависимостей и скрытых абстракций. Состояние хранится прозрачно в файле `registry.json` на диске.
2. **Crash-resilience (устойчивость к сбоям):** Если агент упал, сеть оборвалась или закончился тайм-аут — весь прогресс сохранен. Оркестратор запускает `python runner.py next --run-id <id>` и продолжает ровно с того шага и той порции текста, на которой произошел сбой.
3. **Полная независимость исполнителей:** Субагенты физически не имеют доступа к чужим чатам и файлам; контроль обеспечивается кодом среды запуска и скриптами проверки.
4. **Легковесность и скорость:** Все скрипты запускаются за миллисекунды, используют стандартный Python 3.10+ и не требуют сборки.
